# 极巨团体战

本地极巨团体战是剑／盾在 LDN 场景 60006 上最多四个站点的会话。主机在巢穴处用「邀请他人」开设，访客在自己的 Y 通讯列表里找到它，对着主机的名字用「开始对战」加入。大厅运行在可靠广播协议 0x80 上，战斗在 0x7C 上。`bin/swsh_connect.py --preset raid` 在一台主机的大厅里占一个访客席位，用选定的宝可梦（`--offer-file`）和招式（`--raid-move`）准备并战斗；应用的「极巨团体战（加入）」工具运行它。

## 网络

| 字段 | 值 |
|---|---|
| LDN 场景 id | 60006（旷野地带为 65535） |
| 参与者 | 开设时为 4 个中的 1 个 |
| 广播数据字节 `0x97` | `0x11` |
| Pia 会话上限 | 4（`0x0110e5e0`，从巢穴大厅 `0x01031c74` 调用） |
| 广播 `0xb0` 与 `0xd4` | 头目和巢穴记录（[巢穴记录](#the-den-record)） |

巢穴大厅的代码位于 `0x0102aba4..0x010370cc`（`View_NestHole`、`StateGuestReady`、`StateHostReady`）。访客的 Y 通讯列表会略过广播携带其自身设备 id 和账号 uid 的团体战。

## 大厅消息

每条大厅消息的 id 都是 2000，`net_contents.nesthole.protocol_buffers.NestholeAsyncDataHolder`（`main` 中的描述符 `0x1bfde43`、`0x20677b0`）。每个字段都是一个 holder，带一个 `bytes` 字段 1。

| 字段 | 名称 | 大小 | 内容 |
|---|---|---|---|
| 1 | NestholeTimeLimit | 4 | u32 剩余秒数；主机每秒发三次 |
| 2 | NestholePlayerInfo | 40 | 8 个零字节、u32（零售版剑 0x11，模拟的盾 0x12）、13 个字符的 UTF-16 名字、`00 03` |
| 3 | NestholeBattleReady | 16 | 玩家按下准备后第 8 字节为 1；战斗开始后第 12 字节为 1 |
| 4 | NestholeSelectPokemon | 352 | 8 个零字节，然后是选定宝可梦的加密队伍 PK8（0x158） |
| 5 | NestholeBattleStart | 32 | 参与者的 Pia 常量 id，共四个 u64，主机的排第一，未用的槽为零 |
| 6 | NestholeBossPokemon | 364 | 19 个零字节和 `ff`，然后是头目的加密队伍 PK8 |
| 7 | NestholeRewards | 120 | 十五对 u32：道具 id、数量；未用的对为零 |
| 8 | NestholeBattleSeed | 16 | u64 种子，然后是 `00 ff ff ff 1e 00 03 00` |

PlayerInfo 以 4 KB 窗口的 zlib（头部 `48 4b`）在可靠标志 0x10 下发出；其余明文发出。`pokeldn/swsh/raid.py` 构建每个字段。头目记录完整携带头目；BattleSeed 喂给什么尚未读出（把巢穴的团体战生成器用在它上面，既得不到头目的加密常量，也得不到它的 PID）。

## 访客的序列

快照在 0x84 上交换（主机的先发）；PlayerInfo、BattleReady 和 SelectPokemon 在 0x80 端口 0 上；准备时发第 8 字节置位的 BattleReady。所有玩家都准备好后，主机依次发 BattleStart、SelectPokemon、BossPokemon、Rewards、BattleSeed 和第 8、12 字节都置位的 BattleReady；访客用自己的 SelectPokemon 和同样的 BattleReady 应答，战斗在 0x7C 上开始（端口 0 上 ping 80，端口 1 上框架 40000，之后每回合 10000 和 20000）。在第 8 字节置位的 BattleReady 之后停下的访客，会让零售版剑主机停在 "Connexion en cours"，最终报错 2-ALZAA-0016。

## 战斗

主机跑战斗；访客在 0x7C 上应答（`pokeldn/swsh/raid_battle.py`）。从网状网加入起，访客运行 SyncClockProtocol 0x1C（每秒一次请求），并发送一次 ClockProtocol 0x77 请求（16 个 `00` 然后 `00 6f`），两者都发往目的地位图 1。

| 端口 | 消息 | 访客 |
|---|---|---|
| 0 | sync 80：ping、pingReply、pingSynced | 用 ping 和 pingReply 应答 ping，用 pingSynced 应答 pingSynced |
| 1 | 40000，内容 0 的框架：字段 2 基准（10000 或 20000，0 时缺省）、3 站点常量 id、4 时钟、5 主体 | 在 pingSynced 之后发三对 base-10000 / base-20000（主体 `00000000`、`000018fc`），然后用自己的站点 id 镜像主机的每个 base-20000 主体 |
| 0 | 10000，字段 3 {1 站点、2 槽、3 版本} | 在主机列出自己的座位后发一次（base 0，16 字节主体：常量 id、槽、版本字节 0x6e） |
| 0 | 10000，字段 1 为空 | 在主机的 base-8 消息（24 字节主体，战斗的种子）之后发 |
| 0 | 20000，字段 1 {1 发送者、2 槽、3 计数、4 数据} | 应答主机的每条命令 |
| 0 | 20000，字段 3 {1 状态、2 槽} | 在自己的行动之前发 {1: 2, 2: 槽} |

主机命令的数据以四个 u16 开头：序号、类型、长度、一个标签。访客用相同的序号、类型和标签、长度 4 和四个零字节应答，例外是类型 0x02（状态消息，然后是它的行动：序号、0x02、0x58、标签、88 字节）和类型 0x21（结束：发送者 1，数据 `0000 1e00 0000 2f00`）。见过的主机类型：0x01、0x0d、0x07、0x0e、0x02、0x10、0x09（该回合的日志，zlib）、0x04、0x11、0x0a、0x21。

### 哪个站点做服务器

服务器是 ServerVersion 记录在每台主机各自维护的表里胜出的那个站点。ServerVersion 是 `btl.net.protocol_buffers.BtlDataHolder`（id 10000）的字段 3：站点 id u64、客户端 id u32、版本 u32（版本 `0x6e`）。八个 {站点、客户端 id、版本、有效} 槽位于战斗网络对象 `+0x190 + 16 * i`；`0x8b4030` 取版本最高的第一个有效槽，`0x8b1990`（IsServer）把它的客户端 id 与主机自己的比较。一台主机的客户端 id 是它在 BattleStart 中的位置（`0x1025120`）。收集方站点把各槽作为 40000 框架对象 0 到 7 发布。

### 行动

88 字节的行动是十一个 8 字节条目。条目 2 作为小端 u24 是 `move id << 13 | target << 8 | 0xc1`。

| 招式 | 条目 2 | 目标 |
|---|---|---|
| 拍击（1） | `c1 28 00` | 8 |
| 绑紧（20） | `c1 88 02` | 8 |
| 叫声（45） | `c1 a2 05` | 2 |
| 水枪（55） | `c1 e8 06` | 8 |

叫声打每个对手，目标码为 2；单体招式的目标码为 8。访客无法行动的回合把条目 2 发成全零。`raid_battle.action(move, target)` 构建它；`--raid-move N` 选择招式槽。0x7C 的确认携带 32 个槽；只有槽 0 追踪访客的流，所以以各槽最大值为门槛的重发永远不会重发。

## 巢穴记录

巢穴主机的广播描述它的团体战；访客的 Y 通讯条目构建器（`0x00fa1560`）读取它。

| 偏移 | 内容 |
|---|---|
| `0x5F` 第 1 位 | 主机的版本：清零为剑，置位为盾 |
| `0xAF` | 活动种类：0 星为 `0x11`，以上为 `0x13 + 2 (rank - 1)`；`0xFF` 从不列出 |
| `0xB0` | 展示的头目：u16 物种（第 0 到 9 位）和形态（10 到 15 位）、一个第 4、5 位为 1 普通 2 超极巨化的字节，以及 u32 加密常量 |
| `0xD4` | 巢穴记录，同样的八字节布局 |
| `0xDC` | 高半字节：星级，0 到 4 |
| `0xDD` | 第 3 到 5 位：巢穴种类，普通巢穴为 0 |
| `0xDE`、`0xE0` | u16 遭遇表，在主机版本的表里计数，以及 u16 槽 |
| `0xE6` 到 `0xED` | `bin/archive/field/resident/data_table.gfpak` 第 8、6、7、9 号文件的 CRC16 |

`0xD4` 处物种非零时，访客只有在自己的表 CRC 匹配、巢穴种类为 0、且主机版本的 `0xDE` 表 `0xE0` 槽持有该物种、形态和超极巨化标志时才列出该团体战（`0x00ea5160`）。物种为 0 时跳过这些检查。`0x02510b2c` 处的字节为 1 或 2 且主机不是好友时，星级不得超过访客自己的星级（由徽章数得出）。`0xB0` 处的记录只做范围检查。访客会丢弃设备 id 和账号 uid（`0x1F` 到 `0x3E`）都与自己相同的站点（`0x0111b160`）。`pokeldn/swsh/data/nest_slots.json` 保存 1.3.2 的槽（`scripts/gen_swsh_nest_data.py`）；`raid.den_advert` 把巢穴记录指向持有头目的槽，或把它清零。

### 头目记录

访客在发出自己已开始的 BattleReady 之前检查 BossPokemon 和 Rewards（`0x01030d14`）；检查失败就以 2-ALZAA-0016 离开。

| 检查 | 代码 | 通过条件 |
|---|---|---|
| 头目 | `0x01032270` | 物种、形态和队伍 `+0x156`（1 普通，2 超极巨化）与巢穴记录指名的条目相同：种类 0 用广播版本的 `0xDE` 基表、槽 `0xE0`；种类 1 到 3 用访客自己存档中的活动遭遇、槽 `0xE0`；种类 4 用它存档中的极巨结晶遭遇 |
| 奖励 | `0x01032570` | 每对带道具和数量，要么是该槽奖励表在广播星级下恰好该数量的加成行，要么是它掉落表中在该星级有概率的道具（数量不限） |

等级、招式、个体值、PID、特性、异色和训练家字段都不比较。全零的巢穴记录指种类 0、表 0、槽 0（巴尔郎）。在零售版剑访客上观察到：带训练家数据的头目记录、队伍极巨化类型为 0，或对任何基表巢穴都不持有的头目（梦幻、某活动的超极巨化颤弦蝾螈）使用全零巢穴记录，即使团体战被列出也会以 2-ALZAA-0016 离开；只改物种的巢穴头目记录，以及 `raid.boss_record` 构建的头目，都被接受。基表巢穴不持有传说或幻之宝可梦，所以托管的头目必须是 `nest_slots.json` 列出的物种、形态和超极巨化状态；只有另一版本持有该头目时，`raid.den_advert` 切换广播的版本，并把活动头目显示成持有该物种的基表巢穴槽。`bin/swsh_host.py` 和应用的主持工具都拒绝基表巢穴不持有的头目。

带 `--raid-boss-as-is` 时，`raid.boss_record` 保留巢穴头目的 TID 28222 和 SID 36500。异色是 PID 对照它们算出的，所以 `raid.same_shine` 会移动 PID 的高半，以保住头目在自身文件训练家下的方形、星形或普通闪光；为玩家做成异色却按原 PID 发送的头目，被画成了普通。`raid.reward_choices` 列出该槽在某星级下允许什么；`raid.den_rewards` 构建该槽自己的行。

巢穴头目的队伍 HP 种族值和当前 HP 是普通 HP 种族值乘以 `(150 + 5 * 极巨化等级) / 100` 后向下取整；其他能力值是普通值。极巨化等级在 `+0x90`，特性槽位在 `+0x16` 的第 0 到 2 位，经验值是该等级所需的最小值。

### 捕获后仍然合法的头目

巢穴主机的 BossPokemon 是某颗种子的团体战掷骰 [PKHeX RaidRNG]。模拟的盾主机发出的两个巢穴头目都是一次掷骰：种子 `0xF41D53DF6C576FFD` 的豆豆鸽（`raid_boss_template.ek8`），种子 `0xBA7E50A969044287` 的咕咕，各自靠搜索加密常量留空的 32 个种子位找到（`tests/test_swsh_raid.py`）。以该种子和 `0x82A2B175229D6A5B` 播种的 xoroshiro128+ 的抽取，依序为：

| 抽取 | 字段 |
|---|---|
| u32 | 加密常量 |
| u32 | 记录的 TID（低半）和 SID（高半） |
| u32 | PID；其闪光对照该 TID 和 SID 判定 |
| rand(6)，直到抽到尚无个体值的项 | 巢穴的每一项满值个体值 |
| rand(32) | 其余每项个体值，按 HP、攻击、防御、特攻、特防、速度的顺序 |
| rand(3) 或 rand(2) | 特性槽，限于巢穴会抽的那种 |
| rand(253) + 1 < 性别比例 | 雌性，限于有双性的物种 |
| rand(25) | 性格；颤弦蝾螈按其形态的表抽 |
| rand(129) + rand(128)，两次 | 先身高，再体重 |

同一颗种子上的第二个生成器给出等级，即该星级的最小值（15 + 10 rank）加 rand(6)，然后是极巨化等级，rank + 1 加 rand(2)，4 星时为 6 加 rand(3) [PKHeX EncounterStatic8N]。当该物种、形态和超极巨化状态的某个巢穴遭遇的某颗种子给出上述全部，且其 PID 把掷骰的闪光带给它的训练家时，PKHeX 接受捕获来的巢穴宝可梦；在共用巢穴（地点 162）相遇时，任何巢穴表的遭遇都算匹配。文件自带的头目作为捕获会通不过该检查："PID+ correlation does not match"，或没有巢穴会在该等级给出的遭遇。

访客的捕获保留头目记录。模拟的盾访客捕获了从种子 `0xF3D291D263CC680F` 托管的毛辫羊：捕获记录带掷骰的加密常量、PID、个体值、性格、性别、体型、特性槽和极巨化等级，头目的招式和 17 级，并取用捕获者的训练家、相遇地点 162、相遇等级 17、一颗精灵球和日期。同样方式捕获的异色毛辫羊保留了掷骰的各项值，只换了 PID 的高半，使捕获者 TID 和 SID 下的闪光为 1（掷骰在原记录自己的 TID／SID 下是 5）；主机把它画成了异色。PKHeX 两者都接受（`tests/test_pokemon_service.py`）。

`bin/swsh_host.py --raid-boss` 发送一次掷骰：PKHeX 辅助的 `raid_boss` 按头目物种、形态和超极巨化状态，在其等级所指的星级（或巢穴给出的最近星级）上取 PKHeX 的巢穴遭遇，并取一颗掷骰结果带文件闪光的种子，优先匹配其性格和性别。记录保留文件的招式。`--raid-boss-as-is` 发送文件自己的等级、个体值、性格、体型和 PID。活动头目（`raid_event.boss_pk8`）是对随机种子的一次掷骰，套用活动表的满值个体值、特性、性别、性格和闪光规则，等级取表里的。

## 主持

`bin/swsh_host.py --raid-boss PK8 --raid-console-serves` 托管一个巢穴大厅，主机从 Y 通讯列表加入（`pokeldn/swsh/raid_host.py`）。广播和快照来自一台模拟的盾巢穴主机，使用全新的站点配置、板子的名字且无账号 id（`pokeldn/swsh/data/raid_advert.bin`、`raid_snapshot.bin`；`--advert` 和 `--snapshot` 替换它们）。`--raid-boss` 通过 `raid.boss_record` 接受任何 PK8。主机的快照先于访客发出。`--raid-reward ITEM:COUNT` 填充 Rewards，`--raid-seed` 填充 BattleSeed；主机拒绝广播的巢穴槽在其星级下不给出的行，并打印该槽给什么。

应用的「极巨团体战（主持）」工具用这些开关运行，带一个头目（或基表巢穴持有的旷野地带活动头目，`raid_event.hostable`）、玩家的宝可梦和最多 15 行奖励；不给行时，主机给出巢穴槽自己的奖励。它的奖励编辑器只提供头目所在广播巢穴槽的道具（`raid.boss_den`、`pokeldn.app.raid_rewards.swsh_den`），并修正加成道具的数量。

带 `--raid-console-serves` 时，加入的那台主机做服务器，我方主机作为客户端 1 应答（`raid_battle.Master`）：

| 步骤 | 主机 |
|---|---|
| BattleStart | 把主机列在第一位，所以它的客户端 id 是 0 |
| 0x7C 端口 0 | 发 ping；应答主机的 ping 和 pingSynced |
| 框架对象 | 发布对象 0 = 主机的 ServerVersion 记录，对象 1 = 自己的 |
| 0x7C 端口 0 | 发自己的 ServerVersion（客户端 id 1） |
| base 20000 | 发布计数器和自己的主体，0000 / 00000100，然后 0100 / 01000100、01000200、0200 / 02000200，每次都在主机镜像上一主体之后 |
| 对象 8 | 由主机发布（24 字节，一颗种子）；主机回 EmptyCommand（10000 字段 1） |
| 战斗命令 | 按访客的方式应答，行动指名主机宝可梦的第一个招式 |

一台零售版剑这样打完了整场团体战、赢下它并收到主机的 Rewards，然后发网状网离开请求。

我们自己的记录以版本 `0x6d` 发出，比主机的 `0x6e` 低一，所以无论各自落在哪个槽，主机的记录都是唯一最高版本。在 LAN 模式下，零售版剑把会话主机的记录归到槽 0（主机的 Pia 站点索引），所以版本相同时它选了我方主机，把我方记录发布为对象 0，发出 EmptyCommand，然后黑屏等待一个从未启动的服务器；用 `0x6d` 时它做了服务器，战斗正常载入。

### 多台主机

最多三台主机共用一个托管大厅（`raid_host.RaidParty`）。每台加入的主机都准备好后，我方主机才开始战斗；BattleStart 按加入顺序列出各主机，然后是我方主机。第一台主机做服务器。我方主机把框架对象 k 发布为主机 k 的 ServerVersion 记录，自己的放在最后，并在每台主机镜像其主体后推进 base-20000 的屏障。

第二台主机需要从 Pia 主机得到：投递给它的会话更新（在回环上每个站点得到自己的一份）；网状网加入响应的第 8 字节，即活跃站点上限，要高于已入座的站点数（否则结果为 1、错误 2618-0502）；以及在发送者流的端口（主机 0，第一个加入者 1，第二个 2）上的确认，因为未被确认的流会无休止重复。

访客之间直接相连：站点连接请求、0x84 上彼此的快照，以及 0x80 上同时寻址主机和另一访客的大厅消息。

## 活动团体战

旷野地带活动是一次 BCAT 下发，包含巢穴遭遇表和奖励表，每次下发一个编号索引。Project Pokemon 的 EventsGallery 把每个都放在 `Released/Gen 8/SwSh/Wild Area Events/Index NNN/` 下。`pokeldn/swsh/raid_event.py` 读取一个；`pokeldn.app.events_gallery` 在游戏 `swsh` 名下保存副本。

| 文件 | 内容 |
|---|---|
| `normal_encount` | 旷野地带各巢穴的活动遭遇 |
| `normal_encount_rigel1`、`normal_encount_rigel2` | 铠之孤岛和王冠雪原的（在 Index 080 和 117 中，010 里没有） |
| `drop_rewards`、`bonus_rewards` | 该次下发的奖励表 |
| `dai_encount` | 极巨结晶遭遇 [pkNX `NestHoleCrystalEncounterArchive`]；未读出 |

每个文件都以 0x20 字节的头部开头：偏移 0 是 u8 的 BCAT 索引，4 处是 `ff ff ff ff`，8 处是 u32 `0x20`，`0x10` 处是 u32 文件大小减 4。FlatBuffer 从 `0x20` 到末尾四个字节之前，后者是 CRC [pkNX `GameDumperSWSH.GetDistributionContents`]。

遭遇文件是一个表向量（字段 0）：TableID u64、GameVersion u32（1 剑，2 盾）和 Entries（字段 4）。条目字段：0 索引；1、2、3 物种、形态、等级；4 极巨化等级；11 特性（0、1、2 为第 1、第 2、隐藏特性；3 为前两者之一；4 任意）；12 超极巨化；13、14 掉落表和加成表的 id（u64）；15 五个星级概率，单位为百分比（每个版本各星级合计 100）；16 性别（0 抽取，否则性别 + 1）；17 满值个体值个数；18 异色（0 抽取，1 从不，2 总是）；21 性格（25 抽取）；23 到 26 四个招式；30 盾牌和 31 到 36 两个额外招式，按 PyNXBot 的 schema。

其他字段未读出。Index 010 解码为旷野地带活动 #7：3 到 5 星的超极巨化颤弦蝾螈、每星都有的超极巨化小仙奶、剑里的巨钳蟹和长毛巨魔、盾里的以欧路普和布莉姆温；它的 5 星颤弦蝾螈等于 PKHeX `encounter_sw_dist.pkl` 中索引 10 的记录。

下发奖励文件是一个表向量（字段 0）：TableID u64 和 Entries（字段 1），每个条目是 1 到 5 星的五个 u8 值（字段 0 到 4）和一个 u16 道具（字段 5）。游戏自己的表 `data_table.gfpak` 第 7 号（掉落）和第 6 号（加成）持有 TableID，然后是 u32 条目索引、u32 道具和一个五值的 u32 向量（`pokeldn/swsh/data/nest_rewards.json`、`scripts/gen_swsh_nest_data.py`）。遭遇用 id 在两者中指名它的表，游戏自己的优先 [pkNX `NestHoleDistributionEncounterTable`]。加成值是数量，掉落值是百分比概率。1 星巢穴的 Rewards（`raid.DEN_REWARDS`）以加成表 `0xf966212316b78eb6` 在 1 星、按其数量的行开头（经验糖果 XS x5、S x1、极巨糖果 x1），然后两个道具各一。`raid_event.rewards` 先构建加成行，然后每个掉落一行，掷每个掉落的概率或全部保留。

`raid_event.boss_pk8` 在 `raid.boss_record` 上构建头目：表里的物种、形态、等级、招式、超极巨化和极巨化等级，以及表所允许的特性、个体值、性格、性别和 PID，队伍能力值来自 `pokeldn/swsh/data/species.json`（`scripts/gen_swsh_species_data.py`）。

    bin/swsh_host.py --raid-event "FOLDER/Index 010" --raid-stars 5 --raid-event-boss 4 --raid-console-serves

不给 `--raid-stars` 或 `--raid-event-boss` 时，主机列出它取什么。`--raid-version` 选择表的版本（默认取广播的），`--raid-area` 选巢穴区域，`--raid-event-drops all` 要全部掉落；`--raid-reward` 的行替换活动自带的。

## 极巨大冒险

极巨大冒险（Max Lair，二进制中为 `chika`）在本地通信中，当每个玩家都在极巨巢穴选择「邀请他人」时匹配：第一个开网络，其余扫描并连接。Y 通讯从不列出它：主机广播活动种类 0xFF。该网络使用本地通信 id `0x0100abf008968000`、场景 50000、NodeCountMax 4（从 `0x00bd9b30` 调用的 Pia 上限，位于 `ChikaMatchingState*` `0x00bd1978..0x00bda158`）。主机在 "Communicating" 下从 3:00 倒数；没有访客时它取消冒险。冒险开始后，电脑伙伴填补空席位。

场景不是固定的。`0x00bd7e80` 从 `[comm+0x80]` 读两个 u32，先一个标志再一个值，并从 `comm+0x74` 读连接密码。`0x006a9cb0` 返回 false 时，它把场景设为 50000 + 该值，标志置位时再加 1000（`0x00bd7fdc`）。一台玩家的零售主机在场景 50480 广播了极巨巢穴网络；480 是 由克希，极巨巢穴的传说宝可梦之一。该值是玩家选择要针对的传说宝可梦，这只是一个假设；此处实测的主机都广播 50000。另一条路径上游戏模式是 50000，标志置位时为 50001，非零值进入一个搜索属性。`swsh_lair.is_scene` 接受 50000 + 0，或极巨巢穴某传说宝可梦的物种 + 0 或 1000。

极巨巢穴的匹配参数以 `0x0101` 结尾（`0x00bd7f60`），保存在 `[matching+0x280]`；交换传零（`0x010967e0`）。`+0x281` 字节置位时，对找到的网络场景的匹配（`0x006cba10`、`0x006cb5e8`）先比千位再比余数；清零时两个场景必须相等：

| 搜索方的场景 | 它接受的找到的场景 |
|---|---|
| 50000 | 任何 50xxx |
| 50480 | 只有 50480 |
| 51000 | 任何 51xxx |

`swsh_host.py --lair-legendary` 在一块射频上扫描主机自己的大厅并广播它的场景，找不到时为 50000；`--lair-scene` 设定它。所以带有目标的主机会越过 50000 的主机去搜索，而且它必须在主机启动之前就处在「邀请他人」。在 LAN 下游戏模式保持 50000 或 50001，所以目标在那儿从不隐藏大厅。

可靠 0x80 端口 0 上运行两个消息 holder，每个字段都是一个带单个字段 1 的 holder：

- id 7000，`net_contents.chika.protocol_buffers.ChikaAsyncDataHolder`（描述符 `0x1c3adb5`、`0x2066654`），大厅；
- id 8000，`net_contents.underground.protocol_buffers.UndergroundAsyncDataHolder`（描述符 `0x1c36fab`、`0x20681cc`），战斗之间。

送进极巨巢穴大厅的巢穴消息（id 2000）会被确认，但不安排任何座位。战斗像巢穴团体战那样在 0x7C 上运行，有两处不同：

- 行动是条目 1 为 `01 ff ff ff ff ff ff ff`，条目 2 是巢穴团体战那样的招式，其余九个条目 `0xff`；条目 2 的第 3 字节在极巨化回合为 `0x80`，它之前的状态消息随后携带状态 1 而不是 2；
- 访客的宝可梦倒下后，主机发类型 0x04、数据 `01 00 ff ff ff ff`；访客用一个 88 字节的行动应答，其条目 2 为零。

`pokeldn/swsh/lair.py` 是这两个 holder 的访客侧；`bin/swsh_connect.py --preset lair`（应用的「极巨大冒险（加入）」）作为玩家 1 入座，并取主机留下的第一个提供位（租借按轮选择，主机的先）。`lair.rental_pk8` 构建的租借是所记录租借的记录，加上该行的物种、形态、65 级和招式、四项 31 的个体值其余随机、随机性格、特性槽 1 或 2、性别、PID 和加密常量；初训家为研究员，精灵球，相遇等级 65，队伍能力值不含极巨化加成。一台零售版剑主机接受了它。

### 大厅 holder，id 7000

指名某个玩家的记录以它的 Pia 常量 id（u64）和玩家索引字节开头；电脑伙伴的 id 为零，索引为 2 和 3。

| 字段 | 名称 | 大小 | 内容 |
|---|---|---|---|
| 1 | ChikaTimeLimit | uint32 | 剩余秒数，来自主机 |
| 2 | ChikaPlayerInfo | 48 | 12 个零字节、13 个字符的 UTF-16 名字，然后 `02 00 00 00 00 2d 00 00 00`；zlib 压缩（可靠标志 0x10） |
| 3 | ChikaBattleReady | 16 | 玩家按下准备后第 8 字节为 1；冒险开始后第 12 字节为 1 |
| 4 | ChikaSelectPokemon | 360 | 8 个零字节、u32 该租借在共享提供中的位次、租借作为加密队伍 PK8、四个零字节 |
| 5 | ChikaBattleStart | 32 | 人类玩家的常量 id，访客的在前 |
| 8 | ChikaBattleSeed | uint64 | 来自主机；为租借提供和遭遇播种（[冒险种子](#the-adventure-seed)） |
| 9 | ChikaRentalPokemonSeed | uint64 | 来自主机，在选租借之前 |
| 11 | ChikaPlayerNumber | 40 | 四个常量 id（主机、访客、零、零），然后玩家索引 `00 01 02 03` |
| 12 | ChikaBigBoss | 16 | 第 12 字节为 1；每个玩家随 PlayerInfo 发自己的 |
| 13 | ChikaBigBossFixed | 4 | u32 冒险传说宝可梦的物种 |

字段 6、7 和 10 不发送。顺序：每个玩家加入时的 PlayerInfo、BattleReady 和 BigBoss；第 8 字节置位的 BattleReady；主机发 BattleStart、BattleSeed、RentalPokemonSeed、PlayerNumber、第 12 字节置位的 BattleReady 和 BigBossFixed；然后每个玩家的 SelectPokemon。

### 冒险 holder，id 8000

| 字段 | 名称 | 大小 | 内容 |
|---|---|---|---|
| 1 | UndergroundWaySelect | 16 | 常量 id、玩家索引、所选路径 |
| 3 | UndergroundWayResult | 1 | 所走的路径，来自主机 |
| 4 | UndergroundTradeWant | 16 | 常量 id、玩家索引，1 表示用捕获的宝可梦交换 |
| 6 | UndergroundTradeResult | 360 | 交换方的常量 id、索引、两个字节，然后是 `+11` 处的新宝可梦（加密队伍 PK8） |
| 10 | UndergroundRaidCapture | 16 | 常量 id、玩家索引、第 9 字节 |
| 11 | UndergroundRaidWant | 16 | 常量 id、玩家索引，1 表示拿走捕获的宝可梦 |
| 12 | UndergroundRaidResult | 360 | 8 个零字节、拿取方的索引（无则为 `ff`）、一个字节，然后是 `+10` 处的宝可梦（加密队伍 PK8） |

字段 2、5、7、8、9 和 13 不发送。每个访客发自己的 WaySelect、TradeWant、RaidCapture 和 RaidWant；主机用自己的以及每个电脑伙伴的一份应答，然后发结果。

### 主持一场冒险

`bin/swsh_host.py --lair-legendary SPECIES [--lair-seed N]`（`pokeldn/swsh/lair_host.py`）用一台模拟的盾主机的广播（场景 50000）广播极巨巢穴网络，像连接交换那样交换快照，然后发大厅：PlayerInfo、BattleReady 和 BigBoss，限时每秒三次，以及准备；访客准备好后，BattleStart、BattleSeed、RentalPokemonSeed 和 PlayerNumber；访客应答已开始后，已开始的 BattleReady 和 BigBossFixed。五秒后它像主持的剑那样离开（[离开](swsh_session.md#leaving)）：MIGRATION_START `44 00 01`、带主机迁移字节的会话更新、每 0.33 秒一次 START_HOST_MIGRATION，并在主机离开后或 10 秒后关闭网络。

应用的「极巨大冒险（主持）」工具运行这些开关：传说宝可梦、可选的连接密码和种子。它的种子选择器显示 `lair.adventure` 为某颗种子给出的三个租借和十次遭遇，可以抽新的，并搜索符合指定租借的种子（约每 75 个有一个提供该租借）。地图尽头的传说宝可梦是 BigBossFixed 指名的物种；访客自己的 BigBoss 全为零。租借按轮选择，主机的先，电脑伙伴会接替已离开玩家的席位。

极巨巢穴的连接密码在接待员处用 + 设定。广播携带该密码十进制值的 CRC32，前导零去掉（0000 7777 为 `7777`）；用不同的密码或不带密码搜索永远不会列出该大厅。带密码时，未发 MIGRATION_START 就关闭网络的主机会让访客停在租借界面的错误 2618-0006；有移交时，访客在 MIGRATION_START 后 0.1 秒离开，冒险继续。

### 冒险种子

冒险的宝可梦是 RomFS `bin/appli/chika/data_table/underground_exploration_poke.bin` 的行，一个 273 行的 FlatBuffer：226 个 65 级的租借和遭遇，然后 47 个 70 级的传说宝可梦（头目标志置位）。一行携带物种、形态、等级和四个招式。

ChikaBattleSeed 决定六个租借的提供和遭遇；`lair.adventure(seed)` 计算它们。Xoroshiro128+ 用该 u64 和 `0x82A2B175229D6A5B` 播种。每次选取用下一个 32 位输出为 MT19937 播种，打乱 273 个行索引（索引 i 与 i 加一个到 272 - i 的抽取交换，抽取按 `0x1ff` 掩码并在超出时重抽），然后取第一个既不是传说宝可梦、也未被选过的行。四次选取，然后在接下来两次选取之前各一次 0 到 2 的抽取，再一次，分别在入座的电脑伙伴多于 2、1、0 个时；然后是 0 到 2 和 0 到 9 的抽取，再是十次遭遇选取，每次在该行有两个属性时再跟一个输出。有三个电脑伙伴时，先有一次 0 到 27 的抽取。

租借界面显示提供位 0 到 2。每个席位依次选择，主机的先，它取走的位由下一个未用的位（3，然后 4，然后 5）补上。电脑伙伴在玩家之后选择，从不经过网络：各自取自己 0 到 2 抽取给出的界面位置，第一个伙伴取第一个抽取。`lair.partner_places(seed, taken)` 计算它；它在三次记录的冒险中（一台模拟主机与访客、我方访客对模拟主机、以及对零售版剑主机）点名两个伙伴的租借，依据是每个战斗位在主机类型 0x10 命令中使用的招式。该规则只需要 ChikaBattleSeed。某条路径会遇到哪些遭遇未知。

`swsh_connect.py --preset lair` 作为零售版剑主机的访客走过了每条路径和每次捕获选择，经过三次遭遇和传说宝可梦（雷公），其租借在每场战斗中都用了第一个招式；主机的玩家输掉了最后一场战斗，会话无错结束。

## 离开

玩家的奖励界面一结束，零售版剑主机就以每 0.33 秒一次 START_HOST_MIGRATION 关闭网络，持续 10 秒，与连接交换之后相同（[离开](swsh_session.md#leaving)）。不离开的访客会把主机的玩家冻结在旷野地带直到超时；`--leave-with-host` 在第一次时就离开。

### 战斗中离开

在本地巢穴团体战中离开的站点不会为其他人结束战斗。战斗的离开服务（由 `0x8b7830` 构建，保存在 btl-net `+0x3b8`）在处理函数 `0x8c4570` 中听到 Pia 会话的站点离开事件（`0x6b4850`，类型 1）。在本地巢穴团体战中（设置 `+4` = 2，`+0x3b8` = 1，由 `0x7e7c50` 在 `nn::pia::local` 模式下设置），它把该座位保持为已连接 30 秒（`0x7530`），然后移除该站点（`0x8c3f70`、`0x8b4140`）并重跑服务器选择；做服务器的那台主机把该座位的备用客户端（`main+0x1c0 + 8 * i`、`0x8dfcb0`）放进其中（`0x7f8450`）。丢失会话（类型 3）经 `0x10f8e30` 抛出错误 (2,4)。

在模拟的盾 1.3.2 上实测，战斗中杀掉板子的进程且不发送任何东西：

| 板子 | 主机做了什么 |
|---|---|
| 主机巢穴大厅里的访客 | 战斗继续，无错误；下一回合的菜单照常出现 |
| 主机，由主机做服务器（`--raid-console-serves`） | 战斗暂停约一分钟，然后继续，无错误；下一回合头目受到伤害 |

在经 ESP32 板子的零售版剑上，战斗进行 10 秒时杀掉板子的进程，两种角色结果相同：无错误，战斗继续。

改为干净移交（战斗中 5 秒时 MIGRATION_START，然后关闭网络）时，主机在 0x18 端口 0 上应答 `48 01`，0.1 秒后离开网络并显示 2618-0006，之后战斗离线继续。在战斗开始前离开的主机会让主机停在 "Connexion en cours"（[访客的序列](#the-guests-sequence)）。

## 尚未解决

- 不是 Pia 主机的主机会不会发布框架对象 0 到 7。
- 备用客户端会为已离开玩家的座位挑选什么。
- 零售硬件上多台主机共处一个托管大厅；目前只在模拟的盾上测过。
- PlayerInfo 的 u32 和末尾字节的含义。
- 行动的其余十个条目、极巨化，以及 8 和 2 之外的目标码。原样重放时，一段录下的水枪行动会让任何访客宝可梦使用水枪，在零售版剑主机上也是。
- 极巨大冒险：有三个电脑伙伴时伙伴的顺序；在租借界面接替已离开主机席位的伙伴，在 `partner_places` 给出位 2 的地方取了位 1。
- 极巨大冒险：PlayerInfo 的尾部字节、BigBoss、RaidCapture 与结果记录中玩家索引之后的字节，以及两个 holder 中不发送的字段。
- 零售访客会不会接受巢穴记录为零的巢穴广播中的活动头目，以及零售的活动巢穴主机会在巢穴种类位和巢穴记录里写什么。
