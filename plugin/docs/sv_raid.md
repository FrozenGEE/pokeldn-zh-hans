# 太晶团体战

本地太晶团体战是 朱/紫 的一个 LDN 场景 7 会话，最多四个站点。主机运行大厅，然后向每个参与者发送一条引导消息，其中装有四名玩家的宝可梦、头目及其 RaidPoint，之后每台主机各自进行战斗。`bin/sv_host.py --raid-seed` 主持一场零售主机可加入的团体战，`bin/sv_join.py --raid-pokemon` 加入一场由主机主持的团体战；两种情况下，程序中的玩家都会在战斗开始时离场，其宝可梦作为主机的 AI 伙伴继续战斗。地址是 朱 4.0.0 解压后 `main` 的偏移；紫 4.0.0 在相同偏移处有相同的代码（[docs/sv.md](sv.md)）。

## 主持

主机宣告场景 7、四个参与者和连接码 4970。主机通过 X、宝可入口站、太晶团体战、离线搜索加入。`--raid-seed` 配合四个上下文标志选择团体战（[种子](#the-seed)），`--raid-pokemon` 是我们玩家带来的队伍记录（PKHeX 会校验它），`--raid-reward ITEM:QUANTITY` 可重复，用 朱/紫 背包能容纳的物品行替换种子自带的奖励（即 PKHeX 辅助工具的 `bag` 列表：除关键物品外的每个口袋，未发布的物品排除在外）。`--raid-partner TRAINER` 最多为每台主机留空的槽位使用一次（一台主机时两次，两台时一次），按槽位顺序让这些 NPC 伙伴入座，`--raid-partner-progress STAGE` 选择他们来自的阶段（[伙伴](#partners)）。应用的「太晶团体战（主持）」工具带有下列标志。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

在团体战模式下，主机与交换主机在寻址对象和时机上不同：

| | 团体战主机 |
|---|---|
| 网状寻址消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播；在 ldn_mitm 上以单播发送，因为它不向对端传递广播 |
| Net 0x11 | 一条序列，重复到出现 0x12 为止 |
| 站点列表的主机条目 | 主机加入请求所指名的玩家；若玩家为占位符，则主机入座但不出现在大厅中 |
| 站点列表 | 每 2 秒重发一次，直到主机的 type 6 |
| 开场 | 只在那个 type 6 之后：十一次初始批量确认、0x81 端口 5 打开和一次 RTT 请求合并在一个数据包中；0x81 端口 1 打开、通道表和端口 2 的 type 6；20 毫秒后是身份，每 3 毫秒一条记录 |
| 端口 2 的 type 3 | 用两个 type 9 应答：主机自己的站点带代码 0，另一台主机的带代码 1 |

开场的 0x7C、0x81 端口 5 和 0x80 端口 2 消息每 0.25 秒重发一次，直到被确认，主机发送的每个 ACK 都声明该流中最低的未确认序列。

### 多台主机

`--raid-players N`（1 到 3，应用中的「加入的主机」）在一个大厅里安排最多三台主机，每台占用最低的空闲站点索引。它们共享大厅和开始流程；从第一回合起，各自带着自己的 NPC 伙伴和奖励进行自己的战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。主机为每台主机保留一组流，使用该主机的索引 *k*，而在单台主机的团体战中这里是 1：

| | 索引为 *k* 的主机 |
|---|---|
| 加入响应 | 站点索引和加入顺序 *k* |
| 站点列表 | 每个已入座的站点，我方在前；每次座位变化都以下一序列发给每台已入座的主机，重发到各自出现 type 6 为止 |
| Net 0x11 | 我方站点、按索引排列的已入座主机，然后是加入方 |
| 目标位图 | 在三个目标位下为 `1 << k` |
| 批量确认 | 第 *k* 项 |
| 开场 | 0x81 端口 *k* 和 4 + *k* |
| 端口 2 的 type 6 | 我方和已入座的成员，按加入顺序，带代码和计数 |
| 端口 2 的 type 9 | 我方的代码 0，每个已入座成员各自的代码，最后是该主机的代码 *k*；每个已入座成员都会收到该主机的 |
| 引导 | 它在槽位 *k* 的宝可梦；空位则用空槽位 |

发现座位已满，或在开始之后才到达的加入请求，会得不到应答。主机会丢弃头部和尾部都未指明其可变 ID 的每个数据包，以及位图缺少站点 0 的每条可靠消息，因为同一大厅中的主机会通过同一广播互相寻址。

端口 2 的槽位在 `+0x170` 处以 u8 代码和 u64 站点 ID 保存其成员；`0x138d208` 返回站点的代码，非成员返回 0xfd。主机的 type 3 处理函数 `0x1981e94` 取 0 到 7 中既没有成员持有、也没有排队中的 type 9 指名的那个最低代码（`0x279c9a0`），然后为每个成员广播一条 type 9，并为加入方广播一条。接收方 `0x18b68fc` 会追加它尚未列出的 `(code, id)`，且从不更改已列出的代码。type 6（`0x12fbf8c`，组装函数 `0xe457cc`）在 `+0xa0` 携带成员 ID，在 `+0xc0` 携带代码，`+0xc4` 是计数，`+0xc5` 是关闭字节；其接收方 `0x279b9c4` 会为每个成员重放一条 type 9。Lua 大厅（代码块 `be21e654`，接收方 `0.15829`；`0.N` 是主函数的原型 N）把每条消息归档到其发送方的代码下，无发送方时用 253。进入大厅的主机发送状态 0x18 和它的宝可梦；收到 0x18 的站点以它的 Ready 状态和宝可梦应答。

可靠头的接收检查（`0x6f0410`..`0x6f0430`）对 1 到 23 的任意目标数量，测试 `index >> 5` 字中接收方的第 `index & 31` 位；零售发送方写 3，即站点容量 4（`0x44dfcb0`）减一（`0x6e71c4`）。

主机把网络移交给仍在其中的最低索引。其他主机只有在下一任主机的 type 8 之后才会收到表示正在迁移的 Net 0x11（对每个已入座站点排名），随后在每台主机都应答 0x12 后收到 NetStartHostMigration，且没有 Session type 7。让这些主机留在同一场战斗中的条件：

| 条件 | 代码 |
|---|---|
| 看到另一台主机离开时，只有在迁移中才保留它：`[net+0x249]` 由表示正在迁移的 0x11 置位，或 `[net+0x1c0]` 由 NetStartHostMigration 置位 | 站点离开处理函数 `0x69d08c`、`0x69d174` |
| 序列更新的 Net 0x11 会丢弃每个被标记为已离开的站点 | `0x69e008`、`0x6b5074` |
| 下一任主机最多等待 8000 毫秒让每个 Net 站点到达状态 2，丢弃其余站点，发送 Net 0x11，等待每个 0x12 后发送 Session type 5 | NetHostMigrationJob `0x6a9cd4`、`0x6aa2a8`；`0x6d44f0` |
| 另一台主机最多等待该 type 5 10000 毫秒，然后失败 | `0x6dc024`、`0x6dc124` |
| type 7 的最后一个 u16 至多为下一任主机已应用的列表序列 | `0x6d9164` |

Pia 主机在 LDN 参与者每次变化时向每个站点发送 Net 0x11（`0x69c310`，`0x69c79c` 递增 `[NetProtocol+0x60]`，排名按 IPv4 升序 `0x6a05ec`）。在 LDN 上，加入方的 0x11 接收方 `0x69db14` 不创建站点（`0x6a2fac` 返回 0）；它的站点来自 `nn::ldn::GetNetworkInfo`（`0x6b43a8`），端口 12345。type 5 的接收方 `0x6d7f8c` 只在其地址位于该节点列表中时（`0x6a8320`）创建列出的站点（`0x6d840c`）；否则它不发送 type 6，并把已应用序列重置为 0xffff（`0x6d81a4`）。Session type 9（`0x6d4ef0`，`09 | constant id | count | constant ids`）每 3000 毫秒指名一个加入方尚未收到其消息的站点（`0x6d4a60`）；主机的接收方 `0x6d940c` 把单个被指名的站点交给踢出任务（`0x6dc878`）。

主机加入后，团体战主机发送数据包 ID 0：已入座的主机会丢弃更高 ID 之后的内容（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。站点列表的玩家 ID 是匿名的 `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）；随机 ID 不会引出 type 6。

## 大厅

团体战消息是 0x80 端口 0 上的游戏消息（[交换](sv.md#the-trade)）：

| 字节 | 字段 |
|---|---|
| 0 | 处理函数键，u16 |
| 2 | kind、step：一个 u16 消息 ID（0x012f 为引导，0x0193 为战斗开始） |
| 4 | 每个发送方的计数器，u16，由 `0xa583fc` 递增 |
| 6 | 压缩，u32：0 无，2 LZ4 |
| 10 | 载荷的明文大小，u32 |
| 14 | 网络对象 ID，u16，除非 `0x14ede48` 找到，否则为零 |
| 16 | 构造函数从不写入的两个填充字节 |
| 18 | 载荷 |

| 键 | kind | 内容 |
|---|---|---|
| 0x3380 | 0x2c | 团体战的描述符：种类（DevID）、形态、星级、太晶属性、性别、遭遇的记录号 |
| 0x3380 | 0x2d | 参与者的状态：0x00 未就绪，0x01 就绪，0x0c 主机的开始，0x0d 访客的应答，0x18 进入大厅，0x1e 主机拒绝迟到的站点（`0.30822`） |
| 0x3380 | 0x2e | 参与者的宝可梦，其加密的 344 字节队伍记录 |
| 0x3380 | 0x2f | 战斗引导 |
| 0x3380 | 0x30 | 大厅计时器，单位剩余秒数 |
| 0x0132 | 0x6e、0x73 | 主机加载战斗，然后已加载 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主机在 0x3480 之后发送的战斗开始消息 |

接收路径 `0x18bec54` 把头部复制到消息对象 `+0x40..+0x4f`，但不比较其中任何内容；它忽略 LZ4 的返回值，只把明文大小用作输出容量。

键 0x007b 上的战斗开始帧是 12 字节端口地址（三个 u32）、一个 u32 长度，以及一个载荷，其前 32 字节是由 `0x1227714` 复制的头部：u32 type 位于 0x00，u64 位于 0x08 和 0x10，u8 位于 0x18 和 0x19，填充位于 0x04 和 0x1a..0x1f。没有读取方会比较填充（`0xf5a2fc`、`0xe10088`、`0xe0fd68`、`0xe106a4`、`0xf5a810`、`0xf5bc10`；18 字节头部的最后两个字节由 `0x18bece4` 存到 `+0x4e`，只有序列化函数 `0x290b150`、`0x14c7904` 读取它们）。一位零售版 朱 访客在消息 15 和 16 的字节 0x1a..0x1f 以及 18 字节头部的最后两个字节都被置零的情况下，开始并赢下了一场战斗。除非有接收端口注册了其地址，否则 `0x14ab234` 会丢弃帧：消息 15 的地址是 (0x2713, 1, 2)，消息 16 到 20 是 (0x2713, 3, 5)；0x2713 是设置的 u32 `+0x2c`。

战斗通过 `0xe0fd68` 读取消息 16（type 0x46）：当 +0x08 处的 u64 为零时，它按 type 分支（`0xe10088`），`0x2897afc` 设置逐帧更新 `0x289358c` 对象（由 `0xfa4bb4` 配合 `0x28950c8` 构建，存放在 `[sm+0x148]`）的 `+0x71`。当 `+0x71` 为 0 时，更新会驱动读取方（`0xe0f014`）并调用 `0xfc363c([+0x48], 0)`；为 1 时，它每一帧调用 `0xfc363c([+0x48], 1)`，直到该调用返回 true（`0x28935b8` 将其清除）。

团体战主机在 0x7C 端口 1 宣告的通道表包含六个键：连接交换的四个（`0x007b`、`0x0132`、`0x0232`、`0x0332`）以及 `0x3380`、`0x3480`。零售访客先宣告那四个，0.79 秒后再宣告团体战的两个。端口 2 携带主机的 type 6：kind 5 和容量 4 下 type 7 的会话块，然后是四个槽位，主机的站点 ID 在前（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 按顺序向一台主机释放主机的消息，每条都在该主机的上一步之后；`RaidGroup` 保存同一大厅中各主机共享的内容：

| seq | 消息 | 由……释放 |
|---|---|---|
| 1 | 描述符（zlib，INITIALIZED） | 主机的厅内宝可梦（0x2e） |
| 2、3 | 状态 0x18、我们的宝可梦 | |
| | 计时器，每次下降时 | 第一台主机应答后 0.73 秒起，每秒一步 |
| | 状态 0x01 | 3.19 秒 |
| | 状态 0x0c，开始 | 在 `--raid-players` 台主机入座且都发送 0x01 之后，或计时器为 0 时 |
| | Net 0x50，属性状态 7 | 主机的 0x0d |
| | Session 站点列表，下一序列 | 主机的 Net 0x51 |
| | 引导，两个分片 | 主机的 type 6 |
| | 已加载，`0x320173` | 主机的 0x6e 或 0x73 |
| | 战斗开始，`0x803493` | 主机的 0x73 |
| | 六条战斗开始消息 | 主机的 0x93；然后是 0、0.10、0.12、0.16、0.18 秒 |

零售主机开启 180 秒的大厅并每秒发送一次计时器（`0.27104`）；pokeldn 主机在第一台主机应答时从 180 开始。主机的 0x00 或 0x18 会撤回它的 0x01。访客收到 0x0c 会立即以 0x0d 应答，不做 Ready 检查，且只有主机能开始战斗（`Raid_Start_Ready`，`0.27137`）。在主机上，`Raid_Start_Ready` 只在每个访客都就绪时启用开始项；计时器为 0 时，若没有就绪成员就解散大厅，否则开始。`Raid_Start_Go`（`0.27140`）重发 0x0c，直到每个成员都应答 0x0d，然后发送引导，槽位 *k* 放代码为 *k* 的成员的宝可梦。

受门控的消息在其里程碑之后 50 毫秒发出；Net 0x50 和站点列表每 0.5 秒重发一次直到被应答，团体战消息每 0.5 秒重发一次直到被确认。Net 0x50 是交换主机的属性体，序列为 1，字节 27 设为 7，132 个应用字节位于 +38，在标志 0x31 下做 zlib 压缩；不压缩则不会引出 0x51。

最后一台主机的消息 20 之后五秒，主机像离场的零售主机那样把网络移交给该主机（[docs/sv.md](sv.md#leaving)）：每秒发送 Session type 7 直到出现 type 8，每 0.5 秒发送表示正在迁移的 Net 0x11 直到 0x12，每 0.3 秒发送 NetStartHostMigration，最多 4 秒。绝不要改为销毁网络：零售主机会在战斗开场时显示 2318-0006。

## 战斗引导

消息 0x2f 携带一个 0xaa0 字节的记录，经 LZ4 压缩（块格式，`pokeldn.sv.lz4`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 4 x 0x158 | 四个参与者的队伍记录，已加密，主机的在槽位 0 |
| 0x560 | 0x158 | 头目的队伍记录 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化函数 `0xe327fc` 从消息对象 `+0x440`..`+0x458` 和 `+0x50` 写入这五条记录（`0xe329b4`），然后从 `+0x58` 写入四个四字，从 `+0x78` 写入 0x3c8 字节；`0x1592b7c` 选择压缩方式，`0x71d940` 运行 LZ4。RaidPoint 被整体复制（`0x1bae670` -> `0x1bae760`，getter `0x1baff98`）。零售主机会在 1395 字节处拆分该消息。

空的参与者槽位持有种类 0、等级 1、昵称 `Egg`、太晶属性 19、语言 2、当前 HP 11，能力值为 11/5/5/5/5/5。绝不要发送全零的空槽位：零售主机在战斗开始时就会崩溃。

| RaidPoint 偏移 | 大小 | 内容 |
|---|---|---|
| 0x000 | 24 | 名称，ASCII，`RaidPoint_` 加后缀（`RaidPoint_POKELDN_0` 可被接受） |
| 0x018 | u32 | 0x40 |
| 0x020 | 4 x u32 | 星级、结晶（0 普通、1 黑色、[2 和 3 为活动](#event-raids)）、`captureRate`、`captureLv` |
| 0x030 | 7 x u32 | `raidTimeData`：active、`gameLimit`、`clientLimit`、`commandLimit`、`pokeReviveTime`、`aiIntervalTime`、`aiIntervalRand` |
| 0x04c | 37 x u32 | 头目的行动配置（`bossDesc`）：HP 系数、护盾的九个值、六个额外行动（行动、时机、值、招式）、双重行动的三个值 |
| 0x0e4 | 45 x 16 | 奖励行：物品、数量、稀有物品标志、主体 |
| 0x3b4 | u8 | 零售标准点中为 0，黑色点中为 1 |
| 0x3b8 | 7 x u32 | 星级、种类（DevID）、形态、性别、等级、0、太晶属性 |
| 0x3d8 | u64 | `randSeed`，伙伴种子（[伙伴](#partners)）和战斗种子（[战斗的随机数](#the-battles-random-numbers)） |
| 0x3e0 | u32 | `raidNpcGroupID`，主机的团体战解锁阶段（[伙伴](#partners)） |

六星记录的 `raidTimeData` 为 active，`gameLimit` 450、`commandLimit` 60；一星记录为 inactive，`gameLimit` 300；其余为零。它处于 inactive 时，计时器初始化函数 `C2D7F486425487755.F0C64BA9B6853E61A` 使用游戏限制 300、命令限制 60、复活时间 30、AI 间隔 17 和随机量 6。行动：0 无，1 重置头目的能力变化，2 重置玩家的能力变化，3 一个招式，4 吸取太晶珠；时机：0 无，1 时间，2 HP；值是触发它的 HP 或时间比例。P 百分比的 HP 触发在「100 × 头目当前 HP / 其 HP 总量」的整数除法结果小于等于 P 时触发：HP 为 816 中的 414 时，50% 的行动会触发。一到六星的 HP 系数是 500、500、800、1200、2000 和 2500。

零售点的奖励行包括种子固定的行（subject = 表中的 `SubjectType`：0 每个玩家，1 主机，2 访客，3 仅一次）、subject 0 下的抽选、subject 4 下另外三次抽选，以及 subject 5 下头目的太晶碎块，数量取 `RaidGemItemRewardBoost` 的值（一到七星为 0、0、2、5、10、12、0），仅在为正时加入。奖励画面会把稀有物品行列在最前。

Lua 奖励过滤器 `C07C34FC3B976E5A7.F316609DEA110601D` 为每个玩家保留 subject 0，为主机保留 1，为访客保留 2，在符合「仅一次」条件时保留 3，保留前 N 条 subject 4 的行，其中 N 是生效中的团体战之力（料理种类 5）中与头目太晶属性匹配的最高等级（属性 18 匹配全部），并在玩家持有闪耀护符（物品 2481）时保留 subject 5。生效中的料理之力是 u32 种类、u32 属性、u32 等级，以及一个表示剩余秒数的 f32（食用时为 1800）。两个函数都在 Lua 代码块 `be21e65463b9a98f` 中，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 以同样方式构建行；对于种子 7B741233 和 09F3E337，其 45 行与零售点的字节相同。选定的奖励（`--raid-reward`）放在 subject 0 下，不带奖励加成行。

## 伙伴

每台主机用相同的 NPC 训练家填充大厅成员未占的参与者槽位，这些训练家从 RaidPoint 的两个字中抽取：`randSeed`（0x3d8 处的 u64）和 `raidNpcGroupID`（0x3e0 处的 u32）（`0.4453`；getter `0x1be5ac0`、`0x1be5c20`）。零售主机在每次开始时抽取新的 `randSeed`（`Raid_Start_Go`，`0.27140`）。该 u64 以 `0x82A2B175229D6A5B` 作为第二个字，为 xoroshiro128+（`0x17ebec0`）播种。抽取三名训练家（`0.7804`），每次对池中剩余的 n 调用 `next_int(n)`（掩码到 n - 1 的位数，结果大于等于 n 时重抽）并将其移除。空槽位按槽位顺序取这些抽取结果（`0.4455`）。

伙伴的记录从同一个 `randSeed` 取五次抽取，一场战斗中的每个伙伴共享这个种子（`raid_partners.identity`）：加密常量（为 0xffffffff 时重抽）、TID | SID << 16、PID（异色时翻转第 28 位）、身高和体重，各自为 0x30 + next_int(0xa0)。其余部分来自训练家的条目，语言为 2，亲密度为种类的初始亲密度。绑定函数 `f92C18AA6`（`0x1905a10`）构建一个以 `randSeed` 播种的 pml InitialSpec（`0x1905ce0`，转换器 `0x160ffd0`，创建 `0xdef2b8`，抽取顺序 `0xdf011c`）；其第三个参数让随机尺寸属于 M 类（SizeType 3，`0x1611cc4`）。`sex` 为 0 的条目在种类的雌性百分比至少为 15 时为雌性，否则为雄性（`0x1611d1c`）。`gemType` 为 0 时从表 `0xe78418` 取太晶属性，键为种类 × 10000 + 形态。

池为 `world/data/raid/raid_trainer_01`（16 行，阶段 0 和 1）、`_02`（18 行，阶段 2）和 `_03`（18 行，阶段 3 和 4），字段为 `difficulty_0`*N+1*（`0.7797`）。一行包含训练家 ID `raid_assist_NPC_*`、`npcPresetIndex` 和 `nameTextLabel`；该训练家的宝可梦是其 `trdata_array` 条目中的 `poke1`：特性槽位 1、2 或隐藏特性，三个招式，`gemType`，IV 31/10/31/31/10/31，EV 252 HP、128 防御、128 特防，性格勤奋，精灵球，缩放 128，无物品。`scripts/gen_sv_partner_data.py` 把它们解码到 `pokeldn/sv/data/raid_partners.json`。伙伴按等级 int(0.8 × 战斗槽位 0 的宝可梦等级) 构建，后者是主机的（`0.4455`、`0.4901`）。阶段 5 会给出以头目命名的皮卡丘伙伴并导致崩溃，因此 `raid_point` 拒绝大于 4 的阶段。

## 种子

团体战由 32 位种子和主机的状态抽取：版本、地区（帕底亚、北上、蓝莓，表前缀 `""`、`su1_`、`su2_`）、剧情进度和结晶。xoroshiro128+ 从种子和常量 `0x82A2B175229D6A5B` 开始（`0xe29340`）；它的第一次抽取（在一百个值中）按剧情阶段的界限选择普通结晶的星级（黑色结晶固定为六星），第二次在该星级和版本内按概率选择遭遇。`0xe29404` 用 `%sdifficulty_%02d` 构建表名，并把记录传给 `0x1eab5e4`，后者读取其 `raidEnemyInfo`；`0x2935b68` 遍历三个前缀和六个等级。然后，一个由同一种子新建的 xoroshiro 抽取头目：EC（种子的低半部分加 `0x229D6A5B`，因此头目记录能反推出其种子）、伪训练家 ID、PID、满个体值、个体值、特性、性别、性格（颤弦蝾螈的来自其形态的列表）、身高、体重和缩放，与 PKHeX 的 `Encounter9RNG.GenerateData` 一致；太晶属性和奖励抽选各自再用一个新的生成器。

`pokeldn.sv.raid_encounter` 在 `pokeldn/sv/data/raid_base.json` 上实现它，该文件由 `scripts/gen_sv_raid_data.py` 从 Tera-Finder 的遭遇列表和奖励表、PKHeX 的个人表，以及游戏 RomFS 中的十八个 `raid_enemy_XX_array` 表构建（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，FlatBuffers，带有各自的 `.bfbs` schema）。在每个上下文中超过 12600 个种子上，其头目与 PKHeX.Core 26.8.26 逐字段相同，包括六个帕底亚遭遇（记录 5094 到 5099），其零售表给出太晶规则 0（种类自身的属性），而 PKHeX 将其记为规则 1（任意属性）。结晶构建函数 `0xe26ff0` 读取 `gemType`，并在 0 和 1 两种情况下都抽取 18 种之一（`0xe27414` 处的 `cmp w9, #2`，重抽到值小于 18），与 PKHeX 一致；通用转换函数 `0x160e108` 把 0 视为种类自身的属性，但不在团体战的路径上。由种子 `BD13FB43`（紫、帕底亚、四星）构建的头目记录与零售引导逐字节相同；由 `7B741233`（朱、帕底亚、五星）构建的与法文零售版 朱 相同，只是昵称和语言不同：零售主机写入自己的语言和该语言的种类名（`Embrylex`，3），生成器写入英文（2）。无论哪种情况，主机都用自己的语言显示头目名。

团体战表中的种类是游戏的 DevID：916 及以前是全国图鉴编号，917 起是游戏自己的顺序（小锻匠 957 对应 1000），即 `gen9.internal_index`。描述符和 RaidPoint 也携带 DevID：给零售版 朱 一个种类为 1000 的描述符和 RaidPoint，它列出并战斗的是小锻匠。黑色结晶记录的战斗等级为 90，带努力值（例如 128 防御和 128 特防），捕获等级为 75；普通记录的两个等级一致，努力值为零。引导中的头目记录和 RaidPoint 摘要携带战斗等级和努力值，RaidPoint 的 `+0x2c` 是捕获等级：由 `09F3E337`（朱、帕底亚）构建的黑色头目与法文零售版 朱 相同，只是昵称和语言不同。

## 活动团体战

宝可入口站新闻的配送包含 `raid_enemy_array`、`fixed_reward_item_array`、`lottery_reward_item_array`、`raid_priority_array`（按基础表布局的 FlatBuffers）以及 `event_raid_identifier`（一个 u32，等于优先级表的 `VersionNo`）。后续配送会在补丁后缀（`_1_3_0`、`_2_0_0`、`_3_0_0`）下重复每个文件；读取最新的一个。一条记录会加上 `RomVer`（0 两个版本、1 朱、2 紫）、`DeliveryGroupID`、`Difficulty`（七星为 7）、`CaptureRate`（0 从不、1、每存档一次为 2）以及自己的奖励表；其 `BossPokePara` 固定：

| 字段 | 活动记录 |
|---|---|
| `Sex` | 0 抽取；1 雄性、2 雌性，不抽取 |
| `Seikaku` | 0 抽取；性格加 1，不抽取 |
| `TalentType` | 1：`TalentVnum` 个满个体值；2：`TalentValue` 的六个个体值，不抽取 |
| `RareType` | 0 抽取；1 从不异色（翻转第 28 位）；2 总是：把 PID 的高半部分改写为异色异或 0 |
| `ScaleType` | 0 两次抽取；1 到 5 在 0-15、16-47、48-207、208-239、240-255 中各抽一次；6 用 `ScaleValue` |
| `Item`、`EffortValue` | 头目携带的物品和战斗努力值 |

`TimeDesc` 是记录的 `raidTimeData`（RaidPoint 0x030）：在每个七星记录（`gameLimit` 450 到 900，`commandLimit` 60）和五个五星记录上为 active。

巢穴属于一个配送组，1 到 10。由种子初始化的 xoroshiro 抽取并丢弃标准的星级掷骰，然后取一个值，它落在该组中符合主机版本和允许星级的记录的总概率之下，并选取区间包含它的记录 [PKHeX `EncounterDist9.GetIsPossibleSlot`]：

| 进度 | 阶段 | 抽取的星级 |
|---|---|---|
| 开始，太晶团体战 | 0 | 1、2 |
| 三星 | 1 | 1 到 3 |
| 四星 | 2 | 1 到 4 |
| 五星、六星 | 3 | 3 到 7 |

概率为 0 的记录从不会被抽中。奖励是记录的固定表，然后从配送的表中抽选（七星按六星计）。空的数量为 0 的抽选槽位不给出任何东西；索财灵的首次 朱 轮次只有这样的槽位。

`pokeldn.sv.raid_event` 读取一个配送文件夹（一个 [EventsGallery](https://github.com/projectpokemon/EventsGallery) 活动或其 `Files`）：

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint 携带记录的捕获率，并把结晶设为 2（活动）或 3（七星活动）（Tera-Finder `RaidContent`）。应用的「太晶团体战（主持）」工具下载图库，并把版本、进度和结晶收窄到该活动生成的范围（[团体战活动](gui.md#raid-events)，`raid_event.dens`）。

捕获率 2 表示每个存档只能捕捉一次。存档列出已捕捉的记录号（块 `0x8B14392F`；击败标志 `0xA4BA4848`，PKHeX `RaidSevenStar9`），重开的轮次共用同一个编号，因此捕捉一次就关闭所有轮次。主机会按大厅描述符的记录号检查该列表；只要编号在列表中，无论 RaidPoint 携带什么捕获率都会阻止捕捉。`--raid-catch-normal` 把「仅可捕捉一次」的记录当作普通捕捉提供：捕获率为 1，描述符中使用一个替身记录号，即该记录的日期加后缀 99（`raid_event.stand_in`），没有任何配送使用它，捕捉后存档也不会列出它。没有任何 PK9 字段或 PKHeX 遭遇保存该记录号，因此合法性不依赖它；在 331 场「仅可捕捉一次」的团体战上，主机发送的头目与 PKHeX 对该团体战的捕捉结果相同。七星捕捉只有在拥有「最强之证」时才合法，该证章由主机给出。

固定行的 subject 3（七星的招式学习器和特性膏药）由每台主机的奖励过滤器应用。团体战头目之后的种类数据来自 `pokeldn/sv/data/species.json`（`scripts/gen_sv_species_data.py`）。在 EventsGallery 的 153 个配送上，pkNX 的遭遇与 PKHeX.Core 26.8.26 的相同，20 080 个生成的头目与 PKHeX 的 `GenerateSeed32` 相同，`scripts/check_sv_raid_events.py` 与每个 `Encounters.txt` 一致。

## 寻找种子

应用的团体战种子字段显示该种子在工具上下文中给出的头目和奖励，「查找团体战」从第一个种子开始（手动输入或随机选取），在过滤器留下的每个上下文中搜索（`pokeldn.sv.raid_search`），条件包括种类、星级、太晶属性、性格、性别、异色、尺寸证章和个体值范围。它按头目能力值的分数对结果排序（HP 乘以其两项防御之和、单看任一项防御、较高的攻击能力值，或总和），或按想要的奖励排序（见下文的「最想要的奖励」）。除非指定了种类，否则每个种类只保留一个结果。

### 尺寸证章

PKHeX 允许缩放 0 时的「迷你之证」和缩放 255 时的「巨大之证」（`MarkRules`）；查找器的尺寸证章过滤器要求其中之一。缩放在身高和体重之后抽取：

| 缩放规则 | 缩放 | 为 0 或为 255 的概率 |
|---|---|---|
| 两次抽取（规则 0），所有普通和黑色头目 | `next_int(0x81) + next_int(0x80)` | 各为 16 512 分之一 |
| 从 0（规则 1）或从 240（规则 5）开始的活动区间 | `next_int(16) + low` | 触及的那一端为 16 分之一 |
| 活动自己的值（规则 6） | 记录的 `scale` | 总是或从不 |

`raid_search.size_marks` 给出一个活动的头目能取得的证章；查找器会把其余证章置灰。

### 想要的奖励

「奖励」区要求若干物品行以及一场团体战至少应给出的数量，同一物品的数量会相加。可提供的物品和数量是所搜索的团体战能给出的那些（`raid_search.reward_choices`）。搜索会跳过无法给出所需奖励的遭遇，然后在抽取头目之前先抽取种子的奖励。

「最想要的奖励」按顺序以想要的物品对结果排名。一场团体战中某物品的总量算作一位数字，其位次取决于所搜索的团体战能给出的总量（`raid_search.ranked_rewards`）；靠前物品的数字组成一个小于 2^31 的分数，与种子一起保存在 64 位排名中。每个已知团体战都能容纳五件物品。

### 辅助工具的扫描

PKHeX 辅助工具在所有核心上扫描种子（`services/pkhex/RaidScan.cs`，由 `pokeldn.sv.raid_scan` 驱动）：遭遇、直到缩放的头目、分数、过滤器和奖励。它给出某个上下文最好的种子，`search` 再用 Python 重建它们的团体战，因此结果和并列顺序都以 Python 扫描为准（`tests/test_sv_raid.py` 会比较两者）。每个遭遇行的最佳可能排名在每次请求中只计算一次，某行的种子如果无法超过已保留的排名，就在此停止。

一次请求包含 16 777 216 个种子，之后是辅助工具在约 0.25 秒内扫描的数量，最多 268 435 456 个。一次搜索在每个上下文最多覆盖 2^32 个种子（`most_seeds`）；查找器提供一亿个或全部种子。「在第一个匹配处停止」（`stop_at_first`）返回最早的匹配种子。没有辅助工具时，Python 每秒扫描约 22 000 个种子，查找器提供 100 000 个。

| 搜索，Apple M4，辅助工具已预热 | 时间 |
|---|---|
| 42 个上下文各 100 000 000 个种子，查找器默认 | 5.2 秒 |
| 一个上下文的全部种子 | 6.1 秒 |
| 42 个上下文的全部种子 | 4 分 3 秒 |

## 主机之间的战斗

在两台模拟的 朱 4.0.0 之间测得，一台主持四星结晶，另一台从宝可入口站加入，空座位上有两个 NPC 伙伴。主持的主机整场战斗都留在会话中。每条战斗消息都是键 0x007b 上的战斗开始帧，地址为 (0x2713, x, y)，其 32 字节头部的 type 位于 +0x00，u64 步骤计数器位于 +0x08，u64 回合数位于 +0x10，然后是 +0x18 处的 5 和 +0x19 处的对战者或站点字节：

| type | 来自 | 大小 | 内容 |
|---|---|---|---|
| 0x01、0x05、0x11、0x15、0x25、0x29、0x47、0x49 | 主机，地址 (0x2713, 1, 2) | 50 到 20626 | 一个步骤；每个访客在相同计数器下以 type + 1 应答 |
| 0x02、0x12、0x16、0x26、0x2a、0x48、0x4a | 每个站点，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 对一个步骤的应答 |
| 0x06 | 站点为自己的对战者发送；主机为自己的、为每个 NPC 的、再为访客的发送 | 250 | 一个对战者的指令；+0x19 是对战者槽位（0 主机，2 访客，3 和 4 NPC） |
| 0x15 | 主机，每个行动中的对战者一条，包括头目 | 20626 | 回合：+0x20 处五个 0x70 字节的行动块（槽位 0 主机、1 头目、2 访客、3 和 4 NPC），+0x250 处每个槽位一个字节，统计其块中的行动数（[行动](#actions)），+0x258 处服务器命令队列的长度，+0x25c 起是队列；压缩后 123 到 802 字节 |
| 0x46 | 主机，开始时 62 次 | 54 | |
| 0x51 | 主机 | 86 | |

战斗是服务器加客户端。主机的构建函数 `0x113c8a0`（type 0x15 位于 `0x113c908`）复制行动块，运行回合（`0x113e3d0`）并附加它产生的服务器命令队列；主机的 AI 生成 NPC 的指令，头目的行动只会通过 0x15 到达访客。访客执行队列，并且对于 type 0x13、0x15、0x17、0x19、0x1f、0x23、0x25 和 0x4d，它用同一个构建函数从主机的行动块重建消息体，并比较大小和字节（`0xf5cfa4`）；不一致时转到 `0xf5bfd4`，即接收超时处理函数。主持战斗的站点必须从相同状态产生 朱 自身引擎所产生的队列。

### 哪个站点运行服务器

战斗服务器是端口 2 成员列表的第一项，每台主机都根据大厅主机的 Session type 6 和 type 9 构建该列表；`pokeldn.sv.port2.build_session` 把主机放在最前。

| 步骤 | 代码 |
|---|---|
| 团体战开始 `0.4455` 把服务器槽位设为 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`，设置 `+0x94` |
| 成员 i 映射到槽位 0、2、3、4；其代码写入 `+0x99+slot`，对于自己的代码则把槽位写入 `+0x90` | `0x1ccd15c`，作用于端口 2 的 `+0x170`；`0x2d363a0`、`0x130ea2c` |
| `0x2a1cd74` 在战斗开始时把设置的 `+0x94` 复制到 `net+0x58`，把 `+0x90` 复制到 `net+0x5c` | 来自 `0x18915c4` |
| 当 `!setup.710 && slot == net+0x58` 时，主机就是服务器 | net vf `+0x78` = `0x2a1d994` |
| 0x15 检查器只安装在非服务器上 | `0xfb0ee8` |
| 接收超时或检查失败会调用 net vf `+0x70` = `0x2a1d920`；在团体战中 `0x18e217c` 把 `net+0x58` 设为主机自己的槽位 | `0xf5bfd4` |

设置的 `+0x710` 只由 `0x7faed0`（Lua `f3AF42713`）设置，团体战开始从不会设置它。失去服务器的主机会把自己变成服务器，因此当大厅主机停止发送时，每台主机各自进行自己的战斗。成员向量只追加，由 type 6 或 7 的会话块（`0x18b566c`，先追加）、type 6 的重放（`0x279ba2c`）和 type 9（`0x1954bac`）通过 `0x18b65c8` -> `0x18b68fc` 写入；在任何块之前的 type 9 会被丢弃（`0x18b65e4`）。引导中的参与者 k 属于代码为 k 的成员；成员代码指向空的参与者会中止加载（2162-0001）。已失效转移的主机用自己的 AI 运行其他每个对战者（`0xfa52b0`、`0xfa5314`）。它的代码取自向量中第一个具有其站点的条目（`0xd5f3b4`）；Lua 槽位循环没有 break，因此最后一个匹配的条目会设定其槽位。

### 战斗的随机数

回合中的每次随机抽取都来自一个 0x28 字节的 xoroshiro128+ 对象（vtable `0x4500bd0`）：

| 偏移 | 大小 | 内容 |
|---|---|---|
| 0x00 | 8 | vtable |
| 0x08 | 2 x u64 | 状态 |
| 0x18 | u64 | 种子 |
| 0x20 | u64 | 已进行的抽取次数 |

服务器的主模块（0x378 字节，构造函数 `0x12742d0`）把它保存在 `+0x10`；回合代码以 `[[x+0x10]+0x10]` 访问它（`0x11440e8`）。模块的初始化函数 `0x127d824` 把状态设为种子和 `0x82A2B175229D6A5B`，计数设为 0（`0x127d9a8`），种子取自其参数块的 `+0x20`。访客的检查器从战斗设置的 `+0x718` 填入该字（`0x2891748`）；团体战开始 `0.4455`（@1152..@1157）通过 Lua 绑定 `fAF4A81E0`（setter `0x7faf1c`）把 `+0x718` 设为 RaidPoint 的 `randSeed`。伙伴种子同时也是战斗种子，由写入引导的站点选择。服务器构建的每槽位模块（`0x126ba88`，来自 `0xfa9f90`）以种子 0 初始化。

一次抽取会把 `s0 + s1` 相加并推进状态；计数按调用加一，而不是按重抽加一：

| 函数 | 抽取 |
|---|---|
| `0x11440f0(rand, n)` | 小于 n 的 u64：`s0 + s1` 掩码到 n − 1 的位数，结果大于等于 n 时重抽；n 小于 2 时返回 0 且不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f`，结果大于等于 100 时重抽；小于 p 时为 true |

许多回合函数会内联该步骤，而不是调用这些函数。

### 每个招式的伤害与抽取

一次招式使用按下列顺序抽取：

| 抽取 | 时机 | 决定什么 |
|---|---|---|
| `chance(25)` | 使用者麻痹 | 完全麻痹 |
| `chance(33)` | 使用者混乱 | 击中自己，其掷骰是替代该招式抽取的 `below(16)` |
| `chance(accuracy)` | 招式有命中率；100 也会抽取 | 是否命中；命中率是招式的 (3 + n) / 3，n 小于 0 时为 3 / (3 − n)，截断，n 为使用者的命中等级减去目标的闪避等级（在 ±6 内），再加上特性的修正 |
| `below(24)`、`below(8)`、`below(2)` | 伤害招式，按击中要害等级 0、1、2；必定击中要害的招式（冰息、暗冥强击、千变万花、流水连击）不抽取 | 结果为 0 时击中要害 |
| `below(16)` | 伤害招式 | 掷骰 r：伤害乘以 (100 − r) / 100 |
| `chance(p)` | 概率为 p 的追加效果（泰山压顶的 30） | 该效果；火焰牙、冰冻牙和雷电牙在状态之前先抽取畏缩，与 Showdown 的列表顺序相反 |

对头目的畏缩追加效果不抽取（[回合队列中的一个招式](#a-move-in-the-round-queue) 给出了规则）。混乱的追加效果会在其 `chance(p)` 之前，通过 `below` 和 `chance` 之外的一次调用把生成器推进一次：在记录每次抽取的 20 次混乱抽取中，无论该步骤输出什么都是 20 次（念力、幻象光线、水之波动、奇异蒸汽、魔法暴冲）。成功施加的混乱不抽取持续时间。100% 的降低能力追加效果（灵魂冲击、重踏）在某些回合抽取 `chance(0)`，在另一些回合什么都不抽。速度相同的对战者在速度排序中抽取 `below(2)`（[速度相同](#speed-ties)）。面对头目或拥有精神力（特性 39）的目标时，畏缩追加效果不抽取，除非使用者拥有破格、涡轮火焰或兆级电压（104、163、164）；面对本回合已经行动过的玩家时，它会抽取其 `chance(p)`，而成功施加的畏缩不会向队列添加任何内容。接触招式命中静电、毒刺、火焰之躯或迷人之躯（特性 9、38、49、56），或来自拥有毒手（143）的使用者时，会在招式的追加效果之后抽取 `chance(30)`；命中迷人之躯时只在雄性与雌性之间抽取。提高使用者能力的追加效果（蓄能焰袭、钢翼）会抽取其概率，并在命中的 `0x42` 之后、击倒指令之前添加提升，即使该击倒击倒了目标也一样。降低使用者能力的招式（近身战、臂锤、冰锤）会在其掷骰之后抽取 `chance(100)`，并在命中的 `0x42` 之后为每项能力添加 `0x0d (A, stat, n)`、`0x93` 和 `0xcb (A, 31 + stat, A, stat)`（记录每次抽取的战斗会显示这次抽取）。成功触发的静电、毒刺或火焰之躯会在目标的特性发动中、追加效果的指令之后使攻击者麻痹、中毒或灼伤：`0x25 (T)`、`0xc7 (T, 0)`、来自 T 的施加（[状态](#statuses)）、`0xc8 (T)`；已经处于异常状态或免疫的攻击者不显示任何内容。粗糙皮肤和铁刺（24、160）在发动中对接触作出回应（即使该接触击倒了其持有者），使用 `0x01 (A, T, A 最大 HP 的八分之一, 20)`、`0x9a (A, -damage)` 和 `0xcb (A, 143, A)`；黏滑和卷发（183、221）则使攻击者速度下降一级。吸取招式的回复紧接在命中的 `0x42` 之后、追加效果和接触回应之前，并读取它们之前的 HP。击倒头目的一击不抽取追加效果，也不抽取接触概率。在记录每次抽取的 156 场 oracle 战斗中，插件构建的每个回合的抽取都与记录一致。

一场战斗在第一回合之前抽取一次 `below(100)`。伤害采用 Showdown 的第九世代公式（数据来自 Pokemon Showdown 的 `moves.json` 和 `typechart`），使用队伍记录的能力值，且头目只按太晶属性防守：在没有任何能力等级变化之前对头目的 1346 次命中中，有 921 次符合；在记录每次抽取的 140 次命中中，有 137 次的记录掷骰和击中要害抽取给出了记录的伤害。不符合的命中出现在头目开盾期间（约为公式的 0.45）、来自有自己规则的招式（扑击、电力上升、多段招式），或被剩余 HP 上限截断。

特性会像 Showdown 那样改变公式，各自单独应用，带有自己的 4096 分数修正（两个特性串联成一个修正的情况未测量）：活力（55）把物理招式的攻击提高 1.5 倍，并把命中率降到 3277/4096；复眼（14）把命中率提高 5325/4096，上限 100；厚脂肪（47）把攻击方对火和冰的能力值减半，洁净之盐（272）对幽灵减半，且洁净之盐的持有者不会从追加效果获得异常状态；神秘之剑攻击防御能力值，逐步击破、圣剑和 DD金勾臂无视目标的防御和闪避等级；强壮之颚（173）把咬类招式的威力提高 1.5 倍，舍身（120）把反作用力招式的威力乘以 4915/4096；有色眼镜（110）在属性倍率之后把效果不佳的命中翻倍；冰鳞（246）在灼伤减半之后把特殊命中减半，除非攻击者拥有破格、涡轮火焰或兆级电压；过滤器、坚硬岩石（111、116，两者都被破格无视）和棱镜装甲（232）在那里把效果绝佳的命中乘以 0.75。连续攻击（92）给出五次命中，并且仍然抽取命中次数掷骰。天恩（32）使每个追加效果的概率翻倍；恶臭（1）添加 10% 的畏缩，在招式自身的追加效果之前抽取；目标身上的鳞粉（19）移除追加效果及其抽取。坚硬脑袋（69）不受反作用力伤害。在没有对战者携带物品时，贪吃鬼、顺手牵羊、共生、熟成和反刍（82、124、180、247、291）什么都不做。

晴天把火属性命中的基础伤害提高 1.5 倍、把水属性命中减半，雨天相反，均在击中要害之前（Showdown 的 `onWeatherModifyDamage`；125 个带此类命中的语料回合构建结果一致）。悠游自如、叶绿素、拨沙和拨雪（33、34、146、202）在各自的天气中使速度翻倍，对排序键、排序和 `0x5a` 都一样；沙隐和雪隐（8、81）在各自的天气中把针对其持有者的招式命中率降到 3277/4096（83 个语料回合中，六者之一处于其天气，构建结果一致）。沙隐、防尘、拨沙和沙之力（8、142、146、159）不受沙暴伤害。下雪时冰属性面对物理命中时防御提高 1.5 倍，正如沙暴时岩石属性的特防提高。

起死回生和抓狂的威力取自使用者 HP 的 48 分之一数（Showdown 的表：低于 2 为 200，低于 5 为 150，低于 10 为 100，低于 17 为 80，低于 33 为 40，否则为 20）。拥有适应力（91）的头目，其太晶属性同时也是自身属性之一的招式获得 2.25 的本系加成，其他太晶属性招式获得 2.0，自身属性的其他招式获得普通的 1.5。

有自己威力规则的招式遵循 Showdown 的 `moves.ts`：以牙还牙在目标于本回合更早行动时翻倍（被破盾丢弃的头目回应不算），祸不单行对处于异常状态的目标翻倍，电力上升对电气场地中的接地目标翻倍；硬撑在除睡眠外的异常状态下翻倍，毒液冲击对中毒目标翻倍，闪电猛冲和全开猛撞在效果绝佳时对属性倍率之后的伤害乘以 5461/4096，广域战力由接地使用者在地精神场地中使用时为 1.5。翻倍的电力上升在其 `0x8b` 的第五个参数中携带 1；翻倍的以牙还牙携带 0。在构建结果一致的语料回合中，以牙还牙和电力上升各出现一次提升；祸不单行、硬撑、毒液冲击和闪电猛冲只以未提升的形式出现。

场地（青草 1、薄雾 2、电气 3、精神 4）会改变招式威力：接地使用者使用与其同属性的招式时为 5325/4096（草、电、超能力；薄雾场地不增强任何属性），龙属性招式命中薄雾场地中的接地目标、地震或重踏命中青草场地中的接地目标时减半。对战者除非是飞行属性、拥有飘浮或携带气球，否则视为接地。在电气、精神或薄雾场地下的 151 个语料回合（42、57、52）用这些规则构建结果一致。

头目的 HP 总量是其记录的 HP 乘以 RaidPoint 的 HP 系数再除以 100（[战斗引导](#the-battle-bootstrap)）：在赢下的 oracle 战斗中，一星 78 场、二星 84 场、三星 125 场、四星 35 场，分别在 `0x37 (2, 2, damage)` 中承受记录的 HP 的正好 5、5、8 和 12 倍后结束；其余的承受更少，经由护盾和有自己规则的招式。

### 状态

成功施加主要异常状态的追加效果，会在命中的记录之后运行：`0x13 (T, condition, 0, value, A)`、`0x90 (T, condition)`、`0xa7 (T 的位置, code)` 和 `0xcb (A, text, T)`：

| 状态 | condition | value | code | text |
|---|---|---|---|---|
| 麻痹 | 1 | 1 | 46 | 92 |
| 睡眠 | 2 | turns << 3 \| 2 | 42 | 103 |
| 冰冻 | 3 | 1 | 45 | 97 |
| 灼伤 | 4 | 1 | 44 | 86 |
| 中毒 | 5 | 1 | 43 | 79 |
| 剧毒 | 5 | 7801 | 43 | 80 |
| 混乱 | 6（无 `0x90`） | turns << 3 \| 2 | 47 | 116 |

睡眠追加效果把其回合数抽取为 2 + `below(3)`，混乱追加效果为 2 + `below(4)`，均在其 `chance(p)` 之前，通过抽取日志不显示的一次调用（`rand+0x20` 处的调用计数器仍会计入它）。已经处于异常状态的目标，或按其属性免疫的目标（电属性对麻痹、火属性对灼伤、冰属性对冰冻、毒属性和钢属性对中毒）不受任何影响。混乱追加效果命中我行我素（20）时仍会抽取，但不显示任何内容。

在招式之前，畏缩的对战者会显示 `0xcb (A, 122, A)` 和 `0x52 (A, 0)`；冰冻的对战者抽取 `chance(20)` 以解冻，若仍冰冻则显示 `0xcb (A, 98, A)`、`0xa7 (A 的位置, 45)`、`0x52 (A, 0)` 和 `0x1d (A, P, type, 0, 0, M, M)`；麻痹的对战者抽取 `chance(25)`，完全麻痹时以同样方式显示消息 93 和代码 46；睡眠则显示消息 104 和代码 42。每一种都在招式的处理器 `0x5a (A, M, 0x72000 + speed)` 之后，以两次 `0x5b (A, M)` 和 `0x1e (A, 0)` 结束。麻痹的对战者速度在其能力等级之后减半。灼伤使用者的物理伤害在属性相性之后减半，至少为 1。火属性命中冰冻的目标会在其 `0xd1` 之后使其解冻：`0x14 (T)`、`0x90 (T, 0)`、`0xcb (T, 99, T)`。护盾升起以及头目自身的能力重置（在其 `0x0f (2)` 与 `0xc2 (3, 2, 2)` 之间）会用 `0x14 (2)` 和 `0x90 (2, 0)` 治愈头目的异常状态；护盾还会用 `0x15 (2, 6)` 结束其混乱。

混乱在招式之前、冰冻或睡眠检查之后生效；同时混乱且麻痹的对战者未测量。其回合数减一；为 0 时以 `0x15 (A, 6)` 和 `0xcb (A, 118, A)` 结束，招式继续。否则它会显示 `0xa7 (A 的位置, 47)` 和 `0xcb (A, 117, A)`，并抽取 `chance(33)`；击中自己时只抽取其掷骰 `below(16)`，别无其他：Showdown 的 40 威力无属性物理伤害，按对战者自身的攻击和防御等级计算，显示为 `0x91 (A)`、`0x01 (A, 使其混乱的对战者, damage, 2)`、`0x9a (A, -damage)`、`0xca (A, 576, A)`、`0x52 (A, 0)`，然后是被中止招式的结束（头目的则带其 `0x1d`）。头目的额外行动招式在其 `0xc1 (9, 0)` 和 `0xc1 (9, 1)` 内以同样方式检查其混乱和麻痹，被中止的招式以 `0x1d (2, P, type, 0, 0, M, M)` 结束。

濒死会清除对战者的异常状态和混乱。

在回合结束时，灼伤在其 `0x19 (b, 4)` 之后立刻造成对战者记录 HP 的十六分之一（头目的记录 HP，而不是其 HP 总量），中毒在 `0x19 (b, 5)` 之后造成八分之一，剧毒在其第 n 个回合结束时造成 n 个十六分之一：`0xa7 (b 的位置, 44 或 43)`、`0x01 (b, 施加它的对战者, damage, 39 或 38)`、`0x9a (b, -damage)` 和 `0xcb (b, 88 或 82, b)`。盐腌（864）在命中的 `0x42` 之后对目标设置 condition 46（`0x13 (T, 46, 0, 1, A)`、`0xcb (A, 1033, T, A)`，其 100% 概率会抽取；精神噪音的治愈封锁以同样方式，使用 `0x13 (T, 15, 0, 18, A)` 和 `0xcb (A, 283, T)`）；在每个回合结束时，紧接在 `0x19 (b, 46)` 之后，它造成记录 HP 的八分之一，对水或钢属性为四分之一：`0xa7 (b 的位置, 152)`、`0x01 (b, A, damage, 0)`、`0x9a (b, -damage)`、`0xcb (b, 125, b, 864)`。对已被盐腌的目标再次使用盐腌不添加任何内容。

在回合结束时被击倒的玩家（由盐腌、灼伤、中毒或沙暴）会在该伤害的指令之后立刻运行击倒指令，带 `0x49 (V, 0, 0)` 且没有 `0x09`，仅当 s（对其施加盐腌、或升起沙暴的对战者）是其对手时才以 `0x38 (s)` 结束（由同伴的吐沙升起的沙暴不显示任何内容）。显示的伤害是完整的分数值。

头目身上的自信过度（153）在其一击击倒玩家之后、命中的 `0xd1` 之后提高其攻击：`0x25 (2)`、`0xc7 (2, 153)`、`0x0c (2, 1, 1)`、`0x92`、`0xcb (2, 11, 2)`、`0xc8 (2)`。在语料计为 +5 的情形（一场战斗中三次击倒）下它不显示任何内容；当时头目是否已在 +6 未知。加速（特性 3）在 `0x44` 列表之后提高速度（`0x25`、`0xc7`、`0x0c (b, 5, 1)`、`0x92`、消息 15、`0xc8`），在回合结束的最后三次对战者排序之前，例外是此后尚未指挥过一个回合的复活对战者（语料中两种情形各 2 例；Showdown 的 `activeTurns`）。脱皮（61）和湿润之躯（93）在无异常状态时、以及头目身上的治愈之心（131，它没有同伴）在回合结束时不显示也不抽取任何内容；处于异常状态的对战者身上的脱皮会在那里抽取 `chance(33)`（语料中没有出现治愈）。

### 速度相同

战斗用交换排序按速度排列对战者和行动：每个条目与它之后的每个条目比较，当后者的键更大时后者前移。键相等时抽取 `below(2)`，为 1 时后者前移，因此一次相同会在两个相等条目的每次比较中各抽取一次。对战者 id 是 1 到 5，头目是 2。在 142 场把两个对战者的速度强制为相同值的 oracle 战斗中，按 id 顺序对五个对战者排序，在战斗开始时给出的抽取次数与记录一致的为 142 场。

| 何时 | 对什么排序，按此输入顺序 | 排序次数 | 谁读取结果 |
|---|---|---|---|
| 战斗开始时，在复制（Trace）的抽取之前 | 五个对战者，id 顺序 | 1 | 上场事件 |
| 一回合开始时 | 该回合的行动，指令顺序；键为优先度，然后是非慢出，然后是速度 | 3，每次基于前一次的结果 | 第一次：第二次 `0x51` 遍历；第三次：招式的顺序 |
| 每个招式之后、最后一个除外 | 这些行动 | 1 | 队列中没有任何东西 |
| 一回合结束时 | 站着的对战者，每次都按 id 顺序 | 3 | 第二次：`0x43` |
| 头目倒下的那一回合结束时 | 站着的对战者 | 无：不抽取 | 按速度顺序的 `0x43`，相同则按 id 顺序（5 场有相同的语料胜利中 5 场） |
| 回合结束时（每四个回合） | 站着的对战者，每次都按 id 顺序 | 8 | 第四次：沙暴、吃剩的东西和 `0x19` 的顺序；第七次，在回合结束之后：`0x43` |

回合结束的 `0x43` 顺序在 123 场战斗中有 109 场与第二次排序一致；其余 14 场中有对战者的速度在该回合被招式改变。在双方行动者相同的 27 个回合中，链式行动排序在 27 个回合里都与 `0x51` 和招式顺序一致；在到达两个招式的 3 个回合中，第一个招式之后的抽取都出现了。在前五次排序不一致的 12 个语料回合结束中，第四次排序在 12 个里都给出了残余顺序；第一次、第二次、第三次或第五次会在其中一些上失败。

头目的复制对其能复制其特性的玩家按 id 顺序抽取 `below(N)`：当一名玩家拥有面影辉映时抽取 `below(3)`。命中硬壳盔甲（特性 75）的招式不抽取击中要害。

拥有变身者（Imposter）的头目在战斗开始时变成对战者 1，并用该对战者的能力值战斗，但 HP、招式、属性和能力等级仍是自己的（其太晶属性不变）。站点仍会命令它使用变身（Transform），而此后每次都会失败：`0xc9 (2, 0, 144, P, 1)`、`0x7b`、五个零组、`0xca (2, 567)`、`0x1d (2, P, 0, 1, 0, 144, 144)`、两次 `0x5b (2, 144)` 和 `0x1e (2, 0)`，在其处理器的 `0x5a` 之后。与处理器招式并列且键相同的行动会像任何相同一样排序和抽取（11 场语料战斗）。

### 回合队列中的一个招式

在一个回合的队列中，一个对战者的招式是一段连续的指令。对战者的客户端位置对对战者 1、3、4、5 是 0 到 3，对头目是 4；A 是使用者，T 是目标，M 是招式，`type` 是招式的属性索引，`cat` 是其类别（1 物理，2 特殊）。在玩家的招式命中头目、且头目的回应命中玩家的 oracle 回合上测得：

| 指令 | 含义 |
|---|---|
| `0x05 (A, slot, pp)` | 玩家的招式开始，消耗 pp（对拥有压迫感的目标为 2，否则为 1，且绝不超过其剩余量）；头目的没有；`slot` 是招式在使用者招式表中的索引，如同 `0x07 (A, slot)` 和 `0x08 (A, slot)`；团体战行动中位于头目招式表之外的招式没有 `0x07` 也没有 `0x08` |
| `0x07 (A, slot)` | 招式被使用 |
| `0xc9 (A, 0, M, T 的位置, 0)` | 招式及其目标 |
| `0x7b (M, n, A)` | n 计入此回合之前的回合数 |
| 六个全零的 `0xcf` 组 | 20、5、5、5、19 和 20 字节 |
| `0x7e (0, ...)`、`0x7e (1, ...)`、`0x7e (2, e, e, e, e, e)` | 第一个：在 T 的位置 + 1 处为 1；第二个：在彼处为 1 表示击中要害；第三个：每个位置一个效果代码，无效果为 7 |
| `0x8b (A 的位置, T 的位置, M, type, 0, 0, 1, tera, class, 0)` | 命中；当头目使用其太晶属性的伤害招式时 `tera` 为 1（448 次此类命中中的 448 次），否则为 0；`class` 是招式的目标类别：0 一个目标，1 相邻同伴或自己，4 所有相邻，5 所有相邻对手，6 同伴，7 自己，9 随机对手，10 场地，11 对手一侧，12 同伴一侧，13 脚本指定（Showdown 的 `target` 名称，覆盖 19,245 次 oracle 命中） |
| `0x37 (T, 2, damage)`、`0x37 (T, 5, 1)`、`0x02 (T, A, damage, 3)` | 伤害 |
| 字节为 `T, e` 的 `0xd0` | e 是效果：7 一般，6 效果不佳，8 效果绝佳 |
| `0x8e (1, 1, M)`；效果不佳时的 `0x8e (1, 3, M)` 和 `0xca (A, 575, 0xffff0000)`；效果绝佳时的 `0x8e (1, 2, M)` 和 `0xca (A, 574, 0xffff0000)` | 效果消息 |
| `0xa7 (T 的位置, 131)`、`0x20 (A, 26)` | 仅用于击中要害，此时 `0x37 (A, 0, 1)` 也会紧接在伤害指令之前出现 |
| `0x20 (A, 24)` | 仅用于效果绝佳的命中 |
| `0x42 (T, A, A 的位置, type, cat, M, damage)` | 命中的记录 |
| `0x25 (T)`、`0xc7 (T, 0)`、`0x0c (T, 5, 1)`、`0x92 (T, 5, 1, 0)`、`0xcb (T, 15, T)`、`0xc8 (T)` | 受惊（特性 155）在虫、恶或幽灵属性命中之后提高 T 的速度 |
| `0xcb (T, 138, T)`、`0x1e (T, 15)`、`0x26 (T, 0)`、`0x4f (T, 0)`、`0x62 (T)` | T 的气球（道具 541）破裂；它离开 T |
| 吸取，当招式吸取且其使用者未满 HP 时 | `0xa7 (A 的位置, 51)`、`0x03 (A, heal)`、`0x9a (A, heal)`、`0xcb (A, 290, T)`；heal 是伤害乘以吸取比例、四舍五入（半数进位）、不设上限，即使使用者缺少的 HP 更少也一样（2 个此类回合中的 2 个）；它恢复的 HP 止于满值 |
| 追加效果，如有 | 例如麻痹：`0x13`、`0x90`、`0xa7`、`0xcb (2, 92, T)` |
| 字节为 `01 00` 的 `0xd1`、`0x2e (2, A − 1)` | |
| `0x85 (7, damage)` | 仅用于对头目造成的伤害 |
| `0x7c ()`、`0x08 (A, 0)`、`0x1d (A, T 的位置, type, 1, 0, M, M)`、两次 `0x5b (A, M)`、`0x1e (A, 0)` | 招式结束 |

一回合以 `0xb2 (0)` 结束，接着是每个行动过的对战者的 `0x37 (b, 7, 1)`、`0x75 (3, n)`、`0xc5 (1)`、按速度顺序对每个对战者的 `0x43 (b)`（队伍记录的速度处于其能力等级，包含头目）、按 id 顺序对该回合每个行动者的 `0x23 (b)`（战斗第一回合则是全部五个），以及 `0x2d (0)`；`0x75 (3, n)` 计入当前回合的指令回合数，包括这一个。一个回合在每第四个指令回合结束，不论由哪些槽位发出（oracle 语料 4,090 个回合结束中的 3,606 个；其余之间有一或两个团体战行动回合，它们不计入）：其 `0x75 (3, 0)` 之后是 `0xc5 (0)`、`0x50 (0)`、按顺序 36、21、18、5、4、9、10、8、46、43、48、11、12、23、13、31、33、15、19、29、30、38、37、39、40、41、24、45、14、20、1、2、3、7、6、16、17、22、25、26、27、28、32、34、35 对每个回合结束种类 k 的 `0x19 (b, k)`，每种都按速度顺序覆盖对战者，然后是对 k 为 1 到 13 的 `0x44 (k)`，在通常的 `0xc5 (1)` 之前。天气持续五个回合结束，其升起的那一回合计为第一个：在第五个时它紧接在 `0x50 (0)` 之后以 `0x99 (w)`、`0x54 ()`、`0x6a (0)` 结束，而沙暴结束时该回合不造成伤害（oracle 语料中 7 次天气结束中的 7 次）。晴天、雨天和下雪在回合结束时不添加任何内容。场地同样持续五个回合结束，并在 `0x44 (8)` 与 `0x44 (9)` 之间以 `0x34 (8)`、`0x6a (8)`、`0xca (0, text)`、`0x32 (0, 0, 1, 0)`、`0x6a (8)`、`0xb2 (0)`、`0xaa (0)`、`0x69 (8, 0)` 结束；结束文本为青草 705、电气 709、精神 829（薄雾不在语料中）。沙暴在 `0x50 (0)` 之后为它按速度顺序伤害的每个对战者添加（其最大 HP 的十六分之一）：`0xcb (b, 133, b)`、`0xa7 (b 的位置, 14)`、`0x01 (b, s, damage, 1)`（s 为升起沙暴的对战者，即其扬沙或吐沙，或头目的沙暴），以及 `0x9a (b, -damage)`。吃剩的东西（道具 234）随后按速度顺序、在残余种类之前，为每个未满 HP 的持有者恢复其记录 HP 的十六分之一：一个 5 字节的零 `0xcf` 组、`0x9b (b, 0)`、一个 3 字节的零组、`0xa7 (b 的位置, 51)`、`0x03 (b, heal)`、`0x9a (b, heal)` 和 `0xcb (b, 295, b, 234)`；显示的回复是完整的十六分之一，即使缺少的 HP 更少。青草场地在天气的指令之后、吃剩的东西之前，按速度顺序为每个未满 HP 的接地对战者恢复其记录 HP 的十六分之一：`0xa7 (b 的位置, 51)`、`0x03 (b, heal)`、`0x9a (b, heal)`、`0xcb (b, 130, b)`。心情不定（特性 141）在 `0x44` 列表之后、回合结束时生效：一次 `below(20)` 抽取 v 选出被提高的能力（攻击到速度）v // 4，以及其余四项中被降低的能力 v % 4；`0x25 (b)`、`0xc7 (b, 0)`、提高 2 级（从 +5 起为 1 级）、降低 1 级（`0x0d`、`0x93`、`0xcb (b, 31 + stat, b, stat)`）、`0xc8 (b)`（语料中每个心情不定的回合结束都如此；±6 时的能力未测量）。其他携带道具在回合结束时的表现未测量。

目标属性免疫的伤害招式不抽取任何东西，连命中率也不抽，并运行 `0x05`、`0x07`、`0xc9 (A, 0, M, P, 1)`、`0x7b`、五个 `0xcf` 组（20、5、5、5 和 19 个零字节）、`0xcb (A, 72, T)`、`0x52 (A, 3)`、`0x08 (A, slot)`、`0x52 (A, 0)`、`0x1d (A, P, type, 0, 0, M, M)`、两次 `0x5b (A, M)` 和 `0x1e (A, 0)`：oracle 语料中 5,550 次消息 72 运行里的 5,353 次（其余会开启一次特性发动）。地面属性招式命中拥有飘浮（26）且其属性本身不免疫的目标时，以同样方式运行，消息 72 位于目标的特性发动之内：`0x25 (T)`、`0xc7 (T, 0)`、`0xcb (T, 72, T)`、`0xc8 (T)`，然后是 `0x52 (A, 3)`。草属性招式命中食草（157）、或电属性命中电力引擎（78）时，作为免疫招式运行，其发动会把目标的攻击或速度提高一级（`0x25 (T)`、`0xc7 (T, 0)`、`0x0c (T, stat, 1)`、`0x92`、`0xcb (T, 10 + stat, T)`、`0xc8 (T)`），然后是 `0x52 (A, 2)`。

命中率抽取失败的伤害招式会作为免疫招式运行，以消息 73 和 `0x52 (A, 1)` 代替消息 72 和 `0x52 (A, 3)`。没有剩余 PP 的玩家招式（队伍记录的 PP，每次使用减 1，对压迫感为 2）只运行 `0xc9 (A, 0, M, 10, 1)`、`0xca (A, 578, A)`、`0x52 (A, 0)`、两次 `0x5b (A, M)` 和 `0x1e (A, 0)`，在麻痹抽取其 `chance(25)` 之前。

玩家的招式若不在《朱／紫》中（Showdown 的 `isNonstandard` 为 Past 或 LGPE：追打、查封、Sizzly Slide 以及其他）会在其他一切之前失败，不抽取也不消耗 PP：`0xca (A, 567, A)`、`0x52 (A, 0)`、两次 `0x5b (A, M)` 和 `0x1e (A, 0)`，在其处理器的 `0x5a` 之后（若它注册了一个——芳香治疗、Sappy Seed 和 Freezy Frost 都会）。oracle 语料中此类运行的 2,622 次中的 2,622 次符合；没有任何游戏外玩家的招式会到达 `0xc9`。无法获得的那些（居合斩和各 Torque 招式）作为普通招式运行（语料中 183 次运行）。

伤害招式若在其被指向之后目标已经濒死（头目的额外行动招式在其条目加入列表时就被指向），会作为免疫招式运行，以 `0xc9 (A, 0, M, P, 1)` 和 `0xca (A, 567)` 代替消息及其 `0x52 (A, 3)`。

在头目开盾期间指向它的变化招式会在运行之前失败，不抽取：`0x05`、`0x07`、`0xc9 (A, 0, M, P, 1)`、`0xca (A, 567, A)`、`0x52 (A, 0)`、`0x1d (A, P, type, 0, 0, M, M)`、两次 `0x5b (A, M)` 和 `0x1e (A, 0)`（oracle 语料中 120 次降低能力和施加异常状态的招式命中护盾中的 120 次；指向其使用者的招式仍会运行）。降低能力的招式若目标被降低的能力全在 -6，会作为免疫招式运行，对每项能力使用 `0xcb (A, 59 + stat, T)`（攻击为 60）代替消息 72 和 `0x52 (A, 3)`，不抽取；提高能力的招式若其使用者身上相关能力全在 +6，以同样方式运行，对每项能力使用 `0xcb (A, 52 + stat, A)`。伤害招式的追加效果在相应能力为 +6 时不显示任何内容。

命中率抽取失败的变化招式会作为伤害落空运行（消息 73 和 `0x52 (A, 1)`）。其异常状态被目标属性免疫的变化招式（电磁波命中电属性）会作为免疫招式运行，带 `0xcb (A, 72, T)` 而没有 `0x52 (A, 3)`，不抽取；使中毒的招式命中已中毒目标时以同样方式，带 `0xcb (A, 84, T)`。睡眠招式会在其命中率之前，通过抽取日志不显示的那次调用抽取其回合数。

天气招式（大晴天、求雨、下雪、沙暴）作为带场地类别（10）的能力等级变化招式运行，并以天气的开始代替能力变化：`0x6a (0)`、`0x69 (0, w)`、`0x79 (w, 5, 0, A, 0)` 和 `0x88 (w, A, 0)`，w 为 1 晴天、2 雨天、3 下雪、4 沙暴；施加异常状态的变化招式（电磁波、鬼火、剧毒、蘑菇孢子）会在那里运行施加过程（[状态](#statuses)）。被伤害招式命中的 吐沙（245）会在命中的 `0x42` 及其追加效果的指令之后升起沙暴：`0x25 (b)`、`0xc7 (b, 0)`、w 为 4 的天气开始、`0xc8 (b)`，且没有消息，若该命中击倒其持有者则在击倒指令之前；在已经升起的沙暴下它不显示任何内容。在另一种天气之上升起的天气（天气招式或 吐沙）只显示自己的开始并替换旧的，旧天气的结束不显示任何内容。场地招式以同样方式运行，带有场地的开始：`0x32 (t, 0, 42, A)`、`0x6a (8)`、`0xb2 (0)`、`0xaa (t)`、`0x69 (8, t)` 和 `0xca (A, text)`，开始文本为青草 704、薄雾 706、电气 708、精神 828；已有场地时它会以文本 567 失败。场地招式的 `0x8b` 无论被命令的是什么位置都携带位置 10。在 `0x6a`、`0x69` 和 `0x44` 中，天气是场地槽位 0，场地是场地槽位 8。

戏法空间（433）作为天气招式运行，其 `0x8b` 中位置为 10，其效果为 `0x69 (1, 0)`、`0x30 (1, 0, 42, A)` 和 `0xcb (A, 275, A)`（场地槽位 1）。在它存在期间，排序键和排序读取的每个速度都是 Showdown 的 10000 − 速度，包括运行的处理器的键（其下 32 个语料回合构建结果一致；它的结束未曾出现）。

顺风（366）在其使用者一侧（0 为玩家一侧，1 为头目一侧）升起一侧状态 4，持续四个回合结束，其升起的那一回合计为第一个。它作为带侧别类别（12）的天气招式运行，其 `0x8b` 中位置为 10（`0xc9` 保留被命令的位置），然后是 `0x4a (side, 4, 0, 34, A)`（34 是其四回合 << 3 | 2）、相同参数的 `0x65`，以及 `0xca (A, 643, side)`。它在排序键和排序中把其所在侧对战者的速度翻倍，但在处理器的 `0x5a` 中不翻倍。它存在的每个回合结束会在最后一个 `0x19` 之后、`0x44 (1)` 之前添加 `0x4c (side, 4)`；在第四个时出现 `0x4b (side, 4)`、`0x66 (side, 4)` 和 `0xca (A, 645, side)`，其中 A 是升起它的对战者。反射壁、光墙和神秘守护是侧别状态 0、1 和 2，持续五个回合结束，以同样方式升起，使用 `0x4a (side, c, 0, 42, A)` 和开始文本 623、627 和 635，结束文本为 625、629 和 637。反射壁承受物理命中、光墙承受特殊命中，在其一侧对最终伤害乘以 2732/4096，除非是击中要害，两侧皆然（Showdown 在多对战者旁的系数；语料中头目自己的墙也符合）。顺风一侧拥有风力发电（277）的对战者会在开始文本之后立刻充能：`0x25 (b)`、`0xc7 (b, 0)`、`0xcb (b, 1024, b, 366)`、`0xc8 (b)`、`0x1e (b, 20)`、`0x7d (20, b, 0, 0)`；顺风旁的乘风（274）未测量。47 个有顺风的语料回合、3 个有其结束的回合构建结果一致。

2 到 5 次命中的招式在命中率抽取之后立刻抽取其命中次数（`0x19d4f2c`）：对战斗生成器的低 7 位抽取一次，结果大于等于 100 时重抽，小于 35 为 2 次，小于 70 为 3 次，小于 85 为 4 次，否则为 5 次；固定次数（二连踢的 2、三连钻的 3）不抽取。每一次命中都会抽取其击中要害和掷骰，并在一个 20 字节的零组之后运行自己的 `0x7e` 三元组、以命中序号为第六个参数且以命中次数为第十个参数的 `0x8b`、仅带 `0x8e (1, e, M)` 的伤害指令、`0x42` 和 `0xd1`；击倒其目标的命中会结束该次运行，其击倒指令不带濒死消息。每次命中的 `0x8b` 第十个参数都是已命中的次数，因此命中数在其指令发出之前就已统计。最后一次命中之后是效果消息 `0xca (A, 574 或 575)`（非一般时）、`0xca (A, 516, hits)`、效果绝佳时每次命中一次的 `0x20 (A, 24)`、`0xa6 (96)`，然后是招式通常的结束，对头目带 `0x85 (7, 总伤害)`；龙箭不显示消息 516。击倒头目的多段招式在 `0xa6 (96)` 之后添加其濒死消息 `0xcb (A, 0, 2)`；击倒玩家的则不添加。语料中每个 2 到 5 次命中的回合都以这种方式构建一致。

反作用力招式会在命中的 `0xd1` 之后、以及任何击倒的指令之后添加 `0x01 (A, A, r, 4)`、`0x9a (A, -r)`、`0xcb (A, 127, A)` 和 `0x37 (A, 4, r)`，其中 r 是造成的伤害（至多为目标当时拥有的 HP）乘以招式的比例、四舍五入（半数进位）、至少为 1。叶绿爆震以同样的方式结束，代价是其使用者最大 HP 的一半。铁蹄光线在其 `0x8b` 之后、伤害指令之前支付其使用者最大 HP 的一半：`0x01 (A, A, cost, 0)` 和 `0x9a (A, -cost)`，没有消息。携带生命宝珠（道具 270）的玩家会在造成伤害的招式之后、命中的 `0xd1` 之后损失其最大 HP 的十分之一：`0x01 (A, A, cost, 29)`、`0x9a (A, -cost)`、`0xcb (A, 328, A)`；它对头目的命中不带 1.3 倍伤害加成（9 次命中构建一致，另有 7 场战斗在带加成时的第一次此类命中处出现分歧）。

聚气作为作用于其使用者的变化招式（类别 7）运行，其效果为 `0x1e (A, 9)`、`0x7d (9, A, 0, 0)` 和 `0xcb (0, 336, A)`；此后使用者的击中要害等级提高两级（等级 0 的招式变为 `below(2)`）。蓄力的第一层以同样方式运行，带 `0x35 (A, 0, 1)`、`0xcb (0, 236, A, 1)`、防御提升、`0x35 (A, 1, 1)`、特防提升和 `0x35 (A, 2, 1)`（语料中 18 次中的 18 次；未出现第二次蓄力）。

范围招式（Showdown 的 target 为 `allAdjacent` 或 `allAdjacentFoes`）只命中其指令指定的位置，使用单目标伤害且没有范围修正：包含这类招式的每个 oracle 回合都作为单目标命中构建一致，`class` 为 4 或 5。招式按优先度分组顺序运行，然后按能力等级上的速度：头目的水流喷射或影子偷袭会比更快的玩家先行动。

击倒头目的一击赢得战斗。其 `0x42` 之后是 `0x49 (2, A, M)`、`0x09 (A, slot)`（`slot` 是 M 在 A 招式表中的索引；383 次 oracle 击倒中的 382 次）、`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、`0x5d (2)`、按 id 顺序对每个玩家的 `0x41 (b, 2)`、对 k 为 0 到 13 的 `0x33 (2, k)`（仅当有场地存在时才为 8）、`0x80 (2)`、`0x29 (2)` 和 `0x38 (A)`，然后是招式通常的结束。此后没有人行动，回合只以仍站立的对战者的 `0x43`、`0x23` 列表和 `0x2d (0)` 结束。`0x85 (7, damage)` 和伤害指令携带头目剩余的 HP。

前缀以 `0xb5 (0)` 开始，然后按 id 顺序对该回合的行动者运行一次 `0x51 (b, 1)`，再按第一次行动排序的顺序运行一次；在第二次运行中，拥有 慢出（特性 100）的对战者携带 `0x51 (b, 0)`，此后其行动在其分组中排在最后；该回合的第一次排序仍把它计为 1。菌丝之力（298）仅在变化招式上以同样方式携带 `0x51 (b, 0)`，恶作剧之心（158）把变化招式的优先度提高 1。每次行动排序（[速度相同](#speed-ties)）先按列表顺序计算每个招式行动的顺序键，注册了自己处理器的招式会将其显示为 `0x5a (b, M, speed)`（speed 处于其能力等级）和 `0x5b (b, M)`。该回合第一个运行的招式会再计算一次每个招式行动的键，而招式注册了处理器的行动者会在其 `0x05` 之前添加 `0x5a (b, M, key)`，键为 (priority + 7) << 16、其 `0x51` 值 << 13，再加上其速度（优先度为 0 的招式为 `0x72000 + speed`；慢出 为 `0x70000`）。排序的 `0x5a` 只携带能力等级上的速度值；运行的则携带计入顺风和麻痹的速度（oracle 的指令日志与其排序和行动运行交织）。631 个招式中有 347 个注册了一个（硬撑和泰山压顶在列，暗袭要害不在）。

头目从一开始就太晶化：其太晶属性的伤害招式若在基础威力修正之后低于 60 威力、没有优先度且只有一次命中，则按 60 计算，这是第九世代的太晶规则（奥利瓦的太晶一般属性撞击造成 4，而 40 基础威力给出 2；拥有斗争心的头目以太晶恶属性咬住命中另一性别的玩家造成 25，即未修正的 60 威力伤害，而斗争心的 45 至多给出 21）。招式的每个追加效果会按 Showdown 的顺序抽取 `chance(n)`，但对头目的畏缩不抽取：玩家的冰冻牙命中头目只抽取其冰冻概率（冰冻显示为 `0x13 (2, 3, 0, 1, 4)`，消息为 97 和 98，且头目在行动前抽取 `chance(20)` 以解冻），头目的冰冻牙命中玩家时两者都抽取。击倒头目的一击先抽取 `chance(0)`，无论是否有追加效果。

用 Showdown 的招式数据和第九世代伤害公式这样构建，554 场 oracle 战斗中有 56 场的第一回合与 oracle 逐字节一致，且没有一场不同（其余包含被拒绝的某种东西）；20 场完整战斗在每个回合都与 oracle 一致，而在针对脚本主机的服务中，19 场中的 19 场都在同一帧发出 oracle 服务器发出的每一帧。当行动或被命中的对战者拥有其 Showdown 回调可能改变该回合的特性或道具时（活力带来的攻击、斗争心的威力、友情防守的 0.75、受惊在恶属性命中后的速度提升、疾风之翼的优先度），该回合会被拒绝，除非语料测得该特性或道具处于闲置状态；或者当战斗拥有在上场时生效的特性时（威吓在第一回合之前降低攻击方的攻击）。

### 行动

一个回合的行动头（请求块，0x238 字节）是五个 0x70 字节的块，每个客户端槽位一个，每块最多七个 16 字节的行动（一个 u64 行动字、一个 u32 行动者对战者 id、4 个没有代码写入的字节），并在 +0x230 处每个槽位一个字节，统计其块中的行动数。服务器按槽位顺序把它们解码成 0x8c 字节的行动条目（`0x1145e40`，解码器 `0x11461b4`）。行动字的低四位是 kind：

| kind | 条目 kind | 字中的字段 |
|---|---|---|
| 1 | 1，一个招式 | 位 4..7 目标的对战位置，8..23 招式，位 25 一个标志 |
| 2 | 2 | 位 4..19 和 20..27；下一个 u32 |
| 3 | 3，一个替换 | 位 4..7 队伍索引（行动者就是该队伍成员），8..11，位 12 |
| 4 | 6 | 位 4..11、12..15 和 16..23 |
| 5 | 4 | 位 4 |
| 6 | 5 | 位 4..11 |
| 7、10、11 | 7、8、9 | 无 |
| 9 | 10 | 位 4..11 |
| 12 | 11 | 位 4..11；下一个 u32 |
| 13 | 14 | 位 4..7、8..11、12..15、16..27、32..43、44..55、56..59、60..63 |

位 0..3 为 3 且位 12 置位的字会被跳过，kind 0、8、14 和 15 也一样。一条记录的玩家行动 `41 67 03 00 ...` 是一个招式（kind 1），目标位置 4，招式 871（闪焰高歌）。

团体战中的对战者 id：1 是槽位 0 的宝可梦，2 是头目，3 是槽位 2，4 是槽位 3，5 是槽位 4。站点的 type-0x06 指令是 0xe8 字节：0x20 字节的头（+0x19 是槽位）、+0x20 处一个计数字节，然后是从 +0x28 开始的 (u64 字, u64 行动者) 对。它携带该槽位自己的行动以及头目对该槽位的回应：一个访客对槽位 2 的指令包含 `move 871 at position 4 by battler 3` 和 `move 204 at position 1 by battler 2`。站点为其自己的宝可梦选择头目的招式。

### 战斗开始的正文

消息 0x11 的正文是一个没有长度字的指令队列（[服务器的指令队列](#the-server-command-queue)）。对战者 id 为：槽位 0 是 1，头目（槽位 1）是 2，槽位 2 是 3，槽位 3 和 4 是 4 和 5；对战者位于位置 id − 1。正文按 id 顺序送出每个对战者，然后运行上场事件，最后以 `0x2b (0)` 结束：

| 指令 | 作用 |
|---|---|
| `0x3d (pos)`、`0x16 (pos, 0, 0, 0)`、`0x5e (id, ability)`、`0x61 (id)`、`0x6b (id)`、`0x4e (id)` | 一个对战者被送出；`ability` 是其特性 id |
| `0x25 (id)`、`0xc7 (id, 0)`、效果、`0xc8 (id)` | 一次特性发动 |
| `0xcb (id, text, params..., 0xffff0000)`，用零补齐到十个参数 | 一条战斗消息 |

| 上场事件 | 效果 |
|---|---|
| 压迫感（46） | 围绕 `0xcb (id, 162, id)` 的发动 |
| 威吓（22） | 围绕每个目标的 `0x0d (target, 1, 1)`、`0x93 (target, 1, 1, 0)`、`0xcb (id, 32, target, 1)` 的发动 |
| 察觉（119） | 围绕每个携带道具的对手的 `0xcb (0, 146, id, target, item)` 的发动 |
| 紧张感（127） | `0x25 (id)`、`0xc7 (id, 127)`、`0xca (id, 679, side, 0xffff0000)`、`0xc8 (id)`，在其他每个事件之前；`side` 对玩家的紧张感为 1，对头目的为 0 |
| 预知（107） | 当对手知道一个对其效果绝佳的伤害招式或一击必杀招式时，围绕 `0xcb (id, 145, id)` 的发动 |
| 复制（36） | `0x25 (id)`、`0xc7 (id, A)`、`0x89 (id, 36, A)`、`0xcb (id, 128, S, A)`、`0x5f (id)`、`0x24 (id, A)`、`0x5e (id, A)`、两次 `0xc8 (id)`，从 S 复制特性 A：玩家的复制复制头目，头目的则复制 `below(4)` 在对战者 1、3、4、5 中选出的玩家（6 场战斗中的 6 场） |
| 界限盾壳（197） | 对于 HP 高于一半的流星形态（形态 0 到 6）的小陨星没有；核心形态（7 到 13）显示 `0x25`、`0xc7`、`0x57 (id, form − 7, 0)`、`0xac (id)`、`0xca (id, 842)`、`0xc8`（9 场战斗中的 9 场） |
| 携带气球（541） | 在对战者的特性之后 `0xcb (id, 137, id)` |

这些事件按对战者的速度顺序运行（队伍记录速度），紧张感最先。威吓按 id 顺序影响每个对手。拥有我行我素的对手会在其中以自己的 `0x25`/`0xc7`、`0xcb (F, 69, F, 0xffff0000)` 和 `0xc8` 回应，且不损失任何东西。拥有不服输的对手会在其下降之后以 `0x0c (F, 1, 2)`、`0x92 (F, 1, 2, 0)` 和 `0xcb (F, 18, F, 0xffff0000)` 回应。察觉用 `0xcb (0, 146, I, F, item, 0xffff0000)` 指出第一个携带道具的对手，之后的每个用 `0xca (0, 752, F, item, 0xffff0000)`；对手中没有任何道具时它没有事件。这样构建，554 个 oracle 开始正文中有 420 个一致，且没有不同的。

### 服务器的消息

服务器发送的每条消息都是 `0x113bad8(server, kind, destination)` 的一步：

| 步骤 | 代码 |
|---|---|
| 步骤计数器 `server+0x198` 增加 | |
| 该步骤已经收到的正文（[[server+0x448]+0x38]，`0xe63734`）被复用；否则构建器以该 kind 和回合计数器 `server+0x488` 运行 | `0x113c8a0` |
| 32 字节的头：u32 kind、+0x08 处的 u64 step、+0x10 处的 u64 round、+0x18 处的目的地（每个站点都是 5）、+0x19 处的 5 | 栈字节 +0x04..+0x07 和 +0x1a..+0x1f 从不写入 |
| 消息对象：从服务器的分配器 `[server+8]` 取 0x50 字节，vtable `0x44ed338`，+0x40 处是头和正文的缓冲区，+0x48 处是其长度的 u32 | `0x1227714`，析构函数 `0x28015b4` |
| 当 `server+0x490` 置位时，进入每个目的地槽位（dest 5：槽位 0 到 4 和 0xff）的链路：`server+0x1a0` 映射中按槽位的链路，每条链路的出站双端队列在 `[link+0x48]` | `0x113cd5c`、`0x113e17c`、`0x113d33c`、`0x113d4a0` |

| 把 {u8 `[[server+0x448]+0xc4a5]`, u64 step, u8 `+0xc4a4`} 写入 x8：该回合的结果 | |

一个消息双端队列是 libc++ 的 `deque<message*>`：映射在 +0x40，起点 +0x80，大小 +0x88，一个块 0x200 个指针（`0x113d5e0`、`0x113d810`，擦除 `0x131be1c`）。服务器为每个槽位保留两个条目：它发给该槽位的（映射在 `server+0xc8`，`0xf6f324`）和该槽位发给它的（映射在 `server+0x130`，`0xe634c8`）。`0xf6f0a8` 按头部类型查找消息，`0xf6fd7c` 擦除它，`0xe63380` 询问某个槽位是否发送了某步骤的消息。链路的消息作为战斗开始的帧到达线上，寻址为 (0x2713, 1, slot)：u16 键 0x7b、u32 setup `+0x2c`、u32 1、u32 该槽位、u32 长度，然后是消息。把链路排空到网络的代码没有被定位。

### 头目的行动

团体战头目的额外行动在一个可容纳四个的列表中等候（+0x5c + 8i 处 u8 kind，+0x60 + 8i 处 u32 value，+0x7c 处计数），位于 +0x10 处 RaidPoint 行动配置的副本之后。回合引擎的列表是 `[module+0x1b0]`（`0x16e5c90`），每个回合重置；服务器的每帧状态机保留自己的列表。

| kind | 由谁入队 | value |
|---|---|---|
| 1 | 护盾（`0xf6f87c`）：在它开始之前，时间达到或低于配置 +0x14 的百分比，或 HP 达到或低于 +0x12 | 时间触发时为计时器的 `0xf70af0`，HP 触发时为 0 |
| 2 | 护盾的结束（`0xf6f87c`，`0xf70010` 对 +0x18） | 1 |
| 3 | 当一次时间检查发现剩余 10% 或更少时的 `0xf6dd84` | 1 |
| 4 | 六个额外行动（`0xf6fa5c`：kind、时机 1 时间 / 2 HP、阈值、+0x24 + 8i 处的招式），每个一次（记录 +0x86 + i） | 该行动的索引 |
| 5 | 双重行动（`0xf6de7c`）：HP 达到或低于配置 +0x54 | 0 |

value 为 0 的双重行动会在一次命中让头目以 0 的 HP 占比仍站立时触发（配置全零的 2 场 oracle 战斗中的 2 场），出现在该招式与下一个招式之间。它们都不抽取随机数：每个触发都是对头目的 HP 占比或剩余时间（`0xf91070` 作用于战斗计时器）的阈值。作为请求块行动（`0x114fb2c`）时，字的 kind 是 12，位 4..11 是列表的 kind，位 32..47 是其 value，行动者是团体战对战者的 id（`0x114fc70`）。

在一个回合期间，空列表会由 HP 触发填充（`0x11425b0`）；其中没有护盾时这些行动在该回合运行（`0x1145be0`）。一个回合之后，结果的字节 `0xc4a5` 选择下一步；当构建器的 `0xc4a4` 置位时 ServerCommand（`0x16e4f6c`）改为传 8，团体战行动则原样传该字节（`0x16e4ff0`，跳转表 `0x3c61c38`）：0 无，4 一个空回合（`0x16e5cac`），6 当该回合的列表包含护盾时的列表（`0x16e5ad0`），7 战斗结束（[战斗的结束](#the-battles-end)）。一个团体战行动（`0x18c92a8`，载荷由 `0x17b5f3c` 复制）在四个状态中运行：

| 状态 | 服务器 |
|---|---|
| 0 | 向每个站点发送消息 0x47；以原因 0 暂停战斗计时器（`0x18c9a68`） |
| 1 | 等到每个已就座的槽位都发送了该步骤的消息（`0xe63380`） |
| 2 | 一个请求块，其槽位 1 持有这些行动（计数字节 +0x231）；战斗计时器以原因 0 恢复（`0xe63ac4`）；该块作为回合（0x15）发送 |
| 3 | 该回合结果的下一步，列表被清空（`0xfaf024`），每个槽位的 0x47 及其回答 0x48 被擦除 |

一个团体战行动的回合队列，在 oracle 语料 547 个这样的回合上：`0xb5 (0)`、`0x51 (2, 1)`、`0x85 (kind, x)`、`0xc1 (kind, y)`、该行动的效果、`0xb2 (0)`、`0x37 (2, 7, 1)`（在招式或能力重置之后为两次）、`0xc5 (1)`、`0x43`、`0x23 (2)` 和 `0x2d (0)`。对于额外行动，`x` 是其索引（213 次中的 213 次），`y` 是配置行动的 kind（1 到 4）；kind 3 的 `x` 和 `y` 为 0 且没有效果指令（121 个回合）；护盾的开始使两者都等于其 value（95 次 value 为 0，其余为计时器的值）。重置玩家能力变化的额外行动以其效果以 `0xc2 (60, 2, 0)` 结束，在其清除的每个玩家的 `0x10 (b)` 和 `0x13 (b, 16, 0, w, 2)` 之后；重置头目的则用 `0x0f (2)`、`0xc2 (3, 2, 2)` 结束。

在每次行动运行之后（`0x11405a0`），当战斗继续且头目站立时，`0x11425b0` 由 HP 触发填充一个等待团体战行动的空列表：其中没有护盾时它们加入该回合的行动列表；有护盾时它们等待一个团体战行动回合。列表在每个回合开始时清空，运行护盾也会清空它，因此下一次运行会用仍然满足的每个 HP 触发重新填充它，包括已经在列表中的行动：那些行动稍后会再次运行且不显示任何内容。团体战行动回合会让其列表保持原样：在那里于已运行的那个之后重新填充的护盾等待下一个团体战行动回合，在那时它不显示任何内容。当头目被冰冻时，其 HP 触发会略去 kind 3（一个招式）的额外行动并保留其他：头目重置会在其仍冰冻时触发并运行，招式的行动会在头目解冻之后到来。在头目的异常状态阻挡它时被跳过的招式行动可以在护盾治愈该状态之后到来。额外行动的招式会在运行之前检查头目的混乱，如同被命令的招式一样。护盾存在期间，对头目的命中造成伤害乘以护盾的百分比（`0x2a`，标准配置中为 20；太晶化的攻击者使用自身属性招式或其他招式时为 80 或 40），再除以 100，余数为 50 时向上取整（`0x1535c8c`）。一旦头目自护盾升起以来损失了其 HP 总量的配置结束百分比（20），护盾就结束。

回合结束会为列表的每个条目放置一个 `0x37 (b, 7, 1)`，无论是否运行过，按列表最后的顺序：护盾、一次额外的头目重置，以及三个条目被护盾再次入队的额外招式时为 7。`0x75 (3, n)` 只计入有玩家条目的回合，而团体战行动回合仍计入 `0x7b (M, n, A)`。团体战行动回合在其他方面与指令回合一样结束：三次对战者排序、按第二次排序顺序的 `0x43` 和 `0x23 (2)`。

### 战斗计时器

战斗计时器是服务器上下文中 +0x38 处一个 0x28 字节的对象（每帧状态机和每个作业的 `[+0x40]`，该对象还在 +8 处持有 N，在 +0x10 处持有服务器的模块，在 +0x18 处持有服务器）：

| 偏移 | 字段 |
|---|---|
| +0x00 | u64 start，`nn::os::GetSystemTick` 的纳秒；暂停时为 0 |
| +0x08 | u64 上次暂停之前累计的纳秒 |
| +0x10 | u64 上次暂停的时间 |
| +0x18 | u8 已启动 |
| +0x19、+0x1a | u8 暂停原因；两者都为 0 时计时器运行 |
| +0x20 | 创建它时使用的上限 |

| 事件 | 代码 |
|---|---|
| 创建、启动并立刻以原因 0 暂停，上限 N+0x8a 不为 0 时随战斗的第一个作业进行 | `0xf70864`、`0xf70a58` |
| Wild::Setup 结束时以原因 0 恢复（从未启动的计时器在此启动） | `0x2a1fbfc`，`0xe63a6c` 的各个步骤 |

每帧状态机只在计时器已启动（+0x18）且 setup +0x499 的位 2 置位时才检查时间触发（`0xf6d538`）。处于时间 P% 的触发在 100 × 剩余时间 / 上限（整数除法）小于或等于 P 时触发：在 300 秒的计时器上，80% 的触发在剩余 242 秒时触发，即运行 58 秒之后。在下面的实际服务的战斗中，计时器在最后一个站点对消息 0x11 的回答到达服务器时启动，80% 的行动在 58.1 秒后发出。

### 战斗计时器耗尽

在每帧开头，每帧状态机（`0xf6d538`）读取战斗计时器（`0xf91070`）；结果小于或等于 0 时走时间耗尽的支路 `0xf6d830`：

| 步骤 | 代码 |
|---|---|
| 结果为 0 且 N+0x94 = 2 被保留在 N 中，除非已经有一个结果 | `0xe7d570(N, 0, 2, 0)` |
| server+0x208 处的 0x29 正文：N 的槽位、结果（`0x166882c`）、N+0x94 | `0xe7d4c8` |
| 团体战（setup +0x499 的位 2）：ExitBattleEnd，消息 0x2b | `0x201602c`（哈希 `0x2da7b4584624a364`，构造函数 `0x1882dbc`） |
| 否则：AddExpBattleEnd，kind 0 | `0x16e5230`（哈希 `0x23607a0597b3a656`） |

状态机只在没有作业运行时运行，因此在一个回合期间耗尽的时间会在该作业结束后才被看到。团体战的时间耗尽不发送 0x25：先是头目最后一个计时回合，然后是带正文 `00 00 00 00 02 00` 的 0x2b、0x35 和 0x37（[战斗的结束](#the-battles-end)）。头目获胜的团体战以同样的方式结束：主机或零售主机的宝可梦每次濒死（不是 NPC 伙伴的）都会从计时器上扣掉 n 秒（`[[module+0x1b0]+8]` 处的 i16，`0x287f3d4`）：n 是时间上限乘以 0.125 再乘以四个玩家的平均等级与头目等级之比，以 float32 计算并截断（339 场 oracle 战斗中的 339 场；300 秒计时器上为 28 到 61 秒），而击倒的队列携带 `0x81 (-n)`。

宝可梦已濒死的槽位会经过其读取器的子状态：

| 消息 | 发给 | 内容 |
|---|---|---|
| 0x21 | 濒死的槽位，仅头部 | 在该槽位没有可战斗成员之后；其回答 0x22 启动读取器的计时器（reader+0x50），时长按该槽位宝可梦的濒死次数为 5、10、15、20、25 或 30 秒（`0x1ffe4e8`，表 `0x3c69d1c`） |
| 0x23 | 每个槽位，20608 字节 | 该计时器耗尽之后（`0x2016bc8`，该槽位一个行动的 kind 0x23 块，kind 8），由 kind 35 构建（`0x1153350`）：恢复的 HP（`0x288cde8`）、指令 3（对战者，HP）、被重新派上场的成员（`0x2887044`、`0x11482a0`：指令 0x98） |

一次复活的队列：带其满 HP 的 `0x03 (b, HP)`、`0xcb (0, 1, b)`，然后是以客户端槽位 c 的战斗开始的派上场（`0x3d (c)`、`0x16 (c, 0, 0, n)`，其中 n 是到目前为止的回合数、`0x5e (b, ability)`、`0x61`、`0x6b`、`0x4e`）、`0x98 (c, 0, 0, 1)`、`0x20 (b, 18)` 及其上场时的特性（压迫感的消息 162）。其能力变化已消失，而被玩家的重置压制过的特性又成了它自己的（`0x5e` 携带它）。下一回合的 `0x23` 列表以自上一回合以来复活的战斗者开头，按复活顺序，然后是那一回合中尚未列出的行动者。

玩家的宝可梦被击倒时，在该次命中的 `0x42` 之后，用其自己的 id 运行头目的击倒指令（[回合队列中的一个招式](#a-move-in-the-round-queue)）：`0x49 (V, A, M)`、`0x09 (A, slot)`、`0x37 (V, 1, 1)`、`0xcb (V, 0, V)`、`0x94 (V, 0)`、`0x37 (V, 8, 1)`（其濒死次数）、`0x5f`、`0x62`、`0x6c`、`0x5d`，按 id 顺序对每个仍站立的战斗者 `0x41 (b, V)`，对 k 0 到 13 的 `0x33 (V, k)`（仅在场地存在时才有 8）、`0x29 (V)`，对主机或零售主机的宝可梦是计时器的 `0x81 (-n)`，最后是 `0x38 (A)`；没有 `0x80`。其在该回合的行动被标记为已运行，该次命中像头目的击倒一样抽取 `chance(0)`，降低能力变化类的追加效果不抽取，而畏缩或混乱类的追加效果以及接触特性仍会抽取。持有气球的玩家会在该次命中的 `0x42` 之后、这些指令之前使其爆开（消息 138，`0x1e (T, 15)`、`0x26 (T, 0)`、`0x4f (T, 0)`、`0x62 (T)`）。

当头目的护盾以 value 1 结束时，其记录把五个按槽位的计数器（记录 `+0x7c` 处的 u16）设为 -1（`0x15661e0` 事件 2）。在每个回合开始时（`0x114d390`），瞄准计数器为负的槽位的头目招式会随头目的其他行动一起被丢弃，计数器重置（事件 6），并在回合开始的 `0x51` 运行之后入队 `0x85 (6, slot)`：每个玩家的下一回合都得不到回应（oracle 语料中 271 个这样的回合）。

### 服务器的流程

在零售主机上，这些步骤是作业：Wild::Setup、ServerRequest（`0x138d178`，发给一个槽位的消息 5）、ServerCommand（`0x16e4f10`，把一个已投递的请求块作为回合）、RaidAction 和战斗的结束。Wild::Setup（`0x2a1f54c`，跳转表 `0x3c61c1e`）发送消息 1，等待每个回答，发送 0x11，等待，清除每个槽位发送的内容（`0xe0f5f8`），只在启动标志 [[o+0x40]+0x28] 为 1 时发送消息 3（只有 `0x2840fac` 会设置它；团体战让它保持 0），并启动战斗计时器。团体战的 setup +0x30 是 kind 0。每帧状态机（`0xf6d538`）步进五个按槽位的读取器（`0xf6df44`）和头目的列表：

| 读取器状态 | 条件 | 然后 |
|---|---|---|
| 0 | 该槽位的已发送条目中不包含 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d 中的任何一个 | 为该槽位发一个 ServerRequest（`0xf70078`），状态 1 |
| 0 | 否则 | 擦除每个已回答的对（`0xf6edf4`） |
| 1 | 该槽位收到了 5 且发送了 6 | 一个带该槽位指令的块（`0xf6e6a8`、`0xf702ec`）作为 ServerCommand 投递，状态 2 |
| 2 | 该槽位回答了一个回合（0x15 / 0x16） | 状态 0 |

服务器按槽位保留它发送的消息和该槽位发送的消息，按到达顺序；`0xf6edf4` 擦除某类型的第一个已发送消息和第一个已收到的回答，每次调用一对，而状态 0 每帧对每一对 (0x15, 0x16)、(0x23, 0x24)、(0x11, 0x12)、(0x13, 0x14)、(0x17, 0x18)、(0x19, 0x1a)、(0x1b, 0x1c)、(0x1d, 0x1e)、(0x25, 0x26) 和 (0x1f, 0x20) 各调用它一次。因此，在回合发出的同时读取器被停住的槽位（一个濒死的槽位）会在再次被询问之前每帧擦除一个回合的积压：复活后 12 回合要 12 帧。Wild::Setup 的结束会清除两个列表。

头目的槽位（用表 `0x3c6a45a` 对照 N+0x95）只擦除已回答的对。其他读取器路径：发送了 4 的槽位会得到一个 kind 0x13 的块；在团体战中 N 的一侧，reader+9 处的子状态处理濒死的槽位（[战斗计时器耗尽](#the-battle-timer-running-out)）；0xd/0xe 投递 kind 0x1b；7/8、0xb/0xc、0xf/0x10 和收到的 0xa 分别投递 kind 0x17、0x19、0x15 和 0x17。

每帧的 run 步骤 `0x2d383b8(N)` 步进服务器的入站链路（`0xe0f040`、`0xe0fd68`、`0xe0f854` 作用于 [N+0xb0]），然后步进作业图 `0xfc363c(G, 1)`，G = [N+0xa8]（vtable `0x44ee6e8`）：

| G+ | 对象 | |
|---|---|---|
| 0x98 | 请求工厂 | 已投递的请求是一个 0x50 字节的对象：作业类型哈希、计数器、载荷 |
| 0xa0 | 调度器（vtable `0x44eea68`） | +0x40..+0x50 处的已投递请求，由 `0x1479b10` 追加 |
| 0xa8 | 来源（vtable `0x44947d8`） | vf 0x68 `0x14641ec` 选择要启动的请求 |
| 0xb0 | 每帧状态机（vtable `0x4493530`） | vf 0x68 `0xf6d538` |
| 0xb8 | 执行器（vtable `0x4493688`） | 一个作业栈 |

`0xfc363c(G, 1)` 在执行器持有作业时只运行执行器。否则它运行状态机，然后运行来源的选择：在团体战中第一个已投递的团体战行动（哈希 `0x5c307d44ea569b63`），在模块启动第一个 Wild::Setup（哈希 `0x2e9e7a3009002c36`）之前，否则第一个已投递的。执行器（`0xfc38dc`）运行栈顶作业的 vf 0x68：0 结束该帧；2 弹出它，压入其续体 [job+0x70] 并结束该帧；其他任何值都会再次运行它。每帧启动一个已投递的请求，而团体战行动会插队。

状态机的定时检查把其头目列表的副本作为消息 0x51 送入服务器自己的入站链路（`0xe0f440(server, N+0x95)`）；下一帧 `0x2016290` 把它的 0x24 字节复制到状态机的头目列表，后者投递团体战行动。没有这一步，定时行动永远不会触发。状态机的 vf 0x70 `0x20162bc` 还接受 `0x0ab4bce035f3012b`（投递到 `0x201665c`）和 `0xde3856ecc4fe200c`（一个 kind-14 行动，作为 ServerCommand 投递）。

在没有作业的帧上，状态机（`0xf6d538`）先读取战斗计时器，剩余时间为 0 或更少时投递时间耗尽；然后，在已武装时（`+0x118`，0x51 发出时清除，团体战行动被投递时再次置位），如果其头目列表持有行动就结束该帧，否则在副本上评估时间触发，有触发时发送 0x51 并结束该帧；持有行动的头目列表会作为团体战行动投递，帧随即结束；只有到这时才步进读取器。一个头目列表持有护盾的回合会先投递团体战行动本身（`0x16e5ad0`）；团体战行动会插到已投递队列的前面。在语料 794 场 oracle 战斗中，这样构建的服务器在它拒绝的第一个回合之前，以相同的服务器时间发送 oracle 发送的每条消息（31,581 条消息；25 场经过一次濒死，8 场经过一次复活，5 场经过护盾的 0x47）。

状态机的时钟是 19.2 MHz 的系统滴答：每帧把它推进到该帧的时间（若更晚），每次读取 `nn::os::GetSystemTick` 都会加 256 个滴答。因此，在同一时间再次运行的帧（主机会在上一批帧结束的时间启动每一批帧）读到的时间会稍有延后。整秒正好落在某帧时间上的计时器，只有当它的检查在该帧时间内读取时钟不早于其启动时读取的时刻，才会在该帧结束；否则它会晚一帧结束。

读取顺序如下：

| 时机 | 读取 | 代码 |
|---|---|---|
| 创建计时器 | 两次，第二次将其暂停 | `0xf70a58` |
| 恢复已暂停的计时器 | 一次，其 start | `0xe63ac4` |
| Wild::Setup 结束，即每个槽位都回答 0x11 之后的那一帧 | 一次，战斗计时器的 start | `0xe63ac4` |
| 每个状态机帧，战斗计时器运行时 | 一次，用于时间耗尽 | `0xf6d538` 中的 `0xf91070` |
| 时间触发，以空列表武装 | 护盾未升起且低时间行动尚未运行时一次；低时间行动尚未运行时一次；每个尚未触发的基于时间的额外行动各一次 | `0xf6f87c`、`0xf6dd84`、`0xf6fa5c` |
| 每个状态机帧 | 按槽位顺序为每个等待复活计时器的濒死槽位各一次 | `0xf71020` |

濒死槽位的计时器在其 0x22 被擦除时创建并恢复，因此其 start 是这些读取中的第三次。

`Server` 是这一流程的 Python 移植，按状态机的时钟每秒运行 30 帧；任何帧都不能跳过，因为等待濒死槽位计时器的读取器每帧都会推动状态机。主机把它服务器读取的每条消息按一个队列转发给访客，因此该队列的顺序就是服务器读取它们的顺序。从模拟主机的引导和转发的消息出发，该移植逐字节发送零售主机全部 24 帧（未写入的字节除外），而在 unicorn 下，游戏自身代码对这 216 个移植函数的执行留下相同的页，包括时间耗尽和头目获胜。

### 复现一个回合

在 unicorn 下，从一个停在构建器 `0x113c8a0` 处、类型为 0x15 的模拟零售主机出发，一个回合可以精确重放：内存通过 GDB stub 一次一页地取回，`tpidrro_el0` 背后的线程局部页是一个替身，其 `+0x1f8` 命名一个假线程，SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d 和 0x1e 返回 0。一个回合会触及 159 到 353 页。

服务器的 Python 移植为每个游戏函数运行一个函数，以其相对 main 的偏移为键：kind 1、5、17 和 21 的构建器、回合驱动 `0x113e3d0`（伤害 `0xf7c344`、濒死 `0x1144df8`、回合结束 `0x114a094`）、战斗开始 `0x113dca8`、构建步骤 `0x2891748`、`0x2892ac0`、`0x2d381a4` 和 `0x2892dd4`，以及 SDK 的 `nn::mem::StandardAllocator` 及其线程缓存和 TinyMT32 密钥（`0x525f448`）。在 86 台停住的零售主机上，它留下的正文和内存页与游戏相同。当字节 0 和字节 1 都未置位时，`__cxa_guard_acquire`（`0x53c49a0`）返回 1 并把 guard 的字节 1 设为 2。

数据表是由函数局部静态变量持有的 romfs 文件：

| 静态变量 | 文件 | 对象 |
|---|---|---|
| `0x47420b8` | `avalon/data/personal_array.bin` | 映射，键为物种 * 10000 + 形态（u32） |
| `0x47420d8` | `avalon/data/growTable.bin` | FlatBuffers 根，经由 [T+0x30] 的 vf +0x70 |
| `0x4742568` | `avalon/data/waza_array.bin` | 映射，键为招式（u16） |
| `0x4742548` | `avalon/data/tokusei_array.bin` | 映射，键为特性（u16） |
| `0x4734e50` | `world/data/battle/battle_item_conversion/battle_item_conversion_array.bin` | 数组 |

映射是 +0x68 处的 libc++ `unordered_map`：桶 +0x68、桶数 +0x70（不小于记录数的下一个素数）、首节点 +0x98、大小 +0xc0、负载因子 +0xc8（1.0）、默认记录 +0xd0。节点是 {next, hash = key, key, 记录指针}；+0x30 是文件资源（FNV 哈希 +0x48，路径 +0x50）。道具数组（由 `0x1821674` 填充）从 +0x28 起持有 0x18 字节的条目：u32 索引、u32 0、u64 哈希（main `0x3c61260 + 8 * index`）、u16 道具、6 个零字节。这些文件出自 `arc/data.trpfs`（`tools/switch/trpfs_read.py`；Oodle 经由游戏的 `OodleLZ_Decompress` `0xcc8750`）。数据系统的初始化 `0x1641afc` 运行 `0x1643a48`（personal、growth）、`0x1641cf0`（招式）和 `0x1641d78`（特性）；每张表被重置进其静态变量（`0x1643e68`），并通过 `0xf0ba9c` 追加到 `0x4763a18` 处的注册表。在预留记录数之后按文件顺序插入一个文件的记录，就得到零售主机的节点列表。

仅从静态镜像和 romfs 出发，该移植还构建了游戏堆（「Application」分配器 `0x3b78d3d`，上限 0xa0000000，位于 GlobalHeap `0x4763918` 之上）、弱句柄表（`0x165dd08`）和会话，其战斗开始的正文和之后的回合与零售主机相同（请求块未写入的栈字节除外）。改变战斗种子不会改变开始正文，并会改变一个回合的 123 个字节；堆地址和弱句柄 id 不会到达任何正文。

| 步骤 | 代码 | 它创建什么 |
|---|---|---|
| 启动 | `0x168ca58` -> `0x168cb20`，构造函数 `0x168cc48` | 会话管理器 `[[0x46d38e0]]`（0xc0 字节，vtable 0x4483f68）：+0x28 处按 id 的会话、+0xb0 处下一个 id 的 u32、+0xb8 处一个 0x7660 字节对象的通信持有者（vtable 0x4492468，构造函数 `0x168d59c`，端口 0x7b） |
| 团体战开始 | `0x159dba0` -> `0x159dc10`，构造函数 `0x159e860` | 会话 S（0x110 字节，vtable 0x4484008）：+0x40 处作业、+0xe0 处战斗 setup（0x730 字节，vtable 0x44ff070，构造函数 `0x159f8f0`，重置 `0x159fe68`） |
| 团体战开始 | 该 setup 的 Lua 绑定，setter `0x7fa0cc`..`0x7faf24` | 该 setup 的战斗字段 |
| 战斗开始 | `0x1891274(id)` -> `0x1891440` -> `0x18915c4(S, mgr + 0xb8, ...)` | N+0x48（vtable 0x44fef38）、+0x148 处的命名参数表、+0x108 处的选举对象（vtable 0x4492a48），然后是 S+0x48 中的 N（`0x16af068`，构造函数 `0x16b0fb8`） |

### 实测的服务器流程

以下适用于在 [为战斗提供服务](#serving-the-battle) 的脚本化零售主机之上运行的 oracle 服务器，而按这些规则构建的服务器在玩家获胜的九场完整战斗中，向零售主机发送相同的帧（包括通知）：

| 规则 | 实测 |
|---|---|
| 头部计数器 | `step` 每次发送、广播或一个请求增加一；`round` 对消息 1 为 0，从 0x11 起为 1，并随每个 0x15 以及 0x25 增加 |
| 一帧一个作业 | 消息 1 启动 Wild::Setup，它在每个槽位都回答了 1 之后发送 0x11，并在每个槽位都回答了 0x11 之后一帧结束 |
| 请求 | 在没有作业运行的帧上，向没有未回答内容的槽位投递一个请求（5）；请求每帧启动一个，按槽位顺序 0、2、3、4 |
| 一个指令 | 该槽位的 6 被作为作业投递，向每个槽位发送该回合（0x15） |
| 再次被询问 | 已经回答了发给它的每个回合的槽位会在下一帧再次被询问 |
| 获胜 | 获胜的回合之后，在下一帧是一个空回合 0x25（20576 个零字节），然后是带正文 `00 00 01 00 01 00` 的 0x29、0x49、0x35 和 0x37，每个都在每个槽位回答了前一个之后发送一次：在最后一个回答对 0x25 和 0x49 之后 2 帧，对其他消息则是同一帧 |
| 时间耗尽 | 带正文 `00 00 00 00 02 00` 的 0x2b（233 场战斗中的 63 场） |
| 通知 0x46 | 每个有作业启动的帧各一个，或者在没有作业运行时读取了某回合的回答（0x16）的帧各一个 |

### 为战斗提供服务

`bin/sv_host.py --raid-serve [NAME]` 在整个战斗期间保持网络，并用 `pokeldn.sv.raid_battle.RaidBattle` 从主机的站点为它提供服务：这是插件的战斗服务器（[战斗服务器](plugins.md#a-battle-server)），由引导和两个 NPC 伙伴构建，再加上零售主机为自己保留的站点。pokeldn 不附带战斗服务器；如果没有添加它的插件，该标志会被拒绝。所服务的会话让我们的宝可梦、头目、一台位于站点索引 1 的零售主机（引导参与者 1，槽位 2）和两个 NPC 伙伴就座，因此该标志只接受一台零售主机。

| 部分 | 主机发送什么 |
|---|---|
| 服务器发给零售主机的消息 | 寻址为 (0x2713, 1, 2) 的帧 |
| 槽位 0、1、3 和 4 | 每个奇数步骤在 0.05 秒后用类型 + 1 回答；对槽位 0、3 和 4 的请求（5）带一个类型 6 的指令，其中该槽位的宝可梦对头目使用其第一个招式，头目对该宝可梦使用其第一个招式（[行动](#actions)） |
| 服务器读取的每条消息，包括零售主机自己的 | 转发给零售主机，寻址为 (0x2713, 3, 5) |
| 每个推动了战斗的服务器帧 | 在该帧的消息之后，从槽位 0 发一个通知 0x46（步骤 0，4 字节的零正文），寻址为 (0x2713, 3, 5) |

每个帧都在 0x80 端口 0 上作为一个 deflate 压缩的可靠消息发出（标志 `COMPLETE_ZLIB`）；见过的最大者压缩后为 903 字节。复现 Scarlet 4.0.0 发送内容的服务器会把零售主机发送的六条战斗开始消息（`raid.HANDOFF`）作为其前六帧（其栈填充的头部字节除外）按相同顺序发送，因此 `--raid-serve` 会用它们代替 `HANDOFF` 来发送。

零售主机一回答 0x37，或 0x37 发出后 5 秒，主机就停止提供服务并关闭网络。回答 0x37 本身会在服务器上重新运行时间耗尽（[服务器的流程](#the-servers-flow)），因此本地站点不回答它。失败（服务器抛出异常或无法构建）会停止服务，并像不带该标志的主机那样移交网络；零售主机随后会故障转移并打自己的战斗（[哪个站点运行服务器](#which-station-runs-the-server)）。

## 加入

`bin/sv_join.py --raid-pokemon FILE` 加入一个场景 7 的网络并作为访客参与。零售主机的玩家打开一个结晶，选择以团体挑战，然后等待；应用的太晶团体战（加入）工具会运行它。`pokeldn.sv.raid.RaidGuest` 和加入者按顺序做这些事：

| 步骤 | 访客 |
|---|---|
| Net | 在消息标志 0x11 下回答 0x11 和 0x50 |
| Session | 不回答随加入响应而来的站点列表，至少 1 秒后再确认其重传，然后确认之后的每个列表，并发送字节 9 置位的时钟请求 |
| 通道 | 把主机的六键表拆成四个和团体战的两个，宣布四个，0.24 秒后加入端口 2，并在该表之后 0.79 秒宣布团体战的键；把其 0x7C 确认延迟 0.25 秒 |
| 身份 | 在就座后 0.44 秒发送标准记录集（`pokeldn.sv.reference`），记录 1 使用训练家名 |
| 大厅 | 在此之后 0.27 秒发送状态 0x18 及其宝可梦；2 秒后发送状态 0x01 |
| 开始 | 主机的状态 0x0c 到达后发送状态 0x0d；把 0x0d 作为准备信号发送的访客被确认，但从未显示为已准备 |
| 战斗 | 确认主机的 0x3480 0x93，每 0.5 秒发送 Session 类型 3 的离开，直到类型 4 为止（至多四次发送）并离开网络；战斗中的一台零售 Scarlet 对四次都没有回答 |
