# 联盟集友圈

联盟集友圈是 朱/紫 中最多四名玩家共享同一场地的会话。它的代码称之为团队集友圈
（`TeamCircle`），蓝莓任务（BBQ）则是 `bbmission`。pokeldn 以访客身份加入一台主机的
本地联盟集友圈，上报为主机带来 BP、并放出 Snacksworth 的传说的宝可梦的 BBQ 完成，
还在主机的玩家周围生成野生宝可梦
（[野外遭遇](#overworld-encounters)）。应用的两个联盟集友圈工具位于
[应用指南](gui.md#union-circle)。

下面的 Lua 是 朱 4.0.0 的 chunk `be21e65463b9a98f`（`main.blua`，SHA-256
`c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`，也就是
[太晶团体战](sv_raid.md)所用的 chunk），除非它标着 `main_dynamic`。一个 `0.N` 是 chunk 主函数
从 0 计数的第 N 个原型。这些原型编号在公开的 3.0.1 反汇编（Martmists-GH/SV-Script-RE）中相同。
尖括号里的名字来自它的哈希表；其余仍是哈希。

## 获取 Lua

该 chunk 是 `arc/data.trpfs` 中的 `script/lua/bin/release/main/main.blua`，以 Oodle 存储。4.0.0
更新的虚拟 RomFS 需要基础游戏的 RomFS：`arc/data.trpfd` 的一部分位于基础游戏中。

    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
        --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT

`--image` 会运行 `main` 的 `OodleLZ_Decompress`（`0xcc8750`）。该 chunk 是 Lua 5.4 字节码，含
30,829 个顶层原型；`main_dynamic`（`script/lua/bin/release/main_dynamic/main_dynamic.blua`）
存放事件脚本，提取方式相同。

## BBQ

任务进度由原生代码处理，位于 Lua 模块 `c5137FC87` 中。Lua 游戏事件通过
`C00099C1DFBF96B11.S110BDDB84DEB4379`（`0.7064`）上报给它，后者把（任务类型、两个值、计数）
传给 `c5137FC87.f4246D9CA`；例如一次进化会上报类型 28、计数 1。任务在联盟集友圈这一侧的处理
是第二个原生模块 `c4D400AC0`。

每个任务都有一个等级，即俱乐部数据（`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`）
中其 `MissionInfo` 行的 `mission_grade`：0 普通，1 奖励，2 团队。Snacksworth 把团队任务称为
团体任务。完成事件携带其任务的等级。

数据包的 quest 表是一个由 64 个 `MissionInfo` 结构组成的 FlatBuffer：类别（1 对战，2 场地，
3 相机）、`mission_type`、`mission_id`、目标、奖励 BP、刷新 BP（用来换掉该任务）、放出类型、
等级、难度（0 入门到 2 高级）与权重。每条消息里的任务 id 就是其所在行的 `mission_type`；
`mission_id` 区分同一类型的多行，它们在等级、难度、目标或 BP 上不同。BBQ 列表按这一对值查找
任务（`0x29de0f4`）。第二张表 `MissionSettings` 给出某个类型在每种变体下的文本（一种宝可梦
属性、一个生物群系、一种口味），位于 `club_bbmission`。任务表使用的类型：

| id | 任务 | 等级 |
|---|---|---|
| 1 | 用自动对战击败野生宝可梦 | 普通、奖励 |
| 2 | 移动一段距离 | 普通 |

| 5 | 与朋友一起做一个四星三明治 | 团队 |

| 8 | 给宝可梦洗澡 | 奖励 |
| 9 | 从背后偷袭野生宝可梦 | 普通 |
| 10 | 孵化一颗蛋 | 奖励 |
| 11 | 从地上捡起道具 | 普通 |
| 14 | 捕捉提示所描述的宝可梦 | 团队 |
| 15 | 在某个生物群系中找到百变怪方块 | 团队 |
| 21 | 拍摄一只某属性的野生宝可梦 | 奖励 |
| 22 | 拍摄一只飞行中的野生宝可梦 | 普通 |
| 23 | 拍摄一只游泳中的野生宝可梦 | 普通 |
| 25 | 与朋友在某个生物群系拍照 | 团队 |

每个普通行支付 20 到 40 BP，每个奖励行 100 到 200，每个团队行 400 到 600。

BBQ 管理器创建时（`0.7062`），会把若干 getter 交给原生侧。`c16FE4B25` 取得玩家自己的场地
（`f61488ABA`，存档的 `currentFieldId`）与某个成员的场地（`f45B80F87`，某站点索引对应的 110
值）。`c5137FC87` 取得玩家是否在场地中（`f01FF34BD`）以及两个俱乐部等级标志
`FSYS_CLUB_BBMISSION_LVUP_01` 与 `_02`。

管理器的 `PreUpdate`（`0.7069`）每帧排空三个原生队列：

| 队列 | 来源 | Lua 做什么 |
|---|---|---|
| `c5137FC87.fB8D11637` / `f35493666` | 玩家自己的完成 | 在 `c4D400AC0.f5770F782` 成立期间，把每次完成交给 `c4D400AC0.fAC449469`。在集友圈中做出的奖励完成（`c4D400AC0.f48603105`）交给主机上的 `c4D400AC0.f263D7D28` 与 `f07578A96`（`c4D400AC0.fE8E53DDE`），访客不会为它记任何账。其他任何完成则为 BP 排队 |
| `c4D400AC0.fD7C6549F` / `f37737462` | 其他成员的完成 | 把每次作为提示显示；除非是奖励完成，否则为 BP 排队 |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | 来自集友圈的 BP 发放 | 把每笔发放为 BP 排队 |

`0.7075` 把排队的事件合并进同等级的事件并求其 BP 之和（`fBCA6AEB8`）。`0.7076` 把排队的总和
加进货币管理器，`0.7077` 显示 BP 消息。管理器的加法（`0.15120`）把玩家的 BP 夹在 0 到
9,999,999（`0.15128`），所以即使某次完成的 BP 是 s32，单次完成最多也只计 9,999,999 BP。

Lua 什么都不校验：成员的普通或团队完成直接从第二个队列付给主机，奖励完成则只通过原生集友圈
模块放进第三个队列的发放来支付。

## 原生模块

以下地址位于 朱 4.0.0 的 `main` 中。

原生模块与函数名是 `main` rodata 中的普通字符串；每个模块在 `.data` 中有一张 `luaL_Reg` 风格的
{name, function} 表：`c4D400AC0` 位于 `0x442e500`（22 个函数），`c5137FC87` 位于 `0x4420630`
（45 个）。完成事件是一份 userdata（方法位于 `0x441dc50`）：`fBCA6AEB8` 返回 BP（`+0x10` 处的
s32），`f0C278E84` 返回等级（`+0xd` 处的 s8）。`0x29dd878` 从任务所在行构建它：任务 id
（`+0x0` 处的 u16）、`+0x4` 处的 u32、等级与 BP。

`c4D400AC0` 的函数作用于一个集友圈对象，即位于 `0x4739410` 的惰性构建单例：

| 函数 | 作用 |
|---|---|
| `f5770F782` | 集友圈是否就绪（`0xa0d038`） |
| `f48603105`, `fE8E53DDE` | 玩家是否在集友圈中，以及是否为房主（`0xa0e9ac`） |
| `fAC449469` | 把玩家的完成作为消息 3 发出（`0xa0db20`） |
| `f263D7D28` | 在主机上，把一次奖励完成作为消息 5 发出（`0xa0dcf4`） |
| `f07578A96` | 在主机上，为自己的一次奖励完成记账（`0xa0df34`，随后是发放推送 `0xa0e164`） |

集友圈在自己的信道上（对象的 `+0x70`）发送这些消息：0x80 端口 0 上、游戏密钥 0x0048，消息类型
放在 kind 字节里。每条先是游戏带标记格式的完成事件（`0xb9`，18 个字段，由 `0xa17694` 读取），
然后是发送方的消息序号（`+0xb8`）。消息 3 还携带发送方的 BBQ 状态记录（`0xa0f37c`，由
`0xa17170` 读取）。在这种带标记格式中，-64 到 127 的整数就是自身一个字节，更宽的整数放在有符号
标记之后（0x84 到 0x86），浮点数放在 0x88 之后。

完成事件的字段：

| 字段 | 值 |
|---|---|
| 0 | 任务 id |
| 3, 11 | 任务所在的槽位 |
| 4 | 等级 |
| 5 | BP |
| 6 | 发送方站点 id 构成的元组（u64，标记 0x83） |
| 7 | 任务的 `MissionInfo` 行 |
| 12, 13 | 接替该槽位的任务，及其行 |

其余字段为零或空行。在一次完成前十分之一秒，主机会发送 kind 2：任务、-1、-1、其进度（1.0）、
其序号，以及其状态记录。

### BBQ 状态记录

每个玩家的 BBQ 管理器把状态记录存在自己的 `+0x40`；集友圈把它（`0xa0f37c`）写入消息 1、2 和 3。
消息 1（kind 1）只有发送方的消息序号和这份记录。玩家在集友圈启动时发一份，step 1，然后一条
无实体的 kind 4（`480004`），然后 step 2；主机在每位成员完成之后也会再发一份。该记录是一个
11 元组：

| 元素 | 记录偏移 | 值 |
|---|---|---|
| 0 | `+0x0` | 每条记录中都是 1：管理器 `+0x40` 处的字节 |
| 1 到 3 | `+0x4`, `+0x50`, `+0x9c` | 玩家的三个任务槽位 |
| 4 | `+0xe8` | 一个字节的字节串，每条记录中都是 1 |
| 5, 6 | `+0xec`, `+0x138` | 另外两个槽位，在见到的每条记录中都为空 |
| 7 | `+0x184` | 一个有符号字节，在每条记录中都等于元素 9 |
| 8 | `+0x185` | 玩家面向下一次发放的奖励完成数 |
| 9 | `+0x188` | 单人总计（管理器的 `+0x1c8`） |
| 10 | `+0x18c` | 团队总计（管理器的 `+0x1cc`） |

一个槽位（`0xa0fa18`）为 0x4c 字节，记录从中取任务 id（u16，空时为 0）、其进度（float）、其文本
变体（即 `MissionSettings` 的变体，没有则为 0）以及该行的 `mission_id`。若主机第五个槽位指名的
任务与其自己的不同，成员就采用主机的（`0xa14290`）。

`circle.bbq_record` 读取消息 1、2 或 3 末尾的记录。

零售主机的槽位存放其任务类型的入门级普通行（`mission_id` 为 0：20 BP，任务 1 的目标是击败
10 次，其他任务为 1），进度为 0，直到某次上报完成其中之一；更靠后的槽位保持为空，奖励计数
为 0。

### 成员在主机任务上的进度

成员通过消息 2（kind 2，0x80 端口 0）上报进度，来完成主机的一个任务：任务、两个值（没有变体
的任务为 -1、-1）、计数、其消息序号及其自己的状态记录。主机以其显示该进度的记录作答，然后
发送自己的消息 3：这次完成记在成员的站点 id（字段 6）名下，带上 BP、槽位与接替它的任务。它的
单人总计加一。

消息 2 携带 Lua 的进度上报（`c5137FC87.f4246D9CA`）所传的内容：任务、它的两个值与计数。主机的
接收处理器把这四个值，连同成员标志与发送方，交给它自己的上报所到达的同一个原生进度分发器
（`0x29dc838`）（`0x29dc6b0`）。因此主机会把成员的进度当作自己的来计，自己完成任务并结算，
这次完成也像它自己的任何一次那样计入其单人总计。

`circle.progress_message` 构造消息 2。一次 Snacksworth 运行（[加入](#joining)）会按主机最新
记录所示，把每一份依次发往主机三个槽位中的下一个，计数为 500（普通行的最大目标），第一个值为
该槽位的变体，没有变体则为 -1；零售主机会逐个完成它们。

## 主机如何处理成员的完成

接收处理器（`0xa13b00`）通过 `0x3c5b7a4` 处的跳转表按类型分发。对于一条消息 3，主机：

1. 把该成员的奖励计数存入其 BBQ 状态中该成员的槽位；
2. 在自己的 BBQ 列表中查找该任务（`0x29de0f4`，按任务 id 与 `+0x4` 处的 u32）。只有匹配上它
   自己的某个奖励任务，这次完成才计入主机自己的计数，也只有这时主机才为它排队自己的提示。
   除了第 4 步中的一个标志，这个结果不影响下面任何事；
3. 把这次完成作为成员提示排队（`fD7C6549F` 队列）；
4. 如果这次完成是奖励，把事件的 `+0x7c` 设为 min(3, 主机自己的奖励计数加三个成员槽位之和)，
   把 `+0x80` 设为第 2 步是否匹配，把它作为消息 5 发给每位成员，并按收到的样子通过发放推送
   给自己记账；
5. 如果这次完成是团队完成且主机的 BBQ 管理器处于活动状态，就给主机的团队总计加 1（见下文）。

只有在这之后，主机才把该消息的序号与该成员的上一个序号比较，而这个序号只用于把关该成员的状态
记录。

收到消息 5 的成员会通过同一个发放推送为该事件记账，除非其序号比从主机见到的上一个更旧。

主机照成员消息里写的付：没有任何地方校验 `+0x10` 处的 BP，也不校验任务是否存在。普通或团队
完成由 Lua 立即支付。奖励完成要经过发放推送，这是唯一的排序。它把每个事件暂存，仅当其 `+0x7c`
比上一个已放出事件的多 1、或少 2，或两者都为 0 时，才把它放进发放队列（对象的 `+0x108`）。该值
由槽位算出，所以成员的下一次奖励完成必须上报比上次多 1 的计数。

## Snacksworth

BBQ 管理器维护两个累计总计，分别由 `c5137FC87.f6ED7C9B6`（`+0x1c8`）与 `fECB0EBF0`（`+0x1cc`）
读取：

| 总计 | 何时上升 | 还被谁读取 |
|---|---|---|
| 单人，`+0x1c8` | 玩家自己的普通或奖励完成（`0x29dda40`） | 俱乐部的 BBQ 升级事件，在 15 与 45 时 |
| 团队，`+0x1cc` | 玩家自己的团队完成，以及在主机上消息 3 中每位成员的团队完成（`0xa14918`） | |

Snacksworth 是事件 `s2_sub_012`，他的 25 只传说的宝可梦是事件 `s2_sub_013` 到 `s2_sub_037`，
各自的状态在 `WEVT_S2_SUB_0NN_STATE` 中。该事件在 `main_dynamic` 中的类（原型 `0.1995` 到
`0.2032`）通过 `0.2019` 读单人总计、通过 `0.2020` 读团队总计。

当玩家与他交谈时，`0.2002` 会在单人总计减去单人路线上已放出的每只传说的宝可梦所对应的
`missionReleaseCount` 之后达到 `missionReleaseCount` 时，放出下一只单人路线的传说的宝可梦；
`0.2003` 对团队路线做同样的事，用团队总计与 `teamMissionReleaseCount`。两个计数都来自该事件的
配置表（`s2_sub_012.ReleaseConfigTable`，位于
`arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak`）。数据包中唯一形如
该表的表存的是 10 与 1。

同一数据包中的 `s2_sub_012.ReleasePokeTable` 把每只传说的宝可梦放在四条路线中的两条上，两条
单人（`MissionA`、`MissionB`）与两条团队（`TeamMissionA`、`TeamMissionB`）：

| 位置 | 传说的宝可梦 |
|---|---|
| 两条单人路线 | 急冻鸟、闪电鸟、火焰鸟、熊徒弟 |
| 两条团队路线 | 烈空坐、酋雷姆、奈克洛兹玛 |
| 各一条 | 其余 18 只 |

脚本向 `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` 询问玩家处在哪一对路线上，A 路线还是 B 路线；
朱 在 A 路线上（一次团队完成放出了捷克罗姆，而它只在 `TeamMissionA` 上）。每一对都把 25 只
传说的宝可梦分开且不重叠：单人路线 13 只，团队路线 12 只。一次交谈最多放出一份零食，先尝试
团队路线。每条路线在其尚未放出的传说的宝可梦中随机选择（`0.2007`）。一条路线的下一次放出需要
其总计达到「其计数 ×（该路线上已放出的传说的宝可梦数 + 1）」。所以全部 25 只需要单人总计
130 与团队总计 12，以及 25 次交谈。

没有任何消息指名零食：脚本拿主机自己的总计与配置比较。每条携带团队完成的消息 3 都给主机的
团队总计加一，既不校验该任务是它拥有的团队任务，也不做防重复的序号校验；在
`teamMissionReleaseCount` 为 1 时，每一次就是团队路线的一份零食。成员完成的每个主机任务
（[成员在主机任务上的进度](#a-members-progress-on-the-hosts-quests)）都给其单人总计加一，从而
供给单人路线上的那 13 只。

## 加入

`bin/sv_join.py --union-circle` 以团体战访客加入团体战的方式加入一台主机主持的集友圈
（`pokeldn.sv.circle`）。它占下座位，发送自己的身份记录，在 0x7C 端口 1 上镜像主机的信道表，
并在 `--hold` 期间保持座位，默认是整个 `--seconds`。它不发送大厅消息，主机离开时也不接管主机
角色。当主机的场地就绪后，它把自己的玩家放上去（`circle.Member`，[场地](#the-field)）。它打印
用户需要跟随的内容；`--verbose-circle` 还会加上它发送的每条集友圈消息与区域搜索的每一步，这些
`--capture` 文件本来也会保存。

    ./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl

在连接密码下主持集友圈的零售 朱 4.0.0 会广播场景 5、最多四名参与者，以及交换的应用程序数据：
连接码在密码中也在游戏字节中，其长度在 +0x24。游戏字节还在 +0x21 处有 `aa 08 3e`，而搜索中的
主机把那里留为零。

它像连接交换或太晶团体战主机那样让访客入座：加入响应、站点列表、信道表（密钥 0x007B、0x0132、
0x0232 与 0x0332）、两条流的打开、时钟应答及其身份记录。之后访客等待主机的玩家启动集友圈。

## 启动集友圈

启动时，主机发送 Net 0x50，其广播计入成员人数，并在 0x80 端口 2 上发送类型 7 的通告（以及对
每位成员各一条接受它的类型 9），还在 0x80 端口 0 上发送其集友圈消息。

集友圈消息就是 Lua 的 net 消息。每条都是密钥 0x0132 下的一条游戏消息（处理键、kind、step，
然后是序列化器头；[太晶团体战](sv_raid.md#the-lobby)），其 kind 就是 Lua 消息 id。团体战的
「loading」与「loaded」（0x0132，kind 0x6E 与 0x73）就是同一个接收器的消息 110 与 115。有些
载荷是 FlatBuffer 表，其余是固定结构；104 与 106 经过 LZ4 压缩（序列化器压缩 2）。

| 消息 | 来自 | 载荷 | `TeamCircleUI` 的处理 |
|---|---|---|---|
| 100 | 主机，在启动时 | 一个只含一个 u32 的表，总是 12345678 | 启动音效；访客的启动标志 |
| 101 | 每个站点，主机紧接其 100 之后，成员在主机的 100 之后 | 32 字节：站点所站的位置（场地 id、三个宝可梦中心标志） | 按站点 |
| 103 | 每个站点 | 一个只含一个 u32 的表，即同步点的 id | 1 与 2 交给 UI（启动演示已加载、已结束），其余 id 交给同步对象 |
| 111 | 主机 | 5916 字节：四个零字节，然后是两个表向量（30 与 10）的 FlatBuffer | 只用一个标志；内容由原生代码读取 |
| 104 | 主机 | 一个表：游戏时间、现实时间及其经过的秒数（float）、天气种子（u64）、抽签的长度，以及当前与下一个天气的 {type, duration} 对 | 时钟与天气，送进游戏时间管理器与 `WeatherManager.Sync` |
| 102 | 主机 | 两个 u32：成员传送到的飞行点 | 传送 |
| 106 | 每个站点 | 300 个六字节槽位，其太晶团体战结晶；`ffffffff0000` 表示空槽 | 按站点 |

主机按表中顺序发送它们，在其 101 之后还有三条密钥 0x0048 的消息，都在启动后两秒内。

每个站点都到达同步点 2215，等待每个站点的 101，发送自己的 106，并等待其他各方的 106
（`IsGemInfo`）；启动演示中 id 为 1 与 2 的 103 也以同样方式等待。当每位成员都发送了带该 id 的
103 时，一个同步点即算到达（`CEEE8D2836ABEDE23`）。

零售主机会把超过 1395 字节的消息拆成分片，而对未分片的更长消息不予确认，所以 106 会走 LZ4
压缩，主机自己的 106 也是如此。

全部 106 到齐后，主机传送到其 102 的飞行点，并发送 115（1，0）。

## 场地

随后主机的玩家进入场地。它通过向每位成员在 0x7C 端口 1 上发送一条更新（经 zlib 压缩），再打开
14 个信道密钥（低字节 0x1E 到 0x2A，其中一些带子信道 0 与 1）。零售成员以同样方式回发同样的
更新。主机发送密钥 0x0024、kind 1、step 1，没有主体，此后发送它的玩家：

| 内容 | 方式 |
|---|---|
| 动画状态 | 可靠，0x80 端口 0，密钥 0x001E、kind 5，状态的名称（`Top/pc_field/move/defaultwait01`），每 3 到 7 s 一次 |
| 变换 | 不可靠协议 0x68（像 0x80 那样按网格寻址），密钥 0x011E、kind 4，38 字节的 float，每秒约 20 次；kind 6 与 7 各一次 |

在构建启动演示之前，主机会等待（`F9FFADFE613D572B7`），直到其他每个站点的玩家对象都出现在其
场地上。不发送玩家的成员会让它停在黑色的「通信中」画面。主机通过原生模块 `c2A8846F6` 把成员
生成为 `playables.Player` 对象（其 `f6BD530B6` 就在等待之前运行）。

玩家对象在每位成员与主机之间经 0x7C 端口 0 传输，紧接在场地密钥之后：

| 密钥 | 消息 | 内容 |
|---|---|---|
| 0x001F | id（u16）、type（u16） | 一台主机声明它自己的一个对象 |
| 0x001E | kind 0、0、id（u16） | 一台主机请求对方已声明的某个对象 |
| 0x001E | kind 1、2 或 3、0、id（u16）、状态 | 应答：对象的状态，其 kind 为 1、2 或 3，取决于该对象在声明中的位置 |

每台主机声明四个对象（类型 0、1 或 2、3 与 10），id 从站点索引起以 4 递增。一台主机会请求对方
声明的每个对象；没有人应答对类型 10 对象的请求。状态为 70 字节（kind 2）或 214 字节（kind 1 与
3），经 zlib 压缩：句柄、缩放、旋转、位置；kind 1 是玩家，并携带一个 FlatBuffer。主机在成员的
kind 1 应答之后半秒启动它的演示。

随后成员在密钥 0x0025 上向主机询问若干 u64 id 列表，主机对每个列表以标志作答
（[野外遭遇](#overworld-encounters)）。

密钥 0x0048 属于 BBQ 模块（[原生模块](#native-modules)），位于主机的第一张信道表中。在其端口 2
通告前后，主机发送 kind 1 step 1、一条无实体的 kind 4（`480004`）以及 kind 1 step 2，两个 step
都携带其状态记录（[BBQ 状态记录](#the-bbq-status-record)）。

`circle.Member` 做以下事情：
- 它用主机自己的 101 的副本应答主机的 100，于是访客的玩家站在主机玩家所在的位置。
- 它回显主机发送的每一条 103。
- 它用 300 个空槽位应答主机的 106，经 LZ4 压缩：一个没有结晶的世界。
- 它把主机发送的每条 110 与 115 作为自己的副本发出，跟随主机的场地。
- 一旦 `sv_join` 回发了场地密钥，它就声明站点 1 的四个对象，并请求主机的每个对象。对主机的
  每次请求，它都用主机自己该类型对象在访客 id 下的状态作答，于是访客的玩家与主机站得一样。

使用 `--follow-host` 时，访客的玩家也会随主机移动：0x68 上的每帧主机数据与密钥 0x001E 上的对象
消息，都以访客对应的对象发出，按访客自己的 60 Hz 时钟，延迟 0.3 s 重放主机（主机的变换每秒
到达约 27 次）。访客保持在主机 5 m 以内，面朝主机，并按自己的步速缩放主机的移动混合。

使用 `--circle-task` 时，任务完成后访客的玩家离开集友圈，运行随即结束：
- `snacksworth` 从第一条状态记录读取主机的单人总计与团队总计。从启动演示结束（其 id 为 2 的
  103）起，它每秒发送一条，补足团队总计还差的团队完成以达到 12，然后上报完成主机任务直到其
  单人总计为 130（[成员在主机任务上的进度](#a-members-progress-on-the-hosts-quests)），再在其
  团队总计仍有缺口时多发一条团队完成（[Snacksworth](#snacksworth)）。每次团队完成都是按游戏
  抽取方式抽出的团队任务（`circle.TEAM_QUESTS`，每个任务与 BP 及其概率），并支付该任务的 BP。
  它随主机总计上升打印进度，并在连续 20 次发送都没有上升时停止。
- `bp` 在启动演示结束后一秒，发送一次任务 29 的普通完成，支付 `--bbq-clear` 的 BP，1 到
  9,999,999。

每次完成都是一条消息 3，带上其 BP、访客的站点 id 与访客的状态记录。

零售主机会支付每一条这样的完成，即使访客此前没有发过消息 1；提示与 BP 会在其玩家关闭 BP 侧栏
后显示。任意任务的一次团队完成都会放出下一只团队路线的传说的宝可梦（[Snacksworth](#snacksworth)），
无论主机在蓝莓学园内还是外。

## 野外遭遇

集友圈中的每台主机都按自己的游戏版本、围绕自己的玩家生成野生宝可梦，并把每一只广播给其他人，
因此成员能捕捉另一版本的独占宝可梦（零区中的 朱 主机生成 dev id 982，紫 成员生成 992）。版本
不会交换，主机也没有特殊角色。

共享的宝可梦经 0x80 端口 0 与不可靠协议传输，由其所有者广播；只有对其中一只的请求及其拒绝会
发给单个站点，在 0x7c 端口 0 上：

| 密钥 | 消息 | 内容 |
|---|---|---|
| 0x0026 | kind 1，其 96 字节记录作为字节串 | 所有者生成了实体（station, n） |
| 0x0026 | kind 2，(station, n) | 该实体已消失 |
| 0x0026 | kind 5，((station, n), (station, n)) | 一台主机向所有者请求该实体以便与之对战，使用请求方自己的 id；只在 0x7c 端口 0 上发给所有者 |
| 0x0026 | kind 6，同一对 | 所有者拒绝；回到请求方 |
| 0x0026 | kind 7，同一对 | 该实体现在属于第二个 id 的站点，由它与之对战；有一次出现在该实体 kind 2 之前的 15 s |
| 0x0126 | kind 3，(station, n)、(一个 float、0.0、0.0、0、0 或 1) | 实体的状态，每 0.2 s（成员）到 0.5 s（主机）一次；最后一个元素是其状态 |
| 0x011E | 0x68 上的 kind 4，按对象 id | 实体的变换，与玩家相同 |

实体的对象 id 是 station + 4n，即其记录开头的那个 u16。一台主机只把自己的实体分享给玩家站在
其附近的那位成员。每个 id 都是一对无符号整数（分发器 `0x1dbd4b0` 不读取有符号标记）。

零售主机在其每个实体存活期间每秒发送其变换约 27 次，实体会游荡：离开生成处 0 到 41 m，310 s
内 70 个实体中有 61 个在 15 m 以内。每个变换中的高度就是地面的高度。在主机玩家与其实体都经过的
1 m 方格上，两者的最低高度相差在 0.15 m 以内（52 个方格，中位数 0.00 m）。

一台主机把别人的实体标为未稳定（状态 1），并拒绝与之对战（`BattleStartWait`），直到某个状态
指明状态 0。撞上一个已稳定的实体时，它显示「!」并向所有者请求（`0x1972664`）：它为这个实体取
一个自己的新 id，存下这对值与一个回调，其管理器更新（`0x1593884`）把 kind 5 发给发出该实体
记录的站点。随后遭遇（`GameEventEncount`，NetInitWait）无超时地等待所有者给出指名同一对值的
应答（`0x1dbdd70`）。当该实体是它自己的、且没有其他主机持有时，所有者就会交出（`0x1dbdc20`，
然后是更新在 `0x15934c8` 处的广播），否则拒绝（`0x1593914`）。交出时，每台主机都把该实体改名
为请求方的 id（`0x1595a1c`）并标记为已交战；请求方把它收为自己的并开始对战。当它与自己的实体
对战时，一台主机广播一条 kind 7，把这对值重复两次。

记录为 96 字节。`EncountManager.UpdateNetworkSpawn` 通过 Lua 模块 `c4CF1D719` 绑定的 getter
（原生 `0x90e344` 到 `0x90e588`）把其字段复制进一个 `pml.pokepara.InitialSpec`，然后在宝可梦
本身上设置缎带、太晶属性与一只霜奶仙的装饰。捕获到的每条记录都符合这个布局：

| 偏移 | 位 | 字段 |
|---|---|---|
| 0x00 | u16 | 对象 id |
| 0x04 | u64 第 0-10 位 | 开发用物种 |
| | 11-22 | 携带道具 |
| | 23-30 | 尺寸 |
| | 31 | 性别（1 为雌性） |
| | 32 | 闪光；置位时生成的宝可梦为闪光 |
| | 33-37 | 形态 |
| | 38-44 | 等级 |
| | 45-52 | 按 PKHeX 的 `RibbonIndex` 计的缎带（标记），非 0 时应用 |
| | 53-57 | 性格 |
| | 58-62 | 太晶属性 |
| 0x0C | u32 第 0-3 位 | 霜奶仙装饰 |
| | 8-27 | 个体值 体力、攻击、防御、速度，各 5 位 |
| 0x10 | u16 第 0-9 位 | 个体值 特攻、特防 |
| | 10-11 | 特性槽位 |
| 0x24 | s32 | -1；在所见唯一一只百变怪与索罗亚中为 0 |
| 0x30 | 3 个 float | 位置 |
| 0x40 | 4 个 float | 旋转，在每个样本中都是单位量 |

其余字节为 0（零售记录在 0x02、0x28 与 0x54 处留有陈旧内存）。在记录之前，所有者会在 0x68 上
发送该实体的帧：没有父级的 kind 6
（`00000000 00000000 0000003f 0000003f 00000000 0000003f 0000003f`）与尺寸为 1.0 的 kind 7。
`circle.Spawner` 以同样方式发送访客自己的生成物（[自定义遭遇](#crafted-encounters)）。

`UpdateNetworkSpawn` 只凭记录构建宝可梦；闪光位把稀有度字（`+0x18`）设为 `0x2ffffffff` 或
`0x1ffffffff`，所以两种情况都由所有者决定。记录不含招式、PID 或加密常量；捕获时会加上捕获者
的训练家、球、地点、日期与等级。

游戏接受任何记录；PKHeX（Core 26.8.26）把这次捕获判定为在捕获地点的一次野生遭遇：

| 字段 | PKHeX 接受条件 |
|---|---|
| 物种、形态、等级 | 捕获地点处有一个 朱/紫 野生槽位，其物种与形态相符、等级范围包含该等级；闪光锁定或仅限固定出现的物种（如烈空坐）永远不行 |
| 太晶属性 | 该物种自身属性之一，除非该处有配信的大量发生覆盖该物种 |
| 性别 | 在该物种的比例之内 |
| 标记 | 不能是最强之证或泰坦之证；巨无霸仅在尺寸 255 时，迷你仅在尺寸 0 时；天气标记只在某个槽位指名该天气处 |
| 闪光、性格、个体值、特性槽位（含隐藏特性）、尺寸、携带道具 | 任意 |

PKHeX 在两个版本下列出所有 朱/紫 野生槽位，所以另一版本的独占也合法，且分时段的槽位不会限制
已存下的宝可梦。记录中的物种是内部索引（`gen9.national` 给出全国图鉴编号）。

场地的其余部分：

| 内容 | 密钥 |
|---|---|
| 主机的大量发生 | 0x0029 kind 1，场地打开时每次大量发生广播一次 |
| 主机自己的状态 | 0x0024 kind 1 与 0x002A kind 3 到 5，几个小整数 |
| 成员的 id 查询 | 0x0025，仅成员发给主机 |

两款游戏每张地图都带一张遭遇表（`world/data/encount/pokedata/pokedata*_array.bin`），包含两个
版本的行；字段 28 指明某行在哪些版本中出现。

一条大量发生消息是一个元组：中心（三个 float，来自 `world/data/encount/point_data/
outbreak_point_data`）、它附近的第二个点、物种、0、形态、0、90 到 110 的数量、地图（0 帕底亚，
1 北上，2 蓝莓）以及 0。

密钥 0x0025 是成员定期发给主机的查询：kind 1 列出 u64 id，kind 3 对每个 `((id,), flag)` 以 0 或
1 作答，kind 2 列出成员放掉的 id。id 的最高五位是类别；成员大约每九秒遍历类别 1、2、3、4、5、
9、10、13 与 16。

## 自定义遭遇

`sv_join --spawn SPECIES:LEVEL` 以成员身份加入集友圈，并在主机的玩家周围维持三个用户自造的
宝可梦生成；配合 `--follow-host` 时访客的玩家跟随主机的玩家。`--spawn-*` 标志设置一条记录所
携带的内容：形态、闪光、太晶属性、性格、性别、特性槽位、尺寸、携带道具、标记与个体值。未指定的
项按主机自己的野生宝可梦的方式抽取：尺寸、性格与每项个体值随机，特性槽位 0 或 1，没有携带道具，
没有标记。`--spawn-mark` 接受 PKHeX 的 `RibbonIndex`（53 午餐时间到 97 萎靡）；游戏按同一套
编号读取记录的缎带字段：一台零售 朱 捕获了以 58 发送的生成物，带着雨天之证（PK9 在 0x34 处标志
的第 58 位，没有附加称号），PKHeX 判定其合法。主机与之对战（其请求，被交出）、移除（一条指名它
的 kind 2）或走出 50 m 以外的生成物会被放掉，另一个会在主机附近出现。

记录里没有地面数据，因此 `circle.Ground` 保存主机所显示的地面：在每个 1 m 方格中，其玩家（或
坐骑）与实体站过的最低高度。一个生成物出现在离主机玩家 15 到 25 m 处，且只在最近 120 s 内有
主机的某个实体站过、并且 6 m 内至少有八个已知方格的方格上，所以我们没有任何生成物会出现在主机
不生成的地方（一台零售 朱 在其玩家站在城镇中时，没有显示任何发出的生成物）。每个生成物停留
2 到 6 s，然后以 1 m/s 走向其生成处 6 m 内的一个已知方格，高度每 0.5 m 取地面的高度；上升或
下降超过 0.6 m 的一步，或跨过没有已知地面的方格，都不会走。行走中生成物的变换每 1/30 s 发出。
一台零售 朱 显示这些生成物站在地面上并行走，其玩家撞上正在行走的一个就开始了对战。

使用 `--spawn-legal` 时由 PKHeX 决定：辅助程序的 `wild_areas` 命令按地点列出 朱/紫 的野生槽位，
`wild_legal` 对从每个地点捕获的自造生成物运行 PKHeX 的合法性分析，每种太晶属性各一次；只要某
地点有任一槽位接受该生成物，该地点就算数，所以天气标记需要一个指名该天气的槽位（9 级的乌波可以
带雨天，绝不能带下雪）。应用提供 42 种野生标记：时间、天气、命运、罕见、稀有与个性。PKHeX 在
任何地点都不接受的生成物会中止运行。

随后生成物等待主机的区域（`wild.Locator`）。主机分享的每只野生宝可梦（密钥 0x0026 kind 1，
在访客的玩家靠近后）把地点收窄到那些有槽位匹配其物种、形态与等级的地点。当剩下的每个地点都是
PKHeX 接受该生成物的地点时，区域就算找到；它不必只剩一个地点。然后生成物出现，当主机走出找到
区域时所站的 50 m 以外，它们全部消失，寻找重新开始。在那之前，当主机离它衡量过的某个生成物、
或离一个已无地点支持的生成物超过 100 m 时，寻找也会重新开始。没有任何野生槽位支持的生成物
（团体战的、活动的）会被排除。

在零区，主机的玩家不发送其玩家的变换。连续 2 s 没有变换时，主机被放在最近 30 s 内最新的六个
生成物的中间；一个都没有时，不会有新生成物出现。距原点 10 m 以内的变换从不用来放置主机。
