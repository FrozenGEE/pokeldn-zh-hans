# 朱与紫

宝可梦 朱（`0100a3d008c5c000`）与 紫（`01008f6008c5e000`）是原生 Switch 作品，Pia 被链接进
`main`。两者都能以两种角色与零售主机进行交换：`bin/sv_host.py` 为主机的离线连接交换搜索充当
主机，`bin/sv_join.py` 加入主机的网络。零售版 紫 会加入一个广播 朱 的本地通信 ID 的主机，而它
自己的搜索网络也广播 朱 的 ID（`0x0100a3d008c5c000`，应用程序版本 21，场景 4）。

两个启动器也都能以任一角色运行本地太晶团体战（[太晶团体战](sv_raid.md)），并且主机可以向
一台主机交换一只官方礼物宝可梦（[模拟神秘礼物](gift_simulated.md)）。
[联盟集友圈](sv_union_circle.md) 以访客身份加入主机的集友圈，向它的主机上报蓝莓任务完成情况，
并在主机的玩家周围生成由用户设定的野生宝可梦。

地址是更新 4.0.0 解压后 `main` 的偏移（`tools/switch/nso_read.py`）：text
`0x0..0x343fc90`，rodata 从 `0x3440000` 起，data 从 `0x4383000` 起。

## 搜索中的主机会广播什么

连接交换搜索在充当主机（每次都是新 SSID）与扫描之间交替，在信道 1、6、11 之间跳变；一个主机
阶段约持续五秒。

    local_communication_id  0x0100a3d008c5c000, Scarlet's, on both versions
    ldn protocol            1            advertisement version 4
    scene_id                4            app_version 21
    security_mode           1            accept_policy ALL
    participants            1/2
    application_data        132 bytes

应用程序数据是 0x5C 的 Pia 系统属性块加上 40 个游戏字节：

| 字段 | 值 |
|---|---|
| 系统通信版本 | 0x15 |
| 应用程序通信版本 | 0x15 |
| 用户密码 | 十六个零字节，无连接码 |
| 启用玩家上限 | 1，玩家数为 1，一旦有一个站点入座则变为 2 |
| 玩家名 | 一个字节、一个空格、UTF-8 |
| 那 40 个游戏字节 | 为零，或在游戏 `+0x21` 处的一个非零值（见到过 `fb149700`），每隔几秒交替一次；第二台主机在任一种情况下都会关联 |

`pokeldn.sv.build_advertise_data` 逐字节复现了这两种信标。

## 游戏运行的协议

对一对零售主机的被动抓包显示了 Net、RTT、0x80 和 0x81，全部发往该会话 `/24` 的广播地址，
接收方的可变 ID 位于明文尾部。其余六个是单播（两台 Switch 2 主机之间的 802.11ax），在抓包中
不出现。

游戏的初始化 `0x17ff030` 按顺序创建：端口 0 上的 Reliable `0x7C` 与 BroadcastReliable `0x80`、
Unreliable `0x68`、端口 1 和 2 上的 Reliable 与 BroadcastReliable、`[0x44dfcd0]` 的
StreamBroadcastReliable `0x81` 端口（线上为八个）、Clone Clock `0x77` 与 Clone Atomic `0x74`。
Pia 还会加入 Net、RTT、Session `0x98` 与 MonitoringData `0xA4`；仅当网络工厂启用 NAT 穿透
时才加入 NatTraversalResult `0xA0`（`0x6d3138`），而本地网络不会。

| id | 协议 | 版本 |
|---|---|---|
| `0x2C` | Net | 0 |
| `0x58` | RTT | 3 |
| `0x68` | Unreliable | 1 |
| `0x74` | Clone Atomic | 0 |
| `0x77` | Clone Clock | 0 |
| `0x7C` | Reliable | 2 |
| `0x80` | BroadcastReliable | 3 |
| `0x81` | StreamBroadcastReliable | 3 |
| `0x98` | Session | 0 |
| `0xA4` | MonitoringData | 0 |

传说 阿尔宙斯 列出相同的十个版本。一对零售主机的开场：

    +0.00   the joiner associates
    +0.06   host: Net 0x11 (station list), 0.12 s later Net 0x50
    +0.14   host: acks all eleven streams, opens two
    +0.89   joiner: RTT request, acks all eleven, opens two
    +0.97   host: first records on 0x81 port 0
    +1.26   joiner: first records on 0x81 port 1

### Net 0x11，站点列表

布局与 传说 阿尔宙斯 相同，四个站点槽各 21 字节：

    01 11 0054          version 1, type 0x11, payload size 0x54
    00000002            sequence id
    9141                host variable id, fresh every session
    eb9b2220f1480000    host constant id, the LDN MAC reordered
    0000000097392e8a    network id, the low four bytes crc32(ssid[1:16])
    01                  is network open
    0004                station slots
    00                  is migrating host
    ...                 four stations: migration state, ranking (host 0, joiner 1, empty 0xff),
                        one byte, 16 address bytes, big-endian u16 port (12345)

`01 40 00 00` 是一个裸的 NetStartHostMigration，由移交角色的主机发送。零售版 朱 在从搜索状态
充当主机时，会在它交给加入方的座位上重复发送它（[什么决定一个座位](#what-decides-a-seat)）。

主机写入四个站点槽，这是 Pia 的数量；游戏的上限是两个。只有两个槽时，加入方游戏不发送任何
内容，以 ICMP 端口 12345 不可达来回应 Net 0x11，并在关联后 5 秒断开（49 次加入中为 4.98 到
5.01 秒）；有四个槽时它回应 Net 0x12 并发送它的 Session 加入请求。

### 十一条流

    0x80  BroadcastReliable         ports 0, 1, 2
    0x81  StreamBroadcastReliable   ports 0 to 7

两个站点大约每秒用 `pokeldn.ldn.reliable5` 的批量确认来确认全部十一条流：四个条目、站点字节
为零、条目 *k* 是站点 *k* 最高序号加一、目标位计数 3、位图中包含对端的位。一个站点用一条
十一字节的 INITIALIZED 消息打开两条流，并在其站点索引对应的端口上发送记录（如同
`pokeldn.pla.data_exchange`）。

| 站点 | 打开的流 | 发送记录的端口 |
|---|---|---|
| 主机，索引 0 | 0x81 端口 1 和 5 | 0x81 端口 0 |
| 加入方，索引 1 | 0x81 端口 0 和 4 | 0x81 端口 1 |

打开时的载荷在端口 0 和 1 上是 `0000000000f38800000000`，在 4 和 5 上是
`00 <port> 00 00 0ff0 0800000000`：一个 StreamData kind 0，提交一次 0xF388（传输 0）或
0xFF008（4 和 5）的接收。0xFF008 传输在交换中从不发送。
`pokeldn.sv.streams` 构建了这一切；`tests/test_sv.py` 将其固定到零售字节。

### Pia 消息标志

两个零售站点都会发送（未使用 阿尔宙斯 主机的建立标志）：

| 消息 | 标志 |
|---|---|
| RTT、流的打开、一条记录的首次传输 | 0x00 |
| 再次发送的记录 | 0x40 |
| 批量确认 | 0xA0 |
| 主机的 Net 0x11 和 0x50 | 0x31 |
| NetStartHostMigration | 0x11 |

消息的目标字段始终为零。标志 0x40 来自 `ReliableSlidingWindow` 发送循环 `0x6f0638` 的
`w4 = 1`（当发送计数 `[slot+0x14]` 为零时为 0，`0x6f0908`；重发 `0x6f0a9c` 或提前发送
`0x6f0c38` 时为 1），由 `0x6e7250` 存为数据包写入器选项块的第 0 个字节。

### RTT

十一字节：kind、大端 u64 时钟、大端 u16 目标。请求是 kind 0、目标 0；应答是 kind 1，携带同一
时钟和请求方的可变 ID，在零售机上于 20 毫秒内完成。

RttProtocol（虚表 `0x43e5a28`）在 `[proto+0x60] + index*0x40` 处为每个站点保留一条 0x40 字节
的记录：采样计数 `+0`、环形缓冲区头 `+4`、容量 9 在 `+0x10` 且环形缓冲区紧随其后内联存放、
一个中位数缓存在 `+0x3c`，对应 `+0x38` 处的计数。一个采样是当前时钟减去被回显的时钟
（`0x6f34b4`）；小于等于零的采样会被丢弃（`0x6f34e0`）。请求以 `[0x46d1528]` 的间隔发出，
直到每个环形缓冲区都填满，之后以 `[0x46d1520]` = 500 的间隔发出（在 `0x6f2fcc` 处以及由游戏
在 `0x1e7c2bc` 处写入）。站点事件 0 或 1 会清除该站点的记录（vfunc11 `0x6f3bd8`）：新座位没有
采样。

GetRtt（`0x6f4498`；带计数 *n* 的 `0x6f44bc`）在没有采样时返回 -1，否则返回最近
min(count, *n*) 个采样的中位数；最小值 `0x6f44e4`、最大值 `0x6f4508` 与采样计数 `0x6f452c`
位于其旁。唯一的调用者是 SessionTransportAnalyzer 的监控副本（`0x6f9ab0`..`0x6f9ad4`）以及
`ReliableSlidingWindow` 的重传截止时间 `0x6f0d14`，后者在 `0x6f073c` 处从发送循环调用：

    deadline = now + [window+0x80] + 1.4 * (max over the destinations of GetRtt(count))

没有采样时，`0x6f0d14` 返回未调度标记 `[window+0x5c]`：消息在入队时发送一次
（`0x6f1bbc`..`0x6f1bd4`），并在 `0x6f0a18` 处被跳过，直到某个采样重新武装它
（`0x6f09f4`..`0x6f0a08`）。没有 RTT 采样的窗口永不重传。

构造函数 `0x6eeea8`（调用者 `0x6e69f8`、`0x1800038`）把 `[window+0x80]` 设为
`ticks_per_second * 33 / 1000`（`0x6eef34`..`0x6eef74`；633,600 tick，在 19.2 MHz 下为
33.0 毫秒），标记 `[+0x5c]` 为 0，基准序号 `[+0x30]` 为 1，自身索引 `[+0x10]` 为 0xfd，
压缩 `[+0xa4]` 为 1，提前发送上限 `[+0x88]`、`[+0x89]` 为 0。唯一更晚的写入者是 vfunc17
`0x6f1f98` 中的 `0x6f1fc8`（来自 `ReliableProtocol::vfunc17` `0x6eebbc` 与
`BroadcastReliableProtocol::vfunc17` `0x6e6818`，无已知调用者）。发送循环每 16.7 毫秒的帧运行
一次，因此重发会在等于或晚于 `33 + int(1.4 * RTT)` 毫秒的第一个帧发出：RTT 为 34 毫秒时是
83 毫秒，358 毫秒时是 550 毫秒。

### 记录

一条记录就是一个带 ZLIB 标志的可靠消息，一个 4 KB 窗口（`484b`）的 zlib 流，解压后为
1395 字节，`[window+0x70]`：这是 Pia 的 StreamData 头
（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）之下的一个
0x81 传输的一个分块：

    +0x00  1   StreamData kind: 1 the first chunk of the block, 2 a later chunk
    +0x01  1   transfer id, 0
    +0x02  1   percent of the block delivered after this chunk
    +0x03  4   zero, the capacity field of a kind 0
    +0x07  4   big-endian u32 0x00000568, the 1384 bytes that follow

一个站点的块是 0xF388（62,344）字节：45 个 1384 字节的分块和一个 64 字节的分块，ID 从 1 到
46，百分比字节为 `floor(k * 1384 * 100 / 62344)`（2、4、6、8、0x0b、…、0x37 对应 25、
0x52 对应 37、0x64 对应 46）。第一个分块携带屏幕上显示的伙伴：

    +0x0b  4   trainer id, then secret id
    +0x0f  1   version: 50 Scarlet, 51 Violet
    +0x10  1   gender
    +0x11  1   language
    +0x12  1   ball-throw style, 1 the original
    +0x13  26  the player name, UTF-16 little-endian, NUL-padded; --trainer-name on both launchers
    +0x2d  22  the account identifier, ASCII, `u-` and twenty characters
    +0x53  8   story progress, little-endian: 1 the main story cleared, 4 The Indigo Disk cleared

该块在 `0xa52f88`..`0xa530a0` 处的栈上构建：先是来自存档的训练家，然后来自另一个存档块的
投球风格（`0xa53054`），接着是账号标识（`0x1a61a00`），最后是进度字，即游戏保存在
`0x473a040` 处的某个脚本函数的返回值（在 `0xa5309c` 处调用）。原生 `f20A702BD`（`0x877560`）
安装它；在 3.0.1 脚本转储中，`BattleNetworkNetReceiver` 传入一个从 0 开始的函数，当
`FSYS_SCENARIO_GAME_CLEAR` 置位时设为 1，当 `FSYS_SCENARIO_GAME_CLEAR_SU2` 置位时或上 4。
`pokeldn.sv.reference` 发送 1；账号标识全零的零售版 紫 发送 0。

游戏的脚本按以下顺序注册的原生 getter 读取某个站点的玩家：`PlayerId`、`RomCode`、`Sex`、
`LanguageId`、投球风格、`NameStrBuf`（3.0.1 脚本转储中的 `RegisterPlayerData` 与战斗初始化；
投球风格就是存档自己的 `ballThrowId` 所填的槽位）。在零售存档上，ID 对、版本、语言和名字都
取自该存档自己捕获的宝可梦，无论它提供哪只宝可梦。为接收方玩家制作的礼物会读取它们
（`reference.identity_trainer`，[为接收方玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

分块 2 到 24 是高熵的；25 到 46 为零。一个站点会一次性发送它的整套内容，通常第一个数据包里
是 ID 1、25、26 到 36 和 46，第二个里是 2、37 和 38 到 45，然后 3 到 24 每个数据包一个
（48 套零售数据中有 41 套如此），52 次中有 46 次在 0.19 秒内完成。相同的零分块在 0x00 的存在
字节之后传输，所有头字段都继承（[消息分帧](pia.md#message-framing)）。
`pokeldn.sv.streams.decompress` 读取它们。

`pokeldn.sv.reference` 在 0x7C 端口 0 上提供一个站点的 44 条记录及其两个身份分片，它们录制自
一个模拟的 朱，其玩家为 `Player`、账号标识未设置。除非给出 `--record-set`、`--send-on-open`
或 `--no-identity`，`bin/sv_host.py` 与 `bin/sv_join.py` 会发送它们。

### 零售确认，以及重传的洪流

零售站点用连续段之后一个的 ack id、等于它的字段 0x50 以及一个掩码来确认对端的记录流，掩码中
字节 *k* 的第 *b* 位对应 ID `ack_id + 1 + 8k + b`：一个持有 ID 1 到 4 和 7 到 38 的主机发送
`0005 0005 feffffff01`。低于对端自身 `lowest_pending` 的 ID 视为已持有。
`pokeldn.sv.streams.ack_position` 构建它；`bin/sv_join.py --ack-highest` 改为发送所见最高
ID 加一。

主机每一轮重发所有未确认的记录，标志 0x40，最小 ID 优先，每个数据包一轮。轮间隔是
`[window+0x80] + 1.4 x RTT` 向上取整到帧：RTT 为 0.015 秒时是 0.065 秒，0.36 秒时是
0.53 秒。在较小的 RTT 下，这相当于每秒数百条记录，足以占满一块板子的串口线
（[串口上限](hardware_esp32.md#the-serial-ceiling)）。无论确认延迟如何，主机的
`lowest_pending` 都会在整套发出后约 0.5 到 1.0 秒离开 1，因此在此之前应答 RTT 会让它重发
加入方已经持有的记录。`--rtt-delay 0.3` 让 RTT 应答晚 0.3 秒，从而使轮间隔高于该延迟并停止
重发。

`--leave-on-migration N` 在 Session 类型 7 之后 N 秒结束座位，`--announce-timeout SECONDS`
离开一个未被通告的座位；两者都会重新扫描。`bin/sv_join.py` 立即确认一条新记录，对重复记录
每条流最多每 50 毫秒确认一次（`--repeat-ack-gap`）。

没有 RTT 采样时，0x81 流永不重传
（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）：丢失的
记录保持待定，对端永远不会被通告。通告任务没有 RTT 门槛。缺失的身份记录会让 BoxTrade 任务
停留在状态 1（`+0xb8`），已完成的槽计数在 `0x1e51ae8` 处为 1 而非 2。两个启动器都会重试
待定的身份记录（[最低待定与 5 和 6 处的间隙](#lowest-pending-and-the-gap-at-5-and-6)）；
`tests/test_sv_identity_loss.py` 覆盖这一点。

### 抓包中的 A-MSDU 帧

两台主机都会把多个 MSDU 打包进一个 A-MSDU 帧。被动抓包必须拆解子帧，否则会丢掉大部分 Pia
数据包（一次抓包中，不拆时为 313 个可读，拆后为 3667 个）。

## 局域网模式

朱 4.0.0 从它的脚本启动局域网模式。选择器 `0x17fde60` 接受模式 1（本地，`0x17fe5c0`）、
2（`0x26894f0`）或 3（`0x2689600`，局域网服务）；模式是全局变量 `0x475ea40`，由 `0x17fddc0`
从网络任务的 `+0x50` 设置（构造函数 `0x188f488`）。`0x188e998(.., mode)` 创建该任务，并以
1（`0x18871a4`）、2（`0x1de28a4`）和 3（`0x1de6650`）调用。模式 3 的调用者 `0x1de653c` 运行
NetworkUse、InitializeSocket 和 InitializePia，并且是 `0x4430500` 处表中的 Lua 绑定
`f6597D2A6`。

游戏的 Lua（`arc/scriptluabinrelease*.blua.trpak` 中的六个分块；`be21e654` 是 `main`）从战斗
菜单到达它。网络对战接收菜单（类 `C6A68AA55EC501641`，状态 `SET_STATE_NETWORK_VS_RECEPTION`，
更新 `0.25603`）在选择某个条目时清除它的局域网标志，并在条目为 1 或 2 且输入测试
`fFCB9D967`（原生 `0xc60480`，输入 vfunc `+0x70`）对 `UI_ZL` 和 `UI_ZR` 都为真时置位它。
它把该标志作为 `LanMode` 传给匹配参数（`0.25605`：条目 2 时 MatchingType 2，否则为 1）。
匹配任务 `0.25585` 随后调用 `f9C74F2CA`（MatchingType 1）或 `f671B3A6A`（MatchingType 2），
而不是本地的 `f40B78205` 或 `fA775C8D9`；两个局域网绑定都返回回调，其工作 `0xa41c8c` 调用
`0x1de653c`。

交换菜单（类 `CCEC7DC2C9A179FC0`，`SET_STATE_NETWORK_TRADE`，`0.25609`）在 `0.25611` 中用
MatchingType 0 和 `LanMode` false 构建它的匹配参数；没有任何输入会设置它。带 StartLan 方法
（`FDF107F292AE61465`）的请求运行器 `0.28742` 属于类 `CD876458B95753AFF`，没有 Lua 构造它。

| 在零售版 朱 4.0.0 上实测（Switch 2 走 Wi-Fi） | 结果 |
|---|---|
| Combats en réseau、Combat solo，按住 ZL 和 ZR 贯穿 A 键与是/否提示 | 搜索开始；主机保持 Wi-Fi 连接（ping 4/4，重复一次为 6/6） |
| 同样操作但不按 ZL 或 ZR | 主机在搜索期间离开 Wi-Fi（ping 0/6） |
| 在 ZL + ZR 搜索期间主机发出的帧，按 IP 和按 MAC 抓取 | 约 4 分钟内一个都没有，包含 IPv4、IPv6、广播与组播 |

在模拟的 朱 4.0.0 中，同样的搜索会发出一个网络连接请求（nifm；没有网络时游戏显示错误 11），
在 49152 和 35000 上打开 UDP 套接字，向 35000 端口的子网广播发送一个 317 字节的浏览请求，
然后作为主机等待。向它 35000 端口发送的浏览请求会得到 620 字节的应答，其中写明主机的 IPv4
地址和 Pia 端口 49152（`c0a8011f`、`0xc000`）。开头那一次广播解释了那次安静的零售抓包——它
正是在这之后开始的。

| 消息 | 抓到的起始字节；其后的布局未被解读 |
|---|---|
| 浏览请求，317 字节 | `00 00000000 0e000000 00000000 01000200 02000f03 01000000 00000000 01` |
| 浏览应答，620 字节 | `01 0000022d 00000000 1f01a8c0 007c0a00 15` |

停止搜索会关闭这三个套接字并让游戏回到离线模式；网络启动 `0x17fddc0` 会保留正在运行的模式，
但拆卸 `0x1813740` 会先清除 `0x475ea40`，因此交换菜单永远不会继承一个局域网网络。

Pia 6 把浏览端口从 剑 的 30000 移到 35000，并改变两种布局（[局域网模式](pia.md#lan-mode)）。
两台主机都用 ZL + ZR 搜索时能否互相找到，尚未测量。

## 连接码

连接码在广播中搭载两次；场景 ID 保持为 4。用户密码就是该码，用 NUL 填充到十六字节，再与
`e5ab19ed742b6d40885998bf968aa166` 异或，这是同一游戏密钥下 传说 阿尔宙斯 的掩码
（[docs/pla.md](pla.md)）。游戏字节在 +0x00 处以明文携带该码，并在 +0x24 处以 u32 携带其
长度。`pokeldn.sv.build_advertise_data(code=...)` 逐字节复现一台用 12345678 搜索的零售主机。

搜索中的主机只会加入广播其连接码的主机（`bin/sv_host.py --code`）。一台用连接码充当主机的
零售主机接受了一个不广播任何码的加入方。`bin/sv_join.py --code` 只加入用该码搜索的主机。

只有搜索中的主机会检查连接码，且只在它扫描的网络中检查。它的选择器 `0x26e955c`（在加入前由
`0x272d838` 调用）在用连接码搜索时跳过没有密码的网络（`0x26e95f4`），在不用连接码搜索时跳过
有密码的网络（`0x26e960c`）。然后它用 FNV-1a 64 对从 +0x00 到第一个 NUL 的游戏字节和它自己
的码做哈希（素数 `0x100000001b3`，偏移基 `0xcbf29ce484222645` 在 `0x26e96c8` 处加载，不是
标准基），除非两者相等否则跳过该网络（`0x26e972c`）。它既不读取密码的值，也不读取 +0x24 处
的长度。

主机不比较加入方发送的任何内容。LDN 关联使用固定口令，而 Session 加入请求没有密码字段。
Pia 对连接站点的密码检查——Net 0x32 处理器 `0x69ec50` 中的结果 7（`0x69ee5c`、`0x69ee70`）
——需要一条 Net 0x32，而它唯一的发送者 `0x69d42c` 受协议 vfunc 48 控制：在 `LdnProtocol`
中为 0（`0x6a2fac`），在 `LanProtocol` 中为 1（`0x6ba278`）。在加入方一侧，LDN 连接运行
Pia 的网络检查 `0x6a22c4`，其密码比较（`0x6a24a4`）被关闭（`0x6b0d90`）。

已加入的主机不会再次检查该码。Net 0x50 处理器 `0x69ea3c` 校验系统属性大小（0x5c）、应用程序
数据大小（至多 0x124）和四个 Pia 身份字段（`0x69d9d8`），把字节复制进网络属性
（`0x69d8a4`）并以 Net 0x51 确认；它不比较系统属性或游戏字节中的任何一个字节。在 LDN 上，
这份副本落入缓存的广播数据，下一次 `nn::ldn::GetNetworkInfo`（`0x6b30d4`）会覆盖它。游戏只在
选择器中以及 UpdateSessionSetting（`0x26e63b8`）中读取一个会话的前 0x28 个游戏字节，后者会
重写它自己的会话；另外两个读取者（`0x268e988`、`0x268e9bc`）只读取 +0x28 之后的内容。加入
的主机把它的码保留为自己的 Pia 站点密码（加入对象 vfunc `0x274bdb8`，设置器 `0x6a208c`），
它只在充当主机时才广播它。连接交换的端口 2 类型 1 来自 BoxTrade 任务的状态 2
（`0x1e51b68`）：kind 1、静态空名字 `[0x46d3e30]`、无数据。

## Session 协议

`nn::pia::session::SessionProtocol`（id vfunc `0x6d9f3c` 返回 0x98）位于 `JoinMeshJob`、
`CreateMeshJob`、`LeaveMeshJob`、`JoinSessionJob` 以及 `SessionPacketReader`/`Writer` 之旁；
网格加入沿用 传说 阿尔宙斯 的实现。Session 消息在数据包头中携带对端的可变 ID，没有尾部，因此
走单播。加入方在加入请求的源位置 ID 中声明它的可变 ID；主机在关联后 0.14 秒命名它。

### Session 加入请求

写入器 `0x6d5464`..`0x6d58b0`，主机侧解析器 `0x6d5aa4`。布局与零售版 传说 阿尔宙斯 相同
（`docs/pla.md`，Session 加入请求；`tests/test_pla_session_v11.py` 中为 115 字节），由
`pokeldn.ldn.pia6.build_session_join` 构建：

    +0    1    type 0
    +1    1    protocol count, ten
    +2    2n   (id, version) pairs, walked from the protocol manager's list
    +22   4    random, xorshift128 seeded from the system tick (`0x6c70a8`, `0x6c7184`)
    +26   12   source location id: u64 constant id, two zero bytes, u16 variable id, big-endian
    +38   1    NAT mapping, two bits
    +39   1    private-IPv6 flag
    +40   32   identification token
    +72   1    address kind, 0 for IPv4 (1 puts an 18-byte IPv6 address in place of the six bytes)
    +73   4    source IPv4 address
    +77   2    source port, big-endian
    +79   12   destination location id, the host's
    +91   1    player count
    +92   1    a flag the job sets to 1
    +93   ..   player records: a 16-byte id (`1` then `0` as two big-endian u64), a big-endian u32
               name length, a kind byte (1), the name

零售加入方的那一个玩家名是一个空格。数据包头携带目标可变 ID 0 以及作为源的加入方 ID；每次
重发时消息标志为 `0x01`（跳过源检查）。主机按顺序检查：

1. 协议数量等于它自己的；否则不发送任何内容。
2. 每个版本都等于主机的版本（`0x6ed1b8`）；否则返回状态 3，附上 ID 与主机的版本。
3. 目标位置 ID 是主机的常量 ID 与可变 ID；否则丢弃。
4. 源常量 ID 与地址不是主机自己的。
5. 已知的常量 ID 会再次得到状态 1；已关闭的会话得到状态 5；主机侧监听者可以以状态 4 拒绝。

加入响应（类型 2，43 字节，`0x6d6390`）是 阿尔宙斯 的布局：type、protocol id、version、
status、一个大端 u32、四个随机字节、两个位置 ID、路由字节 A 和 B、站点索引、加入顺序、站点
更新必须达到的序号。加入方以 13 字节的类型 6（`0x6d80a4`）回应类型 5 更新：type、常量 ID、
两个零字节、已应用的序号（`pokeldn.ldn.pia_connect`）。

## 座位，以及其上的身份洪流

零售版 朱 主机在 16 毫秒内接受加入请求，发送一个 41 字节的加入响应（状态 1，无路由字节）和
一个无路由的站点更新，并在 0x81 端口 0 上流式发送它的身份。不接受加入方确认的主机会一直重发
每条记录直到座位结束，在零售机上约每秒 350 条。主机也可以改为发送 Session 类型 7，把它的
角色交给加入方（[什么决定一个座位](#what-decides-a-seat)）。

### 让主机把消息计为确认的标志

带第 5 位标志（ZLIB，`[msg+0x29]`，`0x6efc80`）的消息会在站点解析之前于 `0x6e9984`
（`0x69804c`，zlib 解压 `0x2801d0`）中解压；失败时返回 0x2C03（`0x6efd5c`）。标志 0xA0 下的
普通批量确认会在这里失败（模拟主机上 600 次全部失败）。零售 0xA0 确认携带解压后为 99 字节的
zlib 主体（即记录所用的 4 KB 窗口、级别 5 的同步刷新分帧）。在标志 0x00 下，同样的 99 字节
也会被计入：主机每条记录只发送一次（每秒 6.3 条，之后为零，而普通 0xA0 下为每秒 115 到
257 条）。两个零售站点都把批量确认标记为 0xA0 并发送到它们 /24 的 LDN 广播；当
`bin/sv_join.py` 设置第 5 位时会压缩主体（`--ack-flags`、`--ack-entries`、`--ack-dest-bits`、
`--ack-sweep`）。

### 一条流上的首条记录携带 INITIALIZED

一个站点的首条记录携带带 START、END 和 ZLIB 的 INITIALIZED，标志 0x1F；后续记录为 0x17。以
0x17 发送的首条记录永远不会被确认。随后主机把整套确认到 47（掩码 `feffffffff01`），把它的
记录发送一次，并发出一个列出两个站点的类型 5 站点更新。

## 为一台主机充当主机

除了 Net 0x11 中的四个站点槽之外，主机还必须发送：

| 主机发送 | 它必须是什么 |
|---|---|
| Session 加入响应 | 41 字节：无路由字节、站点索引 1、加入顺序 1、序号 0、+8 处的四个随机字节（若用 阿尔宙斯 的 43 字节形式，会遭到重传） |
| Session 类型 1 加入确认 | 什么都不发；一台零售主机发过一次，两秒内就离开了 |
| Session 类型 5 站点列表 | 两次：随加入响应在序号 0 下发送，然后在下一个序号下发送（零售主机：1.5 到 2 秒后） |
| 该列表中的每个站点 | 79 字节：位置 ID、地址与端口、站点索引、大端 u16 加入顺序、NAT 字节、IPv6 标志、32 字节令牌、计数、玩家记录。无路由字节（阿尔宙斯 的为 81） |
| 其中的玩家名 | 一个空格（0x20） |
| 每个 Session 回复的消息标志 | 0x00 |
| Reliable 0x7C 上的确认 | 单条目形式，无目标位图；若未被确认，主机会无休止地重发信道表（实测九十秒内一千次） |
| Reliable 0x7C 上的每条数据消息 | 九字节头、destination_bits 0、无位图 |
| Net 0x11 | 一次；在已入座的站点上重复会被当作新的连接请求 |
| Net 0x50，即更新属性 | 在 0x11 之后 0.2 秒，每 500 毫秒一次，直到该站点的 0x51，并在 +0x82 处带上那四十个游戏广播字节 |
| RTT | 除应答之外还有它自己的请求（一对主机中的主机：每 410 毫秒） |
| 开场 | 座位之后紧接着的加入响应、第一份站点列表、信道表、两条流的打开、时钟应答、Net 0x50 和全部 44 条记录（零售主机：0.3 秒内）；密钥 0x80 的打开要在主机的交换画面绘制之前（[打开信道](#opening-the-channel)） |

那四十个游戏广播字节每个会话都会变化：为零，或在 +0x21 处为非零值（见到过 `648cf4`、
`8170f0` 和 `fb149700`）。使用 `--channel 6`、把 `--player-name` 设为所模拟主机的玩家名，并给出
`--host-player-id 00000000000000010000000000000000` 时，NetworkInfo 除会话 ID 外与一台模拟的
朱 主机一致。在座位之上失败的会话会引起反复加入（实测 16 到 57 次）。

### 最低待定与 5 和 6 处的间隙

一个站点的 ID 5 和 6 从不发送（线上为 44 条记录），其余记录乱序发出（一对主机中的主机：
1、2、3、46、4、7、8、19、9、15、10、16……）。每条记录都声明 `lowest_pending` 为 1、
目标位 3、位图 `[2]`、流 ID 0。这个间隙由发送方在同一流上的下一次批量确认来闭合，其
`lowest_pending` 从 1 跳到 47；对端随后以空掩码把整套确认到 47。若一直停在 1，对端会以
`ack_id` 5、掩码 `feffffffff01` 应答，全程如此。没有间隙的 ID 1 到 44 也会被接受；但没有
零售发送方使用它们。

发送方只能把 `lowest_pending` 推进到已确认记录之后。在初始爆发之后直接推进到 47 可能掩盖
丢失的身份分块：对端确认了 47，而 StreamData 块仍不完整，站点永远不会被通告。

两个 SV 启动器都为身份集维护一个 `reliable5.SendWindow`。对应的批量确认条目会释放低于其
`ack_id` 的记录以及其选择性掩码指名的记录。每 250 毫秒，未确认的记录会带着原来的序号和 Pia
消息标志 `0x40` 重发。发出的数据与批量确认头会声明仍然待定的最低记录，整套确认完毕后则为
47。这样既保留了有意留下的间隙 5 和 6，又保留了真实的丢失。

丢失首条 INITIALIZED 记录会让全部 44 条记录都处于未确认状态，需要重试整套。缺失的中间记录
则单独重试。

## 游戏自己的协议，来自一对主机

测量自两个进行过交换的模拟 朱 4.0.0 实例，各自记录它发出的每个数据报。交换运行在
Reliable 0x7C 上；广播流只承载身份交换。

### 端口 2：通告、加入与应答

Reliable 0x7C（单站点）和 BroadcastReliable 0x80（所有站点）的端口 2 承载游戏的会话消息。
轮询器 `0x1954978` 读取 `[0x475ea70]`（`0x19549e4`）和 `[0x475ea7c]`（`0x1954a54`）交给分发器
`0x1954aec`：首字节、类型 1 到 0xD、表 `0x3c68988`。有三种类型会开启一次交换：

| 时间 | 站点 | 线路 | 类型 | 字节 |
|---|---|---|---|---|
| 0.00 | 主机 | 0x80 端口 2，zlib | 7 | 解压后 167 字节：`07b901b905b906010200bc09`、九个零字节、`bc8080`、128 个零字节、`000000b90183`、主机的站点 ID、`00` |
| 0.09 | 加入方 | 0x7C 端口 2 | 3 | `03b90200bc09` 和九个零字节 |
| 0.15 | 主机 | 0x80 端口 2 | 9 | `09b9030000b90183` 和加入方的站点 ID |

编码是信道表的编码（`pokeldn.ldn.channel_table`）加上标签 `0xbc`，即一个字节串：标签、作为
整数的长度、字节。类型 7 是一个包含一个五元组的元组（写入器 `0xe464fc`）：

    b9 06 ...   the type-1 body as a tuple of six: kind, capacity, a zero byte, the name as a
                nine-byte string, the data as a 128-byte string, the data length
    key         body +0x8e, the relay's counter +0x1c4 before it steps
    index       body +0x8f, the relay's counter +0x1c0 masked to seven bits, before it steps
    b9 01 ...   a tuple of one u64, the station id of the type 1's sender
    0           body +0x98

类型 9 是一个元组：加入的槽键、一个结果字节和一个只含一个 u64 的元组。

类型 7 是一个被中继的类型 1：类型 1 处理器 `0x18ceb70` 无条件复制 0x8e 字节的主体，盖上
key 和 index，推进两个计数器，追加发送方的站点 ID，并将其入队给类型 7 构造器（队列 `+0x200`，
步长 0xa8）。`0x18d5a58` 向一个站点发送端口 2 消息，当目标就是自己时通过 `0x1954aec` 分发，
因此主机会中继它自己的类型 1。

类型 1 的主体（`0x18ab760`）：

    +0x00  kind
    +0x01  the slot's capacity: 2 for kinds 1 to 3, 4 for kinds 4 to 8 and 12, 0 for kinds 9 to 11
    +0x02  zero
    +0x03  a name of up to eight characters, NUL-terminated in nine bytes
    +0x0c  up to 128 bytes of data
    +0x8c  the data length

交换的类型 1 是 kind 1、容量 2、空名字、无数据。一个槽把主体存放在槽 `+0xd0` 处（构造函数
`0x18b73a0`），因此它的 key `0x12fcabc`（槽 `+0x15e`）就是主体 `+0x8e`。每个被中继的类型 1，
无论自己的还是对端的，都会推进 key；只有 `0x12fbef0` 会把计数器归零。像 `03b90200bc09` 那样
指名 key 0 的加入，只能匹配自计数器归零以来的第一次通告。

类型 3 处理器 `0x1981e94` 把加入的第一个字段与槽 key 比较（`0x1981ed4`），接受时把类型 9
入队（`+0x270`），否则在 `+0x350` 上入队一个类型 0x0D，即 `0d b9 01` 加上一个代码：

| 代码 | 拒绝原因 |
|---|---|
| 1 | 没有槽持有该加入的 key（`0x1981ffc`），或 `0x279c8fc` 拒绝 |
| 2 | 槽已满：`0x18f80c8` 对照 `0x1e64914` 读取的容量，或 `0x279c9a0` 返回 0xfd |
| 3 | 加入名字的 FNV-1a 64 哈希与槽的不同（`0x1e648a0`） |
| 4 | 槽已关闭（`0x1e64924`，槽 `+0x160`，在槽创建时清除） |

类型 0x0D 交给 `0x1954f3c`，它要求 `0xb9`，解码一个单元素元组（`0x279c0e8`）并调用接收者
`0x279c1ac`（`0x1954f78`）：

    0x279c1b8  ldr  x8, [x0, #0xb8]     the pending request
    0x279c1bc  cbz  x8, ret             none: nothing happens
    0x279c1d0  strb w9, [x8, #0x43]     result = the code
    0x279c1d8  strb #1, [x8, #0x42]     done
    0x279c1dc  bl   0xc8e6c4            wakes the request's waiter at +0x48

它既不检查请求类型 `+0x40` 也不检查完成字节，因此来自加入方的一条 0x0D 会用它自己的代码完成
主机当前持有的任何请求。类型 9 接收者 `0x18b65c8` 按槽字节选择对象，应用该消息，除非该 u64
是该站点自己的 ID（`[[0x46d0a08]] + 0xb8`）否则丢弃它。

站点 ID 是把 Pia 常量 ID 当作大端 u64（MAC `02:00:7f:00:00:02` 对应 `7f00020000020000`）；
对零售主机而言，类型 9 携带的是它 Session 加入请求中的常量 ID。`pokeldn.sv.port2` 构建这三者
（在 `tests/test_sv.py` 中固定）；`bin/sv_host.py --announce` 在座位之后发送类型 7，并用类型 9
应答类型 3。

### 发送通告的交换任务

连接交换在 `0x1e2ea54` 处创建该任务：配置 `BoxTrade`（`0x3aefac8`），工厂 `0x1e2f3d4`，
模式 4，need 2。两个脚本绑定到达它：`0x1e2e9bc`（GOT `0x46d6608`，由 `0x1b9c8c4` 存入
`0x4717068`，尾调用）和 `0x1e2ec84`（GOT `0x46d6610`，在 `0x1e2ee40` 处 `bl`）。该任务
（构造函数 `0x1e3bd10`，虚表 `0x44568a8`，Update `0x1e51a04`）：result `+0x40`、state `+0xb8`、
会话句柄 `+0xc0`、模式与 need 作为 u16 位于 `+0xc8` 和 `+0xca`、槽对象 `+0xd0`、请求句柄
`+0xf8`。

| 状态 | 地址 | 它做什么 |
|---|---|---|
| 1 | `0x1e51a84` | 若站点计数 `[[0x46d0a08]]+0xe0` 低于 need 则 result 3，若 `0x18ab520` 拒绝该模式（0、5、8 以上）则 result 1；否则无超时地等待 `need` 个完成的身份块（`0x1e52004` 遍历 `[[job+0xd0]+0x10] - 0x28`），然后在主机上进入状态 2（`0x1639910`：自身 ID `+0xb8` 等于主机 ID `+0xc0`），在客户端进入 4 |
| 2，主机 | `0x1e51b2c` | 先取 kind `0x18ab550(mode)`（模式 1 到 8 得到 2、3、4、1、0、5、5、8），然后发出请求 `0x18ab658`；为 null 则以 result 8 结束 |
| 3，主机 | `0x1e51ca8` | 等待该请求，无超时；result 0 进入状态 6，否则任务经 `0x1e5086c` 结束 |
| 4、5，客户端 | `0x1e51b8c`、`0x1e51c74` | 同样的等待，限时 15 秒 |

| 结果 | 含义 |
|---|---|
| 1 | 成功，或模式被拒绝 |
| 2 | 会话处于状态 3 |
| 3 | 站点数少于 need |
| 4 | 客户端的 15 秒超时 |
| 8 | 无会话，或请求被拒绝 |

请求 `0x18ab658` 构建类型 1 主体并通过 `0x18ab83c` 发送它；当该中继的待定请求
`[relay+0xb8]` 的完成字节 `+0x42` 仍为 0（`0x18ab860`、`0x18ab8e8`）或发送失败时，它返回
null。否则它清除 `+0xb8`（`0x18ab894`），存入一个新请求（`0x18ab8a8`；`0x18abec0`：`+0x40`
类型，通告为 0，`+0x42` 完成，`+0x43` 结果），并把类型 1 发往主机 ID（`0x18d58b8`），在主机上
则发往自己；发送失败会清除 `+0xb8`（`0x18ab900`）。

`0x18ab658` 有四个调用者：`0x1e51b68`（BoxTrade 状态 2）、`0x18ab34c`（一个同级任务中的同一
处，虚表 `0x4456490`）、`0xa188f0`（虚表 `0x4452e68`）和 `0x1d99568`（虚表 `0x44536d8`）。
只有这四个请求创建者会写 `+0xb8`；`0x18ab83c` 与 `0x2799b10` 在有请求待定时会拒绝：

| 创建者 | 请求类型 | 存储位置 | 唯一调用者 |
|---|---|---|---|
| `0x18ab83c` | 0，即通告 | `0x18ab8a8` | `0x18ab6bc`，位于 `0x18ab658` 中 |
| `0x2799b10` | 2，即客户端的加入 | `0x2799bd8`（守卫 `0x2799b2c`..`0x2799b40`） | `0x1e635fc` |
| `0x2799c44` | | `0x2799cfc` | `0x1e639ec` |
| `0x2799d6c` | | `0x2799e30` | `0x1e63c88` |

后三个调用者各自位于一个函数中，该函数唯一的调用者在 `0x1d98xxx` 里（`0x1d986d8`、
`0x1d98990`、`0x1d98c20`）。

在连接交换中，类型 2 创建者从 BoxTrade 状态 4 的 `0x1e51c40` 处经 `0x1d986d8` 和 `0x1e635fc`
到达。它只在客户端上、主机的槽出现之后运行（`0x1d999f4`、`0x18c7a40`），把请求保留在任务
`+0xf8`，并进入状态 5。`0x1d98698` 的其他调用者属于其他任务类。

排水 `0xe44cf0` 按顺序走队列 `+0x1c8`、`+0x200`、`+0x238`、`+0x270`、`+0x2a8`、`+0x2e0`、
`+0x318`、`+0x350`；某个构造器返回 false 会结束该帧的排水，因此一个卡住的类型 7 会把它后面
的类型 9 和 0x0D 挡住。类型 7 构造器 `0xe45740` 在站点数为 1 时只在本地分发；否则它会问
`BroadcastReliableProtocol::vfunc20`（`0x6e6638`）0x80 端口 2 能否发送，用 `0x107e060` 发送，
并且只在两者都成功时才在本地分发。当目标列表 `[window+0x40]` 中没有任何条目被设置时，
vfunc20 以 0x2c27 拒绝（`0x6efb98`）；当窗口没有空间容纳分片时以 0x4c0d 拒绝（`0x6f1ef8`）；
无会话或窗口时以 0x10408 拒绝。Pia 在站点加入事件时填充目标列表
（[一个窗口向谁发送](pia.md#who-a-window-sends-to-pia-6)）。

类型 7 接收者 `0x18b566c` 创建并应用该槽，并且对于待定的类型 0 请求和主机自己的站点 ID
（主体 `+0x90`），以 result 0 完成它：主机会停在状态 3，直到它自己的类型 7 已经上线离开。
从中继到上线之间没有任何东西读取 RTT 或计时器。

0x81 身份是每个站点一个块，位于其索引对应的端口上（句柄 `0x475ea48 + 4*index`），由流发送
API `0xe22188` 与接收 API `0xe22458` 为三个同布局对象搬运：

| 对象：Update，虚表 | 发送 | 接收 | 块 |
|---|---|---|---|
| `0xe21104`，`0x4455ec0` 的槽 13 | `0xe21a44`，`0xe21dc4` 处 `bl`，`0xe21db8` 处 `w2 = 0xf388` | `0xe2150c`、`0xe2170c`，`0xe21708` 处 `w3 = 0xf388` | 0xF388 = 62,344 |
| | `0xa62c5c`，`w2 = 0xff008` | `0xa64ddc`，`w3 = 0xff008` | 0xFF008 = 1,044,488 |
| `0x1e5f87c`，`0x4458698` 的槽 13 | `0x1e617a8`、`0x1e61980`，`w2 = 0x97e08` | `0x1e61a74`、`0x1e61c0c`，`w3 = 0x97e08` | 0x97E08 = 622,088 |

交换中只有 0xF388 块会上线，因此该任务的 `+0xd0` 对象属于那个类（实例未追踪；经
`0x1e34b6c` -> `0x1e35e88` 构建）。

`0x1e52004` 统计 `+0xd0 + 0x30*k`（四个）处持有对端指针且字节 `+0xd8` 已置位的槽。主机自己的
槽在 `0xe21154` 中获得它（`0xe21248` 处的 `memcpy(slot, [+0x90], 0xf388)`，`0xe21258` 处
`+0xd8 = 1`；调用自 `0xa536e0`、`0xd6dc88`、`0xe21128`、`0x195160c`）。对端的槽在
`0xe212b8` 中获得它（调用自 `0xa536f0`、`0xd6dc98`、`0xe21138`），且仅当向对端的发送
（`+0xda`）与从对端的接收（`+0xd9`）已经开始、自己的 0x81 流处于状态 3（`0xe2144c`，
自己的每个分块都已确认）而对端的处于状态 6（`0xe21404`，对端的每个分块都已收到）；状态 7 会
清除一个标志
（[协议 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）。0x97E08
类有同样的一对，`0x1e60284` 和 `0x1e615e8`。

在线上，类型 7 通常会在主机自己那套记录的最后一条之后 0.11 秒内出现。

中继是一个 0x388 字节的对象（虚表 `0x44e56f8`），单例 `[0x46da9c0]` = `0x4739430`，仅当不存在
时才由 `0x165a200` 从 `0x1659b70` 创建（`0x1659b18`）。它的站点事件处理器是 `0x12fbb90`，
经由 thunk `0x2b71650`：

| 事件 | 效果 |
|---|---|
| 0，一个站点加入，在主机上 | 除非它就是主机，否则 `0x12fbf8c` 把当前槽发给它 |
| 1，自身 ID | 一个未完成的待定请求以 result 5 完成（`+0x42` 处为 `0x501`），然后 `0x12fbef0` |
| 1，主机的 ID | `0x12fbef0` |
| 1，任意站点，在主机上 | 随后 `0x12fcebc` 丢弃它中继过的元素 |

`0x12fbef0` 通过 `0x12fc644` 移除每个槽（完成 key 匹配的待定类型 1 请求），清空七个队列
（除 `+0x1c8` 之外的全部）并把 `+0x1c0` 与 `+0x1c4` 归零；它保留 `+0xb8` 处的请求。类型 0
请求只会被类型 7 接收者、类型 0x0D 接收者和自身离开事件完成；类型 2 由类型 9 接收者
`0x18b6710` 完成，类型 3 由类型 0xA 接收者 `0x1945404` 完成，类型 4 由类型 0xB 接收者
`0x279be18` 完成。

自身离开路径 `0x12fbc3c..0x12fbc4c` 以 result 5 完成客户端待定的类型 2 请求
（`+0x40..+0x43 = 02 00 01 05`），因此下一个创建者可以替换它。仅针对主机 ID 的离开事件
只调用 `0x12fbef0`。客户端的 BoxTrade 任务在 15 秒时以 result 4 结束（状态 5 的时钟测试
`0x1e51c74`，基准 `+0x108`），但它的超时路径 `0x1e51d50` 和析构函数 `0x1e51740` 都不触碰
中继的请求：它仍停在 `+0xb8` 处待定，而 `0x2799b10` 与 `0x18ab83c` 会拒绝，直到一条类型 9、
一条类型 0x0D 或客户端自己的离开事件完成它。

中继会一直存活到应用退出，因此停在 `+0xb8` 处的请求会跨越每一次座位、搜索和菜单存活下来，
直到某个完成者运行。它的持有者 `0x4739430`（GOT `0x46da9c0`）只由创建者写入（`0x165a2b4`）、
由中继自身 destroy 槽到达的重置 `0x279d610`（`0x279d5ac`、`0x2b71660`）以及静态析构
`0xa15f74`。虚表 `0x44e56f8`：槽 0 `0x279a7b0`、3 `0x279d5ac`、4 `0x12fbb90`；接口 `+0x28`
是监听 thunk `0x2b71650`。创建者用 `0xf0ba9c` 把它注册到 `0x4763a18` 处的终结器列表中，
该列表只在应用终结时遍历（`0x20e9c78`，以 `nn::account::CloseUser` 结尾）。

### 打开通道

| 时间 | 站点 | 端口 | 字节 | |
|---|---|---|---|---|
| 0.29 | 主机 | 1 | 31，INITIALIZED | `b90104b902b9027b0001b902b902320101b902b902320201b902b902320301` |
| 1.84 | 加入方 | 1 | 31，INITIALIZED | 同样的 31 字节 |
| 2.43 | 加入方 | 2 | 15，INITIALIZED | `03b90200bc09000000000000000000` |
| 9.00 | 主机 | 1 | 11 | `b90101b902b90280800001`，加入方回送同样的内容 |

端口 1 是通道表（Arceus 的机制）：一个站点只有在它的对端已经通告某个 key 之后才会在该 key 上
发送。加入方的表与主机逐字节相同；在它到达之前主机会停在搜索界面上。主机在 key 0x80 上的
打开必须先到：如果一个加入方的交换界面先绘制出来，它就永远不会发送自己的第一条游戏消息，
而在宝可梦上按 A 也不会出现菜单。0x7C 可靠头的长度是九字节、无位图、序号与最低待定都等于
消息自身的值；一次打开是 flags 0x0F，之后的更新是 0x07。

更晚的打开会让模拟的 Scarlet 4.0.0 交换箱没有选择光标。这个时限取决于对端：一台零售主机在
座位之后 9.15 秒打开自己的 key 0x80 时，对 6.0 秒打开的主机绘制了菜单，而 11.0 秒打开则没有。

主机会把自己的第一条游戏消息发送四遍（两个分片，然后在接下来的两个 ID 下再发一次，flags
`0x1b`、`0x15`、`0x13`、`0x15`），并且只在站点通告 key 0x80 之后才发。提前发送时，端口 0 上
没有任何东西会被分发；若作为两条发送（就像一对主机对其克隆所做的那样），站点会以 `ack_id` 5、
`lowest_pending` 5 应答（一对的加入方：4 与 3），游戏永远看不到下一条消息，主机则停在
「等待响应」上（`--send-on-open`）。

主机在 0x7C 上的 ack 的 `lowest_pending` 字段携带它自己的下一个序号，与 0x81 上一样。若改成
站点最后一个序号加一，就会让站点等待那个数字，并在 `0x6f03cc` 处丢弃主机下一条更小的消息
（[接收者在静默中丢弃什么](pia.md#what-the-receiver-discards-in-silence)）；两套编号在提交处
分岔，站点先提交。`8001` 步骤成对进行，01 与 02 在第四个字节下依次推进 03、06、0B、0E；
交换在这些步骤之上完成，两个界面都回到交换菜单。

对 `bin/sv_host.py` 而言，主机的交换流消息编号为 5（提出）、6（确认）、7（提交）、8 到 15
（步骤）；主机的 5、6、7 与 8 到 11，它的 key 0x180 打开与关闭是它端口 1 的消息 3 与 4；
它对主机提出的 ack 读作 `ack_id` 6、`lowest_pending` 5。两个完全相同的训练家也能交换。

### 在站点自己的提出之前发送的确认

永远不要在提出 `80000200` 仍在队列中时发送确认 `80000300`：按这个顺序喂给一台零售主机会以
系统错误崩溃。两个启动器上的 `--offer-after-open` 会把提出挂在对端的 key 0x80 通告上，并且
二者都不会把一条交换消息排到已为同一站点和端口排队的消息之前。

交换动画跟随主机的最后一步 `8001010e`，不携带任何交换消息。在它的状态
`b90101b902b90280800100` 之后，主机在玩家退出之前不再发送应用数据。

### 一次座位中的多次交换

key 0x0080 保持打开；key 0x0180 每次交换打开再关闭。第二次交换重复这一循环，序号继续递增
（主机提出 16、确认 17、提交 18、步骤 19 到 26），且没有新的关联、Session 交换或身份。
`TradeStage` 与 `JoinerTradeStage` 接受一个记录列表，每次交换一条；`--trade-offer` 可重复。
座位能否在主机的主机迁移请求下存活尚不清楚。

### 第一条游戏消息，以及它携带什么

`80 00 01 00` 与 2557 字节，分成两个可靠分片，先 START 后 END（一对主机压缩后 238 字节，
零售主机 195 字节），各自是一个 zlib 流（`484b`）；消息是两次解压的拼接：

    b9 02          a tuple of two fields
    bc 81 f6 09    a blob, 0x9f6 = 2550 bytes
    ...            2550 bytes
    04

该 blob 是 850 个小端三字节值，大多为 1，其余是位掩码（`0x0fffff`、`0x0002ff`、`0x00003f`、
0），按站点划分（零售主机与一对主机之间有 38 个条目不同；条目 36：`0x040000` 对 `0x0fffff`）。
索引统计的是什么尚不清楚。它不携带训练家的任何字段：零售主机的记录里既没有 ID 对也没有
名字。一对主机的四个分片重放时会被一台零售主机接受。

### 交换消息携带的记录

`80 00 02 00` 消息的 348 字节主体是常量 `bc 81 58 01` 加上一条 344 字节的第九世代队伍记录
（PKHeX 的 PK9），采用第八世代加密（`pokeldn/gen8.py`）：从 0x08 起的四个 0x50 字节块按
`(EC >> 13) & 31` 置换，对 16 位字施加 LCG `seed = seed * 0x41C64E6D + 0x6073`，以及截至
0x148 的解密主体的 16 位校验和。0x148 处的队伍尾部位于置换与校验和之外，并从加密常量重新
播种 LCG。

    0x000  u32  encryption constant, in the clear
    0x004  u16  sanity, 0 on every record measured
    0x006  u16  checksum, in the clear
    0x008       four 0x50-byte blocks, encrypted and permuted        -> 0x148
    0x148       level, a pad byte and the six stats, encrypted       -> 0x158

字段映射是 PK9 的 [`PKHeX.Core/PKM/PK9.cs`]；`pokeldn/gen9.py` 读写它。

| 偏移 | 字段 | | 偏移 | 字段 |
|---|---|---|---|---|
| 0x08 | 物种，内部索引 | | 0x8A | 当前 HP |
| 0x0A | 携带道具 | | 0x8C | 六个 5 位 IV，然后是蛋与已起昵称位 |
| 0x0C | 训练家 ID、里ID | | 0x90 | 状态异常 |

| 0x18 | 标记 | | 0xC2 | 处理者性别、语言，当前处理者在 0xC4 |
| 0x1C | 性格值 | | 0xC6 | 处理者 ID、亲密度、回忆 |
| 0x20 | 性格、数值性格 | | 0xCE | 版本、对战版本 |
| 0x22 | 位 0 为命中注定，位 1-2 为性别 | | 0xD0 | 形态参数 |

用 344 个零字节加上 `read` 报告的字段重建的记录，输出逐字节相同
（`tests/test_sv_pokemon.py`）。物种是内部索引，它从 917 起与全国图鉴分道
（[`PKHeX.Core/PKM/Util/Conversion/SpeciesConverter.cs:92`]）。错误的块顺序仍能通过校验和；
只有记录读出来像一只自洽的宝可梦才能把它定死。`bin/sv_host.py` 会打印两个提出，
`--offer-out FILE` 写出主机的那个（第一次之后的提出 N 写到带 `-N` 且在扩展名之前的 `FILE`），
`--trade-offer` 接受一条 344 字节记录（明文或加密）、348 字节主体或 352 字节消息。

### 组合出的记录

由 `pokemon.build` 从零字节组合出的记录，或用 `bin/sv_host.py --offer-set`（昵称、已起昵称
标志、性格值、IV）编辑过的记录，会以组合时的每个摘要字段交换进一份零售 Scarlet 存档。交换
界面绘制组合出的记录时不做合法性检查；校验和由主机写入。摘要中的训练家 ID 是
`(TID16 | SID16 << 16) % 1000000`（12345 与 54321 显示为 993401，8131 与 64817 显示为
855043）；特征行来自加密常量与 IV。

等级跟随经验：零经验时字节 0x148 为 100 会以 1 级到达，1,000,000 经验则为 100 级。六条成长
曲线（`PKHeX.Core/PKM/Util/Experience.cs`）在 100 级分别需要 1,000,000、600,000、1,640,000、
1,059,860、800,000 和 1,250,000。物种表 `personal_sv`（每个物种与形态 0x50 字节，
`PersonalInfo9SV.cs`）在 0x00 处持有种族值、0x0C 处性别比例、0x0F 处成长曲线、0x12 处三个
特性（物种 132：曲线 0，特性 7、7、150）。接收方游戏会重新计算队伍数值：

    HP    = (2 * base + IV + EV/4) * level / 100 + level + 10
    other = ((2 * base + IV + EV/4) * level / 100 + 5) * nature

一只完美 IV、无 EV、中性性格的百变怪，从零数值字段出发，在 1 级显示 12 和 6（各五遍），
在 100 级显示 237 和 132（各五遍）；1 级发送的 HP 99/99 会以 12 到达。

### 加入方按顺序发送什么

一对中的加入方在游戏第一条消息之前发送的内容，时间取自一次抓包：

| 时间 | 消息 |
|---|---|
| 0.04 | Session 加入请求 |
| 0.17 | Net 0x12，回显主机 0x11 的序号 |
| 0.38 | Net 0x51，回显主机 0x50 的序号 |
| 1.63 | Session 类型 6，确认站点更新 |
| 1.68 | 十一个批量确认，以及 0x81 端口 0 和 4 上的流打开 |
| 1.68 | 0x7C 端口 1 上的通道表 |
| 1.82 | Clone Clock 0x77，十八个零字节；主机回以 1、十六字节、一个尾字节 |
| 2.03 | 它自己在 0x81 端口 1 上的 44 条记录 |
| 2.43 | 0x7C 端口 2 上的打开 |

若无人应答，主机会重复 Net 0x11 和 0x50；0x12 与 0x51 会止住它们（无此应答时一次座位中有
212 条 Net 消息，有则 2 条）。

### 交换中加入方这一侧

一对加入方在 0x7C 上的完整脚本，含每条消息在其端口上的序号：

| 端口 | 序号 | 消息 |
|---|---|---|
| 1 | 1 | 通道表，主机的四个 key，INITIALIZED |
| 2 | 1 | 类型 3 加入，`03b90200bc09` 加九个零字节 |
| 0 | 1 到 4 | 第一条游戏消息，两遍 |
| 1 | 2 | `b90101b902b90280800001`，key 0x80 打开，在第四个分片之后 |
| 0 | 5 | 被提出的宝可梦 |
| 0 | 6 | 确认 |
| 0 | 7 | 提交，先发 |
| 1 | 3 | `b90101b902b90280800101`，key 0x0180 打开，在主机自己的之后 |
| 0 | 8 到 11 | 每个步骤 `8001 01 SS`（03、06、0B、0E）的回显；`8001 02 SS` 则什么都不发 |
| 1 | 4 | `b90101b902b90280800100`，关闭 |

身份在主机 key 0x80 打开之后 0.15 秒发出，加入方自己的打开再晚 0.21 秒。

`lowest_pending` 规则同样约束加入方：在 0x7C 上是它自己的下一个序号，在 0x81 批量 ack 上是
它最高记录 ID 加一。若用主机编号体系里的数字，主机的接收基址会越过加入方稍后的消息，那些
消息会在 `0x6f03cc` 处被丢弃。

`pokeldn.sv.trade.JoinerTradeStage` 就是这一侧的状态机，由 `bin/sv_join.py --trade-offer`
运行（`--send-on-open` 用于以 key 0x80 打开为条件的身份分片）。`tests/test_sv.py` 用一对
消息中主机的那一半驱动它，并固定加入方的那一半。

### 一次交换会改写什么

一条组合出的记录被交换到零售主机上再被提出回来，有 27 字节、七个字段不同：

| 字段 | 发送时 | 回来时 |
|---|---|---|
| `current_handler` | 0 | 1 |
| `ht_name` | 空 | 主机玩家的名字 |
| `ht_language` | 0 | 接收主机的语言（3，法语） |
| `ht_friendship` | 0 | 50 |
| `nickname` | 空 | 主机语言下的物种名 |
| `current_hp` | 0 | 计算出的最大 HP（237，一只 100 级百变怪） |
| `stats` | 零 | 游戏计算出的那六项 |

其余一切按发送时保留。空名字会以物种名回来，就像 Sword 的神秘礼物记录那样
（`docs/swsh_gift.md`）。

若一条记录的初训家就是接收存档的主人，则处理者保持 0 且没有处理者名字，与 Legends Z-A 中
一样（[交换写入收到的记录什么](za.md#what-the-trade-writes-into-a-received-record)）。一只为
零售 Violet 的训练家制作的神秘礼物宝可梦，用的是该存档自己抓到的宝可梦
（[为接收玩家制作](gift_simulated.md#made-for-the-receiving-player)），从它那里回来时正是
如此。

### 加入正在搜索的主机：一次交换，以及什么决定座位

`bin/sv_join.py` 与一台从连接交换搜索中充当主机的零售 Scarlet 交换，编号方式如同一对中的
加入方。它把站点更新当作座位，用类型 3 加入应答主机的通告，在主机打开 key 0x80 之后发送
四条身份消息，并遵守上面的 `lowest_pending` 规则。

#### 什么决定座位

一台从搜索中充当主机的零售主机要么运行游戏，要么把主机角色交给它的加入方。游戏在 3 到 7
次浏览尝试之后充当一次主机（`RandomMatchingSeq` `0x26e182c`，计数器 `rand%5+4`），并为一个
成员等待 3000 + rand%1000 毫秒，每有一个成员加入再加 5000 毫秒（WaitMember，`0x26df898`）。
等待超时以 JoinRandomRecover `0x26f507c` 结束，它通过 `LeaveMeshWithHostMigrationJob` 离开
会话（[离开](#leaving)），把角色交给 Net 排名最低的站点（`0x6a012c`）。在 WaitMember 期间
被接受的加入会看到游戏运行；在它之后被接受的则收到类型 7。主机玩家在通告之后退出时也会
发送它。

把角色交出去的那台主机会销毁它的网络并重新浏览。`--take-host`（默认）会让 `bin/sv_join.py`
在通告之前收到类型 7 时，用应用的 host flags 在该座位的通道和代码上运行 `bin/sv_host.py`，
就像 `bin/pla_join.py` 为 Legends Arceus 所做的那样。

运行游戏时，主机会按顺序发送：

| | |
|---|---|
| 座位 | 一条类型 5 站点更新，指名加入方的可变 ID 与其请求中声明的玩家 ID，然后是 41 字节的加入应答 |
| 它的打开 | 全部十一条流上的批量确认，0x81 端口 1 上一条 11 字节记录，端口 5 上另一条 |
| 它的身份 | 0x81 端口 0 上 46 条记录，并确认加入方的 44 到 47 |
| 它的通道表 | 在 0x7C 端口 1 上，key `0x007b`、`0x0132`、`0x0232`、`0x0332` |
| `0db90101` | 在 0x7C 端口 2 上，代码 1，只用于应答在通告之前发送的类型 3 加入 |
| 通告 | 在 0x80 端口 2 上，zlib，解压 167 字节：一条 kind 1、容量 2、携带主机站点 ID 的类型 7 |

加入方用类型 3 加入应答通告（`--port2-now` 则让它随通道表一起发送）。仅站点更新就是座位：
永远不要等待加入应答。

## 离开

一台退出座位的主机会按自己的角色运行两个 Pia 任务之一。每个都等待其对端，并在计时器上
放弃。

被加入的主机运行 `LeaveMeshJob`。SendLeaveRequest `0x6db590` 发送 Session 类型 3 离开请求
（布局见 [docs/pla.md](pla.md#leaving)）并设置 500 毫秒的期限（`0x6db6a0`）；
WaitLeaveResponse `0x6db7b0` 在到期时重发，并在第四次发送之后完成（`[job+0x6c]` 超过 2，
`0x6db8e8`），或在 `[job+0x69]` 一被设置时立刻完成。Session 分发器（`0x6d4960`，表
`0x3c0cd3b`，类型 0 到 0xA）把类型 4 交给 `0x6d7b10`，后者为一条 17 字节、其中第 5 到 16
字节是该站点自身位置 ID 的消息设置 `[job+0x69]`：

    04 | u32 random | location id (12), copied from the request

主机的类型 3 处理器 `0x6d7894` 在按常量 ID 与可变 ID 找到该站点之后，写入的正是这些内容
（类型字节在 `0x6d7a50`，从 `0x6c70a8` 取一次新的 xorshift 随机数，在 `0x6d7ad8` 发送）。
若无人应答，零售主机会以约 0.5 秒的间隔发送四次离开请求，并在第一次之后约 2 秒解除认证；
若有应答，则在收到应答后 0.04 秒。`bin/sv_host.py` 应答第一个（`--no-leave-response` 让它
无应答）；`tests/test_sv_departure.py` 在 unicorn 下把该应答跑过 `0x6d7b10`。

一台从搜索中充当主机的主机则交出主机角色。`LeaveMeshWithHostMigrationJob` 向下一任主机发送
Session 类型 7 并每秒重发（`0x6df050`），直到一条类型 8 指名该站点（`0x6ded94`），5 秒后
放弃（`0x6defb8`）。类型 7（写入器 `0x6d8de0`）是 34 字节：

    07 | host location id (12) | 00 | host IPv4, port | next host's location id (12) | u16

最后一个 u16 是该任务的 `+0xe0`（`0x6d8ea8`）。然后 `NetDestroyNetworkJob` 以主机迁移形态
等待每个客户端都收到连接状态更新（最多 4 秒，`0x6ac68c`），每 300 毫秒发送一次
NetStartHostMigration `01400000`（只由 `0x69d310` 写入，只从 `0x6aca54` 调用）
（`0x6aca98`），直到网络的站点数为 1（`0x6acaf4`）或某个期限过去（4 秒；若更新等待已超时
则为 2 秒，`0x6ac984`），然后销毁 LDN 网络。在线上，该更新是带 is-migrating 的 Net 0x11；
在加入方的 Net 0x12 之后，第一个 NetStartHostMigration 在 45 毫秒后出现。客户端在收到
NetStartHostMigration 时启动哪个任务未追踪；`NetHostMigrationJob` 以 DisconnectNetwork 或
EmulateDisconnection 开头（`0x6a93c4`）。

持有座位的加入方会绘制 NetStartHostMigration 约 4 秒。`bin/sv_join.py` 在第一个出现时离开
（`--stay-on-host-migration` 则保住座位）。

一次交换完成之后，两个启动器都会在主机离开时退出。使用 `--hold-after-trade N` 时，
`bin/sv_join.py` 在它最后一条排队的交换之后 N 秒发送类型 3 离开，就像在交换座位上 `--hold`
结束时那样，而 `bin/sv_host.py` 会像 `--seconds` 结束时那样关闭它的网络。没有完成任何交换
的座位会让 `bin/sv_join.py` 恢复扫描（[结束一次运行](architecture.md#ending-a-run)）。
