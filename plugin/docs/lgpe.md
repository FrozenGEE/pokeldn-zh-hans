# Let's Go 皮卡丘与伊布

在《宝可梦 Let's Go 皮卡丘》与《Let's Go 伊布》（2018）中，Pia 被静态链接进 `main`（RTTI 中有 269 个 `nn::pia` 类），游戏的 C++ 代码在其之上通过 `gflnet3` 以协议缓冲区消息通信，而剑与盾一年后使用的正是这套中间件。

静态分析对象是 Let's Go 皮卡丘 1.0.2（`010003f003a34000`，更新 NSP `v131072`，SDK 5.4.151.0）；硬件实测针对一台法版 Let's Go 皮卡丘和一台 Let's Go 伊布。Let's Go 伊布使用皮卡丘的本地通信 id，因此两种角色都能不做改动地与伊布交换。

本地交换与对战会要求双方玩家输入连接码：从固定的十个宝可梦中按顺序选三个，分两行显示：皮卡丘、伊布、妙蛙种子、小火龙、杰尼龟；波波、绿毛虫、小拉达、胖丁、地鼠。该码决定广播的 scene id（[会话页面](lgpe_session.md#the-link-code)）；作主机和加入在任何码下都可用。

## 可用功能

`bin/lgpe_join.py` 加入游戏主机的会话，`bin/lgpe_host.py` 托管一个由游戏主机加入的会话。一个席位可以连续进行多次交换：每次交换正常存档后，交换调度器会从状态 7 回到状态 1，除非存档报告链路结束（`0x886908`）；并且存档会在新通道上重建队伍提供对象（`0x8375a4`）（[会话页面](lgpe_session.md#the-trade-dispatcher)）。两个启动器都接受一个记录队列，席位上每次交换对应一条记录。游戏不校验收到的盒结构中的任何字段：一只闪光、100 级、特性为变身者的百变怪，各项 IV 均为 31、各项 AV 均为 200，也能在概要界面上正确显示。克隆协议的接管交换通过了游戏的 `0x11b080` 闸门，可靠协议承载身份、提供、提交和 kind 4（下一次交换的选择）；`pokeldn.lgpe.pb7` 读写 offer 与 kind 4 所承载的 232 字节盒结构。

每条完成的条目都会保存为带校验和的 260 字节文件；游戏主机离开后，主机程序以退出码 0 结束。由 `pokeldn.pokemon` 构建（等级、性别、性格、球种、选定的 IV 与 AV）并经 `bin/lgpe_host.py --fresh-pid` 提供的记录，会在接收方的概要界面上显示这些字段。

玩家按下 Retour 时，游戏主机离开席位。`bin/lgpe_join.py --leave-after SECONDS` 在首个被应答的交换步骤之后经过该秒数时执行同样的退出，`bin/lgpe_host.py` 会应答游戏主机的 Retour（[加入方离开](lgpe_session.md#a-joiner-leaving)）。`tests/test_lgpe_host_commit.py` 用脚本化的游戏主机固定住主机的提交阶段：错误的提交会让游戏主机停留在确认界面、存档的交换锁被置位（在计时的十分钟游戏时间内无法交换），随后进入致命错误界面。

## 未解决

- 为什么在主机用 A 2 应答了游戏主机撤回的投票之后，一台零售游戏主机对主机的两个 `0xa1` 都没有应答。游戏主机宣告了自己的提交克隆，收到主机的突发 `82, 91, 91, 84, 81, a1, a1`，然后在新时钟下于克隆类型 1 上重新宣告该克隆，而只有克隆类型 2 上的 `0x81` 才会导致这一行为（`0x51ca48` -> `0x520c30`）。克隆类型 1 的 `0xa1` 处理函数（`0x51c714`、`0x522350`）在任何结果下都会发送，并且每个接收闸门（`0x51ae20..0x51ae84`、`0x51ce80`、`0x51c1e0`、`0x51c6b0`）对具有相同发送方、帧计数器和掩码的 `0x81` 都放行了。`0x522a60` 返回 2 只会让克隆类型 4 的 `0xa1` 静默。给定相同输入的模拟 Let's Go 1.0.2 在 30 ms 内用 `0xa2` 应答了两个 `0xa1`，并完成了交换。
