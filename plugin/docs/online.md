# 在线交换

在线交换把相隔很远的两名玩家连接起来：每块板子用自己的主机承载一次本地交换，两个应用通过公共 Nostr
中继传递各自主机提供的宝可梦，中继只能看到加密事件。代码：`pokeldn/online/`；启动器标志 `--online`
和 `--online-code`。

## 房间

两个应用在运行同一款游戏且代码相同时相遇：

    room = sha256("pokeldn online 1|<game>|<code or 'open'>")     64 hex digits

配对的两个版本共享一个游戏键（`frlg`、`sv`）。如果游戏本身有连接码，这里的代码就是主机自己的连接码。
同一张桌子上的两台主机可以直接找到彼此；要在同一张桌子上测试，就给每台主机各自的本地代码，并用
`--online-code` 把两块板子放进同一个房间。

## 中继

每个事件都是临时类型 21059 的 NIP-01 事件，带有 `["t", <room>]` 标签，对某个应用而言还有
`["p", <its signing key>]`。每个应用从启动前 10 秒起订阅带该房间标签的 21059 类型事件，向每个中继
发布，并丢弃重复的事件 id。每个会话用一个全新的 secp256k1 密钥签名（BIP-340，
`pokeldn/online/schnorr.py`）。

| 中继 | 8 个事件，每 2 秒一个 |
|---|---|
| relay.primal.net, relay.snort.social, offchain.pub, relay.nostr.net, nostr.oxtr.dev, nostr-pub.wellorder.net | 8 个送达；默认集合 |
| relay.damus.io | 4 个送达，然后封禁该地址一段时间 |
| nos.lol, nostr.mom | 无（被限速） |
| nostr.wine | 拒绝（付费） |

`POKELDN_RELAYS`（逗号分隔的 URL）会替换默认集合。offchain.pub 拒绝来自未知密钥的突发请求，只接受
有节奏的事件。第二个应用到达 0.4 秒后两个应用配对；一条 344 字节的记录约 0.15 秒传完。

### 存储的事件

在 relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub 和
nostr-pub.wellorder.net 上测得：

| 事件 | 结果 |
|---|---|
| 来自新密钥 | 被接受并回传 |
| 带 NIP-40 `expiration` 的 30402 | 在到期前提供，到期后不再提供 |
| 用相同 `d` 重新发布的 30402 | 一分钟内只提供较新的那个 |
| 指名某个 30402 的 kind 5 | 一分钟内只提供该 kind 5 |
| 仅通过 `a` 地址指名已被替换的 30402 的 kind 5 | 五个中继丢弃；nostr.oxtr.dev 和 nostr-pub.wellorder.net 会保留它，直到某个 kind 5 指名它自己的 id |
| 没有 `expiration` 的 30402、kind 5 和 kind 1059 | 17 天后仍然全部提供 |
| 指名某个 kind 1059 的 kind 5 | 被所有六个提供 1059 的中继丢弃 |
| 通过其 `p` 键读取的 kind 1059 | 六个中继提供；relay.nostr.net 要求 AUTH 并拒绝它 |

## 会面

每个事件的内容都是以 `sha256("pokeldn room key|" + room)` 为密钥的 AES-256-GCM。

| 消息 | 发送时机 | 内容 |
|---|---|---|
| `here` | 每 2.5 秒，发往房间 | 协议 1、X25519 密钥、训练家名称、应用版本、忙碌状态 |
| `invite` | 发往一个应用 | 训练家名称 |
| `yes` / `no` | 应答 | 训练家名称 |
| `bye` | 发往非伙伴 | 原因 |

应用只邀请它见过最久、且签名密钥大于自身的空闲应用，一次只发一个邀请，最长 6 秒，同时以 `no` 应答
其他邀请。被拒绝或未获应答的邀请会使该应用被跳过 10 秒。伙伴的第一条频道消息视为它的 `yes`。

## 频道

伙伴消息在房间密钥层之内携带发送者的 X25519 密钥，以及一层内层 AES-GCM，其密钥为

    sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)

每条消息携带 `s`（自己的编号）和 `a`（按序收到的最高编号）。未确认的消息每 2 秒重发；确认在到达后
0.3 秒发出；ping 每 4 秒一次。伙伴沉默 45 秒即视为失去，如果尚未提供任何内容则会被替换。

| 消息 | 含义 |
|---|---|
| `hello` | 训练家名称和应用版本，一次 |
| `offer` / `withdraw` | 交换 *r*：本地主机提供此记录（base64），或将其收回 |
| `accept` / `unaccept` | 交换 *r*：本地主机已确认，或将其收回 |
| `refused` | 交换 *r*：接收方拒绝了发送方的记录，以及原因 |
| `done` | 交换 *r* 完成；下一个是 *r* + 1 |
| `ping`, `bye` | 保活；离开 |

## 传输内容

只有提供的记录和交换状态。PKHeX 会在主机看到之前检查收到的记录（`pokeldn.online.session.checker`）：

| PKHeX 的判定 | 记录的处理 |
|---|---|
| 无法解析、校验和错误、种类或形态在该游戏中不存在、id 超出游戏的表 | 拒绝，并向发送者显示原因 |
| 未发布的道具或招式（剑的道具止于 1607） | 拒绝 |
| 其他任何合法性标记 | 提供，并向接收方显示该标记 |

## 在启动器中

带 `--online` 的 Host 启动器提供伙伴主机的记录。本地主机的提供以 `offer` 发出；伙伴的提供则提供给
本地主机；只有两台主机都确认后启动器才确认；`done` 从盒子开始下一次交换。

| 标题 | 启动器的提供 | 主机收回自己的提供 | 启动器收回自己的提供 | 启动器的确认 |
|---|---|---|---|---|
| 火红 / 叶绿 | 伙伴的队伍块（三个 200 字节块，邮件 220，缎带 40），每当主机自己的对应块到达就发送一块；带伙伴光标的 `SET_MONS_TO_TRADE` | `READY_CANCEL_TRADE`（以 `PLAYER_CANCEL_TRADE` 应答）、`REQUEST_CANCEL` | `PLAYER_CANCEL_TRADE` | `START_TRADE` |
| Let's Go | 带伙伴 232 字节记录的 kind 2，应答主机的步骤 | 撤回投票（状态 2）、离开（状态 4） | 无 | 在提供的克隆上写 2，把末尾字移到 2 |
| 剑 / 盾 | 带盒子命令 1 的 20030；0x84 快照的队伍槽保留主机自己的宝可梦 | 盒子命令 2（提供）、5（确认） | 盒子命令 2 | 盒子命令 4 |
| 晶灿钻石 / 明亮珍珠 | 应答主机的 0x13 | 0x45 `{1}` | 0x45 `{1}` | 0x21 `{0, 2}`；安全阶段保持自动 |
| 传说 阿尔宙斯 | 应答主机的选择器 4，在其计数器之下；选择器 2 的展示在知道伙伴记录后以其应答 | 选择器 6 | 无 | 主机选择器 5 的镜像 |
| 朱 / 紫 | 带伙伴 348 字节主体的 kind 2 | kind 4 `8000040100` | kind 4 | kind 3 |
| 传说 Z-A | 伙伴选择的预览，0.5 秒后是选择本身 | `0103` | 下一轮的 `0103` | `0102`，然后 `0104` |

火红和叶绿交换整支队伍。每个 Host 都保留自己的一块，直到伙伴的主机发送了同一对；主机在没有计时器的
情况下等待 [trade.c:1478]。只有当 PKHeX 读取块中的每一只宝可梦时，该块才会到达主机。光标以 `pick`
先于记录传输。

伙伴离开或沉默 45 秒视为撤回，除非交换已过不可返回点。伙伴离开后，火红或叶绿的主机会对每次选择收到
`PLAYER_CANCEL_TRADE` [trade.c:1712]；进行到一半的队伍交换会以空队伍结束。在剑中，交换的记录是内容
50 的（[剑的交换](swsh_trade.md)）。

## GTS

GTS 在从不同时在线的玩家之间交换存入银行的宝可梦：玩家从[银行](gui.md#the-bank)中挂出一只宝可梦，
最多指定三个想要的种类、一个等级范围，并可选要求闪光，另一名玩家用自己的一只应答，挂出者的应用在下次
打开时完成交换。代码：`pokeldn/online/gts.py`、`pokeldn/app/gts.py`，以及应用的 GTS 页面。

| 事件 | 类型 | 签名者 | 内容 |
|---|---|---|---|
| 挂单 | 30402（NIP-99），`d` 为随机 id | 每个挂单一个密钥 | JSON：协议 1、游戏、按 PKHeX 读取的宝可梦、记录的 SHA-256、`wants` 和 `also`（见下）、训练家名称、状态、获胜的提供 |
| 提供 | 1059，`p` 为挂单密钥 | 每个提供一个密钥 | 密封：挂单的 `d`、游戏、记录、训练家名称 |
| 应答 | 1059，`p` 为提供密钥 | 挂单密钥 | 密封：提供 id 和挂出的记录，或拒绝及原因 |
| 删除 | 5（NIP-09） | 被指名事件的密钥 | 无 |

挂单带有 `pokeldn-gts`、`pokeldn-gts-has-<species>` 标签，以及每个想要种类的
`pokeldn-gts-wants-<species>`，携带 NIP-99 的 `title`、`summary`、`status`、`published_at`，并在
30 天后过期（NIP-40）。密封正文是以 `sha256("pokeldn gts|" + x)` 为密钥的 AES-256-GCM，其中 x 是
ECDH 的 x 坐标（`schnorr.shared_x`）。每个存储事件的 id 和签名都会被检查。

一个需求是 `{"species", "name", "min_level", "max_level"}`，当只有闪光才应答时再加上
`"shiny": true`。`wants` 保存第一个；`also` 仅在多于一个时出现，最多再保存两个，任何匹配其中一个的
提供都可应答。这两个字段是对协议 1 的增补：0.40.0 或更早的应用会忽略它们，把挂单显示为只要求第一个
需求，而它发出的、不满足闪光要求的提供会被挂出者的应用拒绝并退回。

| 步骤 | 发生的事 |
|---|---|
| 存入 | 宝可梦必须合法；它离开银行，挂单被发布 |
| 提供 | 合法且匹配某个需求的种类、等级和闪光要求；它离开银行，密封给挂单密钥；一个应用对每个挂单只持有一个等待中的提供，该挂单在挂出者的应用应答之前仍对其他玩家的提供开放；页面用一个时钟标记它 |
| 挂出者的应用打开 | 存储的提供按最旧优先应答；第一个有效的被交换，其余被拒绝 |
| 一次交换 | 应答携带挂出的记录；挂单被重新发布为已交换；收到的记录存入银行 |
| 提供者的应用打开 | 记录会对照挂单的 SHA-256 检查并存入银行；被拒绝、竞速失败或挂单已撤回时，它取回自己的宝可梦；它删除自己的提供 |
| 挂单结束 | 30 天后其宝可梦返回；提供者的宝可梦在结束后一小时、中继已发送所有存储的应答之后返回 |
| 撤下 | 重新发布为已撤回；其宝可梦返回；之后的提供被拒绝 |

每个挂单和提供都是 `Documents/pokeldn/GTS`（设置时为 `POKELDN_DATA/GTS`）中的一个文件夹，里面存放
`state.json`（密钥、已签名事件、已发送的应答）和记录。应答在发布之前写入，每个活跃事件都会重发给每个
连接上的中继。已完成的文件夹在 60 天后删除。一轮大约需要 30 秒。

中继即[存储的事件](#stored-events)中那些；`POKELDN_GTS_RELAYS` 会替换它们。被修改的应用可以扣留已
提供的宝可梦，或挂出它并不拥有的宝可梦；SHA-256 只能在事后揭示这一点。没有可信第三方的公平交换是
不可能的（Pagnia 和 Gaertner，1999）。

## 未解决

- 中继在 24 小时之后会保留事件多久，或者对没有过期时间的事件会保留多久。
- 主机在持有提供时，Host 收回提供会如何应答：剑的盒子命令 2（在确认画面上的 Host 版剑，在收到命令 1
  后又收到命令 2 时，4 秒后开始离开）、朱/紫的 kind 4、Z-A 的 `0103`、晶灿钻石在主机选择之后的 0x45。
  Let's Go 和传说 阿尔宙斯保持不动。
- Z-A 是否接受没有预览的选择，以及传说 阿尔宙斯是否接受第二个选择器 4。
- 零售版主机在盒子处等待伙伴多久（超过一分钟的部分）。
