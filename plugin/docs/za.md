# 传说 Z-A

Pokemon Legends: Z-A（标题 id `0100f43008c44000`）是一款原生 Switch 游戏，Pia 被静态链接进 `main`。其数据包头版本为 16，也就是 `pokeldn.ldn.crypto` 为 GBA 应用写出的那个版本。

## 转储

基础应用 `v0`（4.3 GB），更新 `0100f43008c44800` `v393216`（2.1 GB），Mega Dimension DLC `0100f43008c45002`。

| NCA | id | 容器偏移 | 区段密钥 |
|---|---|---|---|
| 程序（更新） | `4a70b3ff963bfe412681185cea68bf55` | `0x2085d0` | `b9de1a0334576634f8fdafdd703f7f9a` |
| 控制 | `3e7ba1cd223145fa4f299a8f4cafd4cb` | `0xbd0` | `a8cb59338ce785237048d52452eb6adf` |

程序 NCA 的 exeFS 位于区段 0，BKTR RomFS 位于区段 1。exeFS 包含 `main`（33,970,422 字节）、`main.npdm`（1,700）、`rtld`（8,550）和 `sdk`（6,247,676），没有 `subsdk0`。解压后，`main` 的 text 为 `0..0x3163f70`，rodata 从 `0x3164000` 起，data 从 `0x3bc2000` 起；本页中的地址都是该映像内的偏移。控制 RomFS 数据位于 NCA `+0x14c00`，区段计数器 `0000000000000005`；`control.nacp` 给出的显示版本是 2.0.2，并在 `+0x30b0` 处给出八个本地通信 id，全都是 `0100f43008c44000`。

## 数据包头

头版本 16，在 wiki 的表格中对应 Pia 6.39 到 7.2。布局为 `pokeldn.ldn.crypto.PiaHeader`（29 字节，magic `32AB9864`，加密时版本字节带 `0x80`；见 [Pia](pia.md)）。

    0x24fadbc   initializer: magic at object +0x08, 0x10 at +0x0c, memsets nonce +0x15 (8), tag +0x1d (16)
    0x24faefc   validator: magic, (version & 0x7f) == 0x10, (length - 0x1d) >> 6 below 0x71
    0x24fb1e0   receive path, branches on bit 7 of the version byte
    0x24fb4b0   send path, writes 0x10 back to +0x0c when it seals nothing
    0x24fb46c   padding-size setter: ORs into bits 4..7 of object +0x0d (wire byte 0x05)

该对象把 nonce 和 tag 存放在比其线上偏移高八个字节的位置，正如传说 阿尔宙斯 的 version-11 头在 `pokeldn.ldn.pia6` 中的做法。

## 广告

处于本地搜索界面的主机会托管一个网络并广播 112 字节：0x5C 的 Pia 系统属性块加上 20 个游戏字节。不随连接码变化的字段：

| 字段 | 值 |
|---|---|
| 本地通信 id | `0100f43008c44000` |
| LDN 协议 | 1 |
| 广告版本 | 4 |
| 场景 id | 1 |
| 应用版本 | 6 |
| 安全模式 | 1 |
| 接受策略 | ALL |
| 参与者 | 1/2 |
| 系统 / 应用通信版本 | 22 / 6 |
| 玩家名称 | 一个字节、一个空格、UTF-8 |

SSID 和信道按会话而定。游戏字节是 ASCII 形式的连接码，用 NUL 补齐到十六个字节，然后是它长度的小端 `u32`。布局和密码字段与传说 阿尔宙斯相同（[pla.md](pla.md)，广告中的连接码）；Z-A 的游戏密钥给出掩码 `1068a742ac3a8787ab6066a161f5d5e1`。`pokeldn.za.build_advertise_data(code)` 仅凭连接码就能复现每一个广告；`tests/test_za.py` 把两者都固定下来。

## 席位

搜索中的主机会接受一个站点并立刻用 Pia 通信：第一个数据报（109 字节）出现在 0.02 秒。数据包在 `AES_ECB(game_key, ssid)` 下以网络 id `CRC32(ssid[1:16])` 认证（32 个中 32 个解密成功）。若无人应答，它在协议 1（Net）上从其 variable id 向目的地 0 发送：

| 消息 | |
|---|---|
| `01 11 ...`，118 字节 | 连接状态，序列 id 2 和 3，每秒两次 |
| `01 40 00 00` | 开始主机迁移，一旦该状态得不到应答 |

连接状态就是 `pokeldn.ldn.pia_connect.parse_net_conn_request` 读取的布局：四个槽，两个已填，都在端口 12345，主机 `169.254.x.1`，加入者 `169.254.x.2`。它在大约 14 秒后停止，并让该站点保持就座。

一对模拟主机的开场：

| | |
|---|---|
| 第一个数据包 | 主机的，109 字节，关联后 48 毫秒；加入者以 45 字节应答，然后是 125 字节 |
| 头 nonce | 每站点计数器，从一个随机 64 位基数起，每发一个包 +1 |
| 加入者的第一个包 | 源 0、目的地 0、包 id 0、无 footer、未压缩 |
| 加入者的第二个包 | 它自己的源 id，zstd 压缩 |
| 主机的下一个包 | 发往该 id，带两字节接收者 footer |

在一个没有 Pia 主机的网络上 LDN 连接成功的加入者会在 7.94 秒后断开，即 Net 连接截止时间 8000 毫秒减去 LDN 连接时间：

    0x251b1bc   LdnProtocol vtable 0x3c8aef8 slot 0x1d8: mov w0, #0x1f40
    0x2513520   NetBackgroundProcessJob StartConnectNetwork: job+0xa0 = now + ticks_per_ms * 8000
    0x25141c4   the WaitConnected step 0x25140bc, while the host is unknown: deadline against now
    0x25143a0   expiry: result 0x647a, state byte +0x100 = 5, a 5000 ms deadline (slot 0x1e8),
                then StartDisconnectNetwork

LdnProtocol 的时序槽 0x1b0 到 0x1f8 分别返回 6000、1000、500、10500、4500、8000、20000、5000、5000 和 10000 毫秒；只有 0x1d8 和 0x1e8 已被识别。

## 会话，在零售主机上

一个发送参考加入者的 Session join 的站点会被立刻接纳。主机的发送：

| 从席位起 | 主机发送什么 |
|---|---|
| 0.02 秒 | Net 连接状态，118 字节 |
| 0.05 秒 | Session join 应答，类型 2，37 字节，发往加入者的 variable id |
| 0.06 秒 | Reliable（协议 10），106 字节，以及两个 Broadcast Reliable（协议 11） |
| 0.08 秒 | Net update property，类型 0x50，150 字节 |
| 从 0.5 秒起 | RTT 请求，约每秒三个 |
| 1.12 秒，重复 | Session update session，类型 5，185 字节 |

加入方在 Net 确认之上欠着：十个协议（`1:0 3:5 5:1 6:0 9:1 10:3 11:4 12:4 13:7 15:0`）、应用通信版本 6、一个先 `0x06` 后接零的标识令牌，以及一个单空格的 PlayerInfo 名称。一个会应答每个 Net、Session、RTT 和 Reliable 消息而不发任何游戏消息的加入者（`bin/za_join.py` 不带 `--game`）能保住零售搜索的席位直到它离开（实测 150 秒）。

| 加入 | 主机的应答 |
|---|---|
| 协议数与主机不同 | 被类型 0 处理函数 `0x254a030` 丢弃（`0x254a090`，对照 `0x256c9f0`），不应答，无站点 |
| 协议或应用版本错误 | 37 字节的类型 2，结果 3（`0x254a2e4`）或 4（`0x254a290`） |
| GBA 应用的六个协议，或十个中的九个 | 没有 Session 消息；就座后 8 到 12 秒发 Net 0x40，然后在新 SSID 下开一个新网络，仍在搜索 |
| 十个协议，但从其 variable id 没有 RTT 应答或其他流量 | 被踢出（[踢出](#the-kick)），就座后约 27 秒显示 "no partner found" |

8 到 12 秒的路径是主机的 WaitMember，3000 ± 999 毫秒（随机 u64 按有符号读取）；到期时，若加入者仍在 Net 层且不在会话中，LeaveMeshWithHostMigration 会轮询 8000 毫秒寻找下一个主机（`0x255a520`），然后发送 Net 0x11 序列 3 和 Net 0x40。踢出序列是从 14 秒起的 Session 类型 13，共九个、间隔 0.5 秒；从 19 秒起每 0.5 秒发一次 Net 0x11 序列 3；从 23 秒起每 0.3 秒发一次 Net 0x40。

## 游戏自身的交换

在 Pia 之上，游戏运行在 Reliable（协议 10）和 Broadcast Reliable（协议 11）上，`pokeldn.ldn.reliable` 解析其子头。一次交换携带下面的应用载荷（参考抓包中有二十个不同的），每个都重发直到被确认，两个站点发出的集合相同，只差站点 id。按消息 id，以首次出现的顺序：

| id | 字节 | 承载什么 |
|---|---|---|
| `1400` | 106 | 站点的身份，玩家名称用 UTF-16 |
| `1403` | 9 | 身份的校验和（SyncDataSet），见下 |
| `0100` | 1211 | 选择界面据以绘制的记录 |
| `0101` | 354 | 报价：九字节头、344 字节 Pokemon 记录、一个尾随字节 |
| `0102`、`0104` | 5 | 步骤消息 |
| `0200` | 5 | 确认步骤，最后一个字节为 3、6、0x0b、0x0e |

`pokeldn.za.reference` 附带身份、其后续、协议 11 的开场和选择记录，录自一对玩家名为 `Player` 的模拟主机；`bin/za_join.py` 和 `bin/za_host.py` 会发送它们（`--game-dir` 指定另一组）。

身份是一个两成员的 `b9` 元组：一个 u32，然后是一个持有 0x5d 字节 `bc` blob 的单成员元组。该 blob 是六成员元组。它的前四个成员是存档的训练家 id（里ID在高半部）、性别、语言和玩家名称。随后是一个 32 字节的全零字段，再是其余部分。

游戏从存档的训练家块填充这四个字段，即 PKHeX 的 `MyStatus9a`，它位于玩家状态对象的 +0x40：

| 成员 | 块偏移 | getter |
|---|---|---|
| 训练家 id | +0x00 | `0x824b2c` |
| 性别 | +0x05 | `0x505c24` |
| 语言 | +0x07 | `0x23c398` |
| 名字，13 个字符 | +0x10 | 由 `0xc90ce4` 复制 |

构建器是 `0xc90b04`；它把该值存储在以 GOT 在 `0x3ec7638` 持有的名称条目下。

接收主机会以相同顺序解码这些成员（`0x9131ec`）。它的名称框 `T_pname_%02d`（`0xb13fd4`）会把语言按 1 到 11 对照游戏的语言表（`0x33a308c`）检查；11 是拉美西班牙语。它把性别与名称一起传入其文本（`0x6b9fb8`）。

记录下来的身份是一个女性、英语存档：`0x378913cf`（5071 和 14217，参考会话中 Pokemon 的训练家）、1 和 2。为接收玩家制作的礼物会读取全部四个（`reference.identity_trainer`，[为接收玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

    1400 b902 82<u32> b901 bc5d b906 82<u32> 01 02 bc1a <name> bc20 <32 bytes> ...

名字是 26 字节，UTF-16LE，用 NUL 补齐：最多十二个字符，位于协议 10 消息的偏移 0x18（协议 11 站点前缀之后的 0x1c）。在那里放上记录的 `Player`，一台零售主机为它的交换伙伴显示了 `Player`。两个启动器都把 `--trainer-name`（默认 `POKELDN`）写入其中（`pokeldn.za.reference.named`）。

信道 0x14 承载一个键值存储，游戏在站点之间保持同步（`gfa::network::p2p`，构建于 `0x7796a0`；消息 id `0x1400 | index`）：1400 是 UpdateValue（`0xc1bdf4`），1402 是 DeleteAllValues，1403 是 SyncDataSet（`0xc4b1b4`）。身份的外层 u32 `0x2abe85e2` 是该值的键，一个位于 `0xdf1b30` 的常量：`UserData` 的 FNV-1a 32，也就是游戏存储身份时所用的名称。1403 对发送者按 key 排序的值携带一个 u32，`h = crc32(le32(fnv1a32(value) + h))`，从 `h = 0` 开始（`0xc4b270`，FNV-1a 在 `0xc4b31c`，标准 CRC-32 在 `0xc4b420`）；对身份而言，值是 `bc5d` 之后的 0x5d 字节。接收方会重新计算它，只有当每个站点的都匹配时才继续（`0xb8c724`，`0xb8c660`）。记录下来的 `Player` 身份给出 `1403b9018269fb308f`，即那条记录的消息。改名后的身份若带着那个过时的 1403 发送，会让零售主机停留在其搜索界面：它会发送自己的 1400 和 1403，但从不发送它的 0100。`pokeldn.za.reference.sync_message` 为所发送的身份构建 1403。

### 交换命令

交换会话设置 `0xca2928` 会在会话的命令信道（session+0xc8）上订阅五种命令类型（按 ctti 字符串命名）。id 是 `0x100 | index`，即该类型在信道 +0x60 列表中位置（`0x96129c`，一次 `strcmp` 遍历）。每个载荷都是一个以 u16 轮次开头的 `b9` 结构体。

| id | 命令 | 处理函数 | 处理函数读取的载荷 | 处理函数做什么 |
|---|---|---|---|---|
| `0100` | CommandReady | `0x2dc4c7c` | 轮次，1200 字节 | 把 1200 字节复制到 session+0x604，设置 session+0xf0 |
| `0101` | CommandSelectPokemon | `0xb2a44c` | 轮次，344 字节记录，一个字节 | 加载记录（报价的 Pokemon）；该字节第 0 位清零则使其成为一次拾取 |
| `0102` | CommandConfirmTrade | `0xc8dda0` | 轮次 | 当 session+0x152 高于该轮次时忽略；否则伙伴状态 +0x134 = 4 |
| `0103` | CommandCancelTrade | `0x2dc51ac` | 轮次，u32 原因 | +0xab4 = 原因（1 与 2 互换），否则 0；+0x152 = 轮次；+0x150 += 1；然后 `0x2dc41f8` |
| `0104` | CommandFinalAgreement | `0x2dc52b4` | 轮次 | 当 +0x152 高于该轮次，或自身状态 +0x130 不为 4 或 5 时忽略；否则伙伴状态 5 |

取消发送器 `0x964a60` 在自身状态 +0x130 为 2 或 5 时不发送任何东西；否则它发送轮次 +0x150 + 1，设置 +0x130 = 2，递增 +0x150 和 +0x152，并把伙伴的状态从 3..5 降为 2（原因为 0 时降为 3）。处理函数只拒绝严格低于 +0x152 的轮次，所以在一次取消之后，过时的 ConfirmTrade 或 FinalAgreement 会被忽略，而更高的轮次会被接受。SelectPokemon 不读轮次。

会话对象（0xab8 字节，由 `0xca2704` 构建，vtable `0x3e3a6e8`）会把 +0x150..+0xab7 清零，所以两个轮次都从 0 开始，一次会话的第一个 `0102` 和 `0104` 是 `b90100`。一次完成的交换之后 `0x964568`（自身状态 6）会清空两个报价，把两个状态设为 2 并把两个轮次清零，所以席位上的下一次交换从轮次 0 开始。`pokeldn.za.host` 每次交换都重置其轮次。

| 自身状态 | 由谁写入 | 何时 |
|---|---|---|
| 5 | 会话更新 `0x95f600`（`0x95f680`） | 自身状态 3 或 4、字节 +0x148 置位、计时器 +0x138 至少 1.5 秒、伙伴状态 4 或 5、`0x963710` 为真 |
| 6 | 委托调用 `0xdfda8c`，在 `0x964e78` 填充 | 交换 worker 的状态 6 委托 |
| 7 | `0x2dc4b94`，由 `0x964f0c` 安装 | worker 的状态 7 委托；2.0.2 中不可达 |

在自身状态 5 时 `0x9610a4` 调用交换对象（session+0x48，由 `0xc8ad1c` 构建，vtable `0x3d8a0d0`），并把交换 worker（`0x966af0`，0xb0 字节）构建到 +0xd0，带状态 6 和状态 7 委托（`0x9649e0`，`0x964a20`）。

worker 的启动 `0x965660` 把主机测试 `0x9157d0` 存到 +0x14，清 +0x15，把 `0x34f2b0(rng, 0x12c) + 2`（2..302）存到 +0x18，清零 +0xc 和 +0x10，把 +9 设为 1。它的更新 `0x960c20`（唯一调用者 `0x95f750`）通过表 `0x33a360d` 对 +9 分派。`0x962ac0(peer, step)` 把 `0x100 | step` 存到 peer+0x48 并发送出去；一次等待会比较伙伴在 +0x70 的步骤，+0x71 置位时有效。

一台 Z-A 在交换提示上选择取消会发送 `0103b9020100`（轮次 1，原因 0）；一旦其玩家再次选择，它会用主机先前的报价重绘提示，并以 `0102b90101` 和 `0104b90101` 确认。轮次 0 下的应答会被忽略，并让主机停留在 "Communicating"。`pokeldn.za.host` 从主机自己的 `0102`、`0103` 和 `0104` 取轮次。

### 加入者在这些流上欠什么

以一对参考主机和一台模拟主机的确认为基准实测：

- 协议 10 发往主机的 variable id，协议 11 发往 mesh id 0x0001；两者都在两字节接收者 footer 中携带主机的 variable id；
- 每个游戏包都做 zstd 压缩；
- 纯确认走流的基准 0xfff0 和消息标志 0x40；一个推进序列的确认会被当作数据读取，后面留着一个洞。应用数据不携带消息标志；
- 协议 11 上的确认是 74 字节：站点的四个字节、一个流字节、计数四，然后是四个条目，每个是一条下一个期望的半字和一个十六字节掩码，最后一个被截短。条目 1 是加入者的流；主机在另外三个中报告空闲基准 0xfff0；
- 身份在 INIT 下发出，选择记录紧随其后，然后在一个新序列下反复发送，每次都是同样的 1211 字节（实测：约 0.5 秒后，然后约每秒四次）；
- 子头的接收者计数在协议 11 上是三，在协议 10 上是零；
- 在协议 11 上，子头长度计算的是四字节站点前缀之后的载荷，所以每一帧都比它声明的多四个字节：开场是 `00000001` 和 `1402 b900`，身份是前缀加上整个协议 10 身份，九字节消息是 `1403b9018269fb308f`，确认是前缀加上四个完整的 18 字节条目。在声明长度处被截断的帧会被丢弃（主机会把它的开场重发约每秒十次）；最后四字节错误的帧会被确认，但会让主机停留在其搜索界面。

LDN NodeInfo 的本地通信版本（0x40 字节中的 +0x2E）在参考站点上是 6；0 被同样对待。

### 踢出

### 保活

设置的 +0x290 是一个以毫秒为单位的发送静默上限（`0x257d12c` -> `0x256a238`；0 变成 1000）。`SessionPacketWriter` vfunc 7 `0x2544004` 在向某站点发送时给该站点在 +0xb0 打上时间戳，并通过 `0x256a2d0` 向任何在时限内未被发送过的站点发送一个额外数据包：一条协议 0、中间字节 0xfd、端口 0、空载荷的 Pia 消息（头字节 `04 00`）。没有协议的 id 是 0；读取者在下一轮接收开始时回收未读消息（`0x2566030`），所以这类消息从不累积。字节 +0xa0 标记一个正在被踢出的站点（`0x2577094`）。

### 数据包 id

数据包 id 在每个发送者上使用两个计数器：一个用于目的地 0x0001，一个用于其他所有目的地（0 和主机的 variable id 共用）。`nn::pia::session::SessionPacketReader::vfunc11` `0x2566920` 在任何协议之前检查：未知源或无站点则接受；否则目的地会选择一个控制器（0x0001 用 station+0x78，其他用 station+0x50），而 `0x2576ad0` 检查数据包 id（线上 0x0a）和大端 nonce（线上 0x0d）：

    id == 0                                         accept, nothing recorded
    last id == 0                                    last id = id - 1
    last nonce == 0 and nonce != 0                  last nonce = nonce - 1
    (s16)(id - last id) < 1                         reject
    nonce != 0 and (s64)(nonce - last nonce) < 1    reject
    otherwise                                       last id = id, last nonce = nonce if non-zero

被拒绝的数据包会送到 `0x25655d8` 并被丢弃：重复的 id，或超前 0x8000 或更多。为目的地 0 使用单独计数器的加入者，其每个 Net 0x51 都会被丢弃，直到它超过主机 id 计数器；主机会重复它的 Net 0x50 直到有一个通过（实测约 10 秒），其更新序列 1 被延迟。Net 0x51 处理函数 `0x2504100` 不读任何头字段。

### 加入的其余部分

- Net：连接状态 0x11 以 0x12 应答，更新属性 0x50 以 0x51 应答。
- Session：类型 5 的 update session 以十五个字节应答：类型、站点的 LDN 常量 id、更新序列作为大端 u32，以及 0x0001。GBA 应用的应答（原始 MAC，无序列）会让 Z-A 主机每隔两秒无限重复其更新。

一个接受更新序列 1 的主机会在大约 50 毫秒后发送其选择记录（实测就座后 1.2 和 1.25 秒），并进入其交换框。

### 协议 10 上的交换

每一方在选择记录之后发送一个 354 字节的 `0101`（实测约 2.5 秒后）。报价的最后一个字节在站点主动发送的预览上是 1（零售主机在其光标于交换框上每次移动时都会发一个），在玩家拾取上是 0；主机的判断依据是那个字节，而不是计数。以 1 发送的拾取会被确认并绘制为空，伙伴会带着空槽等待在 "Communicating"。

加入者用自己拾取的应答主机的拾取，并以 `0102b90100` 确认；主机以相同内容确认，双方都发送 `0104b90100`（主机在加入者的 `0102` 之后 1.5 秒），然后加入者发送四个 `0200b901XX` 步骤：03 和 06 一起，0b 和 0e 在交换动画和交换 worker 的随机等待之后（[交换命令](#the-trade-commands)）。主机在协议 11 上发送 `0000000202`，并在其前缀下以 `0201b901XX` 应答每个步骤。`bin/za_join.py --trade-offer` 运行加入者。

| 0x4b | 能力值等级 = `level + [0x4b]`，上限 200（`0x10f558`） |
| 0x156（s16，PA9.cs 中未映射） | `0xe4163c` 使用 `max(1, maxhp + (s16)[0x156])`；加载路径从不写它，所以组成的值会保留 |
| 0x23 | 模型描述符 `0x106a48` 把 `[0x23] != 0`（`0x106ba0`）存到 +0x13，旁边是 +0x12 的蛋或坏蛋和 `(scale / 255) * 2 - 1` 形式的缩放；只有 `0xe3f140` 调用其 setter。恰好在两条主机生成的记录上为 1，且缩放为 255（Roserade 407、Glaceon 471） |

0x4b 和 0x156 在每一条主机生成的记录上都是零。

#### 每招式标志

PA9.cs 的附加招式记录：360 位，第 k 位在 k 小于 264 时位于 0xd6 + k/8，大于等于 264 时位于 0x94 + (k - 264)/8（Scarlet 在 0x94/0x95 的太晶属性在这里是标志 264..279）。一个招式的索引是它在 rodata `0x3303fb0` 的 340 个 u16 招式 id 中的位置，由线性查找 `0xe669e0` 找到（不存在时为 -1；每个调用者随后跳过该标志）。`0x631834` 设置一个标志，`0x673448` 清除一个，`0xe438e4` 清空该数组，`0xe43068` 读取一个。一只招式是 446、328、103、784 的 Onix 的标志为 33 38 88 91 103 106 157 174 225 231 328 444 446 457 784。招式 58、103、162、247、328、403、423、446、542、573 和 784 都在该列表中。

`0xe343a0(species, form, move)` 读取个人条目（vtable +0x36，经由 `0xe3cb88` 和 `0xe36850`）的第 25 个字段，一个 {u16 招式, u8 等级, u8 解锁等级} 的向量，并返回匹配的解锁等级或 0。学习等级是 1..100、253 或 254。在 2.0.2 的表中：

| 学习等级 | 解锁等级 |
|---|---|
| 1（4,803 条） | 10 |
| 3..100（14,717） | 学习等级 + 3；例外：99 给出 100（六条）和 102（一条），33 给出 37（两条） |
| 254，存在的物种 | 274 条中 266 条为 10；其余为 19、20 或 22 |
| 253 | 192 条中 48 条为 10；其余为 39、15、12、33、38 等 |

vtable 为 `0x3e28e58` 的 PokemonParam 包装（321 个槽，每个都是到 +0x50 处 PokemonParam 的 thunk）以三种方式使用它：

| 槽 | 函数 | 做什么 |
|---|---|---|
| 135 | `0x6a30b0` | 列出解锁等级非零且等于其等级参数的招式 |
| 145 | `0x631834` | 设置一个招式的标志，跳过 `0xe669e0` 找不到的招式 |
| 150 | `0x699308` | 当解锁等级非零且等级（`0xe49760`，或存储记录上由经验得出的 `0xe5ce70`）达到它时为真；否则看标志 |

标志能解锁等级规则不解锁的招式；所有标志为零的记录仍然拥有其等级及以下的所有学习表招式。位写入器 `0xe5c550` 只从 `0x631864`（设置）和 `0x673478`（清除）进入。主机会为槽 135 在某个等级列出的每个招式槽设置标志（`0x52fff0`、`0x824eb0`、`0x28eec70`），而构建例程 `0x656060` 在字节 0x23 置位时把每物种的招式写入并标记到槽 0（`0x6568c4`）。

收到或加载的记录会整体带来它的标志；接收路径上没有任何东西读取该数组。

概要界面 `0x8d0610` 通过槽 150 把每个招式标记为 "/plus_on" 或 "/plus_off"（`0x8d1a18`），在游戏标志 `flag_megaevo_disable` 置位时互换（`0x393b8`，命名标志读取，在 `0x8d1438`；键记录 `0x3db5548`，FNV-1a-64 哈希 `0x5d0f3c74b46a0ff5`）。

主机生成的记录携带其等级及以下每个学习表招式的标志，再加上物种通过进化在学习等级 253 或 254 获得的任何招式以及字节 0x23 的招式。

#### 特性

Scarlet 在 0x14 的 u16，槽位在 0x16。GetAbility `0xe43bec` 在存储值低于 299（0x12b）时返回它，否则从个人表返回 `0xe5d368(species, form, bit 2 ? 2 : bit 1)`。0x14 的其他读取者只有属性 getter `0x99c84` 和 `0xa4354`（物种 493 且特性 121、物种 773 且特性 225 从持有物取属性，`0xe5d528`、`0xe5d5a0`）。创建例程 `0xe3eb34` 和 `0xbb8f04` 从 `0xe5d368` 写入它。主机生成的记录存储 5、30、38、81、151、187。

没有界面显示存储的特性。`0xe43bec` 只从 `0x288d894` 进入，即某个引擎组件的槽 42（vtable `0x3d1a7c8`）；七个 PokemonParam 包装 vtable 让槽 42 返回 0（`0x2d6fd88`），而战斗特性窗口 `0x2d52468` 读取那个槽。

### 加载收到的记录时检查什么

伙伴的 `0101` 到达 `0xb2a44c`，它为 CommandSelectPokemon 注册（`0xca33d8`，从 `0xca2928` 调用）。反序列化器 `0xb4e248` 要求标签 0xb9 且有三个成员（`0xb4e33c`），把第一个读作 u16（`0xa91178`），要求第二个是恰好 0x158 字节的标签 0xbc（`0xb4e4b8`），并把第三个保留在 struct+0x15a；任何错误时处理函数都不被调用（`0xb4e1c8`）。处理函数分配一个 PokemonParam（`0x82713c`）并用 `0x270994` 加载那 344 字节：

1. `0xe47e94` 把 0x148 字节复制到核心、16 字节到尾部，解密两者并比较校验和；不匹配则设置 Bad Egg 位。它会清除快速模式，所以加载结束时重写校验和并重新加密：错误的校验和被保留为已修正，并置上 Bad Egg 位。
2. `0xe3f18c`：对非零物种，`0x2901a4(species, form)` 在个人表（`0xe366b0`，一个以 `species * 10000 + form` 为键的映射）中查找该对，并读取 FlatBuffers 字段 1 的字节（vtable +6，`0xe3bbfc`），不存在时为 0。为 0 时设置 Bad Egg 位（`0xe51698(acc, 1)`）。缺失的键回退到 map+0x80，即物种 0 的条目，它没有字段 1。
3. `0xe41750(pp, 1)` 把由经验得出的等级写入尾部，并依据物种、形态、能力值等级、IV、极限特训位、EV 和能力值性格重新计算最大 HP 和五项能力值。当前 HP 为 0 时保持 0，否则按最大 HP 的增量上升。
4. `0xe42584` 把从槽 0 起计数的非零招式的 PP 限制到带 PP up 的最大值（`0xe6646c`）；蛋或 Bad Egg（`0xe4c950`、`0xe485f0`）会被跳过，除非 `[0x3f0784()+0x380]` 置位或 `0xe483b4` 为真。
5. `0xb2a4a4` 用 PokemonParam 调用 session+0x88 处的可调用对象，忽略其结果，把它移入 session+0x128，并在第三个成员的第 0 位清零时把伙伴状态 +0x134 设为 3（一次拾取）。该可调用对象总是 `0xad2c68`，即下面的名称检查（`0xca20a4` 在 `0xca2520`、`0xca25d8` 处用它构建配置；没有别处引用它）。

没有任何东西对照学习表、球、相遇数据、训练家 id、特性或尾部的等级来检查招式。组成的记录只会因校验和错误或个人表字段 1 为零而失败，两者都会产生 Bad Egg，从不拒绝；被拒绝的名字会被重写。校验和错误的记录会被画成蛋图标、等级 0、雄性符号，放在报价的昵称下，并提供 "Trade it"；交换后它作为 "Egg" 落入箱子，概要为空，游戏继续运行。

### 收到的 Pokemon 上的名称检查

`0xad2c68` 对空记录返回（IsEmpty `0x13778`），否则运行 `0x89f250`（另一个调用者 `0x89de34`）：它把一个 `nn::ngc::ProfanityFilter` 打开到全局 `0x612d3d0`，带一个 0x20000 字节的缓冲区（`0x912e10`），用 `0x9138d4(str, len, language)` 检查三个名字并收尾（`0x912d80`）。

| 名字 | 传入的语言 | 失败时 |
|---|---|---|
| 昵称，0x58 | 记录的，0xd5 | `0x8a0370` 用该语言写入物种名（`0xe33ca0`）并清除昵称位（0x8c 第 31 位） |
| 初训家的，0xf8 | 记录的，0xd5 | `0x3d8a248[language]`，用 `0xe579a0` 写入 |
| 处理者的，0xa8 | 处理者的，0xc3 | `0x3d8a248[language]`，用 `0xe5a190` 写入 |

语言为 12 或更高时按 0 索引该表。当 `[0x3f0784()]+0x380` 和 accessor+0x1a 都为 0 时，`0x8a0370` 对蛋或 Bad Egg 不写入任何东西（`0xe4c950`、`0xe485f0`）。替换表 `0x3d8a248` 持有十二个 UTF-16 字符串：0、1、6 为 `ゼット.`；2 为 `Z`；3 为 `Zed`；4、7、11 为 `Zeta`；5 为 `Zett`；8 为 `제트.`；9、10 为 `Z.`。

`0x9138d4` 在以下情况判定名字失败：

- 长度为 0 或其第一个单元为 0；
- 长度为 7 个单元或更长，且任一单元落在 0x3041..0x3090、0x30a1..0x30fa、0x4e00..0x9fcc 或 0xac00..0xd7a3（区间表在 `0x3308840`、`0x33087b8`）；
- 语言为 1..5、7 或 11，且第一个 0 之前的任一单元落在 0x4e00..0x9fa0 中除 0x4edd 之外；
- L（来自 `0x444330`）为 0、6 或大于 11；
- 过滤器的 vfunc +0x28 被 `0x913ad0` 以 `(&result, pattern, &str, 1)` 调用，pattern 为 `0x339f650[L - 1]`，结果非零。

长度扫描 `0x913a80`（跳过 0x10 标记的串）测得为 0 的字符串不经过滤器即通过，过滤器调用返回错误也一样（`0x913b08`）。处理者名为空且处理者语言为 0 时会变成 `ゼット.`，初训家名为空时变成记录语言的字符串；完成的交换随后会覆盖处理者的名字。PKLDN 和参考中的名字都通过。

L，即游戏的文本语言，是单例 `0x6131800` 的字节 +0x14（GOT `0x3ec7800`；`0x444330` 通过 `0x410a20` 读取，一旦 +0x80 标记它已构造）。它按与记录的语言字节相同的编号，并索引消息目录表 `0x3e278b8`（步长 0x18，`0x940dd8`）：0、1、6 为 "jpn"，2 为 "English"，3 为 "French"，4 为 "Italian"，5 为 "German"，7 为 "Spanish"，8 为 "Korean"，9 为 "Simp_Chinese"，10 为 "Trad_Chinese"，11 为 "Latam"，12 为 "item"。加载器 `0x410a30` 在其语言参数为 0 时使用 L（`0x410a68`）。

启动时 L 通过 `0x17d6368` 和表 `0x330f728`（1..5 或 7..11）来自 `nn::oe::GetDesiredLanguage()`。setter `0x17d62ec` 是它唯一的写入者；它的其他调用者是语言选择视图（只存储它列出的十个值）、带训练家记录 +0x47 的 `0xbb9d30`，以及一个没有任何已发布 Lua 包命名的脚本绑定 `0x1673170`。

### 交换向收到的记录写入什么

交换的步骤 6 调用交换对象 vfunc +0x80，即 `0xcbc68c`，它调用 `0xcbc7fc`。除非 `0xcbc9e8` 返回 null（`0xcbc854`，跳过更新），否则它用 `0x882104` 从玩家的训练家记录（GOT `0x3ec28d8` 的单例上的 `0x505c30`）填充一个结构体：u32 +0x40（训练家 id 和里ID）、性别 +0x45、语言 +0x47、从 +0x50 起的 13 个单元的名字。它用 `0x825358` 包装伙伴的 PokemonParam（交换对象 +0x78），并调用包装的槽 167（`0xcbc888`，+0x538；两个包装 vtable 中都是 `0xcebfe0`），这是到 `0xcebfe8` 的 thunk：

- 初训家的性别（`0xe4f570`，0x125 第 7 位）、u32 0x0c（`0xe49d50`）和名字（`0xe510c0`）都与结构体匹配：0xc4 = 0（`0xe58a70`），调用 `0xe3f900`，返回 1；
- 否则 0xc4 = 1，结构体的名字（`0xe5a190`）、性别写入 0xc2（`0xe5a3a0`）、语言写入 0xc3（`0xe5a5c0`），0 写入处理者的记忆 0xc9、0xca、0xcb 和 u16 0xcc（`0xe59910`、`0xe59b30`、`0xe59f70`、`0xe59d50`），`0xe340ac(species, form)` 写入亲密度 0xc8（`0xe58eb0`），调用 `0xe3f900`，返回 0。

除非接收玩家是它的初训家，否则收到的 Pokemon 会把接收玩家作为处理者。每个 setter 在记录仍标记为加密（+0x18）时会重新求和（`0xe5d810`），并在不匹配时设置 Bad Egg 位（`0xe58b60..0xe58b80`）；对 Bad Egg 它会写入 `0x3f7ef98` 处的一个接收槽（`0xe58bcc`）。

## 与零售主机的交换

在 Link Trade 搜索中的零售 Z-A 与 `bin/za_join.py` 交换，并保留组成的记录。交换后主机在同一席位上回到它的交换箱，可以再次交换：`0x964568` 把两个状态都重置为 2、两个轮次都重置为 0（[交换命令](#the-trade-commands)）。重复的 `--trade-offer` 在两种角色下按顺序交换一个队列：第四步之后 2.7 秒，下一条记录被预览，并在主机的下一次选取时于轮次 0 下被选中（`tests/test_za_host.py`）。

交换动画在第四步之后播放，不携带消息。从该步起：1.1 秒时动画，约 26 秒时收到的 Pokemon 出现在屏幕上，30.2 秒时主机的下一次预览（`0101`，354 字节），约 31.7 秒时玩家恢复控制。

在主机阶段后期形成的席位会被移交：第一个数据报在关联后约 1.4 秒到达，随后没有更新序列 1，主机每秒重复一次会话类型 9，直到它重启自己的 Net（实测 6.5 秒）。wiki 把这个类型编号为开始主机迁移、把踢出编号为 12，而 Z-A 用 13。它背后的代码未被追踪。

## 主机

搜索中的主机也会扫描，并加入一个携带该作品广告与链接码的网络。`bin/za_host.py` 担任主机；`pokeldn.za.host` 与模拟一对主机的交换逐字节核对。

| 从席位起 | 主机发送什么 |
|---|---|
| 0 秒起，每 0.46 秒一次直到被应答 | Net 连接状态 0x11：序列 2，四个槽，主机和加入者都在 12345 |
| 收到 Session 加入时 | 加入响应（类型 2，37 字节）给加入者的 id，更新会话（类型 5，序列 0）到 0x0001 |
| 随附 | INIT 下协议 10 上的身份；协议 11 上再把身份与 `1403b9018269fb308f` 打包，前缀 `00000002` |
| 随附 | Net 更新属性 0x50，每 0.5 秒一次直到 0x51 |
| 从 0.2 秒起 | 向 0x0001 发 RTT 请求，约每秒三次；对加入者的每个请求各回一个 |
| 更新 0 被确认后 1.15 秒 | 更新会话序列 1 |
| 更新 1 被确认后 | 1211 字节的选择记录两次，相隔 60 毫秒 |
| 2.7 秒后 | 预览 `0101` |

与 GBA 应用的主机不同：

- 主机在更新会话中的站点条目携带标识令牌 `0x06`；
- 更新序列被写两次，+1 和 +21 处各一次；
- 属性更新在场景 id 之后携带 `02`，而 GBA 应用写 `01`（CloseParticipation，见下）；
- 广播确认在第 1 个条目报告加入者的流，另外三个为 0xfff0。

零售 Z-A 会加入 `bin/za_host.py` 并在任意链接码（`--code`）下交换。主机在第四步交换后保留会话，并在主机按 B 离开时关闭。`--hold-after-trade` 选择定时关闭，从主机在交换后的第一次预览起计时；总体的 `--seconds` 限制仍然生效。定时关闭、`--seconds` 限制和 Ctrl-C 时，主机会先向已落座的主机移交会话（[主机离开](#a-host-leaving)）；随后停在交换箱上的主机会显示 "Your trading partner chose to quit trading. The Link Trade will now end." 并返回 Link Play。

陷阱：交换存档后未移交就关闭网络，或在交换动画期间发送移交，会在主机上画出 "Error Number: 6"（交换已存档）。

交换后回到交换箱的主机会预览光标下的 Pokemon，所以 `--offer-out` 只保留选择。

### 属性更新

Net 更新属性（类型 0x50）由 `0x2502960` 构建（序列在 NetProtocol+0x160，经由 `0x250f5d0`），并由 `0x250e414` 按大端序序列化。偏移从 0x26 字节 Net 消息的开头算起：

| 线上 | 大小 | 字段 |
|---|---|---|
| 0x04 | 4 | 序列 id，NetProtocol+0x160 |
| 0x08 | 8 | 网络 id，会话属性 +0x90 |
| 0x10 | 2 | 参与者数（`0x25050dc`） |
| 0x12 | 2 | 站点槽，NetProtocol+0x1216 |
| 0x14 | 8 | 会话属性值（`vfunc +0x10`）；LDN 属性把场景 id（NetworkInfo +0x0a）保留在 +0x98 |
| 0x1c | 1 | 接受状态（`0x2505ec0`） |
| 0x1d | 1 | 会话属性 `vfunc +0x80` 的第 0 位 |
| 0x1e | 4 | 系统属性大小（`0x24fe4dc`） |
| 0x22 | 4 | 游戏数据大小（`vfunc +0x50`） |

`0x2505ec0` 在主机地址（+0x1280）和站点自己的地址（+0x1260）都设置之后，或 +0x12d0 非零时，返回 NetProtocol+0x340 处的字节；否则返回 0。它的写入者：

| 写入者 | 值 |
|---|---|
| 网络创建与自动连接任务（`0x2511b94`、`0x2511658`），第三个任务站点 `0x2515714` | 会话属性字节 +0xa6 置位时为 1，清零时为 2 |
| `0x2515434`，来自任务字节 +0xc0（由 `0x2515220` 存储） | 经 `0x250758c`（`NetFacade` vfunc 17）为 1，经 `0x2507828`（vfunc 19）为 2 |
| 主机迁移 `0x250b060` | 该字节为 1 时重跑 1 路径，否则重跑 2 路径 |
| setter `0x2500a9c` | 从 `0x25fdc90` 和 `0x25fe1ec` 写入 1 |
| 收到 0x50 的站点（`0x25035bc`） | 消息中的字节；`0x2502e70` 把它自己的 +0xa6 设为 `byte != 2` |

LDN 会话属性把 +0xa6 设为 `stationAcceptPolicy == 0`（NetworkInfo +0x62，`0x25234b8`）。1 表示接受全部；2 表示该标志为清零。

    0x2515220   0x250758c passes 1, 0x2507828 passes 2; when [[job+0xe0]+0x344] is 1 and 0x2513c0c

`nn::ldn::SetStationAcceptPolicy`（PLT `0x3163b60`）由 LdnProtocol 索引 23（0，接受全部）、24（1，拒绝）和 21（3，白名单）调用。游戏只在它是会话主机时，从 CloseSession 任务的更新 `0x1a25454` 关闭参与，随后策略 1 跟上。

任务构建器 `0x1a228f0` 在两个会话驱程上以 "CloseSession"（哈希 `0x0dd344f64c81e84d`）调用。网络管理器（vtable `0x3c16978`）把驱程保留在 +0x38；它的 setter `0x199e850` 按模式安装：0 无，1 本地驱程（`0x199eaa0`），2 互联网驱程（`0x199ecc0`，用于排位战），3 LAN 驱程（`0x199ef70`）。模式来自 "InitializePia" 任务，由 to-local 序列（Link Trade、私人对战）以 1 构建、由 to-internet 序列以 2 构建；没有调用以 3 构建它，所以 LAN 驱程在 2.0.2 中从不安装。

| 构建器 | 驱程，槽 | 游戏功能 |
|---|---|---|
| `0x19d7a70` | 本地，13（RandomMatchingSeq 的 CloseSession 步骤） | Link Trade 搜索 |
| `0x19a7590` | 本地，19 | 私人对战 |

槽 13 在 `0xc8a224` 处被调用一次，来自 Link Trade（`0xc9f8ec`，会话 "BoxTrade"）和排位战。Link Trade 搜索以第四个参数常量 1（`0xc8a194` 处的 `mov w3, #1`）运行本地驱程的槽 13（`0x19a1310`），所以它的 CloseSession 步骤构建该任务。槽 19 的调用者只有私人对战页面。

在零售 Link Trade 搜索中，广告在席位处持有策略 0；Pia 玩家数（广告数据 +0x16，`e1 01 01 00` 到 `e1 01 02 00`）在 0.6 秒内变为 2，随后在主机唯一的一条 Net 0x50（150 字节，序列 1，接受状态 `02`）之前广告策略 1，并在整个会话中保持 1。它之前没有主机迁移，所以 `02` 来自 CloseParticipation，即槽 13 的步骤 `0x19d7a70`。在 2 个参与者中的 2 个参与的情况下，该策略并没有拒绝容量本可容纳的任何人。

## 离开

一个站点通过两个 `nn::pia::session` 任务之一离开，各自等待对方的回复。调度器 `0x2547490` 读取的会话类型（表 `0x336a9b7`，类型 0 到 17）：

| 类型 | 大小 | 发送者 | 消息 |
|---|---|---|---|
| 3 | 22 | 离开的加入者 | 离开请求：类型、随机 u32、它的常量 id（8，大端）、它的变量 id（2）、地址类型 0、它的 IPv4、端口 |
| 4 | 15 | 主机 | 离开响应：类型、随机 u32、从请求复制的离开者常量 id 与变量 id |
| 9 | 30 | 离开的主机 | 开始主机迁移：类型、主机的常量 id 与变量 id、0、主机的 IPv4 与端口、下一任主机的常量 id 与变量 id、`00 01` |
| 10 | 21 | 类型 9 指名的站点 | 它的确认：类型、它自己的常量 id 与变量 id，然后是主机的 |

`pokeldn.za` 构建全部四种（`build_leave_request`、`build_leave_response`、`build_migration_ack`）。

### 加入者离开

`LeaveMeshJob::SendLeaveRequest`（`0x2557e54`）向主机发送类型 3 并设置 500 毫秒的截止时间；`WaitLeaveResponse`（`0x2558098`）在收到类型 4 时完成，并在每个截止时间重发，共发送四次（计数器 +0x9c，`0x25581e0` 处的 `cmp w8, #2; b.gt`），之后即使没有类型 4 也完成。类型 4 只在 15 字节且第 5 到 14 字节是该站点自己的 id（+0x1b8、+0x1c0）时被 `0x25474f8` 接受；它设置任务的字节 +0x99。主机的类型 3 处理函数 `0x254c5ac`（22 或 34 字节，仅主机）在 `0x254c740` 写出类型 4 并移除该站点（`0x2548500`）。

主机不发送类型 4 的零售 Z-A 会以约 0.5 秒的间隔发送四个类型 3，并在第一个之后 2.0 秒取消认证。`bin/za_host.py` 对每个类型 3 回一个类型 4；`bin/za_join.py` 在 `--hold` 或 `--hold-after-trade` 离开时发送它自己的类型 3，并在收到类型 4 或第四次发送之后继续。

### 主机离开

`LeaveMeshWithHostMigrationJob` 指名下一任主机（`CalcNextHost` `0x255a6fc`），然后 `SendStartHostMigrationMessage`（`0x255a91c`）每秒发送一次类型 9，直到 5000 毫秒的截止时间（`0x255a8c8`），之后任务以 `0x6c0e` 失败。`WaitStartHostMigrationAck`（`0x255abb4`）在字节 +0xe0 置位时立即完成。类型 10 的读取者 `0x2550a64` 只在主机上、且第 11 到 20 字节是主机自己的 id 时才接受 21 字节的消息，并在第 1 到 10 字节是指名的下一任主机时通过 `0x255a630` 设置 +0xe0。

| 加入者的应答 | 零售主机在其类型 9 之后 |
|---|---|
| 无 | 每秒一个类型 9，共五个；Net 0x11 序列 3 每 0.5 秒一次，持续 4 秒；Net 0x40 持续 2 秒；10.8 秒时静默；11.3 秒时网络断开 |
| 类型 10，然后 0x12 `0112000000000003` | 0.04 秒时的 0x11；加入者停留期间，Net 0x40（`01 40 00 00`，源 0）每 0.3 秒一次，持续 4 秒 |

加入者的类型 10 和 0x12 以头部标志 2、目的地 0、数据包 id 0 发出，不带尾部。

Net 0x11 是离开的主机在 `NetDestroyNetworkJob` 迁移形式中的连接状态（`0x2516444`，标志在任务 +0xd8，在断开的站点是主机时置位，`0x2503c44`）：`0x2501930` 递增序列（NetProtocol+0x15c），而字节 29（is-migrating 字节）在 NetHostMigration 状态 NetProtocol+0x12d0 为 1 时为 1（`0x250f084`）。它向每个客户端索取该序列的 Net 0x12；客户端存储序列、设置 NetProtocol+0x308 并应答（`0x2503164`、`0x25035c0`）。主机为每个 0x12 最多等 4000 毫秒，然后每 300 毫秒发送一次 0x40，持续 4000 毫秒（等待超时时为 2000 毫秒），直到它独自一人，并销毁它的网络（`0x251693c`、`0x25169f8`）。

迁移形式与开场的 0x11 有三处不同：序列、字节 26（开场形式中为 1，迁移形式中为 2；含义未被读取）和字节 29。零售与模拟主机都从源 0、目的地 0、数据包 id 0 发出它，头部标志 `0x3`（建立、压缩），不带尾部；0x40 以同样方式发出，标志为 2。类型 9 从主机的变量 id 发往指名站点的变量 id，带尾部。

0x40 在非主机站点上启动主机迁移（`0x2503d44` -> `0x25099a4`，`NetHostMigrationJob` `0x2509da0`）：下一任主机打开网络并为其他人等 6000 毫秒；客户端等 1000 毫秒后重新连接。

Link Trade 在移交时结束：类型 9 的处理函数 `0x2550684` 移除离开主机的站点，而交换场景的更新 `0x95f398` 在会话的站点数（session+0x110）为 1 时以原因 3（`0x95f508`）结束交换。

在两个坐在交换箱中的模拟 Z-A 2.0.2 主机之间，主机中的玩家退出（B，然后 Yes）依次执行类型 9、类型 10、带字节 29 置位的 Net 0x11 序列 3、0x12，然后是在类型 9 之后 0.12 秒的 0x40；另一个站点在 0x40 之后 4 毫秒离开网络，不创建网络，并显示 "Your trading partner chose to quit trading. The Link Trade will now end."

`bin/za_join.py` 用类型 10 应答指名它的类型 9，用 0x12 应答其后的 Net 0x11，并在第一个 Net 0x40 上离开网络（或主机静默一秒之后）。

`pokeldn.za.host.HostSession.leave` 以相同的时序执行同样的离开；`tests/test_za_host.py` 核对了类型 9 和两条 Net 消息。

## LAN 模式

传说 Z-A 2.0.2 有一条它的代码从不走的 LAN 路径。网络启动 `0x1911540` 为模式 1 构建本地服务、为 2 构建互联网服务、为 3 构建 LAN 服务（`0x2523710`）。模式来自网络任务的 `+0x50`（构造函数 `0xc5a5f4`），只通过 `0xc5a3e4(.., mode)` 创建，而它的两个调用者传 1（`0xc57600`）和 2（`0x2a0bcc4`）。Scarlet 的模式 3 调用者在这里没有对应物。
