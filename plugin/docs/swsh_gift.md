# 神秘礼物菜单的本地无线分支

剑与盾的神秘礼物菜单通过本地无线接收神秘卡片：分发端广播一个 LDN 网络，其广播数据以分片形式携带卡片。除标注为剑以外，地址都出自盾 1.3.2 的 `main`；空口行为以零售主机实测为准。

## 菜单

接收方式选择器 `StateSelectReceiveDataBase` 为每个菜单按钮（`L_mystery_top_btn_00` .. `_04`）各有一个子类：

| 状态 | 方法 |
|---|---|
| `StateSelectReceiveDataInternet` | 通过网络 |
| `StateSelectReceiveDataSerial` | 序列号或密码 |
| `StateSelectReceiveDataLocal` | 本地无线 |
| `StateSelectReceiveDataFromBall` | 精灵球 Plus |
| `StateSelectReceiveDataRankMatch` | 排位对战奖励 |

接收状态有 `StateReceiveBase`、`StateReceiveInternet`、`StateReceiveSerial`、`StateReceiveLocal`（`0x01004938`，其自身代码只引用了自己的进度条布局）、`StateReceiveFromBall`、`StateReceiveRankMatch`、`StateReceiveNews` 和 `StateReceiveComplete`。游戏记录键 `fushigi_net`、`fushigi_serial` 和 `fushigi_p2p` 按渠道统计接收次数，与 `yy_battle_single_p2p` / `_net` 并列。

本地无线按钮是 `/bin/message/<lang>/common/mystery.dat` 的第 69 行；第 9 行是搜索消息，第 11 行是「未找到礼物」。

### 应用的状态机

调度器 `0x00FE6F80` 读取 `app+0x718` 处的请求对象：`+0x60` 是就绪标志，`+0x64` 是下一个状态 id。标志置位且 id 不超过 16 时，它经 `0x020641A4` 跳转并构建该状态。`SetNextState(id)` 是 `0x00FF0DE0`，有 63 处调用点。

| id | 状态 | id | 状态 |
|---|---|---|---|
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | （默认，TopMenu） |
| 8 | SelectReceiveDataInternet | | |

本地无线是状态 2，即搜索；然后是 7，即从分发端提供的内容中挑选；状态 7 不接触网络，其列表在进入之前就已填好。是什么把 2 推进到 7 尚不清楚。`0x00FE700C`（`mov w8, w21`）是调度器的跳转表索引。该类的主动虚表是 `0x025737C8`；`main` 中没有任何东西指向这个应用，所以要靠在堆里扫描虚表来找到它。镜像里没有神秘礼物的 protocol buffer 模块。

## 礼物界面的网络

在本地无线界面上，主机广播它常驻的本地游玩网络：本地通信 id `0x0100ABF008968000`（两作相同）、版本 4、场景 id 65535（连接交换上为 60001）、接受策略 ALL、`NodeCountMax` 2、384 字节广播数据、密码 CRC 为零。游戏只在载入后 16 到 31 秒创建一次该接入点；进出神秘礼物不会发起任何 LDN 调用。礼物界面只设置自己的广播数据并启用 Pia 加入过滤器。

在该界面上，游戏每分钟调用约四十次 `nn::ldn::Scan`，其间夹杂 `SetAdvertiseData` 和 `GetNetworkInfo`，从不调用 `Connect` 或 `CreateNetwork`。扫描在 802.11 层是被动的（没有探测请求）。其过滤器只点名本地通信 id 和网络类型；`SessionId` 和 `SceneId` 不过滤。

### 模式字节

`session_config+0x70` 是本地游玩模式。`0x01096730` 经跳转表 `0x02066C14` 把它映射为 Pia 场景 id 和参与者数；`0x010961a8` 经 `0x02066C40` 把它映射为广播数据字节 `0x97`（广播 `0xAF`；游戏的数据从 `0x18` 开始）：

| 模式 | 场景 id | 参与者 | 广播数据 `0x97` |
|---|---|---|---|
| 0 | 无，创建者在 `0x01096764` 返回 false | | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

连接交换是模式 2；礼物界面运行模式 0，不创建会话。进入应用时把模式保存到 `app+0xFE8` 并置 0（`0x01022f08`）；离开时恢复（`0x01023198`）。极巨团体战的主机广播 `0x11`，它不在表中。另一个随界面变化的广播字节只有 `0xB9`（礼物 0x00，交换 0xAA），含义未知。

## 礼物界面上的 Pia 网状网

该界面上的网状网不接纳任何加入者；卡片走[信标传输](#the-card-travels-in-beacon-advertise-data)。加入者完成 0x14 上的站点握手，而它在 0x18 上的网状网加入请求被拒绝：

    02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1

`ProcessJoinRequestJob` 依次运行 `InitialStep`、`CheckApprovalJoin`、`SendJoinRefused`、`SendJoinResponse`、`WaitResponseAck` 和 `JoinSucceeded`。原因 1 只来自应用回调；其余原因由传输检查给出。

| | 剑 | 盾 |
|---|---|---|
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| 原因 1 的存储 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| `MeshProtocol+0x60` 处的 Pia 跳板 | `0x0157fcfc`，全局 `0x04c4b848` | `0x018414b0`，全局 `0x02616a30` |
| `SendJoinRefused` | `0x01553d80` | |
| 传输检查 | `0x0154806c` | `0x017bb2e0` |

当对象 `+0xb0` 为空时，跳板直接批准；否则尾调用它。游戏在 `0x006b47b0` 处把跳板设为加入过滤器 `0x006b41c0`，在 `0x006b5340` 处清除，两处都在模式切换 `0x006a9af0` 之内。

### 加入过滤器 0x006b41c0

`manager` 是 `[0x02610000 + 0x4b0]`，`session` 是 `[manager+0x58]`。四道闸门依次为（取值为礼物界面上的值）：

| 顺序 | 位置 | 检查 | 取值 | 结论 |
|---|---|---|---|---|
| 1 | `0x006b4204` | 阻止列表已启用（`manager+0x21C`）且非空（`+0x1C0`） | 已启用，空 | 通过 |
| 2 | `0x006b8260` | Pia 站点数 `pia_obj+0x1A8` 低于 `session+0x1F0` | 计数 1，上限 0 | 拒绝 |
| 3 | `0x006b827c` | 允许列表标志 `session+0x4f5`；置位则遍历 `session+0x4c0` 处的列表 | 0 | 批准 |
| 4 | `0x006b4248` | 身份 `+0x10` 处的半字（地址第 8 字节，IPv4 下为零） | 0 | 批准 |

`session+0x1F0` 的上限只由 `0x006b9900` 写入，可达路径是极巨大冒险匹配（`0x00bd9b30`）和极巨团体战巢穴（`0x01031c74`）：礼物界面上为 0，主持连接交换时为 2，主持极巨团体战时为 4。在礼物界面上把它写成 8 会接纳一次加入，但入座的场景不发送应用载荷，也不在 0x84 上打开任何东西。

### 传输检查

`0x017bb2e0` 在回调之前运行，返回 `0xFF` 或原因字节。它的对象是 `read_u64(read_u64(main + 0x0262F7B0))`。

| 字段 | 宽度 | 内容 |
|---|---|---|
| `+0xA8` | u16 | 站点数上限 |
| `+0xAA` | u8 | 启用字节；为零时在任何其他检查之前返回 2 |
| `+0xAB` | u8 | 选择计数读取哪个位掩码字 |
| `+0xAC` | u8 | 计数遍历位掩码的多少位 |
| `+0xC4` | u32 | 占用位掩码，在 `[0xAC] == [0xAB]` 时读取 |
| `+0xC8` | u32 | 否则读取的占用位掩码，空闲槽搜索只读这一个 |

| 位置 | 在以下情况返回 0 |
|---|---|
| `0x017bb380` | 计数（1 加上每个置位）`>= max`，或没有空闲槽（`0xFD`） |
| `0x017bb498` | `mesh_obj+0x370` 处的表已满，对照的是 `read_u64(main + 0x02616710) + 0x70` 处的 u16 或其容量 `table+0x48` |
| `0x017bb4d4` | `mesh_obj+0x132` 处的字节，在类型 0x18 事件上置位 |

类型 0x19 事件置位 `mesh_obj+0x131` 时，它返回 4。

## 接收作业与导入器

gfl 网络管理器是 `read_u64(read_u64(main+0x0261CBA8))`（虚表 `0x025819A0`）；全局为空是每个发送存根上的无会话守卫。它在 `+0xD0`/`+0xD8` 处没有条目数组。进入本地无线分支时，`StateReceiveLocal` 的驱动 `0x01004C80`（`state+0x2A0` 上的 case 机）经 `0x010B7100` 构建一个接收作业（构造函数 `0x010B73E0`、虚表组 `0x0257DD88`、轮询 `0x010B74D0`），把它链接到 `manager+0x68`，并在 `state+0xB0` 处安装接收委托（`0x0100504C` 组）。

作业在 `job+0x60` 持有数据接收器（目标 `0x01005BC0`），在 `job+0xE0` 持有进度回调（`0x01005C70`），其消息源是 `job+0x08` 处的会话对象（虚表 `0x0250DAE0`）。它随搜索界面打开而出现，随界面关闭而释放。陷阱：重新进入该界面会在新地址重建作业和接收器的对象。

接收器尾调用 `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170`，即导入器；它拒绝长度不是 0x2D0 字节记录（720 字节，PKHeX 第八世代神秘卡片的尺寸；`0x00ff22f4`）整数倍的主体。每条记录在 `0x00FF2354` 处通过[记录必须携带的内容](#what-a-record-must-carry)的检查，再经 `0x01449820` 过滤，由 `0x00FF3EC0` 实体化。

导入器的第二个参数是路由；它成为卡片 `+0x64`（`0x00FF3F5C`），并在 `route != 0` 时成为头部 `+0x0E`（`0x010B5FAC`）。每个调用者都是某个接收状态虚表第 16 槽中的 lambda：

| 状态 | 路由 | 调用点 |
|---|---|---|
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`、`0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`、`0x0100a2d0` |
| `StateReceiveFromBall` | 2 | `0x0100fc78`、`0x0100fce0` |
| `StateReceiveRankMatch` | 3、4 | `0x01012458`、`0x010124c0` |

除 0 以外的任何路由都会覆写记录的日期（[卡片的日期](#the-cards-date)）。路由 3 和 4 还会在块 `0xa83021c1` 和 `0xce07d358` 中置位字节（`0x00ff24e0..0x00ff26d4`）；路由 0 两者都不碰。

## 卡片随信标广播数据传送

分发端不加入任何网络。它广播一个网络，其广播数据携带卡片，接收方从自己的 `Scan` 结果中重组出它。

礼物是 gflnet3 核心的一个使用者，与交换同步泵分开。核心管理器 `read_u64(read_u64(main+0x02616B80))` 自称 `BeaconCommunication`（`0x02068858`），驱动 `nn::ldn::Scan`、`GetNetworkInfo`、`SetAdvertiseData` 和 `OpenAccessPoint`（包装函数 `0x017978F0`、`0x01794C3C`/`0x01799BE0`、`0x017961B0`、`0x01794CF0`）。Pia 网状网的加入不会改变其中的任何东西。

## 信标主体帧

0x180 字节的 LDN 广播数据由一个 0x18 字节的头部和一个 0x168 字节的主体组成，后者由信标核心封装。

| 主体内偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 2 | 覆盖 `body[2:0x168]` 的 CRC-16/ARC，初值 0，无最终异或 |
| `+0x02` | 12 位 | 网络 id，低 8 位在 `body[2]`，高 4 位在 `body[3]` 的低半字节 |
| `+0x03` 高半字节 | 4 位 | 每次抓包都为零 |
| `+0x04` | 1 | 每次抓包都为零 |
| `+0x05` | 最多 0x163 | 应用载荷 |

网络 id 在神秘礼物、连接交换和极巨团体战界面上都是 `0xD70`。载荷上限是 `0x006c2174` 处的 `cmp x2, #0x163`。

校验和例程是 `0x0065dcb0`（表由 `0x0065def0` 构建），反射 CRC-16/ARC，多项式 `0xA001`。

构建器 `0x006c1fa0` 清零主体，用位打包写入器 `0x006c1830` 把网络 id 写到 `body+2`，把载荷复制到 `body+5`，并把覆盖 `body+2` 起 `0x166` 字节的校验和存到 `body+0`；载荷缺失或超长时改存 `0xFFFF`（`0x006c21d4`）。

## 收到的信标要通过的闸门

`0x006c1be0` 返回 1 表示接纳一个条目。收到的广播（`0x006bb9d4`、`0x006c4b38`、`0x006ca0dc`）只有在它接纳时才进入存储 `0x006c53b0`。任何一项测试失败都会被拒绝：

1. `0x02616b80` 背后的核心对象存在；
2. `body+0` 等于在 `body[2:0x168]` 上重算的校验和；
3. 主体的网络 id 与 `0x02616b88` 背后的半字不同，后者是核心缺失时构建器的回退值；
4. 网络 id 与核心自己的值逐半字节一致（`0x006c1cf0`）：低半字节必须相等；第二半字节不同则接纳；否则第三半字节必须相等。

校验和过期的信标会被扫描到，但从不存储。

陷阱：0x480 字节的 `NetworkInfo` 扫描结果槽（其中包括 `pia_obj+0x3C0`）会完整复制任何主体的 0x180 字节，不论其校验和；那里的标记只能证明收到过。

`0x006c53b0` 只在条目是新的时追加。存储的数组在 `+0x40`，计数在 `+0x48`，容量在 `+0x50`（0x32），互斥量在 `+0x60`；一个条目 0x180 字节，先是虚表指针，主体在 `+8`。两个存储经 `0x006c5300` 交替。

`0x010f6600` 遍历一个存储，经 `0x006c1d50` 读网络 id、经 `0x006c1f80` 读载荷（返回 `body+5`；唯一调用者 `0x010f66c4`），并把载荷交给 `0x010f8cf0`，后者把它存入一个消息对象，供 `[gfl_job+0x68]` 处、虚表 `+0x38` 的处理函数使用。接收方自己的站点信息结构就是这份载荷，所以它的偏移位于广播数据内 0x1d 字节处。

## 轮询重组出的消息

载荷第 0 字节是消息类型。`0x010f6600` 为每个已知类型构建一个类型化视图，指向 `payload+1`：

| 类型 | 视图 | 去向 |
|---|---|---|
| 0 | `0x010f8730` | `0x0110f270`，带 `0x02610958` 背后的对象；接收方自己的信标（站点信息） |
| 1 | `0x010f8830` | `[manager+0x68]` 处的作业，虚表槽 `+0x38` |

在礼物界面上，那个作业就是接收作业，槽 `+0x38`（`0x0257dd88+0x48`；虚表指针是组加 0x10）是它的轮询 `0x010b74d0`，所以类型 1 的载荷会送进导入器。

轮询经 `0x010f7bf0` 读取 `payload+1` 处的十字节头部（字段访问器 `0x010F7A40..0x010F7A80`；发送侧在 `0x010F7C08` 处布局）；分片紧随其后：

| 偏移 | 大小 | 含义 |
|---|---|---|
| `+0` | 4 | 为零，否则轮询立刻返回 |
| `+4` | 2 | 消息总长度 |
| `+6` | 1 | 分片数 |
| `+7` | 1 | 本分片的索引，不低于分片数则拒绝 |
| `+8` | 2 | 重组后消息的 CRC-16/ARC（`0x0065dcb0`） |

每个在途消息一个 0x88 字节的重组上下文，位于 `job+0x160` 与 `job+0x168` 之间，除索引外按头部的每个字段匹配（`0x010f7550`）。`0x010f7100` 把分片复制到 `index * 300`；索引越过缓冲区或该位已置位的分片被丢弃。一条消息最多 65535 字节、256 个分片；720 字节的卡片是 300、300 和 120 三个分片。

`0x010f7610` 报告所有位都已置位后，`0x010f7680` 把 `context+0x18` 与 `0x010f71e0`（经 `0x0065dcb0` 计算的缓冲区）比较，不匹配则返回空。轮询在返回空时跳过接收器（`0x010b77fc`），并在同一次轮询内无论结果如何都抹掉该上下文。

陷阱：校验和错误的消息不会留下痕迹，而空上下文列表也正是消息完成后留下的样子。

## 记录必须携带的内容

| 偏移 | 大小 | 字段 |
|---|---|---|
| `+0x00` | 8 | 日期（[卡片的日期](#the-cards-date)） |
| `+0x08` | 4 | 卡片 id，u16，按整字比较：`+0x0A..+0x0B` 必须为零 |
| `+0x0C` | 2 | 无作用 |
| `+0x0E` | 2 | 游戏版本掩码 |
| `+0x10` | 1 | 标志：第 0 位跳过每卡一次表，第 2 位按卡片日期一次 |
| `+0x11` | 1 | 礼物种类，1 到 5 |
| `+0x12` | 1 | 每卡一次的上限 |
| `+0x13` | 1 | 每卡一次的标记 |
| `+0x15` | 1 | 标题索引 |
| `+0x1C` | 1 | 保留到头部 `+0xf` |
| `+0x20` | | 该种类的载荷 |
| `+0x2CC` | 2 | 把本字段清零后整条记录的 CRC-16/CCITT-FALSE |

版本掩码：导入器调用 `0x007d4270`（盾：`mov w0,#0x2d; ret`），值为 `0x2D` 时对掩码测试 `1 << 1`，否则测试 `1 << 0`（`0x00ff2330..0x00ff2358`）。盾接受第 1 位；`0xFFFF` 通过任一版本；零则跳过。

每卡一次表：`+0x13` 非零时（`0x00ff236c`），如果相册 `+0x1660` 处那张表（块 `0x112D5141` 偏移 `0x1600`；五十个四字节条目，一个半字卡片 id 和一个字节）中某个条目的卡片 id 与 `+8` 处相同、字节与 `+0x13` 相同，`0x01449820` 就拒绝该记录。保留时，如果 `+0x12` 非零且 `+0x10` 的第 0 位清零（`0x00ff152c`），`0x00ff1544` 会调用 `0x014494a0(album, record)`：它把五十个条目整体下移，在 `+0x1724` 追加 `{card id, +0x13}`，当该 id 的、字节非零的条目达到 `+0x12` 个时，在前 49 个中把它们清零。`+0x13` 或 `+0x12` 为零，或 `+0x10` 的第 0 位置位时，卡片每次都会被导入。

最近接收表：`+0x10` 的第 2 位让保留路径调用 `0x01449560(album, record)`（`0x00ff1548`、`0x00ff1558`）：相册 `+0x15c0` 处十个 16 字节条目，`+0` 是 u64 日期，`+8` 是 u16 卡片 id。持有该 id 的条目取用记录的日期（`0x01449650`）；否则第一个日期更早（`0x016cc1f0`，无符号比较）的条目取用 id 和日期（`0x01449804`、`0x0144980c`）。空条目因为日期为零而更早，会被取用。

被接纳的记录复制进一个 `0x338` 字节的结构（记录在 `+0x68`，`0x00ff2380`），交给校验器 `0x010b5de0`；它清零 `+0x2CC`，对全部 0x2D0 字节运行 CRC-16/CCITT-FALSE（多项式 `0x1021`，初值 `0xFFFF`，`0x010b5e60`、`0x010b5f54`）。空指针或长度不是 `0x2D0` 时返回 `0x80000000`，校验和不匹配时返回 `0x80000001`（导入器把它映射为 1，`0x00ff23d0`），其他情况（包括种类不在 1..5 内）返回 0。它填充 `0x68` 字节的头部：卡片 id 到 `+8`，`+0x15` 到 `+0xa`，`+0x11` 到 `+0xc`，`route != 0` 到 `+0xe`，`+0x1C` 到 `+0xf`。卡片对象是 `0x3A8` 字节，把该结构保存在 `+0x70`。

卡片 id：`0x00ff2f50` 把记录 `+0x08` 处的 u32（`0x00ff30c0`）与 16 位 id 比较，因此 `+0x0A` 或 `+0x0B` 处任何非零值都匹配不上，导入器报告 2（在本作中无法获得的礼物）。没有任何东西读取 `+0x0C`。

标题：`+0x15` 索引 PKHeX 以 `text_wondercard8_<lang>.txt` 提供的标题表，卡片被接受之前就显示在列表里。构建器用到的索引：1 宝可梦蛋，3 道具名，21 "{species} (Gigantamax Pokemon)"，34 零花钱，36 服装，39 对战点数。索引 0 只有物种名；索引 11 是 "{species} de {original trainer}"。

种类：1 到 5 经 `0x02067620` 分发；其他值返回成功但不构建任何东西。种类 3 和 5（`0x010b5fd8`）把 `+0x20` 处的字保留到头部 `+0x30`，不构建任何东西。种类 1 进入 `0x010b58f0`，种类 2 复制其道具对，种类 4 进入 `0x010b5bb0`。

语言索引来自 `0x02067650` 处的表（游戏语言到 0..8）。奖章字节送到 `0x00775d50`；超过 127 的索引不设置任何东西。奖章字节全为零的记录会把奖章 0 写三十二次：把列表填满 `0xFF`。

解析器不读取等级和相遇等级；这两个偏移来自认领的卡片。

等级 0：构建器反复取 `r = random & 0x7f` 直到 `r <= 99`，然后取 `r + 1`，在 1..100 上均匀（`0x010b6218`），相遇等级为 0。蛋无论如何都是 1 级（`0x010b6400`）。经验值按物种的成长组计算。

个体值：构建器按 HP、攻击、防御、特攻、特防、速度的顺序检查六个字节；第一个落在 `0xFC..0xFE` 的值把一个满值数量 `byte - 0xFB`（1 到 3）存到 `[sp+0x110]`，并把该物种六项个体值全设为 `0xFFFF`，丢弃其余（`0x010b6300..0x010b63c4`）。否则 32 及以上的字节变成 `0xFFFF`，低于 32 的保留。`0x00766660` 把等级压到不超过 100，并往相应数量的不同随机位置写 31（`0x00766a50..0x00766b04`）；仍是 `0xFFFF` 的每项个体值都随机取 0..31（`0x00766de8`）。因此任一个体值字节为 `0xFC`、`0xFD` 或 `0xFE`，就恰好得到 1、2 或 3 项 31 的随机个体值。

全零的记录会给出一只雄性、坦率、第一特性、个体值全 0 的宝可梦。除非显式给出字段，`pokeldn.swsh.wc8.pokemon_card` 会写入性别 3、性格 `0xFF`、特性 3 和每个个体值字节 `0xFF`，让游戏逐项随机。

性别 3 每次构建随机一次，而一次领取会构建两次：揭示 `0x00fe3720`（`0x00fe3a50`）和兑换 `0x010159d0`（`0x01015a0c`），所以揭示时显示的性别可能与队伍收到的不同。性别 0、1 或 2 跳过随机（`0x00766d94`）。应用和 `bin/swsh_gift_host.py` 在构建卡片时只随机一次性别（`r + 1 < ratio` 时为雌性，`r` 小于 253）；`--set gender=3` 会恢复游戏自己的随机。

## 一张卡片经信标送达，端到端

来自合成信标的三分片 720 字节记录能在未修改的主机上到达导入器。导入器的结果在 `bound+0x2C0`，`bound` 即 `job+0x80`；`0x00ff1fb0` 在它非零时返回它，否则在卡片列表为空时返回 2（版本掩码为 0 给出 2，即「在本作中无法获得」；校验和错误给出 1，即「接收礼物失败」）。日期为零的封装种类 3 记录会显示 2070 年 1 月 1 日。

## 一张卡片送达零售主机

`bin/swsh_gift_host.py` 经 LDN 把每一种礼物送达一台零售版剑。主机只在 LDN 协议 1 上列出卡片，且广播数据要以其自身礼物广播的 Pia 头部开场（[卡带与会话](swsh_session.md)）：随机网络 id、密码 CRC 为零、系统通信版本 5、头部大小 0x18、随机会话参数和八个零字节。场景 id 和应用版本不过滤。标题只看 `+0x15`，与种类无关；种类决定送达什么。

种类 2 的记录只需要种类、道具对和数量。解析器把记录 `+0x20..+0x37` 中恰好六组 id/数量对复制到头部 `+0x30..+0x47`（`0x010b6024..0x010b6080`），并把头部 `+0x0D` 设为数量非零的对数（`0x010b6084..0x010b60e4`）；兑换时对每组数量非零的对调用 `Bag::AddItem`（`0x01015d00..0x01015dd0`）。1.3.2 的道具表有 1607 个条目；`bin/message/<lang>/common/itemname.dat` 中名字以 `★` 开头的都是占位项（其中 1279 到 1578）。PKHeX 把 1607 个 id 中的 51 个命名为 `???`；应用的道具选择器列出 `ItemStorage8SWSH.GetAllHeld()` 的 817 个 id，也就是其卡片检查所接受的集合。

种类 4 是服装（[服装](#clothing)）。种类 3 和 5 把 `+0x20` 处的字加到状态对象 `[[0x2610798]+0x208]` 中被钳制的计数器上：

    kind 3  0x01015e00   [status+0x17c] = min(old + amount, 9999)                  0x014390fc
    kind 5  0x010160b0   [status+0x64]: an amount above 9,999,999 sets 9,999,999;
                         otherwise old + amount, clamped to 9,999,999              0x01438f2c

`status+0x64` 是零花钱（`AddPocketMoney_` `0x014ad5e0`，`GetPocketMoney_` `0x014ad700`）。两种兑换都从记录 `+0x20` 读取数量。

种类 1 的兑换 `0x010159d0` 构建宝可梦（`0x010b6110`；空则返回 0）并交给队伍（`0x01015b78`，虚函数 `+0x28`）。队伍拒绝时，它向盒子存储 `[[0x2610798]+0x220]` 要一个空槽（`0x01408000`、`0x01015bd0`），只有存在空槽时才放置（`0x01406b00`、`0x01015c08`）。它的结果从不被检查；通不过空间检查的卡片到不了这里（[菜单拒绝什么](#what-the-menu-refuses)）。

`Bag::AddItem`（`0x01420790`；背包、id、数量、新道具标志）从道具字段 14 取得口袋（`0x00788c50(id, 14)`，道具字节 `+0x11 & 0xF`），找到持有该 id 的槽或第一个空槽，写入 `id | min(count + n, 999) << 15`；已经到 999 的槽拒绝。一个槽是一个 u32：id 在 0-14 位，数量在 15-29 位，第 30 位是新道具标志。存档块由 `0x0141fae0` 注册，键 `0x1177C2C4`，`0x12F8` 字节。口袋，从 `bag+0x1358` 起：

| 3 | 树果 | 80 |

## 作为礼物信标的板子

`bin/swsh_gift_host.py --save-to-board`（应用中的「保留在板子上」）把卡片的广播周期存到 ESP32 板子上然后退出。之后用任意 USB 充电器供电，板子就自行广播该卡片，按启动器 `--dwell` 的节奏每次三个分片，直到有主机打开它（[便携信标](hardware_esp32.md#portable-beacon)）。每次上电都用同一网络和密钥；广播 nonce 每次从随机值开始。仅靠板子向零售主机送达卡片尚未实测。

| Pokemon HOME | 16 |

画廊中的 949 张剑／盾卡片全部通过校验器 `0x010b5de0`。排除在外的有：740 张礼物与已保留卡片重复、只改了日期或卡片 id 的（多为排位对战奖励），12 张道具是 ★ 占位项的，以及 8 张 Pokemon HOME 卡片的第一个修订版。

### Pokemon HOME

该分组收录画廊中剑／盾的 `HOME Simulated WCs`（卡片 id 9000 起，PKHeX 的 `WC8.IsHOMEGift`），每张都与 PKHeX 活动数据库持有的卡片逐字节相同，标题用 projectpokemon 的。卡片 9000 到 9007 的第一个修订版把所有 PID 固定为 0；保留的第二个修订版让游戏随机一个。

从这些卡片收到的宝可梦不带 HOME 追踪码，而 PKHeX 要求 HOME 给出的礼物带上它：宝可梦由主机生成，所以无论 HOME 追踪码设置如何，PKHeX 都会标记追踪码缺失（[HOME 追踪码设置](gui.md#the-home-tracker-setting)），而 Pokemon HOME 目前接受它。应用用琥珀色框出这些卡片并加以说明。

`+0x10` 处的标志决定主机多久能接收一次卡片（[菜单拒绝什么](#what-the-menu-refuses)）：

| 标志 | 卡片 | 接收 |
|---|---|---|
| 第 0 位 | 130 | 每个卡片 id 一次，之后以消息 7 拒绝 |
| 第 2 位 | 13 | 每个卡片日期一次，每天最多十次 |
| 都没有 | 46 | 每次都可以 |

两张宝可梦卡片的版本掩码为 1 或 2，会被另一版本跳过。

## 服装

种类 4 的记录从 `+0x20` 起携带十二对 u32，先是类别再是索引：状态字节 `+0x105` 为零的玩家用前六对（`+0x20..+0x4F`），否则用后六对（`+0x50..+0x7F`）。该字节由 `0x01424c20` 在状态对象 `[[0x2610798]+0x1e8]` 上读取。PKHeX 的 `MyStatus8` 把玩家性别放在块偏移 `0xA5`，比它低 `0x60`；该对象是否在 `+0x60` 持有该块尚未验证。

解析器 `0x010b5bb0` 把玩家的六对复制到头部 `+0x30..+0x5F`，并把索引不为 `0xFFFFFFFF` 的对数复制到头部 `+0x0D`。兑换 `0x01015eb0` 按同样的判断（`0x01015f14`；记录 `+0x20` 是头部加记录 `+0x88`）再次读取记录中的对，并对每个索引不为 `0xFFFFFFFF` 的对，在衣橱 `[[0x2610798]+0x218]` 上调用 `0x0143a450(wardrobe, category, index, 1)`。该设置函数拒绝大于 14 的类别或大于 1023 的索引，否则设置字节 `wardrobe + 0x68 + category * 0x80 + index / 8` 的第 `index & 7` 位。`(0, 0)` 这对会设置类别 0 的第 0 位；索引为 `0xFFFFFFFF` 的槽跳过。

## 菜单拒绝什么

兑换所选卡片之前，`0x01014a60` 读取种类 `card[+0x7c]`（`0x01014bcc`）、`w25 = 0x00ff1750(card) - 1`（`0x01014bd4`、`0x01014be4`）以及记录标志 `[card+0xe8]` 的第 2 位（`0x01014be8 ubfx w24,w8,#2,#1`），并对种类 1 运行空间检查 `0x013adee0`（`0x01014d68`）。依序：

    0x00ff1750 returned 1, 2 or 3    message 7, 0x10 or 0x11     0x01014d9c cmp w25,#3; table 0x02065360 = 7, 16, 17
    kind 1 and no room               message 8                   0x01014c14 mov w21,#8
    flag bit 2 set                   message 0xF, then state 3   0x01014d38 mov w1,#0xf; continuation 0x010156f0
    otherwise                        state 3, the redemption     0x01014e70

`0x02064f80` 保存 `mystery.tbl` 的标签哈希，每个消息索引一个 u64；`0x01000718` 处的初始化器把条目 k 解析到 `owner+0x5f8+8k`，由 `0x01002da0` 读回。以下取自 1.3.2 的英文 `mystery.dat`：

| 消息 | 标签 | 文本 |
|---|---|---|
| 7 | `msg_o_mystery_win_13` | 你无法获得这个礼物，因为你已经收到过同样的礼物。 |
| 8 | `msg_o_mystery_win_14` | 没有空间容纳另一只宝可梦了。请在队伍或宝可梦盒中腾出空间，然后再试。 |
| 0xF | `msg_o_mystery_win_34` | 这个礼物每天只能接收一次。收到后，要到第二天才能再领取。 |
| 0x10 | `msg_o_mystery_win_35` | 这个礼物每天只能接收一次。今天的份额已被领取，请明天再来。 |
| 0x11 | `msg_o_mystery_win_36` | 每天只能接收 10 个礼物。今天已经领取了 10 个，请明天再来领取。 |

拒绝后的续程 `0x01015740` 在 `+0x80` 存 0，即菜单的第一个状态。被拒绝的卡片既不放置也不保留，原因消失后可以再次领取。

盒子存储没有空槽（`0x013adfb4 cset w20,eq`）且队伍报告已满（队伍虚表 `+0x60`，第 12 槽，`0x013adfc4`；`0x013adfd0 and`）时，`0x013adee0` 返回 1（没有空间）。

`0x00ff1750` 只被 `0x01014bd4` 调用，是接收检查。`[card+0x60]` 或 `[card+0x68]` 为零时它立刻返回 1（`0x00ff1750..0x00ff1770`）；对于路由 0 到 2，它经 `0x00ff17b4` 继续到 `0x00ff1a30`：

    data = album+0x60 (0x014480e0)
    record flag bit 0, and the card id's bit set in the bitmap at data+0x1450 (album +0x14b0)   -> 1
    record flag bit 2 clear (0x00ff1ab0)                                                       -> 0
    the record's day invalid (0x00ff1b84)                                                      -> 3
    ten entries of 0x10 bytes from data+0x1560 (album +0x15c0), 0x00ff1b88..0x00ff1c70:
        entry id == card id and card day <= entry day (0x016cc210, cset ls)                   -> 2
        card day > entry day (0x016cc1f0, cset hi): a free entry
    a free entry                                                                               -> 0
    none                                                                                       -> 3

位图读取取字节 `id >> 3`（`0x00ff1a8c ubfx x9, x23, #3, #0xd`），没有边界检查：位图是 0x100 字节（id 0 到 2047），所以带标志第 0 位且 id 为 2048 及以上的记录会读到它之外，id 从 13000 起则读出该块的 0x17C8 字节。标志第 0 位清零的记录从不读它。该位在接收时置位；写入者未知。

这些条目只由 `0x01449560` 写入，其唯一调用者 `0x00ff1558` 位于 `[card+0xe8]` 上 `0x00ff154c tbz w8,#2` 之后；存入的是记录自己的日期（`0x01449570`、`0x01449648`），不是接收时间。带标志第 2 位的卡片每个卡片日期接收一次、每天最多十次；日期不变地重发会以消息 0x10 被拒绝，而其条目仍保留。

保留路径 `0x00ff13f0`（唯一调用者 `0x01014f74`，在宝可梦被放置之前）更新上述各表，把接收时间写到 `card+0x70`（路由 1 到 4；路由 0 则写记录的日期），并把卡片归档（`0x014480f0`）。它不做任何合法性检查。

构建和兑换都不针对物种检查招式、回忆招式、性格、球、携带道具或形态。构建器 `0x010b6110` 只有一个出口，没有拒绝分支：它按给定内容存入四个招式和四个回忆招式（`0x77bfb0`、`0x77b9a0`；存储在 `0x770c7c`），高于 826 的招式 id 只改变 PP 查表（`0x00781490`）。兑换 `0x010159d0` 只检查种类字节、构建非空，以及队伍（`0x7840f0` 拒绝物种 0 或满员队伍）或盒子（`0x1406b00` 需要空槽）中有空间。

唯一的物种检查在 PokemonParam 构造函数 `0x777f40` 中（`0x778118..0x778148`）：如果某物种的 personal 数据条目第 0x21 字节第 6 位清零（`0x764990`、`0x77f530`），就置上记录 `+0x04` 字中的坏蛋第 2 位（`0x76eb40`），此后每个访问器都读取物种 0x383 的静态替身（`0x776c50`），其名为 "Egg"。菜单路径上没有任何东西拒绝它：卡片仍按物种名列出并揭示，而队伍收到一只空白的 "Egg"。高于 898 的物种读取 personal 条目 0（该条目存在），所以不会被标记。绝不要发送剑与盾中不存在的物种；桌面应用的 PKHeX 检查会拒绝。

性别是构建唯一会修正的字段（`0x777490`，`0x7774a4` 处读取 personal 字段 0x14）：比例 0、254 和 255 分别强制为雄性、雌性和无性别（表 `0x1c4d2d0`）；其他比例下请求的 2 会变成 0（`0x7774d8`）。构建器把记录性别 3 变成 0xFF，即随机（`0x010b62ac`）。

## 卡片的日期

记录的前八个字节是相册显示的日期，一个绝对 UTC 时间的小端 u64 位域。没有公开的映射表命名它；PKHeX 的 `WC8.cs` 从 `+0x08` 的卡片 id 开始。

| 位 | 字段 |
|---|---|
| 0-5 | 秒 |
| 6-11 | 分 |
| 12-16 | 时 |
| 17-21 | 日 |
| 22-25 | 月，1 到 12 |
| 26-39 | 年，绝对 |

`0x016cc5e0` 用 days-from-civil 把它转成 posix 时间（其中含有 `146097`、`1461` 和除以 100 的常量），值等于 `main+0x2616900` 背后的哨兵时返回 0。相册绘制 `0x00ffbaa0` 把它传给 `nn::time::ToCalendarTime`（`0x00ffbaf0`），因此主机的时区生效，失败时回退到 `ToCalendarTimeInUtc`。年份用两位数字绘制。

日期为零时显示 01/01/2070。

只有本地无线来的卡片保留自己的日期。其他每条路由都用 `nn::time::StandardNetworkSystemClock::GetCurrentTime`（`0x00ff3f8c` -> `0x01449ca0`；PLT `0x01900050`，GOT `0x0260fbb8`）覆写这八个字节，由 `0x016cbfd0` 和 `0x016cc1d0` 打包。

分发端在发送前用计算机当前的 UTC 时间填充空日期并重新封装校验和；非零日期原样保留，导出的文件也保留其原始日期。宝可梦的相遇日期与相册日期是分开的。

## 相册把卡片保存在哪里

相册是存档块 `0x112D5141`（PKHeX 的 `KMysteryGift`），`0x17C8` 字节，由 `0x01447eb0` 载入 `+0x60` 处的相册对象，由 `0x01449d90` 写回。它保存的是重新编码的头部，从不保存 720 字节的线上记录或其字符串。`tools/switch/swsh_save.py` 把 `main` 读进各个块（PKHeX 的 SwishCrypto：对整个文件的静态 xorpad，每块一个以其密钥为种子的 XorShift32 流，两个常量之间对加密体做 SHA-256）；`--key 112d5141 --out FILE` 写出这个块，`--patch KEY OFF HEX --write OUT` 改写某个块的字节并重新封装文件。

    0x0000  50 slots of 0x68 bytes, newest in slot 0; an insert moves every slot down one
            (0x01449880 indexes them, cmp w1, #0x31; a slot is in use when its +0x0C is non-zero)
    0x1450  0x378 bytes, zero in every save read; the last-receipt table is 0x1560..0x15FF
            (album +0x15c0) and the once-per-card table 0x1600..0x16C8 (album +0x1660)

一个槽就是导入器从记录填充的 `0x68` 字节头部：

    +0x00  8    the record's date bitfield (zero draws 1 January 2070)
    +0x08  u16  card id
    +0x0A  u16  the record's byte at +0x15 (0 on Pokemon cards, 1 on kind-3, 3 on an item card)
    +0x0C  u8   kind: 1 Pokemon, 2 item, 3 the empty kind
    +0x0D  u8   kind 2: how many of the six item quantities are non-zero; 0 otherwise
    +0x0E  u8   1 when the card came by any route but local wireless
    +0x0F  u8   the record's byte at +0x1C (1 on kind-3 cards)
    +0x12  u16  level (kind 1)
    +0x30  u32  species (kind 1); kind 2: the item pairs (u16 id, u16 quantity) as at record +0x20
    +0x38  4 x u32  moves (kind 1)
    +0x48  26   nickname, UTF-16 (kind 1)
    +0x62  u8   3 on every Pokemon card

把某个槽的 `+0x0C..+0x62` 清零就会从相册移除该卡片；它送出的道具仍留在 `MyItem`（`0x1177C2C4`）中。

## 排空存储的每帧更新

`0x010f65a0` 是 gfl 网络管理器的每帧更新（管理器来自 `0x0261cba8`）：它经 `0x006c5300` 排空 `manager+0x60` 处的接收器，遍历条目，并在每次发现存储非空时盖上 `manager+0x80`。它唯一的调用者是 `0x01109240`，位于 `0x00f1df30` 之内，后者经一个注册的回调到达。

陷阱：在某些会话中存储从不被排空，`manager+0x80` 保持不变；读取任何信标结果之前先确认它在前进。原因未知。
