# 朱與紫

寶可夢 朱（`0100a3d008c5c000`）與 紫（`01008f6008c5e000`）是原生 Switch 作品，Pia 被連結進
`main`。兩者都能以兩種角色與零售主機進行交換：`bin/sv_host.py` 為主機的離線連線交換搜尋充當
主機，`bin/sv_join.py` 加入主機的網路。零售版 紫 會加入一個廣播 朱 的本地通訊 ID 的主機，而它
自己的搜尋網路也廣播 朱 的 ID（`0x0100a3d008c5c000`，應用程式版本 21，場景 4）。

兩個啟動器也都能以任一角色執行本地太晶團體戰（[太晶團體戰](sv_raid.md)），並且主機可以向
一臺主機交換一隻官方禮物寶可夢（[模擬神秘禮物](gift_simulated.md)）。
[聯盟集友圈](sv_union_circle.md) 以訪客身份加入主機的集友圈，向它的主機上報藍莓任務完成情況，
並在主機的玩家周圍生成由使用者設定的野生寶可夢。

地址是更新 4.0.0 解壓後 `main` 的偏移（`tools/switch/nso_read.py`）：text
`0x0..0x343fc90`，rodata 從 `0x3440000` 起，data 從 `0x4383000` 起。

## 搜尋中的主機會廣播什麼

連線交換搜尋在充當主機（每次都是新 SSID）與掃描之間交替，在通道 1、6、11 之間跳變；一個主機
階段約持續五秒。

    local_communication_id  0x0100a3d008c5c000, Scarlet's, on both versions
    ldn protocol            1            advertisement version 4
    scene_id                4            app_version 21
    security_mode           1            accept_policy ALL
    participants            1/2
    application_data        132 bytes

應用程式資料是 0x5C 的 Pia 系統屬性塊加上 40 個遊戲位元組：

| 欄位 | 值 |
|---|---|
| 系統通訊版本 | 0x15 |
| 應用程式通訊版本 | 0x15 |
| 使用者密碼 | 十六個零位元組，無連線碼 |
| 啟用玩家上限 | 1，玩家數為 1，一旦有一個站點入座則變為 2 |
| 玩家名 | 一個位元組、一個空格、UTF-8 |
| 那 40 個遊戲位元組 | 為零，或在遊戲 `+0x21` 處的一個非零值（見到過 `fb149700`），每隔幾秒交替一次；第二臺主機在任一種情況下都會關聯 |

`pokeldn.sv.build_advertise_data` 逐位元組復現了這兩種信標。

## 遊戲執行的協議

對一對零售主機的被動抓包顯示了 Net、RTT、0x80 和 0x81，全部發往該會話 `/24` 的廣播地址，
接收方的可變 ID 位於明文尾部。其餘六個是單播（兩臺 Switch 2 主機之間的 802.11ax），在抓包中
不出現。

遊戲的初始化 `0x17ff030` 按順序建立：埠 0 上的 Reliable `0x7C` 與 BroadcastReliable `0x80`、
Unreliable `0x68`、埠 1 和 2 上的 Reliable 與 BroadcastReliable、`[0x44dfcd0]` 的
StreamBroadcastReliable `0x81` 埠（線上為八個）、Clone Clock `0x77` 與 Clone Atomic `0x74`。
Pia 還會加入 Net、RTT、Session `0x98` 與 MonitoringData `0xA4`；僅當網路工廠啟用 NAT 穿透
時才加入 NatTraversalResult `0xA0`（`0x6d3138`），而本地網路不會。

| id | 協議 | 版本 |
|---|---|---|
| `0x2C` | Net | 0 |
| `0x58` | RTT | 3 |
| `0x68` | Unreliable | 1 |
| `0x74` | Clone Atomic | 0 |
| `0x77` | Clone Clock | 0 |
| `0x7C` | Reliable | 2 |
| `0x80` | BroadcastReliable | 3 |
| `0x81` | StreamBroadcastReliable | 3 |
| `0x98` | Session | 0 |
| `0xA4` | MonitoringData | 0 |

傳說 阿爾宙斯 列出相同的十個版本。一對零售主機的開場：

    +0.00   the joiner associates
    +0.06   host: Net 0x11 (station list), 0.12 s later Net 0x50
    +0.14   host: acks all eleven streams, opens two
    +0.89   joiner: RTT request, acks all eleven, opens two
    +0.97   host: first records on 0x81 port 0
    +1.26   joiner: first records on 0x81 port 1

### Net 0x11，站點列表

佈局與 傳說 阿爾宙斯 相同，四個站點槽各 21 位元組：

    01 11 0054          version 1, type 0x11, payload size 0x54
    00000002            sequence id
    9141                host variable id, fresh every session
    eb9b2220f1480000    host constant id, the LDN MAC reordered
    0000000097392e8a    network id, the low four bytes crc32(ssid[1:16])
    01                  is network open
    0004                station slots
    00                  is migrating host
    ...                 four stations: migration state, ranking (host 0, joiner 1, empty 0xff),
                        one byte, 16 address bytes, big-endian u16 port (12345)

`01 40 00 00` 是一個裸的 NetStartHostMigration，由移交角色的主機發送。零售版 朱 在從搜尋狀態
充當主機時，會在它交給加入方的座位上重複傳送它（[什麼決定一個座位](#what-decides-a-seat)）。

主機寫入四個站點槽，這是 Pia 的數量；遊戲的上限是兩個。只有兩個槽時，加入方遊戲不傳送任何
內容，以 ICMP 埠 12345 不可達來回應 Net 0x11，並在關聯後 5 秒斷開（49 次加入中為 4.98 到
5.01 秒）；有四個槽時它回應 Net 0x12 併發送它的 Session 加入請求。

### 十一條流

    0x80  BroadcastReliable         ports 0, 1, 2
    0x81  StreamBroadcastReliable   ports 0 to 7

兩個站點大約每秒用 `pokeldn.ldn.reliable5` 的批次確認來確認全部十一條流：四個條目、站點位元組
為零、條目 *k* 是站點 *k* 最高序號加一、目標位計數 3、點陣圖中包含對端的位。一個站點用一條
十一位元組的 INITIALIZED 訊息開啟兩條流，並在其站點索引對應的埠上傳送記錄（如同
`pokeldn.pla.data_exchange`）。

| 站點 | 開啟的流 | 傳送記錄的埠 |
|---|---|---|
| 主機，索引 0 | 0x81 埠 1 和 5 | 0x81 埠 0 |
| 加入方，索引 1 | 0x81 埠 0 和 4 | 0x81 埠 1 |

開啟時的載荷在埠 0 和 1 上是 `0000000000f38800000000`，在 4 和 5 上是
`00 <port> 00 00 0ff0 0800000000`：一個 StreamData kind 0，提交一次 0xF388（傳輸 0）或
0xFF008（4 和 5）的接收。0xFF008 傳輸在交換中從不傳送。
`pokeldn.sv.streams` 構建了這一切；`tests/test_sv.py` 將其固定到零售位元組。

### Pia 訊息標誌

兩個零售站點都會發送（未使用 阿爾宙斯 主機的建立標誌）：

| 訊息 | 標誌 |
|---|---|
| RTT、流的開啟、一條記錄的首次傳輸 | 0x00 |
| 再次傳送的記錄 | 0x40 |
| 批次確認 | 0xA0 |
| 主機的 Net 0x11 和 0x50 | 0x31 |
| NetStartHostMigration | 0x11 |

訊息的目標欄位始終為零。標誌 0x40 來自 `ReliableSlidingWindow` 傳送迴圈 `0x6f0638` 的
`w4 = 1`（當傳送計數 `[slot+0x14]` 為零時為 0，`0x6f0908`；重發 `0x6f0a9c` 或提前傳送
`0x6f0c38` 時為 1），由 `0x6e7250` 存為資料包寫入器選項塊的第 0 個位元組。

### RTT

十一位元組：kind、大端 u64 時鐘、大端 u16 目標。請求是 kind 0、目標 0；應答是 kind 1，攜帶同一
時鐘和請求方的可變 ID，在零售機上於 20 毫秒內完成。

RttProtocol（虛表 `0x43e5a28`）在 `[proto+0x60] + index*0x40` 處為每個站點保留一條 0x40 位元組
的記錄：取樣計數 `+0`、環形緩衝區頭 `+4`、容量 9 在 `+0x10` 且環形緩衝區緊隨其後內聯存放、
一箇中位數快取在 `+0x3c`，對應 `+0x38` 處的計數。一個取樣是當前時鐘減去被回顯的時鐘
（`0x6f34b4`）；小於等於零的取樣會被丟棄（`0x6f34e0`）。請求以 `[0x46d1528]` 的間隔發出，
直到每個環形緩衝區都填滿，之後以 `[0x46d1520]` = 500 的間隔發出（在 `0x6f2fcc` 處以及由遊戲
在 `0x1e7c2bc` 處寫入）。站點事件 0 或 1 會清除該站點的記錄（vfunc11 `0x6f3bd8`）：新座位沒有
取樣。

GetRtt（`0x6f4498`；帶計數 *n* 的 `0x6f44bc`）在沒有采樣時返回 -1，否則返回最近
min(count, *n*) 個取樣的中位數；最小值 `0x6f44e4`、最大值 `0x6f4508` 與取樣計數 `0x6f452c`
位於其旁。唯一的呼叫者是 SessionTransportAnalyzer 的監控副本（`0x6f9ab0`..`0x6f9ad4`）以及
`ReliableSlidingWindow` 的重傳截止時間 `0x6f0d14`，後者在 `0x6f073c` 處從傳送迴圈呼叫：

    deadline = now + [window+0x80] + 1.4 * (max over the destinations of GetRtt(count))

沒有采樣時，`0x6f0d14` 返回未排程標記 `[window+0x5c]`：訊息在入隊時傳送一次
（`0x6f1bbc`..`0x6f1bd4`），並在 `0x6f0a18` 處被跳過，直到某個取樣重新武裝它
（`0x6f09f4`..`0x6f0a08`）。沒有 RTT 取樣的視窗永不重傳。

建構函式 `0x6eeea8`（呼叫者 `0x6e69f8`、`0x1800038`）把 `[window+0x80]` 設為
`ticks_per_second * 33 / 1000`（`0x6eef34`..`0x6eef74`；633,600 tick，在 19.2 MHz 下為
33.0 毫秒），標記 `[+0x5c]` 為 0，基準序號 `[+0x30]` 為 1，自身索引 `[+0x10]` 為 0xfd，
壓縮 `[+0xa4]` 為 1，提前傳送上限 `[+0x88]`、`[+0x89]` 為 0。唯一更晚的寫入者是 vfunc17
`0x6f1f98` 中的 `0x6f1fc8`（來自 `ReliableProtocol::vfunc17` `0x6eebbc` 與
`BroadcastReliableProtocol::vfunc17` `0x6e6818`，無已知呼叫者）。傳送迴圈每 16.7 毫秒的幀執行
一次，因此重發會在等於或晚於 `33 + int(1.4 * RTT)` 毫秒的第一個幀發出：RTT 為 34 毫秒時是
83 毫秒，358 毫秒時是 550 毫秒。

### 記錄

一條記錄就是一個帶 ZLIB 標誌的可靠訊息，一個 4 KB 視窗（`484b`）的 zlib 流，解壓後為
1395 位元組，`[window+0x70]`：這是 Pia 的 StreamData 頭
（[協議 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）之下的一個
0x81 傳輸的一個分塊：

    +0x00  1   StreamData kind: 1 the first chunk of the block, 2 a later chunk
    +0x01  1   transfer id, 0
    +0x02  1   percent of the block delivered after this chunk
    +0x03  4   zero, the capacity field of a kind 0
    +0x07  4   big-endian u32 0x00000568, the 1384 bytes that follow

一個站點的塊是 0xF388（62,344）位元組：45 個 1384 位元組的分塊和一個 64 位元組的分塊，ID 從 1 到
46，百分比位元組為 `floor(k * 1384 * 100 / 62344)`（2、4、6、8、0x0b、…、0x37 對應 25、
0x52 對應 37、0x64 對應 46）。第一個分塊攜帶螢幕上顯示的夥伴：

    +0x0b  4   trainer id, then secret id
    +0x0f  1   version: 50 Scarlet, 51 Violet
    +0x10  1   gender
    +0x11  1   language
    +0x12  1   ball-throw style, 1 the original
    +0x13  26  the player name, UTF-16 little-endian, NUL-padded; --trainer-name on both launchers
    +0x2d  22  the account identifier, ASCII, `u-` and twenty characters
    +0x53  8   story progress, little-endian: 1 the main story cleared, 4 The Indigo Disk cleared

該塊在 `0xa52f88`..`0xa530a0` 處的棧上構建：先是來自存檔的訓練家，然後來自另一個存檔塊的
投球風格（`0xa53054`），接著是賬號標識（`0x1a61a00`），最後是進度字，即遊戲儲存在
`0x473a040` 處的某個指令碼函式的返回值（在 `0xa5309c` 處呼叫）。原生 `f20A702BD`（`0x877560`）
安裝它；在 3.0.1 指令碼轉儲中，`BattleNetworkNetReceiver` 傳入一個從 0 開始的函式，當
`FSYS_SCENARIO_GAME_CLEAR` 置位時設為 1，當 `FSYS_SCENARIO_GAME_CLEAR_SU2` 置位時或上 4。
`pokeldn.sv.reference` 傳送 1；賬號標識全零的零售版 紫 傳送 0。

遊戲的指令碼按以下順序註冊的原生 getter 讀取某個站點的玩家：`PlayerId`、`RomCode`、`Sex`、
`LanguageId`、投球風格、`NameStrBuf`（3.0.1 指令碼轉儲中的 `RegisterPlayerData` 與戰鬥初始化；
投球風格就是存檔自己的 `ballThrowId` 所填的槽位）。在零售存檔上，ID 對、版本、語言和名字都
取自該存檔自己捕獲的寶可夢，無論它提供哪隻寶可夢。為接收方玩家制作的禮物會讀取它們
（`reference.identity_trainer`，[為接收方玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

分塊 2 到 24 是高熵的；25 到 46 為零。一個站點會一次性發送它的整套內容，通常第一個資料包裡
是 ID 1、25、26 到 36 和 46，第二個裡是 2、37 和 38 到 45，然後 3 到 24 每個資料包一個
（48 套零售資料中有 41 套如此），52 次中有 46 次在 0.19 秒內完成。相同的零分塊在 0x00 的存在
位元組之後傳輸，所有頭欄位都繼承（[訊息分幀](pia.md#message-framing)）。
`pokeldn.sv.streams.decompress` 讀取它們。

`pokeldn.sv.reference` 在 0x7C 埠 0 上提供一個站點的 44 條記錄及其兩個身份分片，它們錄製自
一個模擬的 朱，其玩家為 `Player`、賬號標識未設定。除非給出 `--record-set`、`--send-on-open`
或 `--no-identity`，`bin/sv_host.py` 與 `bin/sv_join.py` 會發送它們。

### 零售確認，以及重傳的洪流

零售站點用連續段之後一個的 ack id、等於它的欄位 0x50 以及一個掩碼來確認對端的記錄流，掩碼中
位元組 *k* 的第 *b* 位對應 ID `ack_id + 1 + 8k + b`：一個持有 ID 1 到 4 和 7 到 38 的主機發送
`0005 0005 feffffff01`。低於對端自身 `lowest_pending` 的 ID 視為已持有。
`pokeldn.sv.streams.ack_position` 構建它；`bin/sv_join.py --ack-highest` 改為傳送所見最高
ID 加一。

主機每一輪重發所有未確認的記錄，標誌 0x40，最小 ID 優先，每個資料包一輪。輪間隔是
`[window+0x80] + 1.4 x RTT` 向上取整到幀：RTT 為 0.015 秒時是 0.065 秒，0.36 秒時是
0.53 秒。在較小的 RTT 下，這相當於每秒數百條記錄，足以佔滿一塊板子的序列埠線
（[序列埠上限](hardware_esp32.md#the-serial-ceiling)）。無論確認延遲如何，主機的
`lowest_pending` 都會在整套發出後約 0.5 到 1.0 秒離開 1，因此在此之前應答 RTT 會讓它重發
加入方已經持有的記錄。`--rtt-delay 0.3` 讓 RTT 應答晚 0.3 秒，從而使輪間隔高於該延遲並停止
重發。

`--leave-on-migration N` 在 Session 型別 7 之後 N 秒結束座位，`--announce-timeout SECONDS`
離開一個未被通告的座位；兩者都會重新掃描。`bin/sv_join.py` 立即確認一條新記錄，對重複記錄
每條流最多每 50 毫秒確認一次（`--repeat-ack-gap`）。

沒有 RTT 取樣時，0x81 流永不重傳
（[協議 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）：丟失的
記錄保持待定，對端永遠不會被通告。通告任務沒有 RTT 門檻。缺失的身份記錄會讓 BoxTrade 任務
停留在狀態 1（`+0xb8`），已完成的槽計數在 `0x1e51ae8` 處為 1 而非 2。兩個啟動器都會重試
待定的身份記錄（[最低待定與 5 和 6 處的間隙](#lowest-pending-and-the-gap-at-5-and-6)）；
`tests/test_sv_identity_loss.py` 覆蓋這一點。

### 抓包中的 A-MSDU 幀

兩臺主機都會把多個 MSDU 打包進一個 A-MSDU 幀。被動抓包必須拆解子幀，否則會丟掉大部分 Pia
資料包（一次抓包中，不拆時為 313 個可讀，拆後為 3667 個）。

## 區域網模式

朱 4.0.0 從它的指令碼啟動區域網模式。選擇器 `0x17fde60` 接受模式 1（本地，`0x17fe5c0`）、
2（`0x26894f0`）或 3（`0x2689600`，區域網服務）；模式是全域性變數 `0x475ea40`，由 `0x17fddc0`
從網路任務的 `+0x50` 設定（建構函式 `0x188f488`）。`0x188e998(.., mode)` 建立該任務，並以
1（`0x18871a4`）、2（`0x1de28a4`）和 3（`0x1de6650`）呼叫。模式 3 的呼叫者 `0x1de653c` 執行
NetworkUse、InitializeSocket 和 InitializePia，並且是 `0x4430500` 處表中的 Lua 繫結
`f6597D2A6`。

遊戲的 Lua（`arc/scriptluabinrelease*.blua.trpak` 中的六個分塊；`be21e654` 是 `main`）從戰鬥
選單到達它。網路對戰接收選單（類 `C6A68AA55EC501641`，狀態 `SET_STATE_NETWORK_VS_RECEPTION`，

`0x1de653c`。

在模擬的 朱 4.0.0 中，同樣的搜尋會發出一個網路連線請求（nifm；沒有網路時遊戲顯示錯誤 11），
在 49152 和 35000 上開啟 UDP 套接字，向 35000 埠的子網廣播發送一個 317 位元組的瀏覽請求，
然後作為主機等待。向它 35000 埠傳送的瀏覽請求會得到 620 位元組的應答，其中寫明主機的 IPv4
地址和 Pia 埠 49152（`c0a8011f`、`0xc000`）。開頭那一次廣播解釋了那次安靜的零售抓包——它
正是在這之後開始的。

|---|---|
| 瀏覽請求，317 位元組 | `00 00000000 0e000000 00000000 01000200 02000f03 01000000 00000000 01` |
| 瀏覽應答，620 位元組 | `01 0000022d 00000000 1f01a8c0 007c0a00 15` |

兩臺主機都用 ZL + ZR 搜尋時能否互相找到，尚未測量。

## 連線碼

連線碼在廣播中搭載兩次；場景 ID 保持為 4。使用者密碼就是該碼，用 NUL 填充到十六位元組，再與
`e5ab19ed742b6d40885998bf968aa166` 異或，這是同一遊戲金鑰下 傳說 阿爾宙斯 的掩碼
（[docs/pla.md](pla.md)）。遊戲位元組在 +0x00 處以明文攜帶該碼，並在 +0x24 處以 u32 攜帶其
長度。`pokeldn.sv.build_advertise_data(code=...)` 逐位元組復現一臺用 12345678 搜尋的零售主機。

搜尋中的主機只會加入廣播其連線碼的主機（`bin/sv_host.py --code`）。一臺用連線碼充當主機的
零售主機接受了一個不廣播任何碼的加入方。`bin/sv_join.py --code` 只加入用該碼搜尋的主機。

只有搜尋中的主機會檢查連線碼，且只在它掃描的網路中檢查。它的選擇器 `0x26e955c`（在加入前由
`0x272d838` 呼叫）在用連線碼搜尋時跳過沒有密碼的網路（`0x26e95f4`），在不用連線碼搜尋時跳過
有密碼的網路（`0x26e960c`）。然後它用 FNV-1a 64 對從 +0x00 到第一個 NUL 的遊戲位元組和它自己
的碼做雜湊（素數 `0x100000001b3`，偏移基 `0xcbf29ce484222645` 在 `0x26e96c8` 處載入，不是
標準基），除非兩者相等否則跳過該網路（`0x26e972c`）。它既不讀取密碼的值，也不讀取 +0x24 處
的長度。

主機不比較加入方傳送的任何內容。LDN 關聯使用固定口令，而 Session 加入請求沒有密碼欄位。
Pia 對連線站點的密碼檢查——Net 0x32 處理器 `0x69ec50` 中的結果 7（`0x69ee5c`、`0x69ee70`）
——需要一條 Net 0x32，而它唯一的傳送者 `0x69d42c` 受協議 vfunc 48 控制：在 `LdnProtocol`
中為 0（`0x6a2fac`），在 `LanProtocol` 中為 1（`0x6ba278`）。在加入方一側，LDN 連線執行
Pia 的網路檢查 `0x6a22c4`，其密碼比較（`0x6a24a4`）被關閉（`0x6b0d90`）。

已加入的主機不會再次檢查該碼。Net 0x50 處理器 `0x69ea3c` 校驗系統屬性大小（0x5c）、應用程式
資料大小（至多 0x124）和四個 Pia 身份欄位（`0x69d9d8`），把位元組複製進網路屬性
（`0x69d8a4`）並以 Net 0x51 確認；它不比較系統屬性或遊戲位元組中的任何一個位元組。在 LDN 上，
這份副本落入快取的廣播資料，下一次 `nn::ldn::GetNetworkInfo`（`0x6b30d4`）會覆蓋它。遊戲只在
選擇器中以及 UpdateSessionSetting（`0x26e63b8`）中讀取一個會話的前 0x28 個遊戲位元組，後者會
重寫它自己的會話；另外兩個讀取者（`0x268e988`、`0x268e9bc`）只讀取 +0x28 之後的內容。加入
的主機把它的碼保留為自己的 Pia 站點密碼（加入物件 vfunc `0x274bdb8`，設定器 `0x6a208c`），
它只在充當主機時才廣播它。連線交換的埠 2 型別 1 來自 BoxTrade 任務的狀態 2
（`0x1e51b68`）：kind 1、靜態空名字 `[0x46d3e30]`、無資料。

## Session 協議

`nn::pia::session::SessionProtocol`（id vfunc `0x6d9f3c` 返回 0x98）位於 `JoinMeshJob`、
`CreateMeshJob`、`LeaveMeshJob`、`JoinSessionJob` 以及 `SessionPacketReader`/`Writer` 之旁；
網格加入沿用 傳說 阿爾宙斯 的實現。Session 訊息在資料包頭中攜帶對端的可變 ID，沒有尾部，因此
走單播。加入方在加入請求的源位置 ID 中宣告它的可變 ID；主機在關聯後 0.14 秒命名它。

### Session 加入請求

寫入器 `0x6d5464`..`0x6d58b0`，主機側解析器 `0x6d5aa4`。佈局與零售版 傳說 阿爾宙斯 相同
（`docs/pla.md`，Session 加入請求；`tests/test_pla_session_v11.py` 中為 115 位元組），由
`pokeldn.ldn.pia6.build_session_join` 構建：

    +0    1    type 0
    +1    1    protocol count, ten
    +2    2n   (id, version) pairs, walked from the protocol manager's list
    +22   4    random, xorshift128 seeded from the system tick (`0x6c70a8`, `0x6c7184`)
    +26   12   source location id: u64 constant id, two zero bytes, u16 variable id, big-endian
    +38   1    NAT mapping, two bits
    +39   1    private-IPv6 flag
    +40   32   identification token
    +72   1    address kind, 0 for IPv4 (1 puts an 18-byte IPv6 address in place of the six bytes)
    +73   4    source IPv4 address
    +77   2    source port, big-endian
    +79   12   destination location id, the host's
    +91   1    player count
    +92   1    a flag the job sets to 1
    +93   ..   player records: a 16-byte id (`1` then `0` as two big-endian u64), a big-endian u32
               name length, a kind byte (1), the name

零售加入方的那一個玩家名是一個空格。資料包頭攜帶目標可變 ID 0 以及作為源的加入方 ID；每次
重發時訊息標誌為 `0x01`（跳過源檢查）。主機按順序檢查：

1. 協議數量等於它自己的；否則不傳送任何內容。
2. 每個版本都等於主機的版本（`0x6ed1b8`）；否則返回狀態 3，附上 ID 與主機的版本。
3. 目標位置 ID 是主機的常量 ID 與可變 ID；否則丟棄。
4. 源常量 ID 與地址不是主機自己的。
5. 已知的常量 ID 會再次得到狀態 1；已關閉的會話得到狀態 5；主機側監聽者可以以狀態 4 拒絕。

加入響應（型別 2，43 位元組，`0x6d6390`）是 阿爾宙斯 的佈局：type、protocol id、version、
status、一個大端 u32、四個隨機位元組、兩個位置 ID、路由位元組 A 和 B、站點索引、加入順序、站點
更新必須達到的序號。加入方以 13 位元組的型別 6（`0x6d80a4`）回應型別 5 更新：type、常量 ID、
兩個零位元組、已應用的序號（`pokeldn.ldn.pia_connect`）。

## 座位，以及其上的身份洪流

零售版 朱 主機在 16 毫秒內接受加入請求，傳送一個 41 位元組的加入響應（狀態 1，無路由位元組）和
一個無路由的站點更新，並在 0x81 埠 0 上流式傳送它的身份。不接受加入方確認的主機會一直重發
每條記錄直到座位結束，在零售機上約每秒 350 條。主機也可以改為傳送 Session 型別 7，把它的
角色交給加入方（[什麼決定一個座位](#what-decides-a-seat)）。

### 讓主機把訊息計為確認的標誌

帶第 5 位標誌（ZLIB，`[msg+0x29]`，`0x6efc80`）的訊息會在站點解析之前於 `0x6e9984`
（`0x69804c`，zlib 解壓 `0x2801d0`）中解壓；失敗時返回 0x2C03（`0x6efd5c`）。標誌 0xA0 下的
普通批次確認會在這裡失敗（模擬主機上 600 次全部失敗）。零售 0xA0 確認攜帶解壓後為 99 位元組的
zlib 主體（即記錄所用的 4 KB 視窗、級別 5 的同步重新整理分幀）。在標誌 0x00 下，同樣的 99 位元組
也會被計入：主機每條記錄只發送一次（每秒 6.3 條，之後為零，而普通 0xA0 下為每秒 115 到
257 條）。兩個零售站點都把批次確認標記為 0xA0 併發送到它們 /24 的 LDN 廣播；當
`bin/sv_join.py` 設定第 5 位時會壓縮主體（`--ack-flags`、`--ack-entries`、`--ack-dest-bits`、
`--ack-sweep`）。

### 一條流上的首條記錄攜帶 INITIALIZED

一個站點的首條記錄攜帶帶 START、END 和 ZLIB 的 INITIALIZED，標誌 0x1F；後續記錄為 0x17。以
0x17 傳送的首條記錄永遠不會被確認。隨後主機把整套確認到 47（掩碼 `feffffffff01`），把它的
記錄傳送一次，併發出一個列出兩個站點的型別 5 站點更新。

## 為一臺主機充當主機

| 主機發送 | 它必須是什麼 |

那四十個遊戲廣播位元組每個會話都會變化：為零，或在 +0x21 處為非零值（見到過 `648cf4`、
`8170f0` 和 `fb149700`）。使用 `--channel 6`、把 `--player-name` 設為所模擬主機的玩家名，並給出
`--host-player-id 00000000000000010000000000000000` 時，NetworkInfo 除會話 ID 外與一臺模擬的
朱 主機一致。在座位之上失敗的會話會引起反覆加入（實測 16 到 57 次）。

### 最低待定與 5 和 6 處的間隙

一個站點的 ID 5 和 6 從不傳送（線上為 44 條記錄），其餘記錄亂序發出（一對主機中的主機：
1、2、3、46、4、7、8、19、9、15、10、16……）。每條記錄都宣告 `lowest_pending` 為 1、
目標位 3、點陣圖 `[2]`、流 ID 0。這個間隙由傳送方在同一流上的下一次批次確認來閉合，其
`lowest_pending` 從 1 跳到 47；對端隨後以空掩碼把整套確認到 47。若一直停在 1，對端會以
`ack_id` 5、掩碼 `feffffffff01` 應答，全程如此。沒有間隙的 ID 1 到 44 也會被接受；但沒有
零售傳送方使用它們。

傳送方只能把 `lowest_pending` 推進到已確認記錄之後。在初始爆發之後直接推進到 47 可能掩蓋
丟失的身份分塊：對端確認了 47，而 StreamData 塊仍不完整，站點永遠不會被通告。

兩個 SV 啟動器都為身份集維護一個 `reliable5.SendWindow`。對應的批次確認條目會釋放低於其
`ack_id` 的記錄以及其選擇性掩碼指名的記錄。每 250 毫秒，未確認的記錄會帶著原來的序號和 Pia
訊息標誌 `0x40` 重發。發出的資料與批次確認頭會宣告仍然待定的最低記錄，整套確認完畢後則為
47。這樣既保留了有意留下的間隙 5 和 6，又保留了真實的丟失。

丟失首條 INITIALIZED 記錄會讓全部 44 條記錄都處於未確認狀態，需要重試整套。缺失的中間記錄
則單獨重試。

## 遊戲自己的協議，來自一對主機

測量自兩個進行過交換的模擬 朱 4.0.0 例項，各自記錄它發出的每個資料包。交換執行在
Reliable 0x7C 上；廣播流只承載身份交換。

### 埠 2：通告、加入與應答

Reliable 0x7C（單站點）和 BroadcastReliable 0x80（所有站點）的埠 2 承載遊戲的會話訊息。
輪詢器 `0x1954978` 讀取 `[0x475ea70]`（`0x19549e4`）和 `[0x475ea7c]`（`0x1954a54`）交給分發器
`0x1954aec`：首位元組、型別 1 到 0xD、表 `0x3c68988`。有三種類型會開啟一次交換：

| 時間 | 站點 | 線路 | 型別 | 位元組 |
|---|---|---|---|---|
| 0.00 | 主機 | 0x80 埠 2，zlib | 7 | 解壓後 167 位元組：`07b901b905b906010200bc09`、九個零位元組、`bc8080`、128 個零位元組、`000000b90183`、主機的站點 ID、`00` |
| 0.09 | 加入方 | 0x7C 埠 2 | 3 | `03b90200bc09` 和九個零位元組 |
| 0.15 | 主機 | 0x80 埠 2 | 9 | `09b9030000b90183` 和加入方的站點 ID |

編碼是通道表的編碼（`pokeldn.ldn.channel_table`）加上標籤 `0xbc`，即一個位元組串：標籤、作為
整數的長度、位元組。型別 7 是一個包含一個五元組的元組（寫入器 `0xe464fc`）：

    b9 06 ...   the type-1 body as a tuple of six: kind, capacity, a zero byte, the name as a
                nine-byte string, the data as a 128-byte string, the data length
    key         body +0x8e, the relay's counter +0x1c4 before it steps
    index       body +0x8f, the relay's counter +0x1c0 masked to seven bits, before it steps
    b9 01 ...   a tuple of one u64, the station id of the type 1's sender
    0           body +0x98

型別 9 是一個元組：加入的槽鍵、一個結果位元組和一個只含一個 u64 的元組。

型別 7 是一個被中繼的型別 1：型別 1 處理器 `0x18ceb70` 無條件複製 0x8e 位元組的主體，蓋上
key 和 index，推進兩個計數器，追加發送方的站點 ID，並將其入隊給型別 7 建構子（佇列 `+0x200`，
步長 0xa8）。`0x18d5a58` 向一個站點發送埠 2 訊息，當目標就是自己時通過 `0x1954aec` 分發，
因此主機會中繼它自己的型別 1。

型別 1 的主體（`0x18ab760`）：

    +0x00  kind
    +0x01  the slot's capacity: 2 for kinds 1 to 3, 4 for kinds 4 to 8 and 12, 0 for kinds 9 to 11
    +0x02  zero
    +0x03  a name of up to eight characters, NUL-terminated in nine bytes
    +0x0c  up to 128 bytes of data
    +0x8c  the data length

交換的型別 1 是 kind 1、容量 2、空名字、無資料。一個槽把主體存放在槽 `+0xd0` 處（建構函式
`0x18b73a0`），因此它的 key `0x12fcabc`（槽 `+0x15e`）就是主體 `+0x8e`。每個被中繼的型別 1，
無論自己的還是對端的，都會推進 key；只有 `0x12fbef0` 會把計數器歸零。像 `03b90200bc09` 那樣
指名 key 0 的加入，只能匹配自計數器歸零以來的第一次通告。

型別 3 處理器 `0x1981e94` 把加入的第一個欄位與槽 key 比較（`0x1981ed4`），接受時把型別 9
入隊（`+0x270`），否則在 `+0x350` 上入隊一個型別 0x0D，即 `0d b9 01` 加上一個程式碼：

| 程式碼 | 拒絕原因 |
|---|---|
| 1 | 沒有槽持有該加入的 key（`0x1981ffc`），或 `0x279c8fc` 拒絕 |
| 2 | 槽已滿：`0x18f80c8` 對照 `0x1e64914` 讀取的容量，或 `0x279c9a0` 返回 0xfd |
| 3 | 加入名字的 FNV-1a 64 雜湊與槽的不同（`0x1e648a0`） |
| 4 | 槽已關閉（`0x1e64924`，槽 `+0x160`，在槽建立時清除） |

型別 0x0D 交給 `0x1954f3c`，它要求 `0xb9`，解碼一個單元素元組（`0x279c0e8`）並呼叫接收者
`0x279c1ac`（`0x1954f78`）：

    0x279c1b8  ldr  x8, [x0, #0xb8]     the pending request
    0x279c1bc  cbz  x8, ret             none: nothing happens
    0x279c1d0  strb w9, [x8, #0x43]     result = the code
    0x279c1d8  strb #1, [x8, #0x42]     done
    0x279c1dc  bl   0xc8e6c4            wakes the request's waiter at +0x48

它既不檢查請求型別 `+0x40` 也不檢查完成位元組，因此來自加入方的一條 0x0D 會用它自己的程式碼完成
主機當前持有的任何請求。型別 9 接收者 `0x18b65c8` 按槽位元組選擇物件，應用該訊息，除非該 u64
是該站點自己的 ID（`[[0x46d0a08]] + 0xb8`）否則丟棄它。

站點 ID 是把 Pia 常量 ID 當作大端 u64（MAC `02:00:7f:00:00:02` 對應 `7f00020000020000`）；
對零售主機而言，型別 9 攜帶的是它 Session 加入請求中的常量 ID。`pokeldn.sv.port2` 構建這三者
（在 `tests/test_sv.py` 中固定）；`bin/sv_host.py --announce` 在座位之後傳送型別 7，並用型別 9
應答型別 3。

### 傳送通告的交換任務

連線交換在 `0x1e2ea54` 處建立該任務：配置 `BoxTrade`（`0x3aefac8`），工廠 `0x1e2f3d4`，
模式 4，need 2。兩個指令碼繫結到達它：`0x1e2e9bc`（GOT `0x46d6608`，由 `0x1b9c8c4` 存入
`0x4717068`，尾呼叫）和 `0x1e2ec84`（GOT `0x46d6610`，在 `0x1e2ee40` 處 `bl`）。該任務
（建構函式 `0x1e3bd10`，虛表 `0x44568a8`，Update `0x1e51a04`）：result `+0x40`、state `+0xb8`、
會話控制代碼 `+0xc0`、模式與 need 作為 u16 位於 `+0xc8` 和 `+0xca`、槽物件 `+0xd0`、請求控制代碼
`+0xf8`。

| 狀態 | 地址 | 它做什麼 |
|---|---|---|
| 1 | `0x1e51a84` | 若站點計數 `[[0x46d0a08]]+0xe0` 低於 need 則 result 3，若 `0x18ab520` 拒絕該模式（0、5、8 以上）則 result 1；否則無超時地等待 `need` 個完成的身份塊（`0x1e52004` 遍歷 `[[job+0xd0]+0x10] - 0x28`），然後在主機上進入狀態 2（`0x1639910`：自身 ID `+0xb8` 等於主機 ID `+0xc0`），在客戶端進入 4 |
| 2，主機 | `0x1e51b2c` | 先取 kind `0x18ab550(mode)`（模式 1 到 8 得到 2、3、4、1、0、5、5、8），然後發出請求 `0x18ab658`；為 null 則以 result 8 結束 |
| 3，主機 | `0x1e51ca8` | 等待該請求，無超時；result 0 進入狀態 6，否則任務經 `0x1e5086c` 結束 |
| 4、5，客戶端 | `0x1e51b8c`、`0x1e51c74` | 同樣的等待，限時 15 秒 |

| 結果 | 含義 |
|---|---|
| 1 | 成功，或模式被拒絕 |
| 2 | 會話處於狀態 3 |
| 3 | 站點數少於 need |
| 4 | 客戶端的 15 秒超時 |
| 8 | 無會話，或請求被拒絕 |

請求 `0x18ab658` 構建型別 1 主體並通過 `0x18ab83c` 傳送它；當該中繼的待定請求
`[relay+0xb8]` 的完成位元組 `+0x42` 仍為 0（`0x18ab860`、`0x18ab8e8`）或傳送失敗時，它返回
null。否則它清除 `+0xb8`（`0x18ab894`），存入一個新請求（`0x18ab8a8`；`0x18abec0`：`+0x40`
型別，通告為 0，`+0x42` 完成，`+0x43` 結果），並把型別 1 發往主機 ID（`0x18d58b8`），在主機上
則發往自己；傳送失敗會清除 `+0xb8`（`0x18ab900`）。

`0x18ab658` 有四個呼叫者：`0x1e51b68`（BoxTrade 狀態 2）、`0x18ab34c`（一個同級任務中的同一
處，虛表 `0x4456490`）、`0xa188f0`（虛表 `0x4452e68`）和 `0x1d99568`（虛表 `0x44536d8`）。
只有這四個請求建立者會寫 `+0xb8`；`0x18ab83c` 與 `0x2799b10` 在有請求待定時會拒絕：

| 建立者 | 請求型別 | 儲存位置 | 唯一呼叫者 |
|---|---|---|---|
| `0x18ab83c` | 0，即通告 | `0x18ab8a8` | `0x18ab6bc`，位於 `0x18ab658` 中 |
| `0x2799b10` | 2，即客戶端的加入 | `0x2799bd8`（守衛 `0x2799b2c`..`0x2799b40`） | `0x1e635fc` |
| `0x2799c44` | | `0x2799cfc` | `0x1e639ec` |
| `0x2799d6c` | | `0x2799e30` | `0x1e63c88` |

後三個呼叫者各自位於一個函式中，該函式唯一的呼叫者在 `0x1d98xxx` 裡（`0x1d986d8`、
`0x1d98990`、`0x1d98c20`）。

在連線交換中，型別 2 建立者從 BoxTrade 狀態 4 的 `0x1e51c40` 處經 `0x1d986d8` 和 `0x1e635fc`
到達。它只在客戶端上、主機的槽出現之後執行（`0x1d999f4`、`0x18c7a40`），把請求保留在任務
`+0xf8`，並進入狀態 5。`0x1d98698` 的其他呼叫者屬於其他任務類。

排水 `0xe44cf0` 按順序走佇列 `+0x1c8`、`+0x200`、`+0x238`、`+0x270`、`+0x2a8`、`+0x2e0`、
`+0x318`、`+0x350`；某個建構子返回 false 會結束該幀的排水，因此一個卡住的型別 7 會把它後面
的型別 9 和 0x0D 擋住。型別 7 建構子 `0xe45740` 在站點數為 1 時只在本地分發；否則它會問
`BroadcastReliableProtocol::vfunc20`（`0x6e6638`）0x80 埠 2 能否傳送，用 `0x107e060` 傳送，
並且只在兩者都成功時才在本地分發。當目標列表 `[window+0x40]` 中沒有任何條目被設定時，
vfunc20 以 0x2c27 拒絕（`0x6efb98`）；當視窗沒有空間容納分片時以 0x4c0d 拒絕（`0x6f1ef8`）；
無會話或視窗時以 0x10408 拒絕。Pia 在站點加入事件時填充目標列表
（[一個視窗向誰傳送](pia.md#who-a-window-sends-to-pia-6)）。

型別 7 接收者 `0x18b566c` 建立並應用該槽，並且對於待定的型別 0 請求和主機自己的站點 ID
（主體 `+0x90`），以 result 0 完成它：主機會停在狀態 3，直到它自己的型別 7 已經上線離開。
從中繼到上線之間沒有任何東西讀取 RTT 或計時器。

0x81 身份是每個站點一個塊，位於其索引對應的埠上（控制代碼 `0x475ea48 + 4*index`），由流傳送
API `0xe22188` 與接收 API `0xe22458` 為三個同佈局物件搬運：

| 物件：Update，虛表 | 傳送 | 接收 | 塊 |
|---|---|---|---|
| `0xe21104`，`0x4455ec0` 的槽 13 | `0xe21a44`，`0xe21dc4` 處 `bl`，`0xe21db8` 處 `w2 = 0xf388` | `0xe2150c`、`0xe2170c`，`0xe21708` 處 `w3 = 0xf388` | 0xF388 = 62,344 |
| | `0xa62c5c`，`w2 = 0xff008` | `0xa64ddc`，`w3 = 0xff008` | 0xFF008 = 1,044,488 |
| `0x1e5f87c`，`0x4458698` 的槽 13 | `0x1e617a8`、`0x1e61980`，`w2 = 0x97e08` | `0x1e61a74`、`0x1e61c0c`，`w3 = 0x97e08` | 0x97E08 = 622,088 |

交換中只有 0xF388 塊會上線，因此該任務的 `+0xd0` 物件屬於那個類（例項未追蹤；經
`0x1e34b6c` -> `0x1e35e88` 構建）。

`0x1e52004` 統計 `+0xd0 + 0x30*k`（四個）處持有對端指標且位元組 `+0xd8` 已置位的槽。主機自己的
槽在 `0xe21154` 中獲得它（`0xe21248` 處的 `memcpy(slot, [+0x90], 0xf388)`，`0xe21258` 處
`+0xd8 = 1`；呼叫自 `0xa536e0`、`0xd6dc88`、`0xe21128`、`0x195160c`）。對端的槽在
`0xe212b8` 中獲得它（呼叫自 `0xa536f0`、`0xd6dc98`、`0xe21138`），且僅當向對端的傳送
（`+0xda`）與從對端的接收（`+0xd9`）已經開始、自己的 0x81 流處於狀態 3（`0xe2144c`，
自己的每個分塊都已確認）而對端的處於狀態 6（`0xe21404`，對端的每個分塊都已收到）；狀態 7 會
清除一個標誌
（[協議 0x81](pia.md#protocol-0x81-the-stream-broadcast-reliable-transfer-pia-6)）。0x97E08
類有同樣的一對，`0x1e60284` 和 `0x1e615e8`。

在線上，型別 7 通常會在主機自己那套記錄的最後一條之後 0.11 秒內出現。

中繼是一個 0x388 位元組的物件（虛表 `0x44e56f8`），單例 `[0x46da9c0]` = `0x4739430`，僅當不存在
時才由 `0x165a200` 從 `0x1659b70` 建立（`0x1659b18`）。它的站點事件處理器是 `0x12fbb90`，
經由 thunk `0x2b71650`：

| 事件 | 效果 |
|---|---|
| 0，一個站點加入，在主機上 | 除非它就是主機，否則 `0x12fbf8c` 把當前槽發給它 |
| 1，自身 ID | 一個未完成的待定請求以 result 5 完成（`+0x42` 處為 `0x501`），然後 `0x12fbef0` |
| 1，主機的 ID | `0x12fbef0` |
| 1，任意站點，在主機上 | 隨後 `0x12fcebc` 丟棄它中繼過的元素 |

`0x12fbef0` 通過 `0x12fc644` 移除每個槽（完成 key 匹配的待定型別 1 請求），清空七個佇列
（除 `+0x1c8` 之外的全部）並把 `+0x1c0` 與 `+0x1c4` 歸零；它保留 `+0xb8` 處的請求。型別 0
請求只會被型別 7 接收者、型別 0x0D 接收者和自身離開事件完成；型別 2 由型別 9 接收者
`0x18b6710` 完成，型別 3 由型別 0xA 接收者 `0x1945404` 完成，型別 4 由型別 0xB 接收者
`0x279be18` 完成。

自身離開路徑 `0x12fbc3c..0x12fbc4c` 以 result 5 完成客戶端待定的型別 2 請求
（`+0x40..+0x43 = 02 00 01 05`），因此下一個建立者可以替換它。僅針對主機 ID 的離開事件
只調用 `0x12fbef0`。客戶端的 BoxTrade 任務在 15 秒時以 result 4 結束（狀態 5 的時鐘測試
`0x1e51c74`，基準 `+0x108`），但它的超時路徑 `0x1e51d50` 和解構函式 `0x1e51740` 都不觸碰
中繼的請求：它仍停在 `+0xb8` 處待定，而 `0x2799b10` 與 `0x18ab83c` 會拒絕，直到一條型別 9、
一條型別 0x0D 或客戶端自己的離開事件完成它。

中繼會一直存活到應用退出，因此停在 `+0xb8` 處的請求會跨越每一次座位、搜尋和選單存活下來，
直到某個完成者執行。它的持有者 `0x4739430`（GOT `0x46da9c0`）只由建立者寫入（`0x165a2b4`）、
由中繼自身 destroy 槽到達的重置 `0x279d610`（`0x279d5ac`、`0x2b71660`）以及靜態析構
`0xa15f74`。虛表 `0x44e56f8`：槽 0 `0x279a7b0`、3 `0x279d5ac`、4 `0x12fbb90`；介面 `+0x28`
是監聽 thunk `0x2b71650`。建立者用 `0xf0ba9c` 把它註冊到 `0x4763a18` 處的終結器列表中，
該列表只在應用終結時遍歷（`0x20e9c78`，以 `nn::account::CloseUser` 結尾）。

### 開啟通道

| 時間 | 站點 | 埠 | 位元組 | |
|---|---|---|---|---|
| 0.29 | 主機 | 1 | 31，INITIALIZED | `b90104b902b9027b0001b902b902320101b902b902320201b902b902320301` |
| 1.84 | 加入方 | 1 | 31，INITIALIZED | 同樣的 31 位元組 |
| 2.43 | 加入方 | 2 | 15，INITIALIZED | `03b90200bc09000000000000000000` |
| 9.00 | 主機 | 1 | 11 | `b90101b902b90280800001`，加入方回送同樣的內容 |

埠 1 是通道表（Arceus 的機制）：一個站點只有在它的對端已經通告某個 key 之後才會在該 key 上
傳送。加入方的表與主機逐位元組相同；在它到達之前主機會停在搜尋介面上。主機在 key 0x80 上的
開啟必須先到：如果一個加入方的交換介面先繪製出來，它就永遠不會發送自己的第一條遊戲訊息，
而在寶可夢上按 A 也不會出現選單。0x7C 可靠頭的長度是九位元組、無點陣圖、序號與最低待定都等於
訊息自身的值；一次開啟是 flags 0x0F，之後的更新是 0x07。

更晚的開啟會讓模擬的 Scarlet 4.0.0 交換箱沒有選擇游標。這個時限取決於對端：一臺零售主機在
座位之後 9.15 秒開啟自己的 key 0x80 時，對 6.0 秒開啟的主機繪製了選單，而 11.0 秒開啟則沒有。

### 交換

埠 0 承載遊戲：一個四位元組頭和一個主體。

| 時間 | 站點 | 主體 | |

「等待響應」上（`--send-on-open`）。

站點最後一個序號加一，就會讓站點等待那個數字，並在 `0x6f03cc` 處丟棄主機下一條更小的訊息
（[接收者在靜默中丟棄什麼](pia.md#what-the-receiver-discards-in-silence)）；兩套編號在提交處
分岔，站點先提交。`8001` 步驟成對進行，01 與 02 在第四個位元組下依次推進 03、06、0B、0E；
交換在這些步驟之上完成，兩個介面都回到交換選單。

對 `bin/sv_host.py` 而言，主機的交換流訊息編號為 5（提出）、6（確認）、7（提交）、8 到 15
（步驟）；主機的 5、6、7 與 8 到 11，它的 key 0x180 開啟與關閉是它埠 1 的訊息 3 與 4；
它對主機提出的 ack 讀作 `ack_id` 6、`lowest_pending` 5。兩個完全相同的訓練家也能交換。

### 在站點自己的提出之前傳送的確認

永遠不要在提出 `80000200` 仍在佇列中時傳送確認 `80000300`：按這個順序餵給一臺零售主機會以
系統錯誤崩潰。兩個啟動器上的 `--offer-after-open` 會把提出掛在對端的 key 0x80 通告上，並且
二者都不會把一條交換訊息排到已為同一站點和埠排隊的訊息之前。

交換動畫跟隨主機的最後一步 `8001010e`，不攜帶任何交換訊息。在它的狀態
`b90101b902b90280800100` 之後，主機在玩家退出之前不再發送應用資料。

### 一次座位中的多次交換

key 0x0080 保持開啟；key 0x0180 每次交換開啟再關閉。第二次交換重複這一迴圈，序號繼續遞增
（主機提出 16、確認 17、提交 18、步驟 19 到 26），且沒有新的關聯、Session 交換或身份。
`TradeStage` 與 `JoinerTradeStage` 接受一個記錄列表，每次交換一條；`--trade-offer` 可重複。
座位能否在主機的主機遷移請求下存活尚不清楚。

### 第一條遊戲訊息，以及它攜帶什麼

`80 00 01 00` 與 2557 位元組，分成兩個可靠分片，先 START 後 END（一對主機壓縮後 238 位元組，
零售主機 195 位元組），各自是一個 zlib 流（`484b`）；訊息是兩次解壓的拼接：

    b9 02          a tuple of two fields
    bc 81 f6 09    a blob, 0x9f6 = 2550 bytes
    ...            2550 bytes
    04

該 blob 是 850 個小端三位元組值，大多為 1，其餘是位掩碼（`0x0fffff`、`0x0002ff`、`0x00003f`、
0），按站點劃分（零售主機與一對主機之間有 38 個條目不同；條目 36：`0x040000` 對 `0x0fffff`）。
索引統計的是什麼尚不清楚。它不攜帶訓練家的任何欄位：零售主機的記錄裡既沒有 ID 對也沒有
名字。一對主機的四個分片重放時會被一臺零售主機接受。

### 交換訊息攜帶的記錄

`80 00 02 00` 訊息的 348 位元組主體是常量 `bc 81 58 01` 加上一條 344 位元組的第九世代隊伍記錄
（PKHeX 的 PK9），採用第八世代加密（`pokeldn/gen8.py`）：從 0x08 起的四個 0x50 位元組塊按
`(EC >> 13) & 31` 置換，對 16 位字施加 LCG `seed = seed * 0x41C64E6D + 0x6073`，以及截至
0x148 的解密主體的 16 位校驗和。0x148 處的隊伍尾部位於置換與校驗和之外，並從加密常量重新
播種 LCG。

    0x000  u32  encryption constant, in the clear
    0x004  u16  sanity, 0 on every record measured
    0x006  u16  checksum, in the clear
    0x008       four 0x50-byte blocks, encrypted and permuted        -> 0x148
    0x148       level, a pad byte and the six stats, encrypted       -> 0x158

欄位對映是 PK9 的 [`PKHeX.Core/PKM/PK9.cs`]；`pokeldn/gen9.py` 讀寫它。

只有記錄讀出來像一隻自洽的寶可夢才能把它定死。`bin/sv_host.py` 會列印兩個提出，
`--offer-out FILE` 寫出主機的那個（第一次之後的提出 N 寫到帶 `-N` 且在副檔名之前的 `FILE`），
`--trade-offer` 接受一條 344 位元組記錄（明文或加密）、348 位元組主體或 352 位元組訊息。

### 組合出的記錄

由 `pokemon.build` 從零位元組組合出的記錄，或用 `bin/sv_host.py --offer-set`（暱稱、已起暱稱
標誌、性格值、IV）編輯過的記錄，會以組合時的每個摘要欄位交換進一份零售 Scarlet 存檔。交換
介面繪製組合出的記錄時不做合法性檢查；校驗和由主機寫入。摘要中的訓練家 ID 是
`(TID16 | SID16 << 16) % 1000000`（12345 與 54321 顯示為 993401，8131 與 64817 顯示為
855043）；特徵行來自加密常量與 IV。

等級跟隨經驗：零經驗時位元組 0x148 為 100 會以 1 級到達，1,000,000 經驗則為 100 級。六條成長
曲線（`PKHeX.Core/PKM/Util/Experience.cs`）在 100 級分別需要 1,000,000、600,000、1,640,000、
1,059,860、800,000 和 1,250,000。物種表 `personal_sv`（每個物種與形態 0x50 位元組，
`PersonalInfo9SV.cs`）在 0x00 處持有種族值、0x0C 處性別比例、0x0F 處成長曲線、0x12 處三個
特性（物種 132：曲線 0，特性 7、7、150）。接收方遊戲會重新計算隊伍數值：

    HP    = (2 * base + IV + EV/4) * level / 100 + level + 10
    other = ((2 * base + IV + EV/4) * level / 100 + 5) * nature

一隻完美 IV、無 EV、中性性格的百變怪，從零數值欄位出發，在 1 級顯示 12 和 6（各五遍），
在 100 級顯示 237 和 132（各五遍）；1 級傳送的 HP 99/99 會以 12 到達。

| 1.68 | 十一個批次確認，以及 0x81 埠 0 和 4 上的流開啟 |

### 交換中加入方這一側

一對加入方在 0x7C 上的完整指令碼，含每條訊息在其埠上的序號：

| 埠 | 序號 | 訊息 |
|---|---|---|
| 1 | 1 | 通道表，主機的四個 key，INITIALIZED |
| 2 | 1 | 型別 3 加入，`03b90200bc09` 加九個零位元組 |
| 0 | 1 到 4 | 第一條遊戲訊息，兩遍 |
| 1 | 2 | `b90101b902b90280800001`，key 0x80 開啟，在第四個分片之後 |
| 0 | 5 | 被提出的寶可夢 |
| 0 | 6 | 確認 |
| 0 | 7 | 提交，先發 |
| 1 | 3 | `b90101b902b90280800101`，key 0x0180 開啟，在主機自己的之後 |
| 0 | 8 到 11 | 每個步驟 `8001 01 SS`（03、06、0B、0E）的回顯；`8001 02 SS` 則什麼都不發 |
| 1 | 4 | `b90101b902b90280800100`，關閉 |

身份在主機 key 0x80 開啟之後 0.15 秒發出，加入方自己的開啟再晚 0.21 秒。

`lowest_pending` 規則同樣約束加入方：在 0x7C 上是它自己的下一個序號，在 0x81 批次 ack 上是
它最高記錄 ID 加一。若用主機編號體系裡的數字，主機的接收基址會越過加入方稍後的訊息，那些
訊息會在 `0x6f03cc` 處被丟棄。

`pokeldn.sv.trade.JoinerTradeStage` 就是這一側的狀態機，由 `bin/sv_join.py --trade-offer`
執行（`--send-on-open` 用於以 key 0x80 開啟為條件的身份分片）。`tests/test_sv.py` 用一對
訊息中主機的那一半驅動它，並固定加入方的那一半。

### 一次交換會改寫什麼

一條組合出的記錄被交換到零售主機上再被提出回來，有 27 位元組、七個欄位不同：

| 欄位 | 傳送時 | 回來時 |
|---|---|---|
| `current_handler` | 0 | 1 |
| `ht_name` | 空 | 主機玩家的名字 |
| `ht_language` | 0 | 接收主機的語言（3，法語） |
| `ht_friendship` | 0 | 50 |
| `nickname` | 空 | 主機語言下的物種名 |
| `current_hp` | 0 | 計算出的最大 HP（237，一隻 100 級百變怪） |
| `stats` | 零 | 遊戲計算出的那六項 |

其餘一切按傳送時保留。空名字會以物種名回來，就像 Sword 的神秘禮物記錄那樣
（`docs/swsh_gift.md`）。

若一條記錄的初訓家就是接收存檔的主人，則處理者保持 0 且沒有處理者名字，與 Legends Z-A 中
一樣（[交換寫入收到的記錄什麼](za.md#what-the-trade-writes-into-a-received-record)）。一隻為
零售 Violet 的訓練家制作的神秘禮物寶可夢，用的是該存檔自己抓到的寶可夢
（[為接收玩家制作](gift_simulated.md#made-for-the-receiving-player)），從它那裡回來時正是
如此。

### 加入正在搜尋的主機：一次交換，以及什麼決定座位

`bin/sv_join.py` 與一臺從連線交換搜尋中充當主機的零售 Scarlet 交換，編號方式如同一對中的
加入方。它把站點更新當作座位，用型別 3 加入應答主機的通告，在主機開啟 key 0x80 之後傳送
四條身份訊息，並遵守上面的 `lowest_pending` 規則。

#### 什麼決定座位

一臺從搜尋中充當主機的零售主機要麼運行遊戲，要麼把主機角色交給它的加入方。遊戲在 3 到 7
次瀏覽嘗試之後充當一次主機（`RandomMatchingSeq` `0x26e182c`，計數器 `rand%5+4`），併為一個
成員等待 3000 + rand%1000 毫秒，每有一個成員加入再加 5000 毫秒（WaitMember，`0x26df898`）。
等待超時以 JoinRandomRecover `0x26f507c` 結束，它通過 `LeaveMeshWithHostMigrationJob` 離開
會話（[離開](#leaving)），把角色交給 Net 排名最低的站點（`0x6a012c`）。在 WaitMember 期間
被接受的加入會看到遊戲執行；在它之後被接受的則收到型別 7。主機玩家在通告之後退出時也會
傳送它。

把角色交出去的那臺主機會銷燬它的網路並重新瀏覽。`--take-host`（預設）會讓 `bin/sv_join.py`
在通告之前收到型別 7 時，用應用的 host flags 在該座位的通道和程式碼上執行 `bin/sv_host.py`，
就像 `bin/pla_join.py` 為 Legends Arceus 所做的那樣。

運行遊戲時，主機會按順序傳送：

| | |
|---|---|
| 座位 | 一條型別 5 站點更新，指名加入方的可變 ID 與其請求中宣告的玩家 ID，然後是 41 位元組的加入應答 |
| 它的開啟 | 全部十一條流上的批次確認，0x81 埠 1 上一條 11 位元組記錄，埠 5 上另一條 |
| 它的身份 | 0x81 埠 0 上 46 條記錄，並確認加入方的 44 到 47 |
| 它的通道表 | 在 0x7C 埠 1 上，key `0x007b`、`0x0132`、`0x0232`、`0x0332` |
| `0db90101` | 在 0x7C 埠 2 上，程式碼 1，只用於應答在通告之前傳送的型別 3 加入 |
| 通告 | 在 0x80 埠 2 上，zlib，解壓 167 位元組：一條 kind 1、容量 2、攜帶主機站點 ID 的型別 7 |

加入方用型別 3 加入應答通告（`--port2-now` 則讓它隨通道表一起傳送）。僅站點更新就是座位：
永遠不要等待加入應答。

## 離開

一臺退出座位的主機會按自己的角色執行兩個 Pia 任務之一。每個都等待其對端，並在計時器上
放棄。

被加入的主機執行 `LeaveMeshJob`。SendLeaveRequest `0x6db590` 傳送 Session 型別 3 離開請求
（佈局見 [docs/pla.md](pla.md#leaving)）並設定 500 毫秒的期限（`0x6db6a0`）；
WaitLeaveResponse `0x6db7b0` 在到期時重發，並在第四次傳送之後完成（`[job+0x6c]` 超過 2，
`0x6db8e8`），或在 `[job+0x69]` 一被設定時立刻完成。Session 分發器（`0x6d4960`，表
`0x3c0cd3b`，型別 0 到 0xA）把型別 4 交給 `0x6d7b10`，後者為一條 17 位元組、其中第 5 到 16
位元組是該站點自身位置 ID 的訊息設定 `[job+0x69]`：

    04 | u32 random | location id (12), copied from the request

主機的型別 3 處理器 `0x6d7894` 在按常量 ID 與可變 ID 找到該站點之後，寫入的正是這些內容
（型別位元組在 `0x6d7a50`，從 `0x6c70a8` 取一次新的 xorshift 隨機數，在 `0x6d7ad8` 傳送）。
若無人應答，零售主機會以約 0.5 秒的間隔傳送四次離開請求，並在第一次之後約 2 秒解除認證；
若有應答，則在收到應答後 0.04 秒。`bin/sv_host.py` 應答第一個（`--no-leave-response` 讓它
無應答）；`tests/test_sv_departure.py` 在 unicorn 下把該應答跑過 `0x6d7b10`。

一臺從搜尋中充當主機的主機則交出主機角色。`LeaveMeshWithHostMigrationJob` 向下一任主機發送
Session 型別 7 並每秒重發（`0x6df050`），直到一條型別 8 指名該站點（`0x6ded94`），5 秒後
放棄（`0x6defb8`）。型別 7（寫入器 `0x6d8de0`）是 34 位元組：

    07 | host location id (12) | 00 | host IPv4, port | next host's location id (12) | u16

最後一個 u16 是該任務的 `+0xe0`（`0x6d8ea8`）。然後 `NetDestroyNetworkJob` 以主機遷移形態
等待每個客戶端都收到連線狀態更新（最多 4 秒，`0x6ac68c`），每 300 毫秒傳送一次
NetStartHostMigration `01400000`（只由 `0x69d310` 寫入，只從 `0x6aca54` 呼叫）
（`0x6aca98`），直到網路的站點數為 1（`0x6acaf4`）或某個期限過去（4 秒；若更新等待已超時
則為 2 秒，`0x6ac984`），然後銷燬 LDN 網路。在線上，該更新是帶 is-migrating 的 Net 0x11；
在加入方的 Net 0x12 之後，第一個 NetStartHostMigration 在 45 毫秒後出現。客戶端在收到
NetStartHostMigration 時啟動哪個任務未追蹤；`NetHostMigrationJob` 以 DisconnectNetwork 或
EmulateDisconnection 開頭（`0x6a93c4`）。

持有座位的加入方會繪製 NetStartHostMigration 約 4 秒。`bin/sv_join.py` 在第一個出現時離開
（`--stay-on-host-migration` 則保住座位）。

一次交換完成之後，兩個啟動器都會在主機離開時退出。使用 `--hold-after-trade N` 時，
`bin/sv_join.py` 在它最後一條排隊的交換之後 N 秒傳送型別 3 離開，就像在交換座位上 `--hold`
結束時那樣，而 `bin/sv_host.py` 會像 `--seconds` 結束時那樣關閉它的網路。沒有完成任何交換
的座位會讓 `bin/sv_join.py` 恢復掃描（[結束一次執行](architecture.md#ending-a-run)）。
