# 傳說 Z-A

Pokemon Legends: Z-A（標題 id `0100f43008c44000`）是一款原生 Switch 遊戲，Pia 被靜態連結進 `main`。其資料包頭版本為 16，也就是 `pokeldn.ldn.crypto` 為 GBA 應用寫出的那個版本。

## 轉儲

基礎應用 `v0`（4.3 GB），更新 `0100f43008c44800` `v393216`（2.1 GB），Mega Dimension DLC `0100f43008c45002`。

| NCA | id | 容器偏移 | 區段金鑰 |
|---|---|---|---|
| 程式（更新） | `4a70b3ff963bfe412681185cea68bf55` | `0x2085d0` | `b9de1a0334576634f8fdafdd703f7f9a` |
| 控制 | `3e7ba1cd223145fa4f299a8f4cafd4cb` | `0xbd0` | `a8cb59338ce785237048d52452eb6adf` |

程式 NCA 的 exeFS 位於區段 0，BKTR RomFS 位於區段 1。exeFS 包含 `main`（33,970,422 位元組）、`main.npdm`（1,700）、`rtld`（8,550）和 `sdk`（6,247,676），沒有 `subsdk0`。解壓後，`main` 的 text 為 `0..0x3163f70`，rodata 從 `0x3164000` 起，data 從 `0x3bc2000` 起；本頁中的地址都是該映像內的偏移。控制 RomFS 資料位於 NCA `+0x14c00`，區段計數器 `0000000000000005`；`control.nacp` 給出的顯示版本是 2.0.2，並在 `+0x30b0` 處給出八個本地通訊 id，全都是 `0100f43008c44000`。

## 資料包頭

頭版本 16，在 wiki 的表格中對應 Pia 6.39 到 7.2。佈局為 `pokeldn.ldn.crypto.PiaHeader`（29 位元組，magic `32AB9864`，加密時版本位元組帶 `0x80`；見 [Pia](pia.md)）。

    0x24fadbc   initializer: magic at object +0x08, 0x10 at +0x0c, memsets nonce +0x15 (8), tag +0x1d (16)
    0x24faefc   validator: magic, (version & 0x7f) == 0x10, (length - 0x1d) >> 6 below 0x71
    0x24fb1e0   receive path, branches on bit 7 of the version byte
    0x24fb4b0   send path, writes 0x10 back to +0x0c when it seals nothing
    0x24fb46c   padding-size setter: ORs into bits 4..7 of object +0x0d (wire byte 0x05)

該物件把 nonce 和 tag 存放在比其線上偏移高八個位元組的位置，正如傳說 阿爾宙斯 的 version-11 頭在 `pokeldn.ldn.pia6` 中的做法。

## 廣告

處於本地搜尋介面的主機會託管一個網路並廣播 112 位元組：0x5C 的 Pia 系統屬性塊加上 20 個遊戲位元組。不隨連線碼變化的欄位：

| 欄位 | 值 |
|---|---|
| 本地通訊 id | `0100f43008c44000` |
| LDN 協議 | 1 |
| 廣告版本 | 4 |
| 場景 id | 1 |
| 應用版本 | 6 |
| 安全模式 | 1 |
| 接受策略 | ALL |
| 參與者 | 1/2 |
| 系統 / 應用通訊版本 | 22 / 6 |
| 玩家名稱 | 一個位元組、一個空格、UTF-8 |

SSID 和通道按會話而定。遊戲位元組是 ASCII 形式的連線碼，用 NUL 補齊到十六個位元組，然後是它長度的小端 `u32`。佈局和密碼欄位與傳說 阿爾宙斯相同（[pla.md](pla.md)，廣告中的連線碼）；Z-A 的遊戲金鑰給出掩碼 `1068a742ac3a8787ab6066a161f5d5e1`。`pokeldn.za.build_advertise_data(code)` 僅憑連線碼就能復現每一個廣告；`tests/test_za.py` 把兩者都固定下來。

## 席位

搜尋中的主機會接受一個站點並立刻用 Pia 通訊：第一個資料包（109 位元組）出現在 0.02 秒。資料包在 `AES_ECB(game_key, ssid)` 下以網路 id `CRC32(ssid[1:16])` 認證（32 箇中 32 個解密成功）。若無人應答，它在協議 1（Net）上從其 variable id 向目的地 0 傳送：

| 訊息 | |
|---|---|
| `01 11 ...`，118 位元組 | 連線狀態，序列 id 2 和 3，每秒兩次 |
| `01 40 00 00` | 開始主機遷移，一旦該狀態得不到應答 |

連線狀態就是 `pokeldn.ldn.pia_connect.parse_net_conn_request` 讀取的佈局：四個槽，兩個已填，都在埠 12345，主機 `169.254.x.1`，加入者 `169.254.x.2`。它在大約 14 秒後停止，並讓該站點保持就座。

一對模擬主機的開場：

| | |
|---|---|
| 第一個資料包 | 主機的，109 位元組，關聯後 48 毫秒；加入者以 45 位元組應答，然後是 125 位元組 |
| 頭 nonce | 每站點計數器，從一個隨機 64 位基數起，每發一個包 +1 |
| 加入者的第一個包 | 源 0、目的地 0、包 id 0、無 footer、未壓縮 |
| 加入者的第二個包 | 它自己的源 id，zstd 壓縮 |
| 主機的下一個包 | 發往該 id，帶兩位元組接收者 footer |

在一個沒有 Pia 主機的網路上 LDN 連線成功的加入者會在 7.94 秒後斷開，即 Net 連線截止時間 8000 毫秒減去 LDN 連線時間：

    0x251b1bc   LdnProtocol vtable 0x3c8aef8 slot 0x1d8: mov w0, #0x1f40
    0x2513520   NetBackgroundProcessJob StartConnectNetwork: job+0xa0 = now + ticks_per_ms * 8000
    0x25141c4   the WaitConnected step 0x25140bc, while the host is unknown: deadline against now
    0x25143a0   expiry: result 0x647a, state byte +0x100 = 5, a 5000 ms deadline (slot 0x1e8),
                then StartDisconnectNetwork

LdnProtocol 的時序槽 0x1b0 到 0x1f8 分別返回 6000、1000、500、10500、4500、8000、20000、5000、5000 和 10000 毫秒；只有 0x1d8 和 0x1e8 已被識別。

## 會話，在零售主機上

一個傳送參考加入者的 Session join 的站點會被立刻接納。主機的傳送：

| 從席位起 | 主機發送什麼 |
|---|---|
| 0.02 秒 | Net 連線狀態，118 位元組 |
| 0.05 秒 | Session join 應答，型別 2，37 位元組，發往加入者的 variable id |
| 0.06 秒 | Reliable（協議 10），106 位元組，以及兩個 Broadcast Reliable（協議 11） |
| 0.08 秒 | Net update property，型別 0x50，150 位元組 |
| 從 0.5 秒起 | RTT 請求，約每秒三個 |
| 1.12 秒，重複 | Session update session，型別 5，185 位元組 |

加入方在 Net 確認之上欠著：十個協議（`1:0 3:5 5:1 6:0 9:1 10:3 11:4 12:4 13:7 15:0`）、應用通訊版本 6、一個先 `0x06` 後接零的標識令牌，以及一個單空格的 PlayerInfo 名稱。一個會應答每個 Net、Session、RTT 和 Reliable 訊息而不發任何遊戲訊息的加入者（`bin/za_join.py` 不帶 `--game`）能保住零售搜尋的席位直到它離開（實測 150 秒）。

| 加入 | 主機的應答 |
|---|---|
| 協議數與主機不同 | 被型別 0 處理函式 `0x254a030` 丟棄（`0x254a090`，對照 `0x256c9f0`），不應答，無站點 |
| 協議或應用版本錯誤 | 37 位元組的型別 2，結果 3（`0x254a2e4`）或 4（`0x254a290`） |
| GBA 應用的六個協議，或十個中的九個 | 沒有 Session 訊息；就座後 8 到 12 秒發 Net 0x40，然後在新 SSID 下開一個新網路，仍在搜尋 |
| 十個協議，但從其 variable id 沒有 RTT 應答或其他流量 | 被踢出（[踢出](#the-kick)），就座後約 27 秒顯示 "no partner found" |

8 到 12 秒的路徑是主機的 WaitMember，3000 ± 999 毫秒（隨機 u64 按有符號讀取）；到期時，若加入者仍在 Net 層且不在會話中，LeaveMeshWithHostMigration 會輪詢 8000 毫秒尋找下一個主機（`0x255a520`），然後傳送 Net 0x11 序列 3 和 Net 0x40。踢出序列是從 14 秒起的 Session 型別 13，共九個、間隔 0.5 秒；從 19 秒起每 0.5 秒發一次 Net 0x11 序列 3；從 23 秒起每 0.3 秒發一次 Net 0x40。

## 遊戲自身的交換

在 Pia 之上，遊戲執行在 Reliable（協議 10）和 Broadcast Reliable（協議 11）上，`pokeldn.ldn.reliable` 解析其子頭。一次交換攜帶下面的應用載荷（參考抓包中有二十個不同的），每個都重發直到被確認，兩個站點發出的集合相同，只差站點 id。按訊息 id，以首次出現的順序：

| id | 位元組 | 承載什麼 |
|---|---|---|
| `1400` | 106 | 站點的身份，玩家名稱用 UTF-16 |
| `1403` | 9 | 身份的校驗和（SyncDataSet），見下 |
| `0100` | 1211 | 選擇介面據以繪製的記錄 |
| `0101` | 354 | 報價：九位元組頭、344 位元組 Pokemon 記錄、一個尾隨位元組 |
| `0102`、`0104` | 5 | 步驟訊息 |
| `0200` | 5 | 確認步驟，最後一個位元組為 3、6、0x0b、0x0e |

`pokeldn.za.reference` 附帶身份、其後續、協議 11 的開場和選擇記錄，錄自一對玩家名為 `Player` 的模擬主機；`bin/za_join.py` 和 `bin/za_host.py` 會發送它們（`--game-dir` 指定另一組）。

身份是一個兩成員的 `b9` 元組：一個 u32，然後是一個持有 0x5d 位元組 `bc` blob 的單成員元組。該 blob 是六成員元組。它的前四個成員是存檔的訓練家 id（裡ID在高半部）、性別、語言和玩家名稱。隨後是一個 32 位元組的全零欄位，再是其餘部分。

遊戲從存檔的訓練家塊填充這四個欄位，即 PKHeX 的 `MyStatus9a`，它位於玩家狀態物件的 +0x40：

| 成員 | 塊偏移 | getter |
|---|---|---|
| 訓練家 id | +0x00 | `0x824b2c` |
| 性別 | +0x05 | `0x505c24` |
| 語言 | +0x07 | `0x23c398` |
| 名字，13 個字元 | +0x10 | 由 `0xc90ce4` 複製 |

構建器是 `0xc90b04`；它把該值儲存在以 GOT 在 `0x3ec7638` 持有的名稱條目下。

接收主機會以相同順序解碼這些成員（`0x9131ec`）。它的名稱框 `T_pname_%02d`（`0xb13fd4`）會把語言按 1 到 11 對照遊戲的語言表（`0x33a308c`）檢查；11 是拉美西班牙語。它把性別與名稱一起傳入其文本（`0x6b9fb8`）。

記錄下來的身份是一個女性、英語存檔：`0x378913cf`（5071 和 14217，參考會話中 Pokemon 的訓練家）、1 和 2。為接收玩家制作的禮物會讀取全部四個（`reference.identity_trainer`，[為接收玩家制作](gift_simulated.md#made-for-the-receiving-player)）。

    1400 b902 82<u32> b901 bc5d b906 82<u32> 01 02 bc1a <name> bc20 <32 bytes> ...

名字是 26 位元組，UTF-16LE，用 NUL 補齊：最多十二個字元，位於協議 10 訊息的偏移 0x18（協議 11 站點字首之後的 0x1c）。在那裡放上記錄的 `Player`，一臺零售主機為它的交換夥伴顯示了 `Player`。兩個啟動器都把 `--trainer-name`（預設 `POKELDN`）寫入其中（`pokeldn.za.reference.named`）。

通道 0x14 承載一個鍵值儲存，遊戲在站點之間保持同步（`gfa::network::p2p`，構建於 `0x7796a0`；訊息 id `0x1400 | index`）：1400 是 UpdateValue（`0xc1bdf4`），1402 是 DeleteAllValues，1403 是 SyncDataSet（`0xc4b1b4`）。身份的外層 u32 `0x2abe85e2` 是該值的鍵，一個位於 `0xdf1b30` 的常量：`UserData` 的 FNV-1a 32，也就是遊戲儲存身份時所用的名稱。1403 對傳送者按 key 排序的值攜帶一個 u32，`h = crc32(le32(fnv1a32(value) + h))`，從 `h = 0` 開始（`0xc4b270`，FNV-1a 在 `0xc4b31c`，標準 CRC-32 在 `0xc4b420`）；對身份而言，值是 `bc5d` 之後的 0x5d 位元組。接收方會重新計算它，只有當每個站點的都匹配時才繼續（`0xb8c724`，`0xb8c660`）。記錄下來的 `Player` 身份給出 `1403b9018269fb308f`，即那條記錄的訊息。改名後的身份若帶著那個過時的 1403 傳送，會讓零售主機停留在其搜尋介面：它會發送自己的 1400 和 1403，但從不傳送它的 0100。`pokeldn.za.reference.sync_message` 為所傳送的身份構建 1403。

### 交換命令

交換會話設定 `0xca2928` 會在會話的命令通道（session+0xc8）上訂閱五種命令型別（按 ctti 字串命名）。id 是 `0x100 | index`，即該型別在通道 +0x60 列表中位置（`0x96129c`，一次 `strcmp` 遍歷）。每個載荷都是一個以 u16 輪次開頭的 `b9` 結構體。

| id | 命令 | 處理函式 | 處理函式讀取的載荷 | 處理函式做什麼 |
|---|---|---|---|---|
| `0100` | CommandReady | `0x2dc4c7c` | 輪次，1200 位元組 | 把 1200 位元組複製到 session+0x604，設定 session+0xf0 |
| `0101` | CommandSelectPokemon | `0xb2a44c` | 輪次，344 位元組記錄，一個位元組 | 載入記錄（報價的 Pokemon）；該位元組第 0 位清零則使其成為一次拾取 |
| `0102` | CommandConfirmTrade | `0xc8dda0` | 輪次 | 當 session+0x152 高於該輪次時忽略；否則夥伴狀態 +0x134 = 4 |
| `0103` | CommandCancelTrade | `0x2dc51ac` | 輪次，u32 原因 | +0xab4 = 原因（1 與 2 互換），否則 0；+0x152 = 輪次；+0x150 += 1；然後 `0x2dc41f8` |
| `0104` | CommandFinalAgreement | `0x2dc52b4` | 輪次 | 當 +0x152 高於該輪次，或自身狀態 +0x130 不為 4 或 5 時忽略；否則夥伴狀態 5 |

取消傳送器 `0x964a60` 在自身狀態 +0x130 為 2 或 5 時不傳送任何東西；否則它傳送輪次 +0x150 + 1，設定 +0x130 = 2，遞增 +0x150 和 +0x152，並把夥伴的狀態從 3..5 降為 2（原因為 0 時降為 3）。處理函式只拒絕嚴格低於 +0x152 的輪次，所以在一次取消之後，過時的 ConfirmTrade 或 FinalAgreement 會被忽略，而更高的輪次會被接受。SelectPokemon 不讀輪次。

會話物件（0xab8 位元組，由 `0xca2704` 構建，vtable `0x3e3a6e8`）會把 +0x150..+0xab7 清零，所以兩個輪次都從 0 開始，一次會話的第一個 `0102` 和 `0104` 是 `b90100`。一次完成的交換之後 `0x964568`（自身狀態 6）會清空兩個報價，把兩個狀態設為 2 並把兩個輪次清零，所以席位上的下一次交換從輪次 0 開始。`pokeldn.za.host` 每次交換都重置其輪次。

|---|---|---|
| 5 | 會話更新 `0x95f600`（`0x95f680`） | 自身狀態 3 或 4、位元組 +0x148 置位、計時器 +0x138 至少 1.5 秒、夥伴狀態 4 或 5、`0x963710` 為真 |

| 7 | `0x2dc4b94`，由 `0x964f0c` 安裝 | worker 的狀態 7 委託；2.0.2 中不可達 |

### 加入者在這些流上欠什麼

以一對參考主機和一臺模擬主機的確認為基準實測：

- 協議 10 發往主機的 variable id，協議 11 發往 mesh id 0x0001；兩者都在兩位元組接收者 footer 中攜帶主機的 variable id；
- 每個遊戲包都做 zstd 壓縮；
- 純確認走流的基準 0xfff0 和訊息標誌 0x40；一個推進序列的確認會被當作資料讀取，後面留著一個洞。應用資料不攜帶訊息標誌；
- 協議 11 上的確認是 74 位元組：站點的四個位元組、一個流位元組、計數四，然後是四個條目，每個是一條下一個期望的半字和一個十六位元組掩碼，最後一個被截短。條目 1 是加入者的流；主機在另外三個中報告空閒基準 0xfff0；
- 身份在 INIT 下發出，選擇記錄緊隨其後，然後在一個新序列下反覆傳送，每次都是同樣的 1211 位元組（實測：約 0.5 秒後，然後約每秒四次）；
- 子頭的接收者計數在協議 11 上是三，在協議 10 上是零；
- 在協議 11 上，子頭長度計算的是四位元組站點字首之後的載荷，所以每一幀都比它宣告的多四個位元組：開場是 `00000001` 和 `1402 b900`，身份是字首加上整個協議 10 身份，九位元組訊息是 `1403b9018269fb308f`，確認是字首加上四個完整的 18 位元組條目。在宣告長度處被截斷的幀會被丟棄（主機會把它的開場重發約每秒十次）；最後四位元組錯誤的幀會被確認，但會讓主機停留在其搜尋介面。

LDN NodeInfo 的本地通訊版本（0x40 位元組中的 +0x2E）在參考站點上是 6；0 被同樣對待。

### 保活

設定的 +0x290 是一個以毫秒為單位的傳送靜默上限（`0x257d12c` -> `0x256a238`；0 變成 1000）。`SessionPacketWriter` vfunc 7 `0x2544004` 在向某站點發送時給該站點在 +0xb0 打上時間戳，並通過 `0x256a2d0` 向任何在時限內未被髮送過的站點發送一個額外資料包：一條協議 0、中間位元組 0xfd、埠 0、空載荷的 Pia 訊息（頭位元組 `04 00`）。沒有協議的 id 是 0；讀取者在下一輪接收開始時回收未讀訊息（`0x2566030`），所以這類訊息從不累積。位元組 +0xa0 標記一個正在被踢出的站點（`0x2577094`）。

### 資料包 id

資料包 id 在每個傳送者上使用兩個計數器：一個用於目的地 0x0001，一個用於其他所有目的地（0 和主機的 variable id 共用）。`nn::pia::session::SessionPacketReader::vfunc11` `0x2566920` 在任何協議之前檢查：未知源或無站點則接受；否則目的地會選擇一個控制器（0x0001 用 station+0x78，其他用 station+0x50），而 `0x2576ad0` 檢查資料包 id（線上 0x0a）和大端 nonce（線上 0x0d）：

    id == 0                                         accept, nothing recorded
    last id == 0                                    last id = id - 1
    last nonce == 0 and nonce != 0                  last nonce = nonce - 1
    (s16)(id - last id) < 1                         reject
    nonce != 0 and (s64)(nonce - last nonce) < 1    reject
    otherwise                                       last id = id, last nonce = nonce if non-zero

被拒絕的資料包會送到 `0x25655d8` 並被丟棄：重複的 id，或超前 0x8000 或更多。為目的地 0 使用單獨計數器的加入者，其每個 Net 0x51 都會被丟棄，直到它超過主機 id 計數器；主機會重複它的 Net 0x50 直到有一個通過（實測約 10 秒），其更新序列 1 被延遲。Net 0x51 處理函式 `0x2504100` 不讀任何頭欄位。

### 加入的其餘部分

- Net：連線狀態 0x11 以 0x12 應答，更新屬性 0x50 以 0x51 應答。
- Session：型別 5 的 update session 以十五個位元組應答：型別、站點的 LDN 常量 id、更新序列作為大端 u32，以及 0x0001。GBA 應用的應答（原始 MAC，無序列）會讓 Z-A 主機每隔兩秒無限重複其更新。

一個接受更新序列 1 的主機會在大約 50 毫秒後傳送其選擇記錄（實測就座後 1.2 和 1.25 秒），並進入其交換框。

### 協議 10 上的交換

每一方在選擇記錄之後傳送一個 354 位元組的 `0101`（實測約 2.5 秒後）。報價的最後一個位元組在站點主動傳送的預覽上是 1（零售主機在其游標於交換框上每次移動時都會發一個），在玩家拾取上是 0；主機的判斷依據是那個位元組，而不是計數。以 1 傳送的拾取會被確認並繪製為空，夥伴會帶著空槽等待在 "Communicating"。

加入者用自己拾取的應答主機的拾取，並以 `0102b90100` 確認；主機以相同內容確認，雙方都發送 `0104b90100`（主機在加入者的 `0102` 之後 1.5 秒），然後加入者傳送四個 `0200b901XX` 步驟：03 和 06 一起，0b 和 0e 在交換動畫和交換 worker 的隨機等待之後（[交換命令](#the-trade-commands)）。主機在協議 11 上傳送 `0000000202`，並在其字首下以 `0201b901XX` 應答每個步驟。`bin/za_join.py --trade-offer` 執行加入者。

### 載入收到的記錄時檢查什麼

夥伴的 `0101` 到達 `0xb2a44c`，它為 CommandSelectPokemon 註冊（`0xca33d8`，從 `0xca2928` 呼叫）。反序列化器 `0xb4e248` 要求標籤 0xb9 且有三個成員（`0xb4e33c`），把第一個讀作 u16（`0xa91178`），要求第二個是恰好 0x158 位元組的標籤 0xbc（`0xb4e4b8`），並把第三個保留在 struct+0x15a；任何錯誤時處理函式都不被呼叫（`0xb4e1c8`）。處理函式分配一個 PokemonParam（`0x82713c`）並用 `0x270994` 載入那 344 位元組：

1. `0xe47e94` 把 0x148 位元組複製到核心、16 位元組到尾部，解密兩者並比較校驗和；不匹配則設定 Bad Egg 位。它會清除快速模式，所以載入結束時重寫校驗和並重新加密：錯誤的校驗和被保留為已修正，並置上 Bad Egg 位。
2. `0xe3f18c`：對非零物種，`0x2901a4(species, form)` 在個人表（`0xe366b0`，一個以 `species * 10000 + form` 為鍵的對映）中查詢該對，並讀取 FlatBuffers 欄位 1 的位元組（vtable +6，`0xe3bbfc`），不存在時為 0。為 0 時設定 Bad Egg 位（`0xe51698(acc, 1)`）。缺失的鍵回退到 map+0x80，即物種 0 的條目，它沒有欄位 1。
3. `0xe41750(pp, 1)` 把由經驗得出的等級寫入尾部，並依據物種、形態、能力值等級、IV、極限特訓位、EV 和能力值性格重新計算最大 HP 和五項能力值。當前 HP 為 0 時保持 0，否則按最大 HP 的增量上升。

### 收到的 Pokemon 上的名稱檢查

`0xad2c68` 對空記錄返回（IsEmpty `0x13778`），否則執行 `0x89f250`（另一個呼叫者 `0x89de34`）：它把一個 `nn::ngc::ProfanityFilter` 開啟到全域性 `0x612d3d0`，帶一個 0x20000 位元組的緩衝區（`0x912e10`），用 `0x9138d4(str, len, language)` 檢查三個名字並收尾（`0x912d80`）。

| 名字 | 傳入的語言 | 失敗時 |

| 暱稱，0x58 | 記錄的，0xd5 | `0x8a0370` 用該語言寫入物種名（`0xe33ca0`）並清除暱稱位（0x8c 第 31 位） |
| 初訓家的，0xf8 | 記錄的，0xd5 | `0x3d8a248[language]`，用 `0xe579a0` 寫入 |
| 處理者的，0xa8 | 處理者的，0xc3 | `0x3d8a248[language]`，用 `0xe5a190` 寫入 |

語言為 12 或更高時按 0 索引該表。當 `[0x3f0784()]+0x380` 和 accessor+0x1a 都為 0 時，`0x8a0370` 對蛋或 Bad Egg 不寫入任何東西（`0xe4c950`、`0xe485f0`）。替換表 `0x3d8a248` 持有十二個 UTF-16 字串：0、1、6 為 `ゼット.`；2 為 `Z`；3 為 `Zed`；4、7、11 為 `Zeta`；5 為 `Zett`；8 為 `제트.`；9、10 為 `Z.`。

`0x9138d4` 在以下情況判定名字失敗：

- 長度為 0 或其第一個單元為 0；
- 長度為 7 個單元或更長，且任一單元落在 0x3041..0x3090、0x30a1..0x30fa、0x4e00..0x9fcc 或 0xac00..0xd7a3（區間表在 `0x3308840`、`0x33087b8`）；

- L（來自 `0x444330`）為 0、6 或大於 11；
- 過濾器的 vfunc +0x28 被 `0x913ad0` 以 `(&result, pattern, &str, 1)` 呼叫，pattern 為 `0x339f650[L - 1]`，結果非零。

## 與零售主機的交換

在 Link Trade 搜尋中的零售 Z-A 與 `bin/za_join.py` 交換，並保留組成的記錄。交換後主機在同一席位上回到它的交換箱，可以再次交換：`0x964568` 把兩個狀態都重置為 2、兩個輪次都重置為 0（[交換命令](#the-trade-commands)）。重複的 `--trade-offer` 在兩種角色下按順序交換一個佇列：第四步之後 2.7 秒，下一條記錄被預覽，並在主機的下一次選取時於輪次 0 下被選中（`tests/test_za_host.py`）。

交換動畫在第四步之後播放，不攜帶訊息。從該步起：1.1 秒時動畫，約 26 秒時收到的 Pokemon 出現在螢幕上，30.2 秒時主機的下一次預覽（`0101`，354 位元組），約 31.7 秒時玩家恢復控制。

在主機階段後期形成的席位會被移交：第一個資料包在關聯後約 1.4 秒到達，隨後沒有更新序列 1，主機每秒重複一次會話型別 9，直到它重啟自己的 Net（實測 6.5 秒）。wiki 把這個型別編號為開始主機遷移、把踢出編號為 12，而 Z-A 用 13。它背後的程式碼未被追蹤。

## 主機

搜尋中的主機也會掃描，並加入一個攜帶該作品廣告與連結碼的網路。`bin/za_host.py` 擔任主機；`pokeldn.za.host` 與模擬一對主機的交換逐位元組核對。

| 從席位起 | 主機發送什麼 |
|---|---|
| 0 秒起，每 0.46 秒一次直到被應答 | Net 連線狀態 0x11：序列 2，四個槽，主機和加入者都在 12345 |
| 收到 Session 加入時 | 加入響應（型別 2，37 位元組）給加入者的 id，更新會話（型別 5，序列 0）到 0x0001 |
| 隨附 | INIT 下協議 10 上的身份；協議 11 上再把身份與 `1403b9018269fb308f` 打包，字首 `00000002` |
| 隨附 | Net 更新屬性 0x50，每 0.5 秒一次直到 0x51 |
| 從 0.2 秒起 | 向 0x0001 發 RTT 請求，約每秒三次；對加入者的每個請求各回一個 |
| 更新 0 被確認後 1.15 秒 | 更新會話序列 1 |
| 更新 1 被確認後 | 1211 位元組的選擇記錄兩次，相隔 60 毫秒 |
| 2.7 秒後 | 預覽 `0101` |

與 GBA 應用的主機不同：

- 主機在更新會話中的站點條目攜帶標識令牌 `0x06`；
- 更新序列被寫兩次，+1 和 +21 處各一次；
- 屬性更新在場景 id 之後攜帶 `02`，而 GBA 應用寫 `01`（CloseParticipation，見下）；
- 廣播確認在第 1 個條目報告加入者的流，另外三個為 0xfff0。

零售 Z-A 會加入 `bin/za_host.py` 並在任意連結碼（`--code`）下交換。主機在第四步交換後保留會話，並在主機按 B 離開時關閉。`--hold-after-trade` 選擇定時關閉，從主機在交換後的第一次預覽起計時；總體的 `--seconds` 限制仍然生效。定時關閉、`--seconds` 限制和 Ctrl-C 時，主機會先向已落座的主機移交會話（[主機離開](#a-host-leaving)）；隨後停在交換箱上的主機會顯示 "Your trading partner chose to quit trading. The Link Trade will now end." 並返回 Link Play。

陷阱：交換存檔後未移交就關閉網路，或在交換動畫期間傳送移交，會在主機上畫出 "Error Number: 6"（交換已存檔）。

交換後回到交換箱的主機會預覽游標下的 Pokemon，所以 `--offer-out` 只保留選擇。

### 屬性更新

Net 更新屬性（型別 0x50）由 `0x2502960` 構建（序列在 NetProtocol+0x160，經由 `0x250f5d0`），並由 `0x250e414` 按大端序序列化。偏移從 0x26 位元組 Net 訊息的開頭算起：

| 線上 | 大小 | 欄位 |
|---|---|---|
| 0x04 | 4 | 序列 id，NetProtocol+0x160 |
| 0x08 | 8 | 網路 id，會話屬性 +0x90 |
| 0x10 | 2 | 參與者數（`0x25050dc`） |
| 0x12 | 2 | 站點槽，NetProtocol+0x1216 |
| 0x14 | 8 | 會話屬性值（`vfunc +0x10`）；LDN 屬性把場景 id（NetworkInfo +0x0a）保留在 +0x98 |
| 0x1c | 1 | 接受狀態（`0x2505ec0`） |
| 0x1d | 1 | 會話屬性 `vfunc +0x80` 的第 0 位 |
| 0x1e | 4 | 系統屬性大小（`0x24fe4dc`） |
| 0x22 | 4 | 遊戲資料大小（`vfunc +0x50`） |

`0x2505ec0` 在主機地址（+0x1280）和站點自己的地址（+0x1260）都設定之後，或 +0x12d0 非零時，返回 NetProtocol+0x340 處的位元組；否則返回 0。它的寫入者：

| 寫入者 | 值 |
|---|---|
| 網路建立與自動連線任務（`0x2511b94`、`0x2511658`），第三個任務站點 `0x2515714` | 會話屬性位元組 +0xa6 置位時為 1，清零時為 2 |
| `0x2515434`，來自任務位元組 +0xc0（由 `0x2515220` 儲存） | 經 `0x250758c`（`NetFacade` vfunc 17）為 1，經 `0x2507828`（vfunc 19）為 2 |
| 主機遷移 `0x250b060` | 該位元組為 1 時重跑 1 路徑，否則重跑 2 路徑 |
| setter `0x2500a9c` | 從 `0x25fdc90` 和 `0x25fe1ec` 寫入 1 |
| 收到 0x50 的站點（`0x25035bc`） | 訊息中的位元組；`0x2502e70` 把它自己的 +0xa6 設為 `byte != 2` |

LDN 會話屬性把 +0xa6 設為 `stationAcceptPolicy == 0`（NetworkInfo +0x62，`0x25234b8`）。1 表示接受全部；2 表示該標誌為清零。

                while the session's (u64, u16) at +0xe0/+0xe8 is non-zero and equals +0xf0/+0xf8,

                0x255c404 calls index 19 (0x255c484)

    0x2515220   0x250758c passes 1, 0x2507828 passes 2; when [[job+0xe0]+0x344] is 1 and 0x2513c0c

    0x2513c0c   stores it at LdnBackgroundProcessJob+0x9b (0x2513c6c, the only writer), schedules

`nn::ldn::SetStationAcceptPolicy`（PLT `0x3163b60`）由 LdnProtocol 索引 23（0，接受全部）、24（1，拒絕）和 21（3，白名單）呼叫。遊戲只在它是會話主機時，從 CloseSession 任務的更新 `0x1a25454` 關閉參與，隨後策略 1 跟上。

任務構建器 `0x1a228f0` 在兩個會話驅程上以 "CloseSession"（雜湊 `0x0dd344f64c81e84d`）呼叫。網路管理器（vtable `0x3c16978`）把驅程保留在 +0x38；它的 setter `0x199e850` 按模式安裝：0 無，1 本地驅程（`0x199eaa0`），2 網際網路驅程（`0x199ecc0`，用於排位戰），3 LAN 驅程（`0x199ef70`）。模式來自 "InitializePia" 任務，由 to-local 序列（Link Trade、私人對戰）以 1 構建、由 to-internet 序列以 2 構建；沒有呼叫以 3 構建它，所以 LAN 驅程在 2.0.2 中從不安裝。

| 構建器 | 驅程，槽 | 遊戲功能 |
|---|---|---|
| `0x19d7a70` | 本地，13（RandomMatchingSeq 的 CloseSession 步驟） | Link Trade 搜尋 |
| `0x19a7590` | 本地，19 | 私人對戰 |

槽 13 在 `0xc8a224` 處被呼叫一次，來自 Link Trade（`0xc9f8ec`，會話 "BoxTrade"）和排位戰。Link Trade 搜尋以第四個引數常量 1（`0xc8a194` 處的 `mov w3, #1`）執行本地驅程的槽 13（`0x19a1310`），所以它的 CloseSession 步驟構建該任務。槽 19 的呼叫者只有私人對戰頁面。

在零售 Link Trade 搜尋中，廣告在席位處持有策略 0；Pia 玩家數（廣告資料 +0x16，`e1 01 01 00` 到 `e1 01 02 00`）在 0.6 秒內變為 2，隨後在主機唯一的一條 Net 0x50（150 位元組，序列 1，接受狀態 `02`）之前廣告策略 1，並在整個會話中保持 1。它之前沒有主機遷移，所以 `02` 來自 CloseParticipation，即槽 13 的步驟 `0x19d7a70`。在 2 個參與者中的 2 個參與的情況下，該策略並沒有拒絕容量本可容納的任何人。

## 離開

一個站點通過兩個 `nn::pia::session` 任務之一離開，各自等待對方的回覆。排程器 `0x2547490` 讀取的會話型別（表 `0x336a9b7`，型別 0 到 17）：

| 型別 | 大小 | 傳送者 | 訊息 |
|---|---|---|---|
| 3 | 22 | 離開的加入者 | 離開請求：型別、隨機 u32、它的常量 id（8，大端）、它的變數 id（2）、地址型別 0、它的 IPv4、埠 |
| 4 | 15 | 主機 | 離開響應：型別、隨機 u32、從請求複製的離開者常量 id 與變數 id |
| 9 | 30 | 離開的主機 | 開始主機遷移：型別、主機的常量 id 與變數 id、0、主機的 IPv4 與埠、下一任主機的常量 id 與變數 id、`00 01` |
| 10 | 21 | 型別 9 指名的站點 | 它的確認：型別、它自己的常量 id 與變數 id，然後是主機的 |

`pokeldn.za` 構建全部四種（`build_leave_request`、`build_leave_response`、`build_migration_ack`）。

### 加入者離開

`LeaveMeshJob::SendLeaveRequest`（`0x2557e54`）向主機發送型別 3 並設定 500 毫秒的截止時間；`WaitLeaveResponse`（`0x2558098`）在收到型別 4 時完成，並在每個截止時間重發，共傳送四次（計數器 +0x9c，`0x25581e0` 處的 `cmp w8, #2; b.gt`），之後即使沒有型別 4 也完成。型別 4 只在 15 位元組且第 5 到 14 位元組是該站點自己的 id（+0x1b8、+0x1c0）時被 `0x25474f8` 接受；它設定任務的位元組 +0x99。主機的型別 3 處理函式 `0x254c5ac`（22 或 34 位元組，僅主機）在 `0x254c740` 寫出型別 4 並移除該站點（`0x2548500`）。

主機不傳送型別 4 的零售 Z-A 會以約 0.5 秒的間隔傳送四個型別 3，並在第一個之後 2.0 秒取消認證。`bin/za_host.py` 對每個型別 3 回一個型別 4；`bin/za_join.py` 在 `--hold` 或 `--hold-after-trade` 離開時傳送它自己的型別 3，並在收到型別 4 或第四次傳送之後繼續。

### 主機離開

`LeaveMeshWithHostMigrationJob` 指名下一任主機（`CalcNextHost` `0x255a6fc`），然後 `SendStartHostMigrationMessage`（`0x255a91c`）每秒傳送一次型別 9，直到 5000 毫秒的截止時間（`0x255a8c8`），之後任務以 `0x6c0e` 失敗。`WaitStartHostMigrationAck`（`0x255abb4`）在位元組 +0xe0 置位時立即完成。型別 10 的讀取者 `0x2550a64` 只在主機上、且第 11 到 20 位元組是主機自己的 id 時才接受 21 位元組的訊息，並在第 1 到 10 位元組是指名的下一任主機時通過 `0x255a630` 設定 +0xe0。

| 加入者的應答 | 零售主機在其型別 9 之後 |
|---|---|
| 無 | 每秒一個型別 9，共五個；Net 0x11 序列 3 每 0.5 秒一次，持續 4 秒；Net 0x40 持續 2 秒；10.8 秒時靜默；11.3 秒時網路斷開 |
| 型別 10，然後 0x12 `0112000000000003` | 0.04 秒時的 0x11；加入者停留期間，Net 0x40（`01 40 00 00`，源 0）每 0.3 秒一次，持續 4 秒 |

加入者的型別 10 和 0x12 以頭部標誌 2、目的地 0、資料包 id 0 發出，不帶尾部。

Net 0x11 是離開的主機在 `NetDestroyNetworkJob` 遷移形式中的連線狀態（`0x2516444`，標誌在任務 +0xd8，在斷開的站點是主機時置位，`0x2503c44`）：`0x2501930` 遞增序列（NetProtocol+0x15c），而位元組 29（is-migrating 位元組）在 NetHostMigration 狀態 NetProtocol+0x12d0 為 1 時為 1（`0x250f084`）。它向每個客戶端索取該序列的 Net 0x12；客戶端儲存序列、設定 NetProtocol+0x308 並應答（`0x2503164`、`0x25035c0`）。主機為每個 0x12 最多等 4000 毫秒，然後每 300 毫秒傳送一次 0x40，持續 4000 毫秒（等待超時時為 2000 毫秒），直到它獨自一人，並銷燬它的網路（`0x251693c`、`0x25169f8`）。

遷移形式與開場的 0x11 有三處不同：序列、位元組 26（開場形式中為 1，遷移形式中為 2；含義未被讀取）和位元組 29。零售與模擬主機都從源 0、目的地 0、資料包 id 0 發出它，頭部標誌 `0x3`（建立、壓縮），不帶尾部；0x40 以同樣方式發出，標誌為 2。型別 9 從主機的變數 id 發往指名站點的變數 id，帶尾部。

0x40 在非主機站點上啟動主機遷移（`0x2503d44` -> `0x25099a4`，`NetHostMigrationJob` `0x2509da0`）：下一任主機開啟網路併為其他人等 6000 毫秒；客戶端等 1000 毫秒後重新連線。

Link Trade 在移交時結束：型別 9 的處理函式 `0x2550684` 移除離開主機的站點，而交換場景的更新 `0x95f398` 在會話的站點數（session+0x110）為 1 時以原因 3（`0x95f508`）結束交換。

在兩個坐在交換箱中的模擬 Z-A 2.0.2 主機之間，主機中的玩家退出（B，然後 Yes）依次執行型別 9、型別 10、帶位元組 29 置位的 Net 0x11 序列 3、0x12，然後是在型別 9 之後 0.12 秒的 0x40；另一個站點在 0x40 之後 4 毫秒離開網路，不建立網路，並顯示 "Your trading partner chose to quit trading. The Link Trade will now end."

`bin/za_join.py` 用型別 10 應答指名它的型別 9，用 0x12 應答其後的 Net 0x11，並在第一個 Net 0x40 上離開網路（或主機靜默一秒之後）。

`pokeldn.za.host.HostSession.leave` 以相同的時序執行同樣的離開；`tests/test_za_host.py` 核對了型別 9 和兩條 Net 訊息。

## LAN 模式

傳說 Z-A 2.0.2 有一條它的程式碼從不走的 LAN 路徑。網路啟動 `0x1911540` 為模式 1 構建本地服務、為 2 構建網際網路服務、為 3 構建 LAN 服務（`0x2523710`）。模式來自網路任務的 `+0x50`（建構函式 `0xc5a5f4`），只通過 `0xc5a3e4(.., mode)` 建立，而它的兩個呼叫者傳 1（`0xc57600`）和 2（`0x2a0bcc4`）。Scarlet 的模式 3 呼叫者在這裡沒有對應物。

## 神秘禮物

2.0.2 中的神秘禮物提供通過網際網路獲取、用序列號/密碼獲取和檢視神秘禮物；沒有本地無線路徑。
