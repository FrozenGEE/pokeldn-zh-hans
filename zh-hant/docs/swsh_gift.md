# 神秘禮物選單的本地無線分支

劍與盾的神秘禮物選單通過本地無線接收神秘卡片：分發端廣播一個 LDN 網路，其廣播資料以分片形式攜帶卡片。除標註為劍以外，地址都出自盾 1.3.2 的 `main`；空口行為以零售主機實測為準。

## 選單

接收方式選擇器 `StateSelectReceiveDataBase` 為每個選單按鈕（`L_mystery_top_btn_00` .. `_04`）各有一個子類：

| 狀態 | 方法 |
|---|---|
| `StateSelectReceiveDataInternet` | 通過網路 |
| `StateSelectReceiveDataSerial` | 序列號或密碼 |
| `StateSelectReceiveDataLocal` | 本地無線 |
| `StateSelectReceiveDataFromBall` | 精靈球 Plus |
| `StateSelectReceiveDataRankMatch` | 排位對戰獎勵 |

接收狀態有 `StateReceiveBase`、`StateReceiveInternet`、`StateReceiveSerial`、`StateReceiveLocal`（`0x01004938`，其自身程式碼只引用了自己的進度條佈局）、`StateReceiveFromBall`、`StateReceiveRankMatch`、`StateReceiveNews` 和 `StateReceiveComplete`。遊戲記錄鍵 `fushigi_net`、`fushigi_serial` 和 `fushigi_p2p` 按渠道統計接收次數，與 `yy_battle_single_p2p` / `_net` 並列。

本地無線按鈕是 `/bin/message/<lang>/common/mystery.dat` 的第 69 行；第 9 行是搜尋訊息，第 11 行是「未找到禮物」。

### 應用的狀態機

排程器 `0x00FE6F80` 讀取 `app+0x718` 處的請求物件：`+0x60` 是就緒標誌，`+0x64` 是下一個狀態 id。標誌置位且 id 不超過 16 時，它經 `0x020641A4` 跳轉並構建該狀態。`SetNextState(id)` 是 `0x00FF0DE0`，有 63 處呼叫點。

| id | 狀態 | id | 狀態 |
|---|---|---|---|
| 0 | TopMenu | 9 | SelectReceiveDataSerial |
| 1 | ReceiveMenu | 10 | SelectReceiveDataRankMatch |
| 2 | ReceiveLocal | 11 | SelectReceiveDataFromBall |
| 3 | ReceiveInternet | 12 | ConfirmGift |
| 4 | ReceiveSerial | 13 | ReceiveNews |
| 5 | ReceiveRankMatch | 14 | ReceiveComplete |
| 6 | ReceiveFromBall | 15 | ConnectPalma |
| 7 | SelectReceiveDataLocal | 16 | （預設，TopMenu） |
| 8 | SelectReceiveDataInternet | | |

本地無線是狀態 2，即搜尋；然後是 7，即從分發端提供的內容中挑選；狀態 7 不接觸網路，其列表在進入之前就已填好。是什麼把 2 推進到 7 尚不清楚。`0x00FE700C`（`mov w8, w21`）是排程器的跳轉表索引。該類的主動虛表是 `0x025737C8`；`main` 中沒有任何東西指向這個應用，所以要靠在堆裡掃描虛表來找到它。映象裡沒有神秘禮物的 protocol buffer 模組。

## 禮物介面的網路

在本地無線介面上，主機廣播它常駐的本地遊玩網路：本地通訊 id `0x0100ABF008968000`（兩作相同）、版本 4、場景 id 65535（連線交換上為 60001）、接受策略 ALL、`NodeCountMax` 2、384 位元組廣播資料、密碼 CRC 為零。遊戲只在載入後 16 到 31 秒建立一次該接入點；進出神秘禮物不會發起任何 LDN 呼叫。禮物介面只設置自己的廣播資料並啟用 Pia 加入過濾器。

在該介面上，遊戲每分鐘呼叫約四十次 `nn::ldn::Scan`，其間夾雜 `SetAdvertiseData` 和 `GetNetworkInfo`，從不呼叫 `Connect` 或 `CreateNetwork`。掃描在 802.11 層是被動的（沒有探測請求）。其過濾器只點名本地通訊 id 和網路型別；`SessionId` 和 `SceneId` 不過濾。

### 模式位元組

`session_config+0x70` 是本地遊玩模式。`0x01096730` 經跳轉表 `0x02066C14` 把它對映為 Pia 場景 id 和參與者數；`0x010961a8` 經 `0x02066C40` 把它對映為廣播資料位元組 `0x97`（廣播 `0xAF`；遊戲的資料從 `0x18` 開始）：

| 模式 | 場景 id | 參與者 | 廣播資料 `0x97` |
|---|---|---|---|
| 0 | 無，建立者在 `0x01096764` 返回 false | | 0xFF |
| 1 | 60021 | 2 | 0x01 |
| 2 | 60001 | 2 | 0x0D |
| 3 | 60002 | 2 | 0x0E |
| 4 | 60003 | 2 | 0x0F |
| 5 | 60004 | 4 | 0x10 |
| 6 | 60005 | 2 | 0x1E |

連線交換是模式 2；禮物介面執行模式 0，不建立會話。進入應用時把模式儲存到 `app+0xFE8` 並置 0（`0x01022f08`）；離開時恢復（`0x01023198`）。極巨團體戰的主機廣播 `0x11`，它不在表中。另一個隨介面變化的廣播位元組只有 `0xB9`（禮物 0x00，交換 0xAA），含義未知。

## 禮物介面上的 Pia 網狀網

該介面上的網狀網不接納任何加入者；卡片走[信標傳輸](#the-card-travels-in-beacon-advertise-data)。加入者完成 0x14 上的站點握手，而它在 0x18 上的網狀網加入請求被拒絕：

    02 00 ff ff 01        JOIN_RESPONSE, refused, reason 1

`ProcessJoinRequestJob` 依次執行 `InitialStep`、`CheckApprovalJoin`、`SendJoinRefused`、`SendJoinResponse`、`WaitResponseAck` 和 `JoinSucceeded`。原因 1 只來自應用回撥；其餘原因由傳輸檢查給出。

| | 劍 | 盾 |
|---|---|---|
| `CheckApprovalJoin` | `0x01553d20` | `0x017cc450` |
| 原因 1 的儲存 | `0x01553d58 strb w9, [x19, #0xbc]` | `0x017cc59c strb w9, [x19, #0xba]` |
| `MeshProtocol+0x60` 處的 Pia 跳板 | `0x0157fcfc`，全域性 `0x04c4b848` | `0x018414b0`，全域性 `0x02616a30` |
| `SendJoinRefused` | `0x01553d80` | |
| 傳輸檢查 | `0x0154806c` | `0x017bb2e0` |

當物件 `+0xb0` 為空時，跳板直接批准；否則尾呼叫它。遊戲在 `0x006b47b0` 處把跳板設為加入過濾器 `0x006b41c0`，在 `0x006b5340` 處清除，兩處都在模式切換 `0x006a9af0` 之內。

### 加入過濾器 0x006b41c0

`manager` 是 `[0x02610000 + 0x4b0]`，`session` 是 `[manager+0x58]`。四道閘門依次為（取值為禮物介面上的值）：

| 順序 | 位置 | 檢查 | 取值 | 結論 |
|---|---|---|---|---|
| 1 | `0x006b4204` | 阻止列表已啟用（`manager+0x21C`）且非空（`+0x1C0`） | 已啟用，空 | 通過 |
| 2 | `0x006b8260` | Pia 站點數 `pia_obj+0x1A8` 低於 `session+0x1F0` | 計數 1，上限 0 | 拒絕 |
| 3 | `0x006b827c` | 允許列表標誌 `session+0x4f5`；置位則遍歷 `session+0x4c0` 處的列表 | 0 | 批准 |
| 4 | `0x006b4248` | 身份 `+0x10` 處的半字（地址第 8 位元組，IPv4 下為零） | 0 | 批准 |

`session+0x1F0` 的上限只由 `0x006b9900` 寫入，可達路徑是極巨大冒險匹配（`0x00bd9b30`）和極巨團體戰巢穴（`0x01031c74`）：禮物介面上為 0，主持連線交換時為 2，主持極巨團體戰時為 4。在禮物介面上把它寫成 8 會接納一次加入，但入座的場景不傳送應用載荷，也不在 0x84 上開啟任何東西。

### 傳輸檢查

`0x017bb2e0` 在回撥之前執行，返回 `0xFF` 或原因位元組。它的物件是 `read_u64(read_u64(main + 0x0262F7B0))`。

| 欄位 | 寬度 | 內容 |
|---|---|---|
| `+0xA8` | u16 | 站點數上限 |
| `+0xAA` | u8 | 啟用位元組；為零時在任何其他檢查之前返回 2 |
| `+0xAB` | u8 | 選擇計數讀取哪個位掩碼字 |
| `+0xAC` | u8 | 計數遍歷位掩碼的多少位 |
| `+0xC4` | u32 | 佔用位掩碼，在 `[0xAC] == [0xAB]` 時讀取 |
| `+0xC8` | u32 | 否則讀取的佔用位掩碼，空閒槽搜尋只讀這一個 |

| 位置 | 在以下情況返回 0 |
|---|---|
| `0x017bb380` | 計數（1 加上每個置位）`>= max`，或沒有空閒槽（`0xFD`） |
| `0x017bb498` | `mesh_obj+0x370` 處的表已滿，對照的是 `read_u64(main + 0x02616710) + 0x70` 處的 u16 或其容量 `table+0x48` |
| `0x017bb4d4` | `mesh_obj+0x132` 處的位元組，在型別 0x18 事件上置位 |

型別 0x19 事件置位 `mesh_obj+0x131` 時，它返回 4。

## 接收作業與匯入器

gfl 網路管理器是 `read_u64(read_u64(main+0x0261CBA8))`（虛表 `0x025819A0`）；全域性為空是每個傳送存根上的無會話守衛。它在 `+0xD0`/`+0xD8` 處沒有條目陣列。進入本地無線分支時，`StateReceiveLocal` 的驅動 `0x01004C80`（`state+0x2A0` 上的 case 機）經 `0x010B7100` 構建一個接收作業（建構函式 `0x010B73E0`、虛表組 `0x0257DD88`、輪詢 `0x010B74D0`），把它連結到 `manager+0x68`，並在 `state+0xB0` 處安裝接收委託（`0x0100504C` 組）。

作業在 `job+0x60` 持有資料接收器（目標 `0x01005BC0`），在 `job+0xE0` 持有進度回撥（`0x01005C70`），其訊息源是 `job+0x08` 處的會話物件（虛表 `0x0250DAE0`）。它隨搜尋介面開啟而出現，隨介面關閉而釋放。陷阱：重新進入該介面會在新地址重建作業和接收器的物件。

接收器尾呼叫 `0x00FF0E00` -> `0x00FF1FB0` -> `0x00FF2170`，即匯入器；它拒絕長度不是 0x2D0 位元組記錄（720 位元組，PKHeX 第八世代神秘卡片的尺寸；`0x00ff22f4`）整數倍的主體。每條記錄在 `0x00FF2354` 處通過[記錄必須攜帶的內容](#what-a-record-must-carry)的檢查，再經 `0x01449820` 過濾，由 `0x00FF3EC0` 實體化。

匯入器的第二個引數是路由；它成為卡片 `+0x64`（`0x00FF3F5C`），並在 `route != 0` 時成為頭部 `+0x0E`（`0x010B5FAC`）。每個呼叫者都是某個接收狀態虛表第 16 槽中的 lambda：

| 狀態 | 路由 | 呼叫點 |
|---|---|---|
| `StateReceiveLocal` | 0 | `0x01005bf8` |
| `StateReceiveInternet` | 1 | `0x01011588`、`0x010115f0` |
| `StateReceiveSerial` | 2 | `0x0100a268`、`0x0100a2d0` |
| `StateReceiveFromBall` | 2 | `0x0100fc78`、`0x0100fce0` |
| `StateReceiveRankMatch` | 3、4 | `0x01012458`、`0x010124c0` |

除 0 以外的任何路由都會覆寫記錄的日期（[卡片的日期](#the-cards-date)）。路由 3 和 4 還會在塊 `0xa83021c1` 和 `0xce07d358` 中置位位元組（`0x00ff24e0..0x00ff26d4`）；路由 0 兩者都不碰。

## 卡片隨信標廣播資料傳送

分發端不加入任何網路。它廣播一個網路，其廣播資料攜帶卡片，接收方從自己的 `Scan` 結果中重組出它。

禮物是 gflnet3 核心的一個使用者，與交換同步泵分開。核心管理器 `read_u64(read_u64(main+0x02616B80))` 自稱 `BeaconCommunication`（`0x02068858`），驅動 `nn::ldn::Scan`、`GetNetworkInfo`、`SetAdvertiseData` 和 `OpenAccessPoint`（包裝函式 `0x017978F0`、`0x01794C3C`/`0x01799BE0`、`0x017961B0`、`0x01794CF0`）。Pia 網狀網的加入不會改變其中的任何東西。

## 信標主體幀

0x180 位元組的 LDN 廣播資料由一個 0x18 位元組的頭部和一個 0x168 位元組的主體組成，後者由信標核心封裝。

| 主體內偏移 | 大小 | 欄位 |
|---|---|---|
| `+0x00` | 2 | 覆蓋 `body[2:0x168]` 的 CRC-16/ARC，初值 0，無最終異或 |
| `+0x02` | 12 位 | 網路 id，低 8 位在 `body[2]`，高 4 位在 `body[3]` 的低半位元組 |
| `+0x03` 高半位元組 | 4 位 | 每次抓包都為零 |
| `+0x04` | 1 | 每次抓包都為零 |
| `+0x05` | 最多 0x163 | 應用載荷 |

網路 id 在神秘禮物、連線交換和極巨團體戰介面上都是 `0xD70`。載荷上限是 `0x006c2174` 處的 `cmp x2, #0x163`。

校驗和例程是 `0x0065dcb0`（表由 `0x0065def0` 構建），反射 CRC-16/ARC，多項式 `0xA001`。

構建器 `0x006c1fa0` 清零主體，用位打包寫入器 `0x006c1830` 把網路 id 寫到 `body+2`，把載荷複製到 `body+5`，並把覆蓋 `body+2` 起 `0x166` 位元組的校驗和存到 `body+0`；載荷缺失或超長時改存 `0xFFFF`（`0x006c21d4`）。

## 收到的信標要通過的閘門

`0x006c1be0` 返回 1 表示接納一個條目。收到的廣播（`0x006bb9d4`、`0x006c4b38`、`0x006ca0dc`）只有在它接納時才進入儲存 `0x006c53b0`。任何一項測試失敗都會被拒絕：

1. `0x02616b80` 背後的核心物件存在；
2. `body+0` 等於在 `body[2:0x168]` 上重算的校驗和；
3. 主體的網路 id 與 `0x02616b88` 背後的半字不同，後者是核心缺失時構建器的回退值；
4. 網路 id 與核心自己的值逐半位元組一致（`0x006c1cf0`）：低半位元組必須相等；第二半位元組不同則接納；否則第三半位元組必須相等。

校驗和過期的信標會被掃描到，但從不儲存。

陷阱：0x480 位元組的 `NetworkInfo` 掃描結果槽（其中包括 `pia_obj+0x3C0`）會完整複製任何主體的 0x180 位元組，不論其校驗和；那裡的標記只能證明收到過。

`0x006c53b0` 只在條目是新的時追加。儲存的陣列在 `+0x40`，計數在 `+0x48`，容量在 `+0x50`（0x32），互斥量在 `+0x60`；一個條目 0x180 位元組，先是虛表指標，主體在 `+8`。兩個儲存經 `0x006c5300` 交替。

`0x010f6600` 遍歷一個儲存，經 `0x006c1d50` 讀網路 id、經 `0x006c1f80` 讀載荷（返回 `body+5`；唯一呼叫者 `0x010f66c4`），並把載荷交給 `0x010f8cf0`，後者把它存入一個訊息物件，供 `[gfl_job+0x68]` 處、虛表 `+0x38` 的處理函式使用。接收方自己的站點資訊結構就是這份載荷，所以它的偏移位於廣播資料內 0x1d 位元組處。

## 輪詢重組出的訊息

載荷第 0 位元組是訊息型別。`0x010f6600` 為每個已知型別構建一個型別化檢視，指向 `payload+1`：

| 型別 | 檢視 | 去向 |
|---|---|---|
| 0 | `0x010f8730` | `0x0110f270`，帶 `0x02610958` 背後的物件；接收方自己的信標（站點資訊） |
| 1 | `0x010f8830` | `[manager+0x68]` 處的作業，虛表槽 `+0x38` |

在禮物介面上，那個作業就是接收作業，槽 `+0x38`（`0x0257dd88+0x48`；虛表指標是組加 0x10）是它的輪詢 `0x010b74d0`，所以型別 1 的載荷會送進匯入器。

輪詢經 `0x010f7bf0` 讀取 `payload+1` 處的十位元組頭部（欄位訪問器 `0x010F7A40..0x010F7A80`；傳送側在 `0x010F7C08` 處佈局）；分片緊隨其後：

| 偏移 | 大小 | 含義 |
|---|---|---|
| `+0` | 4 | 為零，否則輪詢立刻返回 |
| `+4` | 2 | 訊息總長度 |
| `+6` | 1 | 分片數 |
| `+7` | 1 | 本分片的索引，不低於分片數則拒絕 |
| `+8` | 2 | 重組後訊息的 CRC-16/ARC（`0x0065dcb0`） |

每個在途訊息一個 0x88 位元組的重組上下文，位於 `job+0x160` 與 `job+0x168` 之間，除索引外按頭部的每個欄位匹配（`0x010f7550`）。`0x010f7100` 把分片複製到 `index * 300`；索引越過緩衝區或該位已置位的分片被丟棄。一條訊息最多 65535 位元組、256 個分片；720 位元組的卡片是 300、300 和 120 三個分片。

`0x010f7610` 報告所有位都已置位後，`0x010f7680` 把 `context+0x18` 與 `0x010f71e0`（經 `0x0065dcb0` 計算的緩衝區）比較，不匹配則返回空。輪詢在返回空時跳過接收器（`0x010b77fc`），並在同一次輪詢內無論結果如何都抹掉該上下文。

陷阱：校驗和錯誤的訊息不會留下痕跡，而空上下文列表也正是訊息完成後留下的樣子。

## 記錄必須攜帶的內容

| 偏移 | 大小 | 欄位 |
|---|---|---|
| `+0x00` | 8 | 日期（[卡片的日期](#the-cards-date)） |
| `+0x08` | 4 | 卡片 id，u16，按整字比較：`+0x0A..+0x0B` 必須為零 |
| `+0x0C` | 2 | 無作用 |
| `+0x0E` | 2 | 遊戲版本掩碼 |
| `+0x10` | 1 | 標誌：第 0 位跳過每卡一次表，第 2 位按卡片日期一次 |
| `+0x11` | 1 | 禮物種類，1 到 5 |
| `+0x12` | 1 | 每卡一次的上限 |
| `+0x13` | 1 | 每卡一次的標記 |
| `+0x15` | 1 | 標題索引 |
| `+0x1C` | 1 | 保留到頭部 `+0xf` |
| `+0x20` | | 該種類的載荷 |
| `+0x2CC` | 2 | 把本欄位清零後整條記錄的 CRC-16/CCITT-FALSE |

版本掩碼：匯入器呼叫 `0x007d4270`（盾：`mov w0,#0x2d; ret`），值為 `0x2D` 時對掩碼測試 `1 << 1`，否則測試 `1 << 0`（`0x00ff2330..0x00ff2358`）。盾接受第 1 位；`0xFFFF` 通過任一版本；零則跳過。

每卡一次表：`+0x13` 非零時（`0x00ff236c`），如果相簿 `+0x1660` 處那張表（塊 `0x112D5141` 偏移 `0x1600`；五十個四位元組條目，一個半字卡片 id 和一個位元組）中某個條目的卡片 id 與 `+8` 處相同、位元組與 `+0x13` 相同，`0x01449820` 就拒絕該記錄。保留時，如果 `+0x12` 非零且 `+0x10` 的第 0 位清零（`0x00ff152c`），`0x00ff1544` 會呼叫 `0x014494a0(album, record)`：它把五十個條目整體下移，在 `+0x1724` 追加 `{card id, +0x13}`，當該 id 的、位元組非零的條目達到 `+0x12` 個時，在前 49 箇中把它們清零。`+0x13` 或 `+0x12` 為零，或 `+0x10` 的第 0 位置位時，卡片每次都會被匯入。

最近接收表：`+0x10` 的第 2 位讓保留路徑呼叫 `0x01449560(album, record)`（`0x00ff1548`、`0x00ff1558`）：相簿 `+0x15c0` 處十個 16 位元組條目，`+0` 是 u64 日期，`+8` 是 u16 卡片 id。持有該 id 的條目取用記錄的日期（`0x01449650`）；否則第一個日期更早（`0x016cc1f0`，無符號比較）的條目取用 id 和日期（`0x01449804`、`0x0144980c`）。空條目因為日期為零而更早，會被取用。

被接納的記錄複製進一個 `0x338` 位元組的結構（記錄在 `+0x68`，`0x00ff2380`），交給校驗器 `0x010b5de0`；它清零 `+0x2CC`，對全部 0x2D0 位元組執行 CRC-16/CCITT-FALSE（多項式 `0x1021`，初值 `0xFFFF`，`0x010b5e60`、`0x010b5f54`）。空指標或長度不是 `0x2D0` 時返回 `0x80000000`，校驗和不匹配時返回 `0x80000001`（匯入器把它對映為 1，`0x00ff23d0`），其他情況（包括種類不在 1..5 內）返回 0。它填充 `0x68` 位元組的頭部：卡片 id 到 `+8`，`+0x15` 到 `+0xa`，`+0x11` 到 `+0xc`，`route != 0` 到 `+0xe`，`+0x1C` 到 `+0xf`。卡片物件是 `0x3A8` 位元組，把該結構儲存在 `+0x70`。

卡片 id：`0x00ff2f50` 把記錄 `+0x08` 處的 u32（`0x00ff30c0`）與 16 位 id 比較，因此 `+0x0A` 或 `+0x0B` 處任何非零值都匹配不上，匯入器報告 2（在本作中無法獲得的禮物）。沒有任何東西讀取 `+0x0C`。

標題：`+0x15` 索引 PKHeX 以 `text_wondercard8_<lang>.txt` 提供的標題表，卡片被接受之前就顯示在列表裡。構建器用到的索引：1 寶可夢蛋，3 道具名，21 "{species} (Gigantamax Pokemon)"，34 零花錢，36 服裝，39 對戰點數。索引 0 只有物種名；索引 11 是 "{species} de {original trainer}"。

種類：1 到 5 經 `0x02067620` 分發；其他值返回成功但不構建任何東西。種類 3 和 5（`0x010b5fd8`）把 `+0x20` 處的字保留到頭部 `+0x30`，不構建任何東西。種類 1 進入 `0x010b58f0`，種類 2 複製其道具對，種類 4 進入 `0x010b5bb0`。

語言索引來自 `0x02067650` 處的表（遊戲語言到 0..8）。獎章位元組送到 `0x00775d50`；超過 127 的索引不設定任何東西。獎章位元組全為零的記錄會把獎章 0 寫三十二次：把列表填滿 `0xFF`。

解析器不讀取等級和相遇等級；這兩個偏移來自認領的卡片。

等級 0：構建器反覆取 `r = random & 0x7f` 直到 `r <= 99`，然後取 `r + 1`，在 1..100 上均勻（`0x010b6218`），相遇等級為 0。蛋無論如何都是 1 級（`0x010b6400`）。經驗值按物種的成長組計算。

個體值：構建器按 HP、攻擊、防禦、特攻、特防、速度的順序檢查六個位元組；第一個落在 `0xFC..0xFE` 的值把一個滿值數量 `byte - 0xFB`（1 到 3）存到 `[sp+0x110]`，並把該物種六項個體值全設為 `0xFFFF`，丟棄其餘（`0x010b6300..0x010b63c4`）。否則 32 及以上的位元組變成 `0xFFFF`，低於 32 的保留。`0x00766660` 把等級壓到不超過 100，並往相應數量的不同隨機位置寫 31（`0x00766a50..0x00766b04`）；仍是 `0xFFFF` 的每項個體值都隨機取 0..31（`0x00766de8`）。因此任一個體值位元組為 `0xFC`、`0xFD` 或 `0xFE`，就恰好得到 1、2 或 3 項 31 的隨機個體值。

全零的記錄會給出一隻雄性、坦率、第一特性、個體值全 0 的寶可夢。除非顯式給出欄位，`pokeldn.swsh.wc8.pokemon_card` 會寫入性別 3、性格 `0xFF`、特性 3 和每個個體值位元組 `0xFF`，讓遊戲逐項隨機。

性別 3 每次構建隨機一次，而一次領取會構建兩次：揭示 `0x00fe3720`（`0x00fe3a50`）和兌換 `0x010159d0`（`0x01015a0c`），所以揭示時顯示的性別可能與隊伍收到的不同。性別 0、1 或 2 跳過隨機（`0x00766d94`）。應用和 `bin/swsh_gift_host.py` 在構建卡片時只隨機一次性別（`r + 1 < ratio` 時為雌性，`r` 小於 253）；`--set gender=3` 會恢復遊戲自己的隨機。

## 一張卡片經信標送達，端到端

來自合成信標的三分片 720 位元組記錄能在未修改的主機上到達匯入器。匯入器的結果在 `bound+0x2C0`，`bound` 即 `job+0x80`；`0x00ff1fb0` 在它非零時返回它，否則在卡片列表為空時返回 2（版本掩碼為 0 給出 2，即「在本作中無法獲得」；校驗和錯誤給出 1，即「接收禮物失敗」）。日期為零的封裝種類 3 記錄會顯示 2070 年 1 月 1 日。

## 一張卡片送達零售主機

`bin/swsh_gift_host.py` 經 LDN 把每一種禮物送達一臺零售版劍。主機只在 LDN 協議 1 上列出卡片，且廣播資料要以其自身禮物廣播的 Pia 頭部開場（[卡帶與會話](swsh_session.md)）：隨機網路 id、密碼 CRC 為零、系統通訊版本 5、頭部大小 0x18、隨機會話引數和八個零位元組。場景 id 和應用版本不過濾。標題只看 `+0x15`，與種類無關；種類決定送達什麼。

種類 2 的記錄只需要種類、道具對和數量。解析器把記錄 `+0x20..+0x37` 中恰好六組 id/數量對複製到頭部 `+0x30..+0x47`（`0x010b6024..0x010b6080`），並把頭部 `+0x0D` 設為數量非零的對數（`0x010b6084..0x010b60e4`）；兌換時對每組數量非零的對呼叫 `Bag::AddItem`（`0x01015d00..0x01015dd0`）。1.3.2 的道具表有 1607 個條目；`bin/message/<lang>/common/itemname.dat` 中名字以 `★` 開頭的都是佔位項（其中 1279 到 1578）。PKHeX 把 1607 個 id 中的 51 個命名為 `???`；應用的道具選擇器列出 `ItemStorage8SWSH.GetAllHeld()` 的 817 個 id，也就是其卡片檢查所接受的集合。

種類 4 是服裝（[服裝](#clothing)）。種類 3 和 5 把 `+0x20` 處的字加到狀態物件 `[[0x2610798]+0x208]` 中被鉗制的計數器上：

    kind 3  0x01015e00   [status+0x17c] = min(old + amount, 9999)                  0x014390fc

`status+0x64` 是零花錢（`AddPocketMoney_` `0x014ad5e0`，`GetPocketMoney_` `0x014ad700`）。兩種兌換都從記錄 `+0x20` 讀取數量。

種類 1 的兌換 `0x010159d0` 構建寶可夢（`0x010b6110`；空則返回 0）並交給隊伍（`0x01015b78`，虛擬函式 `+0x28`）。隊伍拒絕時，它向盒子儲存 `[[0x2610798]+0x220]` 要一個空槽（`0x01408000`、`0x01015bd0`），只有存在空槽時才放置（`0x01406b00`、`0x01015c08`）。它的結果從不被檢查；通不過空間檢查的卡片到不了這裡（[選單拒絕什麼](#what-the-menu-refuses)）。

## 作為禮物信標的板子

`bin/swsh_gift_host.py --save-to-board`（應用中的「保留在板子上」）把卡片的廣播週期存到 ESP32 板子上然後退出。之後用任意 USB 充電器供電，板子就自行廣播該卡片，按啟動器 `--dwell` 的節奏每次三個分片，直到有主機開啟它（[便攜信標](hardware_esp32.md#portable-beacon)）。每次上電都用同一網路和金鑰；廣播 nonce 每次從隨機值開始。僅靠板子向零售主機送達卡片尚未實測。

| 分組 | 卡片 |
|---|---|
| 寶可夢 | 89 |
| Pokemon HOME | 16 |
| 道具 | 69 |
| 服裝 | 9 |

畫廊中的 949 張劍／盾卡片全部通過校驗器 `0x010b5de0`。排除在外的有：740 張禮物與已保留卡片重複、只改了日期或卡片 id 的（多為排位對戰獎勵），12 張道具是 ★ 佔位項的，以及 8 張 Pokemon HOME 卡片的第一個修訂版。

PKHeX 檢查只在兩種情況下接受超極巨化因子：物種的進化鏈中有超極巨化形態（如卡片 1641 和 1642 把它給了妙蛙種子和傑尼龜），以及美錄梅塔（極巨湯對它無效，`services/pkhex/Program.cs` 中的 `CanGigantamax`）；其他物種一律拒絕。

### Pokemon HOME

該分組收錄畫廊中劍／盾的 `HOME Simulated WCs`（卡片 id 9000 起，PKHeX 的 `WC8.IsHOMEGift`），每張都與 PKHeX 活動資料庫持有的卡片逐位元組相同，標題用 projectpokemon 的。卡片 9000 到 9007 的第一個修訂版把所有 PID 固定為 0；保留的第二個修訂版讓遊戲隨機一個。

從這些卡片收到的寶可夢不帶 HOME 追蹤碼，而 PKHeX 要求 HOME 給出的禮物帶上它：寶可夢由主機生成，所以無論 HOME 追蹤碼設定如何，PKHeX 都會標記追蹤碼缺失（[HOME 追蹤碼設定](gui.md#the-home-tracker-setting)），而 Pokemon HOME 目前接受它。應用用琥珀色框出這些卡片並加以說明。

`+0x10` 處的標誌決定主機多久能接收一次卡片（[選單拒絕什麼](#what-the-menu-refuses)）：

| 標誌 | 卡片 | 接收 |
|---|---|---|
| 第 0 位 | 130 | 每個卡片 id 一次，之後以訊息 7 拒絕 |
| 第 2 位 | 13 | 每個卡片日期一次，每天最多十次 |
| 都沒有 | 46 | 每次都可以 |

兩張寶可夢卡片的版本掩碼為 1 或 2，會被另一版本跳過。

## 服裝

種類 4 的記錄從 `+0x20` 起攜帶十二對 u32，先是類別再是索引：狀態位元組 `+0x105` 為零的玩家用前六對（`+0x20..+0x4F`），否則用後六對（`+0x50..+0x7F`）。該位元組由 `0x01424c20` 在狀態物件 `[[0x2610798]+0x1e8]` 上讀取。PKHeX 的 `MyStatus8` 把玩家性別放在塊偏移 `0xA5`，比它低 `0x60`；該物件是否在 `+0x60` 持有該塊尚未驗證。

解析器 `0x010b5bb0` 把玩家的六對複製到頭部 `+0x30..+0x5F`，並把索引不為 `0xFFFFFFFF` 的對數複製到頭部 `+0x0D`。兌換 `0x01015eb0` 按同樣的判斷（`0x01015f14`；記錄 `+0x20` 是頭部加記錄 `+0x88`）再次讀取記錄中的對，並對每個索引不為 `0xFFFFFFFF` 的對，在衣櫥 `[[0x2610798]+0x218]` 上呼叫 `0x0143a450(wardrobe, category, index, 1)`。該設定函式拒絕大於 14 的類別或大於 1023 的索引，否則設定位元組 `wardrobe + 0x68 + category * 0x80 + index / 8` 的第 `index & 7` 位。`(0, 0)` 這對會設定類別 0 的第 0 位；索引為 `0xFFFFFFFF` 的槽跳過。

## 選單拒絕什麼

兌換所選卡片之前，`0x01014a60` 讀取種類 `card[+0x7c]`（`0x01014bcc`）、`w25 = 0x00ff1750(card) - 1`（`0x01014bd4`、`0x01014be4`）以及記錄標誌 `[card+0xe8]` 的第 2 位（`0x01014be8 ubfx w24,w8,#2,#1`），並對種類 1 執行空間檢查 `0x013adee0`（`0x01014d68`）。依序：

    0x00ff1750 returned 1, 2 or 3    message 7, 0x10 or 0x11     0x01014d9c cmp w25,#3; table 0x02065360 = 7, 16, 17
    kind 1 and no room               message 8                   0x01014c14 mov w21,#8
    flag bit 2 set                   message 0xF, then state 3   0x01014d38 mov w1,#0xf; continuation 0x010156f0
    otherwise                        state 3, the redemption     0x01014e70

`0x02064f80` 儲存 `mystery.tbl` 的標籤雜湊，每個訊息索引一個 u64；`0x01000718` 處的初始化器把條目 k 解析到 `owner+0x5f8+8k`，由 `0x01002da0` 讀回。以下取自 1.3.2 的英文 `mystery.dat`：

| 訊息 | 標籤 | 文本 |
|---|---|---|
| 7 | `msg_o_mystery_win_13` | 你無法獲得這個禮物，因為你已經收到過同樣的禮物。 |
| 8 | `msg_o_mystery_win_14` | 沒有空間容納另一隻寶可夢了。請在隊伍或寶可夢盒中騰出空間，然後再試。 |
| 0xF | `msg_o_mystery_win_34` | 這個禮物每天只能接收一次。收到後，要到第二天才能再領取。 |
| 0x10 | `msg_o_mystery_win_35` | 這個禮物每天只能接收一次。今天的份額已被領取，請明天再來。 |
| 0x11 | `msg_o_mystery_win_36` | 每天只能接收 10 個禮物。今天已經領取了 10 個，請明天再來領取。 |

拒絕後的續程 `0x01015740` 在 `+0x80` 存 0，即選單的第一個狀態。被拒絕的卡片既不放置也不保留，原因消失後可以再次領取。

盒子儲存沒有空槽（`0x013adfb4 cset w20,eq`）且隊伍報告已滿（隊伍虛表 `+0x60`，第 12 槽，`0x013adfc4`；`0x013adfd0 and`）時，`0x013adee0` 返回 1（沒有空間）。

`0x00ff1750` 只被 `0x01014bd4` 呼叫，是接收檢查。`[card+0x60]` 或 `[card+0x68]` 為零時它立刻返回 1（`0x00ff1750..0x00ff1770`）；對於路由 0 到 2，它經 `0x00ff17b4` 繼續到 `0x00ff1a30`：

    data = album+0x60 (0x014480e0)
    record flag bit 0, and the card id's bit set in the bitmap at data+0x1450 (album +0x14b0)   -> 1
    record flag bit 2 clear (0x00ff1ab0)                                                       -> 0
    the record's day invalid (0x00ff1b84)                                                      -> 3
    ten entries of 0x10 bytes from data+0x1560 (album +0x15c0), 0x00ff1b88..0x00ff1c70:
        entry id == card id and card day <= entry day (0x016cc210, cset ls)                   -> 2
        card day > entry day (0x016cc1f0, cset hi): a free entry
    a free entry                                                                               -> 0
    none                                                                                       -> 3

點陣圖讀取取位元組 `id >> 3`（`0x00ff1a8c ubfx x9, x23, #3, #0xd`），沒有邊界檢查：點陣圖是 0x100 位元組（id 0 到 2047），所以帶標誌第 0 位且 id 為 2048 及以上的記錄會讀到它之外，id 從 13000 起則讀出該塊的 0x17C8 位元組。標誌第 0 位清零的記錄從不讀它。該位在接收時置位；寫入者未知。

這些條目只由 `0x01449560` 寫入，其唯一呼叫者 `0x00ff1558` 位於 `[card+0xe8]` 上 `0x00ff154c tbz w8,#2` 之後；存入的是記錄自己的日期（`0x01449570`、`0x01449648`），不是接收時間。帶標誌第 2 位的卡片每個卡片日期接收一次、每天最多十次；日期不變地重發會以訊息 0x10 被拒絕，而其條目仍保留。

保留路徑 `0x00ff13f0`（唯一呼叫者 `0x01014f74`，在寶可夢被放置之前）更新上述各表，把接收時間寫到 `card+0x70`（路由 1 到 4；路由 0 則寫記錄的日期），並把卡片歸檔（`0x014480f0`）。它不做任何合法性檢查。

構建和兌換都不針對物種檢查招式、回憶招式、性格、球、攜帶道具或形態。構建器 `0x010b6110` 只有一個出口，沒有拒絕分支：它按給定內容存入四個招式和四個回憶招式（`0x77bfb0`、`0x77b9a0`；儲存在 `0x770c7c`），高於 826 的招式 id 只改變 PP 查表（`0x00781490`）。兌換 `0x010159d0` 只檢查種類位元組、構建非空，以及隊伍（`0x7840f0` 拒絕物種 0 或滿員隊伍）或盒子（`0x1406b00` 需要空槽）中有空間。

唯一的物種檢查在 PokemonParam 建構函式 `0x777f40` 中（`0x778118..0x778148`）：如果某物種的 personal 資料條目第 0x21 位元組第 6 位清零（`0x764990`、`0x77f530`），就置上記錄 `+0x04` 字中的壞蛋第 2 位（`0x76eb40`），此後每個訪問器都讀取物種 0x383 的靜態替身（`0x776c50`），其名為 "Egg"。選單路徑上沒有任何東西拒絕它：卡片仍按物種名列出並揭示，而隊伍收到一隻空白的 "Egg"。高於 898 的物種讀取 personal 條目 0（該條目存在），所以不會被標記。絕不要傳送劍與盾中不存在的物種；桌面應用的 PKHeX 檢查會拒絕。

性別是構建唯一會修正的欄位（`0x777490`，`0x7774a4` 處讀取 personal 欄位 0x14）：比例 0、254 和 255 分別強制為雄性、雌性和無性別（表 `0x1c4d2d0`）；其他比例下請求的 2 會變成 0（`0x7774d8`）。構建器把記錄性別 3 變成 0xFF，即隨機（`0x010b62ac`）。

## 卡片的日期

記錄的前八個位元組是相簿顯示的日期，一個絕對 UTC 時間的小端 u64 位域。沒有公開的對映表命名它；PKHeX 的 `WC8.cs` 從 `+0x08` 的卡片 id 開始。

| 位 | 欄位 |
|---|---|
| 0-5 | 秒 |
| 6-11 | 分 |
| 12-16 | 時 |
| 17-21 | 日 |
| 22-25 | 月，1 到 12 |
| 26-39 | 年，絕對 |

`0x016cc5e0` 用 days-from-civil 把它轉成 posix 時間（其中含有 `146097`、`1461` 和除以 100 的常量），值等於 `main+0x2616900` 背後的哨兵時返回 0。相簿繪製 `0x00ffbaa0` 把它傳給 `nn::time::ToCalendarTime`（`0x00ffbaf0`），因此主機的時區生效，失敗時回退到 `ToCalendarTimeInUtc`。年份用兩位數字繪製。

日期為零時顯示 01/01/2070。

只有本地無線來的卡片保留自己的日期。其他每條路由都用 `nn::time::StandardNetworkSystemClock::GetCurrentTime`（`0x00ff3f8c` -> `0x01449ca0`；PLT `0x01900050`，GOT `0x0260fbb8`）覆寫這八個位元組，由 `0x016cbfd0` 和 `0x016cc1d0` 打包。

分發端在傳送前用計算機當前的 UTC 時間填充空日期並重新封裝校驗和；非零日期原樣保留，匯出的檔案也保留其原始日期。寶可夢的相遇日期與相簿日期是分開的。

## 相簿把卡片儲存在哪裡

相簿是存檔塊 `0x112D5141`（PKHeX 的 `KMysteryGift`），`0x17C8` 位元組，由 `0x01447eb0` 載入 `+0x60` 處的相簿物件，由 `0x01449d90` 寫回。它儲存的是重新編碼的頭部，從不儲存 720 位元組的線上記錄或其字串。`tools/switch/swsh_save.py` 把 `main` 讀進各個塊（PKHeX 的 SwishCrypto：對整個檔案的靜態 xorpad，每塊一個以其金鑰為種子的 XorShift32 流，兩個常量之間對加密體做 SHA-256）；`--key 112d5141 --out FILE` 寫出這個塊，`--patch KEY OFF HEX --write OUT` 改寫某個塊的位元組並重新封裝檔案。

    0x0000  50 slots of 0x68 bytes, newest in slot 0; an insert moves every slot down one
            (0x01449880 indexes them, cmp w1, #0x31; a slot is in use when its +0x0C is non-zero)
    0x1450  0x378 bytes, zero in every save read; the last-receipt table is 0x1560..0x15FF
            (album +0x15c0) and the once-per-card table 0x1600..0x16C8 (album +0x1660)

一個槽就是匯入器從記錄填充的 `0x68` 位元組頭部：

    +0x00  8    the record's date bitfield (zero draws 1 January 2070)
    +0x08  u16  card id
    +0x0A  u16  the record's byte at +0x15 (0 on Pokemon cards, 1 on kind-3, 3 on an item card)
    +0x0C  u8   kind: 1 Pokemon, 2 item, 3 the empty kind
    +0x0D  u8   kind 2: how many of the six item quantities are non-zero; 0 otherwise
    +0x0E  u8   1 when the card came by any route but local wireless
    +0x0F  u8   the record's byte at +0x1C (1 on kind-3 cards)
    +0x12  u16  level (kind 1)
    +0x30  u32  species (kind 1); kind 2: the item pairs (u16 id, u16 quantity) as at record +0x20
    +0x38  4 x u32  moves (kind 1)
    +0x48  26   nickname, UTF-16 (kind 1)
    +0x62  u8   3 on every Pokemon card

把某個槽的 `+0x0C..+0x62` 清零就會從相簿移除該卡片；它送出的道具仍留在 `MyItem`（`0x1177C2C4`）中。

## 排空儲存的每幀更新

`0x010f65a0` 是 gfl 網路管理器的每幀更新（管理器來自 `0x0261cba8`）：它經 `0x006c5300` 排空 `manager+0x60` 處的接收器，遍歷條目，並在每次發現儲存非空時蓋上 `manager+0x80`。它唯一的呼叫者是 `0x01109240`，位於 `0x00f1df30` 之內，後者經一個註冊的回撥到達。

陷阱：在某些會話中儲存從不被排空，`manager+0x80` 保持不變；讀取任何信標結果之前先確認它在前進。原因未知。
