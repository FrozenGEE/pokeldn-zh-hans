# 線上交換

線上交換把相隔很遠的兩名玩家連線起來：每塊板子用自己的主機承載一次本地交換，兩個應用通過公共 Nostr
中繼傳遞各自主機提供的寶可夢，中繼只能看到加密事件。程式碼：`pokeldn/online/`；啟動器標誌 `--online`
和 `--online-code`。

## 房間

兩個應用在運行同一款遊戲且程式碼相同時相遇：

    room = sha256("pokeldn online 1|<game>|<code or 'open'>")     64 hex digits

配對的兩個版本共享一個遊戲鍵（`frlg`、`sv`）。如果遊戲本身有連線碼，這裡的程式碼就是主機自己的連線碼。
同一張桌子上的兩臺主機可以直接找到彼此；要在同一張桌子上測試，就給每臺主機各自的原生代碼，並用
`--online-code` 把兩塊板子放進同一個房間。

## 中繼

每個事件都是臨時型別 21059 的 NIP-01 事件，帶有 `["t", <room>]` 標籤，對某個應用而言還有
`["p", <its signing key>]`。每個應用從啟動前 10 秒起訂閱帶該房間標籤的 21059 型別事件，向每個中繼
釋出，並丟棄重複的事件 id。每個會話用一個全新的 secp256k1 金鑰簽名（BIP-340，
`pokeldn/online/schnorr.py`）。

| 中繼 | 8 個事件，每 2 秒一個 |
|---|---|
| relay.primal.net, relay.snort.social, offchain.pub, relay.nostr.net, nostr.oxtr.dev, nostr-pub.wellorder.net | 8 個送達；預設集合 |
| relay.damus.io | 4 個送達，然後封禁該地址一段時間 |
| nos.lol, nostr.mom | 無（被限速） |
| nostr.wine | 拒絕（付費） |

`POKELDN_RELAYS`（逗號分隔的 URL）會替換預設集合。offchain.pub 拒絕來自未知金鑰的突發請求，只接受
有節奏的事件。第二個應用到達 0.4 秒後兩個應用配對；一條 344 位元組的記錄約 0.15 秒傳完。

### 儲存的事件

在 relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub 和
nostr-pub.wellorder.net 上測得：

| 事件 | 結果 |
|---|---|
| 來自新金鑰 | 被接受並回傳 |
| 帶 NIP-40 `expiration` 的 30402 | 在到期前提供，到期後不再提供 |
| 用相同 `d` 重新發布的 30402 | 一分鐘內只提供較新的那個 |
| 指名某個 30402 的 kind 5 | 一分鐘內只提供該 kind 5 |
| 僅通過 `a` 地址指名已被替換的 30402 的 kind 5 | 五個中繼丟棄；nostr.oxtr.dev 和 nostr-pub.wellorder.net 會保留它，直到某個 kind 5 指名它自己的 id |
| 沒有 `expiration` 的 30402、kind 5 和 kind 1059 | 17 天后仍然全部提供 |
| 指名某個 kind 1059 的 kind 5 | 被所有六個提供 1059 的中繼丟棄 |
| 通過其 `p` 鍵讀取的 kind 1059 | 六個中繼提供；relay.nostr.net 要求 AUTH 並拒絕它 |

## 會面

每個事件的內容都是以 `sha256("pokeldn room key|" + room)` 為金鑰的 AES-256-GCM。

| 訊息 | 傳送時機 | 內容 |
|---|---|---|
| `here` | 每 2.5 秒，發往房間 | 協議 1、X25519 金鑰、訓練家名稱、應用版本、忙碌狀態 |
| `invite` | 發往一個應用 | 訓練家名稱 |
| `yes` / `no` | 應答 | 訓練家名稱 |
| `bye` | 發往非夥伴 | 原因 |

應用只邀請它見過最久、且簽名金鑰大於自身的空閒應用，一次只發一個邀請，最長 6 秒，同時以 `no` 應答
其他邀請。被拒絕或未獲應答的邀請會使該應用被跳過 10 秒。夥伴的第一條頻道訊息視為它的 `yes`。

## 頻道

夥伴訊息在房間金鑰層之內攜帶傳送者的 X25519 金鑰，以及一層內層 AES-GCM，其金鑰為

    sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)

每條訊息攜帶 `s`（自己的編號）和 `a`（按序收到的最高編號）。未確認的訊息每 2 秒重發；確認在到達後
0.3 秒發出；ping 每 4 秒一次。夥伴沉默 45 秒即視為失去，如果尚未提供任何內容則會被替換。

| 訊息 | 含義 |
|---|---|
| `hello` | 訓練家名稱和應用版本，一次 |
| `offer` / `withdraw` | 交換 *r*：本地主機提供此記錄（base64），或將其收回 |
| `accept` / `unaccept` | 交換 *r*：本地主機已確認，或將其收回 |
| `refused` | 交換 *r*：接收方拒絕了傳送方的記錄，以及原因 |
| `done` | 交換 *r* 完成；下一個是 *r* + 1 |
| `ping`, `bye` | 保活；離開 |

## 傳輸內容

只有提供的記錄和交換狀態。PKHeX 會在主機看到之前檢查收到的記錄（`pokeldn.online.session.checker`）：

| PKHeX 的判定 | 記錄的處理 |
|---|---|
| 無法解析、校驗和錯誤、種類或形態在該遊戲中不存在、id 超出遊戲的表 | 拒絕，並向傳送者顯示原因 |
| 未釋出的道具或招式（劍的道具止於 1607） | 拒絕 |
| 其他任何合法性標記 | 提供，並向接收方顯示該標記 |

## 在啟動器中

帶 `--online` 的 Host 啟動器提供夥伴主機的記錄。本地主機的提供以 `offer` 發出；夥伴的提供則提供給
本地主機；只有兩臺主機都確認後啟動器才確認；`done` 從盒子開始下一次交換。

| 標題 | 啟動器的提供 | 主機收回自己的提供 | 啟動器收回自己的提供 | 啟動器的確認 |
|---|---|---|---|---|
| 火紅 / 葉綠 | 夥伴的隊伍塊（三個 200 位元組塊，郵件 220，緞帶 40），每當主機自己的對應塊到達就傳送一塊；帶夥伴游標的 `SET_MONS_TO_TRADE` | `READY_CANCEL_TRADE`（以 `PLAYER_CANCEL_TRADE` 應答）、`REQUEST_CANCEL` | `PLAYER_CANCEL_TRADE` | `START_TRADE` |
| Let's Go | 帶夥伴 232 位元組記錄的 kind 2，應答主機的步驟 | 撤回投票（狀態 2）、離開（狀態 4） | 無 | 在提供的克隆上寫 2，把末尾字移到 2 |
| 劍 / 盾 | 帶盒子命令 1 的 20030；0x84 快照的隊伍槽保留主機自己的寶可夢 | 盒子命令 2（提供）、5（確認） | 盒子命令 2 | 盒子命令 4 |
| 晶燦鑽石 / 明亮珍珠 | 應答主機的 0x13 | 0x45 `{1}` | 0x45 `{1}` | 0x21 `{0, 2}`；安全階段保持自動 |
| 傳說 阿爾宙斯 | 應答主機的選擇器 4，在其計數器之下；選擇器 2 的展示在知道夥伴記錄後以其應答 | 選擇器 6 | 無 | 主機選擇器 5 的映象 |
| 朱 / 紫 | 帶夥伴 348 位元組主體的 kind 2 | kind 4 `8000040100` | kind 4 | kind 3 |
| 傳說 Z-A | 夥伴選擇的預覽，0.5 秒後是選擇本身 | `0103` | 下一輪的 `0103` | `0102`，然後 `0104` |

火紅和葉綠交換整支隊伍。每個 Host 都保留自己的一塊，直到夥伴的主機發送了同一對；主機在沒有計時器的
情況下等待 [trade.c:1478]。只有當 PKHeX 讀取塊中的每一隻寶可夢時，該塊才會到達主機。游標以 `pick`
先於記錄傳輸。

夥伴離開或沉默 45 秒視為撤回，除非交換已過不可返回點。夥伴離開後，火紅或葉綠的主機會對每次選擇收到
`PLAYER_CANCEL_TRADE` [trade.c:1712]；進行到一半的隊伍交換會以空隊伍結束。在劍中，交換的記錄是內容
50 的（[劍的交換](swsh_trade.md)）。

## GTS

GTS 在從不同時線上的玩家之間交換存入銀行的寶可夢：玩家從[銀行](gui.md#the-bank)中掛出一隻寶可夢，
最多指定三個想要的種類、一個等級範圍，並可選要求閃光，另一名玩家用自己的一隻應答，掛出者的應用在下次
開啟時完成交換。程式碼：`pokeldn/online/gts.py`、`pokeldn/app/gts.py`，以及應用的 GTS 頁面。

| 事件 | 型別 | 簽名者 | 內容 |
|---|---|---|---|
| 掛單 | 30402（NIP-99），`d` 為隨機 id | 每個掛單一個金鑰 | JSON：協議 1、遊戲、按 PKHeX 讀取的寶可夢、記錄的 SHA-256、`wants` 和 `also`（見下）、訓練家名稱、狀態、獲勝的提供 |
| 提供 | 1059，`p` 為掛單金鑰 | 每個提供一個金鑰 | 密封：掛單的 `d`、遊戲、記錄、訓練家名稱 |
| 應答 | 1059，`p` 為提供金鑰 | 掛單金鑰 | 密封：提供 id 和掛出的記錄，或拒絕及原因 |
| 刪除 | 5（NIP-09） | 被指名事件的金鑰 | 無 |

掛單帶有 `pokeldn-gts`、`pokeldn-gts-has-<species>` 標籤，以及每個想要種類的
`pokeldn-gts-wants-<species>`，攜帶 NIP-99 的 `title`、`summary`、`status`、`published_at`，並在
30 天后過期（NIP-40）。密封正文是以 `sha256("pokeldn gts|" + x)` 為金鑰的 AES-256-GCM，其中 x 是
ECDH 的 x 座標（`schnorr.shared_x`）。每個儲存事件的 id 和簽名都會被檢查。

一個需求是 `{"species", "name", "min_level", "max_level"}`，當只有閃光才應答時再加上
`"shiny": true`。`wants` 儲存第一個；`also` 僅在多於一個時出現，最多再儲存兩個，任何匹配其中一個的
提供都可應答。這兩個欄位是對協議 1 的增補：0.40.0 或更早的應用會忽略它們，把掛單顯示為只要求第一個
需求，而它發出的、不滿足閃光要求的提供會被掛出者的應用拒絕並退回。

| 步驟 | 發生的事 |
|---|---|
| 存入 | 寶可夢必須合法；它離開銀行，掛單被髮布 |
| 提供 | 合法且匹配某個需求的種類、等級和閃光要求；它離開銀行，密封給掛單金鑰；一個應用對每個掛單只持有一個等待中的提供，該掛單在掛出者的應用應答之前仍對其他玩家的提供開放；頁面用一個時鐘標記它 |
| 掛出者的應用開啟 | 儲存的提供按最舊優先應答；第一個有效的被交換，其餘被拒絕 |
| 一次交換 | 應答攜帶掛出的記錄；掛單被重新發布為已交換；收到的記錄存入銀行 |
| 提供者的應用開啟 | 記錄會對照掛單的 SHA-256 檢查並存入銀行；被拒絕、競速失敗或掛單已撤回時，它取回自己的寶可夢；它刪除自己的提供 |
| 掛單結束 | 30 天后其寶可夢返回；提供者的寶可夢在結束後一小時、中繼已傳送所有儲存的應答之後返回 |
| 撤下 | 重新發布為已撤回；其寶可夢返回；之後的提供被拒絕 |

每個掛單和提供都是 `Documents/pokeldn/GTS`（設定時為 `POKELDN_DATA/GTS`）中的一個資料夾，裡面存放
`state.json`（金鑰、已簽名事件、已傳送的應答）和記錄。應答在釋出之前寫入，每個活躍事件都會重發給每個
連線上的中繼。已完成的資料夾在 60 天后刪除。一輪大約需要 30 秒。

中繼即[儲存的事件](#stored-events)中那些；`POKELDN_GTS_RELAYS` 會替換它們。被修改的應用可以扣留已
提供的寶可夢，或掛出它並不擁有的寶可夢；SHA-256 只能在事後揭示這一點。沒有可信第三方的公平交換是
不可能的（Pagnia 和 Gaertner，1999）。

## 未解決

- 中繼在 24 小時之後會保留事件多久，或者對沒有過期時間的事件會保留多久。
- 主機在持有提供時，Host 收回提供會如何應答：劍的盒子命令 2（在確認畫面上的 Host 版劍，在收到命令 1
  後又收到命令 2 時，4 秒後開始離開）、朱/紫的 kind 4、Z-A 的 `0103`、晶燦鑽石在主機選擇之後的 0x45。
  Let's Go 和傳說 阿爾宙斯保持不動。
- Z-A 是否接受沒有預覽的選擇，以及傳說 阿爾宙斯是否接受第二個選擇器 4。
- 零售版主機在盒子處等待夥伴多久（超過一分鐘的部分）。
