# 太晶團體戰

本地太晶團體戰是 朱/紫 的一個 LDN 場景 7 會話，最多四個站點。主機執行大廳，然後向每個參與者傳送一條引導訊息，其中裝有四名玩家的寶可夢、頭目及其 RaidPoint，之後每臺主機各自進行戰鬥。`bin/sv_host.py --raid-seed` 主持一場零售主機可加入的團體戰，`bin/sv_join.py --raid-pokemon` 加入一場由主機主持的團體戰；兩種情況下，程式中的玩家都會在戰鬥開始時離場，其寶可夢作為主機的 AI 夥伴繼續戰鬥。地址是 朱 4.0.0 解壓後 `main` 的偏移；紫 4.0.0 在相同偏移處有相同的程式碼（[docs/sv.md](sv.md)）。

## 主持

主機宣告場景 7、四個參與者和連線碼 4970。主機通過 X、寶可入口站、太晶團體戰、離線搜尋加入。`--raid-seed` 配合四個上下文標誌選擇團體戰（[種子](#the-seed)），`--raid-pokemon` 是我們玩家帶來的隊伍記錄（PKHeX 會校驗它），`--raid-reward ITEM:QUANTITY` 可重複，用 朱/紫 背包能容納的物品行替換種子自帶的獎勵（即 PKHeX 輔助工具的 `bag` 列表：除關鍵物品外的每個口袋，未釋出的物品排除在外）。`--raid-partner TRAINER` 最多為每臺主機留空的槽位使用一次（一臺主機時兩次，兩臺時一次），按槽位順序讓這些 NPC 夥伴入座，`--raid-partner-progress STAGE` 選擇他們來自的階段（[夥伴](#partners)）。應用的「太晶團體戰（主持）」工具帶有下列標誌。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

在團體戰模式下，主機與交換主機在定址物件和時機上不同：

| | 團體戰主機 |
|---|---|
| 網狀定址訊息（RTT、0x80、0x81）、Session 站點列表 | 發往子網廣播；在 ldn_mitm 上以單播發送，因為它不向對端傳遞廣播 |
| Net 0x11 | 一條序列，重複到出現 0x12 為止 |
| 站點列表的主機條目 | 主機加入請求所指名的玩家；若玩家為佔位符，則主機入座但不出現在大廳中 |
| 站點列表 | 每 2 秒重發一次，直到主機的 type 6 |
| 開場 | 只在那個 type 6 之後：十一次初始批次確認、0x81 埠 5 開啟和一次 RTT 請求合併在一個數據包中；0x81 埠 1 開啟、通道表和埠 2 的 type 6；20 毫秒後是身份，每 3 毫秒一條記錄 |
| 埠 2 的 type 3 | 用兩個 type 9 應答：主機自己的站點帶程式碼 0，另一臺主機的帶程式碼 1 |

開場的 0x7C、0x81 埠 5 和 0x80 埠 2 訊息每 0.25 秒重發一次，直到被確認，主機發送的每個 ACK 都宣告該流中最低的未確認序列。

### 多臺主機

`--raid-players N`（1 到 3，應用中的「加入的主機」）在一個大廳裡安排最多三臺主機，每臺佔用最低的空閒站點索引。它們共享大廳和開始流程；從第一回合起，各自帶著自己的 NPC 夥伴和獎勵進行自己的戰鬥（[哪個站點執行伺服器](#which-station-runs-the-server)）。主機為每臺主機保留一組流，使用該主機的索引 *k*，而在單臺主機的團體戰中這裡是 1：

| | 索引為 *k* 的主機 |
|---|---|
| 加入響應 | 站點索引和加入順序 *k* |
| 站點列表 | 每個已入座的站點，我方在前；每次座位變化都以下一序列發給每臺已入座的主機，重發到各自出現 type 6 為止 |
| Net 0x11 | 我方站點、按索引排列的已入座主機，然後是加入方 |
| 目標點陣圖 | 在三個目標位下為 `1 << k` |
| 批次確認 | 第 *k* 項 |
| 開場 | 0x81 埠 *k* 和 4 + *k* |
| 埠 2 的 type 6 | 我方和已入座的成員，按加入順序，帶程式碼和計數 |
| 埠 2 的 type 9 | 我方的程式碼 0，每個已入座成員各自的程式碼，最後是該主機的程式碼 *k*；每個已入座成員都會收到該主機的 |
| 引導 | 它在槽位 *k* 的寶可夢；空位則用空槽位 |

發現座位已滿，或在開始之後才到達的加入請求，會得不到應答。主機會丟棄頭部和尾部都未指明其可變 ID 的每個資料包，以及點陣圖缺少站點 0 的每條可靠訊息，因為同一大廳中的主機會通過同一廣播互相定址。

埠 2 的槽位在 `+0x170` 處以 u8 程式碼和 u64 站點 ID 儲存其成員；`0x138d208` 返回站點的程式碼，非成員返回 0xfd。主機的 type 3 處理函式 `0x1981e94` 取 0 到 7 中既沒有成員持有、也沒有排隊中的 type 9 指名的那個最低程式碼（`0x279c9a0`），然後為每個成員廣播一條 type 9，併為加入方廣播一條。接收方 `0x18b68fc` 會追加它尚未列出的 `(code, id)`，且從不更改已列出的程式碼。type 6（`0x12fbf8c`，組裝函式 `0xe457cc`）在 `+0xa0` 攜帶成員 ID，在 `+0xc0` 攜帶程式碼，`+0xc4` 是計數，`+0xc5` 是關閉位元組；其接收方 `0x279b9c4` 會為每個成員重放一條 type 9。Lua 大廳（程式碼塊 `be21e654`，接收方 `0.15829`；`0.N` 是主函式的原型 N）把每條訊息歸檔到其傳送方的程式碼下，無傳送方時用 253。進入大廳的主機發送狀態 0x18 和它的寶可夢；收到 0x18 的站點以它的 Ready 狀態和寶可夢應答。

可靠頭的接收檢查（`0x6f0410`..`0x6f0430`）對 1 到 23 的任意目標數量，測試 `index >> 5` 字中接收方的第 `index & 31` 位；零售傳送方寫 3，即站點容量 4（`0x44dfcb0`）減一（`0x6e71c4`）。

主機把網路移交給仍在其中的最低索引。其他主機只有在下一任主機的 type 8 之後才會收到表示正在遷移的 Net 0x11（對每個已入座站點排名），隨後在每臺主機都應答 0x12 後收到 NetStartHostMigration，且沒有 Session type 7。讓這些主機留在同一場戰鬥中的條件：

| 條件 | 程式碼 |
|---|---|
| 看到另一臺主機離開時，只有在遷移中才保留它：`[net+0x249]` 由表示正在遷移的 0x11 置位，或 `[net+0x1c0]` 由 NetStartHostMigration 置位 | 站點離開處理函式 `0x69d08c`、`0x69d174` |
| 序列更新的 Net 0x11 會丟棄每個被標記為已離開的站點 | `0x69e008`、`0x6b5074` |
| 下一任主機最多等待 8000 毫秒讓每個 Net 站點到達狀態 2，丟棄其餘站點，傳送 Net 0x11，等待每個 0x12 後傳送 Session type 5 | NetHostMigrationJob `0x6a9cd4`、`0x6aa2a8`；`0x6d44f0` |
| 另一臺主機最多等待該 type 5 10000 毫秒，然後失敗 | `0x6dc024`、`0x6dc124` |
| type 7 的最後一個 u16 至多為下一任主機已應用的列表序列 | `0x6d9164` |

Pia 主機在 LDN 參與者每次變化時向每個站點發送 Net 0x11（`0x69c310`，`0x69c79c` 遞增 `[NetProtocol+0x60]`，排名按 IPv4 升序 `0x6a05ec`）。在 LDN 上，加入方的 0x11 接收方 `0x69db14` 不建立站點（`0x6a2fac` 返回 0）；它的站點來自 `nn::ldn::GetNetworkInfo`（`0x6b43a8`），埠 12345。type 5 的接收方 `0x6d7f8c` 只在其地址位於該節點列表中時（`0x6a8320`）建立列出的站點（`0x6d840c`）；否則它不傳送 type 6，並把已應用序列重置為 0xffff（`0x6d81a4`）。Session type 9（`0x6d4ef0`，`09 | constant id | count | constant ids`）每 3000 毫秒指名一個加入方尚未收到其訊息的站點（`0x6d4a60`）；主機的接收方 `0x6d940c` 把單個被指名的站點交給踢出任務（`0x6dc878`）。

主機加入後，團體戰主機發送資料包 ID 0：已入座的主機會丟棄更高 ID 之後的內容（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。站點列表的玩家 ID 是匿名的 `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）；隨機 ID 不會引出 type 6。

## 大廳

團體戰訊息是 0x80 埠 0 上的遊戲訊息（[交換](sv.md#the-trade)）：

| 位元組 | 欄位 |
|---|---|
| 0 | 處理函式鍵，u16 |
| 2 | kind、step：一個 u16 訊息 ID（0x012f 為引導，0x0193 為戰鬥開始） |
| 4 | 每個傳送方的計數器，u16，由 `0xa583fc` 遞增 |
| 6 | 壓縮，u32：0 無，2 LZ4 |
| 10 | 載荷的明文大小，u32 |
| 14 | 網路物件 ID，u16，除非 `0x14ede48` 找到，否則為零 |
| 16 | 建構函式從不寫入的兩個填充位元組 |
| 18 | 載荷 |

| 鍵 | kind | 內容 |
|---|---|---|
| 0x3380 | 0x2c | 團體戰的描述符：種類（DevID）、形態、星級、太晶屬性、性別、遭遇的記錄號 |
| 0x3380 | 0x2d | 參與者的狀態：0x00 未就緒，0x01 就緒，0x0c 主機的開始，0x0d 訪客的應答，0x18 進入大廳，0x1e 主機拒絕遲到的站點（`0.30822`） |
| 0x3380 | 0x2e | 參與者的寶可夢，其加密的 344 位元組隊伍記錄 |
| 0x3380 | 0x2f | 戰鬥引導 |
| 0x3380 | 0x30 | 大廳計時器，單位剩餘秒數 |
| 0x0132 | 0x6e、0x73 | 主機載入戰鬥，然後已載入 |
| 0x3480 | 0x93 | 戰鬥開始 |
| 0x007b | 0x13 | 主機在 0x3480 之後傳送的戰鬥開始訊息 |

接收路徑 `0x18bec54` 把頭部複製到訊息物件 `+0x40..+0x4f`，但不比較其中任何內容；它忽略 LZ4 的返回值，只把明文大小用作輸出容量。

鍵 0x007b 上的戰鬥開始幀是 12 位元組埠地址（三個 u32）、一個 u32 長度，以及一個載荷，其前 32 位元組是由 `0x1227714` 複製的頭部：u32 type 位於 0x00，u64 位於 0x08 和 0x10，u8 位於 0x18 和 0x19，填充位於 0x04 和 0x1a..0x1f。沒有讀取方會比較填充（`0xf5a2fc`、`0xe10088`、`0xe0fd68`、`0xe106a4`、`0xf5a810`、`0xf5bc10`；18 位元組頭部的最後兩個位元組由 `0x18bece4` 存到 `+0x4e`，只有序列化函式 `0x290b150`、`0x14c7904` 讀取它們）。一位零售版 朱 訪客在訊息 15 和 16 的位元組 0x1a..0x1f 以及 18 位元組頭部的最後兩個位元組都被置零的情況下，開始並贏下了一場戰鬥。除非有接收埠註冊了其地址，否則 `0x14ab234` 會丟棄幀：訊息 15 的地址是 (0x2713, 1, 2)，訊息 16 到 20 是 (0x2713, 3, 5)；0x2713 是設定的 u32 `+0x2c`。

戰鬥通過 `0xe0fd68` 讀取訊息 16（type 0x46）：當 +0x08 處的 u64 為零時，它按 type 分支（`0xe10088`），`0x2897afc` 設定逐幀更新 `0x289358c` 物件（由 `0xfa4bb4` 配合 `0x28950c8` 構建，存放在 `[sm+0x148]`）的 `+0x71`。當 `+0x71` 為 0 時，更新會驅動讀取方（`0xe0f014`）並呼叫 `0xfc363c([+0x48], 0)`；為 1 時，它每一幀呼叫 `0xfc363c([+0x48], 1)`，直到該呼叫返回 true（`0x28935b8` 將其清除）。

團體戰主機在 0x7C 埠 1 宣告的通道表包含六個鍵：連線交換的四個（`0x007b`、`0x0132`、`0x0232`、`0x0332`）以及 `0x3380`、`0x3480`。零售訪客先宣告那四個，0.79 秒後再宣告團體戰的兩個。埠 2 攜帶主機的 type 6：kind 5 和容量 4 下 type 7 的會話塊，然後是四個槽位，主機的站點 ID 在前（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 按順序向一臺主機釋放主機的訊息，每條都在該主機的上一步之後；`RaidGroup` 儲存同一大廳中各主機共享的內容：

| seq | 訊息 | 由……釋放 |
|---|---|---|
| 1 | 描述符（zlib，INITIALIZED） | 主機的廳內寶可夢（0x2e） |
| 2、3 | 狀態 0x18、我們的寶可夢 | |
| | 計時器，每次下降時 | 第一臺主機應答後 0.73 秒起，每秒一步 |
| | 狀態 0x01 | 3.19 秒 |
| | 狀態 0x0c，開始 | 在 `--raid-players` 臺主機入座且都發送 0x01 之後，或計時器為 0 時 |
| | Net 0x50，屬性狀態 7 | 主機的 0x0d |
| | Session 站點列表，下一序列 | 主機的 Net 0x51 |
| | 引導，兩個分片 | 主機的 type 6 |
| | 已載入，`0x320173` | 主機的 0x6e 或 0x73 |
| | 戰鬥開始，`0x803493` | 主機的 0x73 |
| | 六條戰鬥開始訊息 | 主機的 0x93；然後是 0、0.10、0.12、0.16、0.18 秒 |

零售主機開啟 180 秒的大廳並每秒傳送一次計時器（`0.27104`）；pokeldn 主機在第一臺主機應答時從 180 開始。主機的 0x00 或 0x18 會撤回它的 0x01。訪客收到 0x0c 會立即以 0x0d 應答，不做 Ready 檢查，且只有主機能開始戰鬥（`Raid_Start_Ready`，`0.27137`）。在主機上，`Raid_Start_Ready` 只在每個訪客都就緒時啟用開始項；計時器為 0 時，若沒有就緒成員就解散大廳，否則開始。`Raid_Start_Go`（`0.27140`）重發 0x0c，直到每個成員都應答 0x0d，然後傳送引導，槽位 *k* 放程式碼為 *k* 的成員的寶可夢。

受門控的訊息在其里程碑之後 50 毫秒發出；Net 0x50 和站點列表每 0.5 秒重發一次直到被應答，團體戰訊息每 0.5 秒重發一次直到被確認。Net 0x50 是交換主機的屬性體，序列為 1，位元組 27 設為 7，132 個應用位元組位於 +38，在標誌 0x31 下做 zlib 壓縮；不壓縮則不會引出 0x51。

最後一臺主機的訊息 20 之後五秒，主機像離場的零售主機那樣把網路移交給該主機（[docs/sv.md](sv.md#leaving)）：每秒傳送 Session type 7 直到出現 type 8，每 0.5 秒傳送表示正在遷移的 Net 0x11 直到 0x12，每 0.3 秒傳送 NetStartHostMigration，最多 4 秒。絕不要改為銷燬網路：零售主機會在戰鬥開場時顯示 2318-0006。

## 戰鬥引導

訊息 0x2f 攜帶一個 0xaa0 位元組的記錄，經 LZ4 壓縮（塊格式，`pokeldn.sv.lz4`）：

| 偏移 | 大小 | 內容 |
|---|---|---|
| 0x000 | 4 x 0x158 | 四個參與者的隊伍記錄，已加密，主機的在槽位 0 |
| 0x560 | 0x158 | 頭目的隊伍記錄 |
| 0x6b8 | 0x3e8 | RaidPoint |

序列化函式 `0xe327fc` 從訊息物件 `+0x440`..`+0x458` 和 `+0x50` 寫入這五條記錄（`0xe329b4`），然後從 `+0x58` 寫入四個四字，從 `+0x78` 寫入 0x3c8 位元組；`0x1592b7c` 選擇壓縮方式，`0x71d940` 執行 LZ4。RaidPoint 被整體複製（`0x1bae670` -> `0x1bae760`，getter `0x1baff98`）。零售主機會在 1395 位元組處拆分該訊息。

空的參與者槽位持有種類 0、等級 1、暱稱 `Egg`、太晶屬性 19、語言 2、當前 HP 11，能力值為 11/5/5/5/5/5。絕不要傳送全零的空槽位：零售主機在戰鬥開始時就會崩潰。

| RaidPoint 偏移 | 大小 | 內容 |
|---|---|---|
| 0x000 | 24 | 名稱，ASCII，`RaidPoint_` 加字尾（`RaidPoint_POKELDN_0` 可被接受） |
| 0x018 | u32 | 0x40 |
| 0x020 | 4 x u32 | 星級、結晶（0 普通、1 黑色、[2 和 3 為活動](#event-raids)）、`captureRate`、`captureLv` |
| 0x030 | 7 x u32 | `raidTimeData`：active、`gameLimit`、`clientLimit`、`commandLimit`、`pokeReviveTime`、`aiIntervalTime`、`aiIntervalRand` |
| 0x04c | 37 x u32 | 頭目的行動配置（`bossDesc`）：HP 係數、護盾的九個值、六個額外行動（行動、時機、值、招式）、雙重行動的三個值 |
| 0x0e4 | 45 x 16 | 獎勵行：物品、數量、稀有物品標誌、主體 |
| 0x3b4 | u8 | 零售標準點中為 0，黑色點中為 1 |
| 0x3b8 | 7 x u32 | 星級、種類（DevID）、形態、性別、等級、0、太晶屬性 |
| 0x3d8 | u64 | `randSeed`，夥伴種子（[夥伴](#partners)）和戰鬥種子（[戰鬥的隨機數](#the-battles-random-numbers)） |
| 0x3e0 | u32 | `raidNpcGroupID`，主機的團體戰解鎖階段（[夥伴](#partners)） |

六星記錄的 `raidTimeData` 為 active，`gameLimit` 450、`commandLimit` 60；一星記錄為 inactive，`gameLimit` 300；其餘為零。它處於 inactive 時，計時器初始化函式 `C2D7F486425487755.F0C64BA9B6853E61A` 使用遊戲限制 300、命令限制 60、復活時間 30、AI 間隔 17 和隨機量 6。行動：0 無，1 重置頭目的能力變化，2 重置玩家的能力變化，3 一個招式，4 吸取太晶珠；時機：0 無，1 時間，2 HP；值是觸發它的 HP 或時間比例。P 百分比的 HP 觸發在「100 × 頭目當前 HP / 其 HP 總量」的整數除法結果小於等於 P 時觸發：HP 為 816 中的 414 時，50% 的行動會觸發。一到六星的 HP 係數是 500、500、800、1200、2000 和 2500。

零售點的獎勵行包括種子固定的行（subject = 表中的 `SubjectType`：0 每個玩家，1 主機，2 訪客，3 僅一次）、subject 0 下的抽選、subject 4 下另外三次抽選，以及 subject 5 下頭目的太晶碎塊，數量取 `RaidGemItemRewardBoost` 的值（一到七星為 0、0、2、5、10、12、0），僅在為正時加入。獎勵畫面會把稀有物品行列在最前。

Lua 獎勵過濾器 `C07C34FC3B976E5A7.F316609DEA110601D` 為每個玩家保留 subject 0，為主機保留 1，為訪客保留 2，在符合「僅一次」條件時保留 3，保留前 N 條 subject 4 的行，其中 N 是生效中的團體戰之力（料理種類 5）中與頭目太晶屬性匹配的最高等級（屬性 18 匹配全部），並在玩家持有閃耀護符（物品 2481）時保留 subject 5。生效中的料理之力是 u32 種類、u32 屬性、u32 等級，以及一個表示剩餘秒數的 f32（食用時為 1800）。兩個函式都在 Lua 程式碼塊 `be21e65463b9a98f` 中，SHA-256 為 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 以同樣方式構建行；對於種子 7B741233 和 09F3E337，其 45 行與零售點的位元組相同。選定的獎勵（`--raid-reward`）放在 subject 0 下，不帶獎勵加成行。

## 夥伴

每臺主機用相同的 NPC 訓練家填充大廳成員未佔的參與者槽位，這些訓練家從 RaidPoint 的兩個字中抽取：`randSeed`（0x3d8 處的 u64）和 `raidNpcGroupID`（0x3e0 處的 u32）（`0.4453`；getter `0x1be5ac0`、`0x1be5c20`）。零售主機在每次開始時抽取新的 `randSeed`（`Raid_Start_Go`，`0.27140`）。該 u64 以 `0x82A2B175229D6A5B` 作為第二個字，為 xoroshiro128+（`0x17ebec0`）播種。抽取三名訓練家（`0.7804`），每次對池中剩餘的 n 呼叫 `next_int(n)`（掩碼到 n - 1 的位數，結果大於等於 n 時重抽）並將其移除。空槽位按槽位順序取這些抽取結果（`0.4455`）。

夥伴的記錄從同一個 `randSeed` 取五次抽取，一場戰鬥中的每個夥伴共享這個種子（`raid_partners.identity`）：加密常量（為 0xffffffff 時重抽）、TID | SID << 16、PID（異色時翻轉第 28 位）、身高和體重，各自為 0x30 + next_int(0xa0)。其餘部分來自訓練家的條目，語言為 2，親密度為種類的初始親密度。繫結函式 `f92C18AA6`（`0x1905a10`）構建一個以 `randSeed` 播種的 pml InitialSpec（`0x1905ce0`，轉換器 `0x160ffd0`，建立 `0xdef2b8`，抽取順序 `0xdf011c`）；其第三個引數讓隨機尺寸屬於 M 類（SizeType 3，`0x1611cc4`）。`sex` 為 0 的條目在種類的雌性百分比至少為 15 時為雌性，否則為雄性（`0x1611d1c`）。`gemType` 為 0 時從表 `0xe78418` 取太晶屬性，鍵為種類 × 10000 + 形態。

池為 `world/data/raid/raid_trainer_01`（16 行，階段 0 和 1）、`_02`（18 行，階段 2）和 `_03`（18 行，階段 3 和 4），欄位為 `difficulty_0`*N+1*（`0.7797`）。一行包含訓練家 ID `raid_assist_NPC_*`、`npcPresetIndex` 和 `nameTextLabel`；該訓練家的寶可夢是其 `trdata_array` 條目中的 `poke1`：特性槽位 1、2 或隱藏特性，三個招式，`gemType`，IV 31/10/31/31/10/31，EV 252 HP、128 防禦、128 特防，性格勤奮，精靈球，縮放 128，無物品。`scripts/gen_sv_partner_data.py` 把它們解碼到 `pokeldn/sv/data/raid_partners.json`。夥伴按等級 int(0.8 × 戰鬥槽位 0 的寶可夢等級) 構建，後者是主機的（`0.4455`、`0.4901`）。階段 5 會給出以頭目命名的皮卡丘夥伴並導致崩潰，因此 `raid_point` 拒絕大於 4 的階段。

## 種子

團體戰由 32 位種子和主機的狀態抽取：版本、地區（帕底亞、北上、藍莓，表字首 `""`、`su1_`、`su2_`）、劇情進度和結晶。xoroshiro128+ 從種子和常量 `0x82A2B175229D6A5B` 開始（`0xe29340`）；它的第一次抽取（在一百個值中）按劇情階段的界限選擇普通結晶的星級（黑色結晶固定為六星），第二次在該星級和版本內按機率選擇遭遇。`0xe29404` 用 `%sdifficulty_%02d` 構建表名，並把記錄傳給 `0x1eab5e4`，後者讀取其 `raidEnemyInfo`；`0x2935b68` 遍歷三個字首和六個等級。然後，一個由同一種子新建的 xoroshiro 抽取頭目：EC（種子的低半部分加 `0x229D6A5B`，因此頭目記錄能反推出其種子）、偽訓練家 ID、PID、滿個體值、個體值、特性、性別、性格（顫弦蠑螈的來自其形態的列表）、身高、體重和縮放，與 PKHeX 的 `Encounter9RNG.GenerateData` 一致；太晶屬性和獎勵抽選各自再用一個新的生成器。

`pokeldn.sv.raid_encounter` 在 `pokeldn/sv/data/raid_base.json` 上實現它，該檔案由 `scripts/gen_sv_raid_data.py` 從 Tera-Finder 的遭遇列表和獎勵表、PKHeX 的個人表，以及遊戲 RomFS 中的十八個 `raid_enemy_XX_array` 表構建（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，FlatBuffers，帶有各自的 `.bfbs` schema）。在每個上下文中超過 12600 個種子上，其頭目與 PKHeX.Core 26.8.26 逐欄位相同，包括六個帕底亞遭遇（記錄 5094 到 5099），其零售表給出太晶規則 0（種類自身的屬性），而 PKHeX 將其記為規則 1（任意屬性）。結晶構建函式 `0xe26ff0` 讀取 `gemType`，並在 0 和 1 兩種情況下都抽取 18 種之一（`0xe27414` 處的 `cmp w9, #2`，重抽到值小於 18），與 PKHeX 一致；通用轉換函式 `0x160e108` 把 0 視為種類自身的屬性，但不在團體戰的路徑上。由種子 `BD13FB43`（紫、帕底亞、四星）構建的頭目記錄與零售引導逐位元組相同；由 `7B741233`（朱、帕底亞、五星）構建的與法文零售版 朱 相同，只是暱稱和語言不同：零售主機寫入自己的語言和該語言的種類名（`Embrylex`，3），生成器寫入英文（2）。無論哪種情況，主機都用自己的語言顯示頭目名。

團體戰表中的種類是遊戲的 DevID：916 及以前是全國圖鑑編號，917 起是遊戲自己的順序（小鍛匠 957 對應 1000），即 `gen9.internal_index`。描述符和 RaidPoint 也攜帶 DevID：給零售版 朱 一個種類為 1000 的描述符和 RaidPoint，它列出並戰鬥的是小鍛匠。黑色結晶記錄的戰鬥等級為 90，帶努力值（例如 128 防禦和 128 特防），捕獲等級為 75；普通記錄的兩個等級一致，努力值為零。引導中的頭目記錄和 RaidPoint 摘要攜帶戰鬥等級和努力值，RaidPoint 的 `+0x2c` 是捕獲等級：由 `09F3E337`（朱、帕底亞）構建的黑色頭目與法文零售版 朱 相同，只是暱稱和語言不同。

## 活動團體戰

寶可入口站新聞的配送包含 `raid_enemy_array`、`fixed_reward_item_array`、`lottery_reward_item_array`、`raid_priority_array`（按基礎表佈局的 FlatBuffers）以及 `event_raid_identifier`（一個 u32，等於優先順序表的 `VersionNo`）。後續配送會在補丁字尾（`_1_3_0`、`_2_0_0`、`_3_0_0`）下重複每個檔案；讀取最新的一個。一條記錄會加上 `RomVer`（0 兩個版本、1 朱、2 紫）、`DeliveryGroupID`、`Difficulty`（七星為 7）、`CaptureRate`（0 從不、1、每存檔一次為 2）以及自己的獎勵表；其 `BossPokePara` 固定：

| 欄位 | 活動記錄 |
|---|---|
| `Sex` | 0 抽取；1 雄性、2 雌性，不抽取 |
| `Seikaku` | 0 抽取；性格加 1，不抽取 |
| `TalentType` | 1：`TalentVnum` 個滿個體值；2：`TalentValue` 的六個個體值，不抽取 |
| `RareType` | 0 抽取；1 從不異色（翻轉第 28 位）；2 總是：把 PID 的高半部分改寫為異色異或 0 |
| `ScaleType` | 0 兩次抽取；1 到 5 在 0-15、16-47、48-207、208-239、240-255 中各抽一次；6 用 `ScaleValue` |
| `Item`、`EffortValue` | 頭目攜帶的物品和戰鬥努力值 |

`TimeDesc` 是記錄的 `raidTimeData`（RaidPoint 0x030）：在每個七星記錄（`gameLimit` 450 到 900，`commandLimit` 60）和五個五星記錄上為 active。

巢穴屬於一個配送組，1 到 10。由種子初始化的 xoroshiro 抽取並丟棄標準的星級擲骰，然後取一個值，它落在該組中符合主機版本和允許星級的記錄的總機率之下，並選取區間包含它的記錄 [PKHeX `EncounterDist9.GetIsPossibleSlot`]：

| 進度 | 階段 | 抽取的星級 |
|---|---|---|
| 開始，太晶團體戰 | 0 | 1、2 |
| 三星 | 1 | 1 到 3 |
| 四星 | 2 | 1 到 4 |
| 五星、六星 | 3 | 3 到 7 |

機率為 0 的記錄從不會被抽中。獎勵是記錄的固定表，然後從配送的表中抽選（七星按六星計）。空的數量為 0 的抽選槽位不給出任何東西；索財靈的首次 朱 輪次只有這樣的槽位。

`pokeldn.sv.raid_event` 讀取一個配送資料夾（一個 [EventsGallery](https://github.com/projectpokemon/EventsGallery) 活動或其 `Files`）：

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint 攜帶記錄的捕獲率，並把結晶設為 2（活動）或 3（七星活動）（Tera-Finder `RaidContent`）。應用的「太晶團體戰（主持）」工具下載相簿，並把版本、進度和結晶收窄到該活動生成的範圍（[團體戰活動](gui.md#raid-events)，`raid_event.dens`）。

捕獲率 2 表示每個存檔只能捕捉一次。存檔列出已捕捉的記錄號（塊 `0x8B14392F`；擊敗標誌 `0xA4BA4848`，PKHeX `RaidSevenStar9`），重開的輪次共用同一個編號，因此捕捉一次就關閉所有輪次。主機會按大廳描述符的記錄號檢查該列表；只要編號在列表中，無論 RaidPoint 攜帶什麼捕獲率都會阻止捕捉。`--raid-catch-normal` 把「僅可捕捉一次」的記錄當作普通捕捉提供：捕獲率為 1，描述符中使用一個替身記錄號，即該記錄的日期加字尾 99（`raid_event.stand_in`），沒有任何配送使用它，捕捉後存檔也不會列出它。沒有任何 PK9 欄位或 PKHeX 遭遇儲存該記錄號，因此合法性不依賴它；在 331 場「僅可捕捉一次」的團體戰上，主機發送的頭目與 PKHeX 對該團體戰的捕捉結果相同。七星捕捉只有在擁有「最強之證」時才合法，該證章由主機給出。

固定行的 subject 3（七星的招式學習器和特性膏藥）由每臺主機的獎勵過濾器應用。團體戰頭目之後的種類資料來自 `pokeldn/sv/data/species.json`（`scripts/gen_sv_species_data.py`）。在 EventsGallery 的 153 個配送上，pkNX 的遭遇與 PKHeX.Core 26.8.26 的相同，20 080 個生成的頭目與 PKHeX 的 `GenerateSeed32` 相同，`scripts/check_sv_raid_events.py` 與每個 `Encounters.txt` 一致。

## 尋找種子

應用的團體戰種子欄位顯示該種子在工具上下文中給出的頭目和獎勵，「查詢團體戰」從第一個種子開始（手動輸入或隨機選取），在過濾器留下的每個上下文中搜索（`pokeldn.sv.raid_search`），條件包括種類、星級、太晶屬性、性格、性別、異色、尺寸證章和個體值範圍。它按頭目能力值的分數對結果排序（HP 乘以其兩項防禦之和、單看任一項防禦、較高的攻擊能力值，或總和），或按想要的獎勵排序（見下文的「最想要的獎勵」）。除非指定了種類，否則每個種類只保留一個結果。

### 尺寸證章

PKHeX 允許縮放 0 時的「迷你之證」和縮放 255 時的「巨大之證」（`MarkRules`）；查詢器的尺寸證章過濾器要求其中之一。縮放在身高和體重之後抽取：

| 縮放規則 | 縮放 | 為 0 或為 255 的機率 |
|---|---|---|
| 兩次抽取（規則 0），所有普通和黑色頭目 | `next_int(0x81) + next_int(0x80)` | 各為 16 512 分之一 |
| 從 0（規則 1）或從 240（規則 5）開始的活動區間 | `next_int(16) + low` | 觸及的那一端為 16 分之一 |
| 活動自己的值（規則 6） | 記錄的 `scale` | 總是或從不 |

`raid_search.size_marks` 給出一個活動的頭目能取得的證章；查詢器會把其餘證章置灰。

### 想要的獎勵

「獎勵」區要求若干物品行以及一場團體戰至少應給出的數量，同一物品的數量會相加。可提供的物品和數量是所搜尋的團體戰能給出的那些（`raid_search.reward_choices`）。搜尋會跳過無法給出所需獎勵的遭遇，然後在抽取頭目之前先抽取種子的獎勵。

「最想要的獎勵」按順序以想要的物品對結果排名。一場團體戰中某物品的總量算作一位數字，其位次取決於所搜尋的團體戰能給出的總量（`raid_search.ranked_rewards`）；靠前物品的數字組成一個小於 2^31 的分數，與種子一起儲存在 64 位排名中。每個已知團體戰都能容納五件物品。

### 輔助工具的掃描

PKHeX 輔助工具在所有核心上掃描種子（`services/pkhex/RaidScan.cs`，由 `pokeldn.sv.raid_scan` 驅動）：遭遇、直到縮放的頭目、分數、過濾器和獎勵。它給出某個上下文最好的種子，`search` 再用 Python 重建它們的團體戰，因此結果和並列順序都以 Python 掃描為準（`tests/test_sv_raid.py` 會比較兩者）。每個遭遇行的最佳可能排名在每次請求中只計算一次，某行的種子如果無法超過已保留的排名，就在此停止。

一次請求包含 16 777 216 個種子，之後是輔助工具在約 0.25 秒內掃描的數量，最多 268 435 456 個。一次搜尋在每個上下文最多覆蓋 2^32 個種子（`most_seeds`）；查詢器提供一億個或全部種子。「在第一個匹配處停止」（`stop_at_first`）返回最早的匹配種子。沒有輔助工具時，Python 每秒掃描約 22 000 個種子，查詢器提供 100 000 個。

| 搜尋，Apple M4，輔助工具已預熱 | 時間 |
|---|---|
| 42 個上下文各 100 000 000 個種子，查詢器預設 | 5.2 秒 |
| 一個上下文的全部種子 | 6.1 秒 |
| 42 個上下文的全部種子 | 4 分 3 秒 |

## 主機之間的戰鬥

在兩臺模擬的 朱 4.0.0 之間測得，一臺主持四星結晶，另一臺從寶可入口站加入，空座位上有兩個 NPC 夥伴。主持的主機整場戰鬥都留在會話中。每條戰鬥訊息都是鍵 0x007b 上的戰鬥開始幀，地址為 (0x2713, x, y)，其 32 位元組頭部的 type 位於 +0x00，u64 步驟計數器位於 +0x08，u64 回合數位於 +0x10，然後是 +0x18 處的 5 和 +0x19 處的對戰者或站點位元組：

| type | 來自 | 大小 | 內容 |
|---|---|---|---|
| 0x01、0x05、0x11、0x15、0x25、0x29、0x47、0x49 | 主機，地址 (0x2713, 1, 2) | 50 到 20626 | 一個步驟；每個訪客在相同計數器下以 type + 1 應答 |
| 0x02、0x12、0x16、0x26、0x2a、0x48、0x4a | 每個站點，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 對一個步驟的應答 |
| 0x06 | 站點為自己的對戰者傳送；主機為自己的、為每個 NPC 的、再為訪客的傳送 | 250 | 一個對戰者的指令；+0x19 是對戰者槽位（0 主機，2 訪客，3 和 4 NPC） |
| 0x15 | 主機，每個行動中的對戰者一條，包括頭目 | 20626 | 回合：+0x20 處五個 0x70 位元組的行動塊（槽位 0 主機、1 頭目、2 訪客、3 和 4 NPC），+0x250 處每個槽位一個位元組，統計其塊中的行動數（[行動](#actions)），+0x258 處伺服器命令佇列的長度，+0x25c 起是佇列；壓縮後 123 到 802 位元組 |
| 0x46 | 主機，開始時 62 次 | 54 | |
| 0x51 | 主機 | 86 | |

戰鬥是伺服器加客戶端。主機的構建函式 `0x113c8a0`（type 0x15 位於 `0x113c908`）複製行動塊，執行回合（`0x113e3d0`）並附加它產生的伺服器命令佇列；主機的 AI 生成 NPC 的指令，頭目的行動只會通過 0x15 到達訪客。訪客執行佇列，並且對於 type 0x13、0x15、0x17、0x19、0x1f、0x23、0x25 和 0x4d，它用同一個構建函式從主機的行動塊重建訊息體，並比較大小和位元組（`0xf5cfa4`）；不一致時轉到 `0xf5bfd4`，即接收超時處理函式。主持戰鬥的站點必須從相同狀態產生 朱 自身引擎所產生的佇列。

### 哪個站點執行伺服器

戰鬥伺服器是埠 2 成員列表的第一項，每臺主機都根據大廳主機的 Session type 6 和 type 9 構建該列表；`pokeldn.sv.port2.build_session` 把主機放在最前。

| 步驟 | 程式碼 |
|---|---|
| 團體戰開始 `0.4455` 把伺服器槽位設為 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`，設定 `+0x94` |
| 成員 i 對映到槽位 0、2、3、4；其程式碼寫入 `+0x99+slot`，對於自己的程式碼則把槽位寫入 `+0x90` | `0x1ccd15c`，作用於埠 2 的 `+0x170`；`0x2d363a0`、`0x130ea2c` |
| `0x2a1cd74` 在戰鬥開始時把設定的 `+0x94` 複製到 `net+0x58`，把 `+0x90` 複製到 `net+0x5c` | 來自 `0x18915c4` |
| 當 `!setup.710 && slot == net+0x58` 時，主機就是伺服器 | net vf `+0x78` = `0x2a1d994` |
| 0x15 檢查器只安裝在非伺服器上 | `0xfb0ee8` |
| 接收超時或檢查失敗會呼叫 net vf `+0x70` = `0x2a1d920`；在團體戰中 `0x18e217c` 把 `net+0x58` 設為主機自己的槽位 | `0xf5bfd4` |

設定的 `+0x710` 只由 `0x7faed0`（Lua `f3AF42713`）設定，團體戰開始從不會設定它。失去伺服器的主機會把自己變成伺服器，因此當大廳主機停止傳送時，每臺主機各自進行自己的戰鬥。成員向量只追加，由 type 6 或 7 的會話塊（`0x18b566c`，先追加）、type 6 的重放（`0x279ba2c`）和 type 9（`0x1954bac`）通過 `0x18b65c8` -> `0x18b68fc` 寫入；在任何塊之前的 type 9 會被丟棄（`0x18b65e4`）。引導中的參與者 k 屬於程式碼為 k 的成員；成員程式碼指向空的參與者會中止載入（2162-0001）。已失效轉移的主機用自己的 AI 執行其他每個對戰者（`0xfa52b0`、`0xfa5314`）。它的程式碼取自向量中第一個具有其站點的條目（`0xd5f3b4`）；Lua 槽位迴圈沒有 break，因此最後一個匹配的條目會設定其槽位。

### 戰鬥的隨機數

回合中的每次隨機抽取都來自一個 0x28 位元組的 xoroshiro128+ 物件（vtable `0x4500bd0`）：

| 偏移 | 大小 | 內容 |
|---|---|---|
| 0x00 | 8 | vtable |
| 0x08 | 2 x u64 | 狀態 |
| 0x18 | u64 | 種子 |
| 0x20 | u64 | 已進行的抽取次數 |

伺服器的主模組（0x378 位元組，建構函式 `0x12742d0`）把它儲存在 `+0x10`；回合程式碼以 `[[x+0x10]+0x10]` 訪問它（`0x11440e8`）。模組的初始化函式 `0x127d824` 把狀態設為種子和 `0x82A2B175229D6A5B`，計數設為 0（`0x127d9a8`），種子取自其引數塊的 `+0x20`。訪客的檢查器從戰鬥設定的 `+0x718` 填入該字（`0x2891748`）；團體戰開始 `0.4455`（@1152..@1157）通過 Lua 繫結 `fAF4A81E0`（setter `0x7faf1c`）把 `+0x718` 設為 RaidPoint 的 `randSeed`。夥伴種子同時也是戰鬥種子，由寫入引導的站點選擇。伺服器構建的每槽位模組（`0x126ba88`，來自 `0xfa9f90`）以種子 0 初始化。

一次抽取會把 `s0 + s1` 相加並推進狀態；計數按呼叫加一，而不是按重抽加一：

| 函式 | 抽取 |
|---|---|
| `0x11440f0(rand, n)` | 小於 n 的 u64：`s0 + s1` 掩碼到 n − 1 的位數，結果大於等於 n 時重抽；n 小於 2 時返回 0 且不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f`，結果大於等於 100 時重抽；小於 p 時為 true |

許多回合函式會內聯該步驟，而不是呼叫這些函式。

### 每個招式的傷害與抽取

一次招式使用按下列順序抽取：

| 抽取 | 時機 | 決定什麼 |
|---|---|---|
| `chance(25)` | 使用者麻痺 | 完全麻痺 |
| `chance(33)` | 使用者混亂 | 擊中自己，其擲骰是替代該招式抽取的 `below(16)` |
| `chance(accuracy)` | 招式有命中率；100 也會抽取 | 是否命中；命中率是招式的 (3 + n) / 3，n 小於 0 時為 3 / (3 − n)，截斷，n 為使用者的命中等級減去目標的閃避等級（在 ±6 內），再加上特性的修正 |
| `below(24)`、`below(8)`、`below(2)` | 傷害招式，按擊中要害等級 0、1、2；必定擊中要害的招式（冰息、闇冥強擊、千變萬花、流水連擊）不抽取 | 結果為 0 時擊中要害 |
| `below(16)` | 傷害招式 | 擲骰 r：傷害乘以 (100 − r) / 100 |
| `chance(p)` | 機率為 p 的追加效果（泰山壓頂的 30） | 該效果；火焰牙、冰凍牙和雷電牙在狀態之前先抽取畏縮，與 Showdown 的列表順序相反 |

對頭目的畏縮追加效果不抽取（[回合佇列中的一個招式](#a-move-in-the-round-queue) 給出了規則）。混亂的追加效果會在其 `chance(p)` 之前，通過 `below` 和 `chance` 之外的一次呼叫把生成器推進一次：在記錄每次抽取的 20 次混亂抽取中，無論該步驟輸出什麼都是 20 次（念力、幻象光線、水之波動、奇異蒸汽、魔法暴衝）。成功施加的混亂不抽取持續時間。100% 的降低能力追加效果（靈魂衝擊、重踏）在某些回合抽取 `chance(0)`，在另一些回合什麼都不抽。速度相同的對戰者在速度排序中抽取 `below(2)`（[速度相同](#speed-ties)）。面對頭目或擁有精神力（特性 39）的目標時，畏縮追加效果不抽取，除非使用者擁有破格、渦輪火焰或兆級電壓（104、163、164）；面對本回合已經行動過的玩家時，它會抽取其 `chance(p)`，而成功施加的畏縮不會向佇列新增任何內容。接觸招式命中靜電、毒刺、火焰之軀或迷人之軀（特性 9、38、49、56），或來自擁有毒手（143）的使用者時，會在招式的追加效果之後抽取 `chance(30)`；命中迷人之軀時只在雄性與雌性之間抽取。提高使用者能力的追加效果（蓄能焰襲、鋼翼）會抽取其機率，並在命中的 `0x42` 之後、擊倒指令之前新增提升，即使該擊倒擊倒了目標也一樣。降低使用者能力的招式（近身戰、臂錘、冰錘）會在其擲骰之後抽取 `chance(100)`，並在命中的 `0x42` 之後為每項能力新增 `0x0d (A, stat, n)`、`0x93` 和 `0xcb (A, 31 + stat, A, stat)`（記錄每次抽取的戰鬥會顯示這次抽取）。成功觸發的靜電、毒刺或火焰之軀會在目標的特性發動中、追加效果的指令之後使攻擊者麻痺、中毒或灼傷：`0x25 (T)`、`0xc7 (T, 0)`、來自 T 的施加（[狀態](#statuses)）、`0xc8 (T)`；已經處於異常狀態或免疫的攻擊者不顯示任何內容。粗糙皮膚和鐵刺（24、160）在發動中對接觸作出回應（即使該接觸擊倒了其持有者），使用 `0x01 (A, T, A 最大 HP 的八分之一, 20)`、`0x9a (A, -damage)` 和 `0xcb (A, 143, A)`；黏滑和捲髮（183、221）則使攻擊者速度下降一級。吸取招式的回覆緊接在命中的 `0x42` 之後、追加效果和接觸回應之前，並讀取它們之前的 HP。擊倒頭目的一擊不抽取追加效果，也不抽取接觸機率。在記錄每次抽取的 156 場 oracle 戰鬥中，外掛構建的每個回合的抽取都與記錄一致。

一場戰鬥在第一回合之前抽取一次 `below(100)`。傷害採用 Showdown 的第九世代公式（資料來自 Pokemon Showdown 的 `moves.json` 和 `typechart`），使用隊伍記錄的能力值，且頭目只按太晶屬性防守：在沒有任何能力等級變化之前對頭目的 1346 次命中中，有 921 次符合；在記錄每次抽取的 140 次命中中，有 137 次的記錄擲骰和擊中要害抽取給出了記錄的傷害。不符合的命中出現在頭目開盾期間（約為公式的 0.45）、來自有自己規則的招式（撲擊、電力上升、多段招式），或被剩餘 HP 上限截斷。

特性會像 Showdown 那樣改變公式，各自單獨應用，帶有自己的 4096 分數修正（兩個特性串聯成一個修正的情況未測量）：活力（55）把物理招式的攻擊提高 1.5 倍，並把命中率降到 3277/4096；複眼（14）把命中率提高 5325/4096，上限 100；厚脂肪（47）把攻擊方對火和冰的能力值減半，潔淨之鹽（272）對幽靈減半，且潔淨之鹽的持有者不會從追加效果獲得異常狀態；神秘之劍攻擊防禦能力值，逐步擊破、聖劍和 DD金勾臂無視目標的防禦和閃避等級；強壯之顎（173）把咬類招式的威力提高 1.5 倍，捨身（120）把反作用力招式的威力乘以 4915/4096；有色眼鏡（110）在屬性倍率之後把效果不佳的命中翻倍；冰鱗（246）在灼傷減半之後把特殊命中減半，除非攻擊者擁有破格、渦輪火焰或兆級電壓；過濾器、堅硬岩石（111、116，兩者都被破格無視）和稜鏡裝甲（232）在那裡把效果絕佳的命中乘以 0.75。連續攻擊（92）給出五次命中，並且仍然抽取命中次數擲骰。天恩（32）使每個追加效果的機率翻倍；惡臭（1）新增 10% 的畏縮，在招式自身的追加效果之前抽取；目標身上的鱗粉（19）移除追加效果及其抽取。堅硬腦袋（69）不受反作用力傷害。在沒有對戰者攜帶物品時，貪吃鬼、順手牽羊、共生、熟成和反芻（82、124、180、247、291）什麼都不做。

晴天把火屬性命中的基礎傷害提高 1.5 倍、把水屬性命中減半，雨天相反，均在擊中要害之前（Showdown 的 `onWeatherModifyDamage`；125 個帶此類命中的語料回合構建結果一致）。悠遊自如、葉綠素、撥沙和撥雪（33、34、146、202）在各自的天氣中使速度翻倍，對排序鍵、排序和 `0x5a` 都一樣；沙隱和雪隱（8、81）在各自的天氣中把針對其持有者的招式命中率降到 3277/4096（83 個語料回合中，六者之一處於其天氣，構建結果一致）。沙隱、防塵、撥沙和沙之力（8、142、146、159）不受沙暴傷害。下雪時冰屬性面對物理命中時防禦提高 1.5 倍，正如沙暴時岩石屬性的特防提高。

起死回生和抓狂的威力取自使用者 HP 的 48 分之一數（Showdown 的表：低於 2 為 200，低於 5 為 150，低於 10 為 100，低於 17 為 80，低於 33 為 40，否則為 20）。擁有適應力（91）的頭目，其太晶屬性同時也是自身屬性之一的招式獲得 2.25 的本系加成，其他太晶屬性招式獲得 2.0，自身屬性的其他招式獲得普通的 1.5。

有自己威力規則的招式遵循 Showdown 的 `moves.ts`：以牙還牙在目標於本回合更早行動時翻倍（被破盾丟棄的頭目回應不算），禍不單行對處於異常狀態的目標翻倍，電力上升對電氣場地中的接地目標翻倍；硬撐在除睡眠外的異常狀態下翻倍，毒液衝擊對中毒目標翻倍，閃電猛衝和全開猛撞在效果絕佳時對屬性倍率之後的傷害乘以 5461/4096，廣域戰力由接地使用者在地精神場地中使用時為 1.5。翻倍的電力上升在其 `0x8b` 的第五個引數中攜帶 1；翻倍的以牙還牙攜帶 0。在構建結果一致的語料回合中，以牙還牙和電力上升各出現一次提升；禍不單行、硬撐、毒液衝擊和閃電猛衝只以未提升的形式出現。

場地（青草 1、薄霧 2、電氣 3、精神 4）會改變招式威力：接地使用者使用與其同屬性的招式時為 5325/4096（草、電、超能力；薄霧場地不增強任何屬性），龍屬性招式命中薄霧場地中的接地目標、地震或重踏命中青草場地中的接地目標時減半。對戰者除非是飛行屬性、擁有飄浮或攜帶氣球，否則視為接地。在電氣、精神或薄霧場地下的 151 個語料回合（42、57、52）用這些規則構建結果一致。

頭目的 HP 總量是其記錄的 HP 乘以 RaidPoint 的 HP 係數再除以 100（[戰鬥引導](#the-battle-bootstrap)）：在贏下的 oracle 戰鬥中，一星 78 場、二星 84 場、三星 125 場、四星 35 場，分別在 `0x37 (2, 2, damage)` 中承受記錄的 HP 的正好 5、5、8 和 12 倍後結束；其餘的承受更少，經由護盾和有自己規則的招式。

### 狀態

成功施加主要異常狀態的追加效果，會在命中的記錄之後執行：`0x13 (T, condition, 0, value, A)`、`0x90 (T, condition)`、`0xa7 (T 的位置, code)` 和 `0xcb (A, text, T)`：

| 狀態 | condition | value | code | text |
|---|---|---|---|---|
| 麻痺 | 1 | 1 | 46 | 92 |
| 睡眠 | 2 | turns << 3 \| 2 | 42 | 103 |
| 冰凍 | 3 | 1 | 45 | 97 |
| 灼傷 | 4 | 1 | 44 | 86 |
| 中毒 | 5 | 1 | 43 | 79 |
| 劇毒 | 5 | 7801 | 43 | 80 |
| 混亂 | 6（無 `0x90`） | turns << 3 \| 2 | 47 | 116 |

睡眠追加效果把其回合數抽取為 2 + `below(3)`，混亂追加效果為 2 + `below(4)`，均在其 `chance(p)` 之前，通過抽取日誌不顯示的一次呼叫（`rand+0x20` 處的呼叫計數器仍會計入它）。已經處於異常狀態的目標，或按其屬性免疫的目標（電屬性對麻痺、火屬性對灼傷、冰屬性對冰凍、毒屬性和鋼屬性對中毒）不受任何影響。混亂追加效果命中我行我素（20）時仍會抽取，但不顯示任何內容。

在招式之前，畏縮的對戰者會顯示 `0xcb (A, 122, A)` 和 `0x52 (A, 0)`；冰凍的對戰者抽取 `chance(20)` 以解凍，若仍冰凍則顯示 `0xcb (A, 98, A)`、`0xa7 (A 的位置, 45)`、`0x52 (A, 0)` 和 `0x1d (A, P, type, 0, 0, M, M)`；麻痺的對戰者抽取 `chance(25)`，完全麻痺時以同樣方式顯示訊息 93 和程式碼 46；睡眠則顯示訊息 104 和程式碼 42。每一種都在招式的處理器 `0x5a (A, M, 0x72000 + speed)` 之後，以兩次 `0x5b (A, M)` 和 `0x1e (A, 0)` 結束。麻痺的對戰者速度在其能力等級之後減半。灼傷使用者的物理傷害在屬性相性之後減半，至少為 1。火屬性命中冰凍的目標會在其 `0xd1` 之後使其解凍：`0x14 (T)`、`0x90 (T, 0)`、`0xcb (T, 99, T)`。護盾升起以及頭目自身的能力重置（在其 `0x0f (2)` 與 `0xc2 (3, 2, 2)` 之間）會用 `0x14 (2)` 和 `0x90 (2, 0)` 治癒頭目的異常狀態；護盾還會用 `0x15 (2, 6)` 結束其混亂。

混亂在招式之前、冰凍或睡眠檢查之後生效；同時混亂且麻痺的對戰者未測量。其回合數減一；為 0 時以 `0x15 (A, 6)` 和 `0xcb (A, 118, A)` 結束，招式繼續。否則它會顯示 `0xa7 (A 的位置, 47)` 和 `0xcb (A, 117, A)`，並抽取 `chance(33)`；擊中自己時只抽取其擲骰 `below(16)`，別無其他：Showdown 的 40 威力無屬性物理傷害，按對戰者自身的攻擊和防禦等級計算，顯示為 `0x91 (A)`、`0x01 (A, 使其混亂的對戰者, damage, 2)`、`0x9a (A, -damage)`、`0xca (A, 576, A)`、`0x52 (A, 0)`，然後是被中止招式的結束（頭目的則帶其 `0x1d`）。頭目的額外行動招式在其 `0xc1 (9, 0)` 和 `0xc1 (9, 1)` 內以同樣方式檢查其混亂和麻痺，被中止的招式以 `0x1d (2, P, type, 0, 0, M, M)` 結束。

瀕死會清除對戰者的異常狀態和混亂。

在回合結束時，灼傷在其 `0x19 (b, 4)` 之後立刻造成對戰者記錄 HP 的十六分之一（頭目的記錄 HP，而不是其 HP 總量），中毒在 `0x19 (b, 5)` 之後造成八分之一，劇毒在其第 n 個回合結束時造成 n 個十六分之一：`0xa7 (b 的位置, 44 或 43)`、`0x01 (b, 施加它的對戰者, damage, 39 或 38)`、`0x9a (b, -damage)` 和 `0xcb (b, 88 或 82, b)`。鹽醃（864）在命中的 `0x42` 之後對目標設定 condition 46（`0x13 (T, 46, 0, 1, A)`、`0xcb (A, 1033, T, A)`，其 100% 機率會抽取；精神噪音的治癒封鎖以同樣方式，使用 `0x13 (T, 15, 0, 18, A)` 和 `0xcb (A, 283, T)`）；在每個回合結束時，緊接在 `0x19 (b, 46)` 之後，它造成記錄 HP 的八分之一，對水或鋼屬性為四分之一：`0xa7 (b 的位置, 152)`、`0x01 (b, A, damage, 0)`、`0x9a (b, -damage)`、`0xcb (b, 125, b, 864)`。對已被鹽醃的目標再次使用鹽醃不新增任何內容。

在回合結束時被擊倒的玩家（由鹽醃、灼傷、中毒或沙暴）會在該傷害的指令之後立刻執行擊倒指令，帶 `0x49 (V, 0, 0)` 且沒有 `0x09`，僅當 s（對其施加鹽醃、或升起沙暴的對戰者）是其對手時才以 `0x38 (s)` 結束（由同伴的吐沙升起的沙暴不顯示任何內容）。顯示的傷害是完整的分數值。

頭目身上的自信過度（153）在其一擊擊倒玩家之後、命中的 `0xd1` 之後提高其攻擊：`0x25 (2)`、`0xc7 (2, 153)`、`0x0c (2, 1, 1)`、`0x92`、`0xcb (2, 11, 2)`、`0xc8 (2)`。在語料計為 +5 的情形（一場戰鬥中三次擊倒）下它不顯示任何內容；當時頭目是否已在 +6 未知。加速（特性 3）在 `0x44` 列表之後提高速度（`0x25`、`0xc7`、`0x0c (b, 5, 1)`、`0x92`、訊息 15、`0xc8`），在回合結束的最後三次對戰者排序之前，例外是此後尚未指揮過一個回合的復活對戰者（語料中兩種情形各 2 例；Showdown 的 `activeTurns`）。脫皮（61）和溼潤之軀（93）在無異常狀態時、以及頭目身上的治癒之心（131，它沒有同伴）在回合結束時不顯示也不抽取任何內容；處於異常狀態的對戰者身上的脫皮會在那裡抽取 `chance(33)`（語料中沒有出現治癒）。

### 速度相同

戰鬥用交換排序按速度排列對戰者和行動：每個條目與它之後的每個條目比較，當後者的鍵更大時後者前移。鍵相等時抽取 `below(2)`，為 1 時後者前移，因此一次相同會在兩個相等條目的每次比較中各抽取一次。對戰者 id 是 1 到 5，頭目是 2。在 142 場把兩個對戰者的速度強制為相同值的 oracle 戰鬥中，按 id 順序對五個對戰者排序，在戰鬥開始時給出的抽取次數與記錄一致的為 142 場。

| 何時 | 對什麼排序，按此輸入順序 | 排序次數 | 誰讀取結果 |
|---|---|---|---|
| 戰鬥開始時，在複製（Trace）的抽取之前 | 五個對戰者，id 順序 | 1 | 上場事件 |
| 一回合開始時 | 該回合的行動，指令順序；鍵為優先度，然後是非慢出，然後是速度 | 3，每次基於前一次的結果 | 第一次：第二次 `0x51` 遍歷；第三次：招式的順序 |
| 每個招式之後、最後一個除外 | 這些行動 | 1 | 佇列中沒有任何東西 |
| 一回合結束時 | 站著的對戰者，每次都按 id 順序 | 3 | 第二次：`0x43` |
| 頭目倒下的那一回合結束時 | 站著的對戰者 | 無：不抽取 | 按速度順序的 `0x43`，相同則按 id 順序（5 場有相同的語料勝利中 5 場） |
| 回合結束時（每四個回合） | 站著的對戰者，每次都按 id 順序 | 8 | 第四次：沙暴、吃剩的東西和 `0x19` 的順序；第七次，在回合結束之後：`0x43` |

回合結束的 `0x43` 順序在 123 場戰鬥中有 109 場與第二次排序一致；其餘 14 場中有對戰者的速度在該回合被招式改變。在雙方行動者相同的 27 個回合中，鏈式行動排序在 27 個回合裡都與 `0x51` 和招式順序一致；在到達兩個招式的 3 個回合中，第一個招式之後的抽取都出現了。在前五次排序不一致的 12 個語料回合結束中，第四次排序在 12 個裡都給出了殘餘順序；第一次、第二次、第三次或第五次會在其中一些上失敗。

頭目的複製對其能複製其特性的玩家按 id 順序抽取 `below(N)`：當一名玩家擁有面影輝映時抽取 `below(3)`。命中硬殼盔甲（特性 75）的招式不抽取擊中要害。

擁有變身者（Imposter）的頭目在戰鬥開始時變成對戰者 1，並用該對戰者的能力值戰鬥，但 HP、招式、屬性和能力等級仍是自己的（其太晶屬性不變）。站點仍會命令它使用變身（Transform），而此後每次都會失敗：`0xc9 (2, 0, 144, P, 1)`、`0x7b`、五個零組、`0xca (2, 567)`、`0x1d (2, P, 0, 1, 0, 144, 144)`、兩次 `0x5b (2, 144)` 和 `0x1e (2, 0)`，在其處理器的 `0x5a` 之後。與處理器招式並列且鍵相同的行動會像任何相同一樣排序和抽取（11 場語料戰鬥）。

### 回合佇列中的一個招式

在一個回合的佇列中，一個對戰者的招式是一段連續的指令。對戰者的客戶端位置對對戰者 1、3、4、5 是 0 到 3，對頭目是 4；A 是使用者，T 是目標，M 是招式，`type` 是招式的屬性索引，`cat` 是其類別（1 物理，2 特殊）。在玩家的招式命中頭目、且頭目的回應命中玩家的 oracle 回合上測得：

一回合以 `0xb2 (0)` 結束，接著是每個行動過的對戰者的 `0x37 (b, 7, 1)`、`0x75 (3, n)`、`0xc5 (1)`、按速度順序對每個對戰者的 `0x43 (b)`（隊伍記錄的速度處於其能力等級，包含頭目）、按 id 順序對該回合每個行動者的 `0x23 (b)`（戰鬥第一回合則是全部五個），以及 `0x2d (0)`；`0x75 (3, n)` 計入當前回合的指令回合數，包括這一個。一個回合在每第四個指令回合結束，不論由哪些槽位發出（oracle 語料 4,090 個回合結束中的 3,606 個；其餘之間有一或兩個團體戰行動回合，它們不計入）：其 `0x75 (3, 0)` 之後是 `0xc5 (0)`、`0x50 (0)`、按順序 36、21、18、5、4、9、10、8、46、43、48、11、12、23、13、31、33、15、19、29、30、38、37、39、40、41、24、45、14、20、1、2、3、7、6、16、17、22、25、26、27、28、32、34、35 對每個回合結束種類 k 的 `0x19 (b, k)`，每種都按速度順序覆蓋對戰者，然後是對 k 為 1 到 13 的 `0x44 (k)`，在通常的 `0xc5 (1)` 之前。天氣持續五個回合結束，其升起的那一回合計為第一個：在第五個時它緊接在 `0x50 (0)` 之後以 `0x99 (w)`、`0x54 ()`、`0x6a (0)` 結束，而沙暴結束時該回合不造成傷害（oracle 語料中 7 次天氣結束中的 7 次）。晴天、雨天和下雪在回合結束時不新增任何內容。場地同樣持續五個回合結束，並在 `0x44 (8)` 與 `0x44 (9)` 之間以 `0x34 (8)`、`0x6a (8)`、`0xca (0, text)`、`0x32 (0, 0, 1, 0)`、`0x6a (8)`、`0xb2 (0)`、`0xaa (0)`、`0x69 (8, 0)` 結束；結束文本為青草 705、電氣 709、精神 829（薄霧不在語料中）。沙暴在 `0x50 (0)` 之後為它按速度順序傷害的每個對戰者新增（其最大 HP 的十六分之一）：`0xcb (b, 133, b)`、`0xa7 (b 的位置, 14)`、`0x01 (b, s, damage, 1)`（s 為升起沙暴的對戰者，即其揚沙或吐沙，或頭目的沙暴），以及 `0x9a (b, -damage)`。吃剩的東西（道具 234）隨後按速度順序、在殘餘種類之前，為每個未滿 HP 的持有者恢復其記錄 HP 的十六分之一：一個 5 位元組的零 `0xcf` 組、`0x9b (b, 0)`、一個 3 位元組的零組、`0xa7 (b 的位置, 51)`、`0x03 (b, heal)`、`0x9a (b, heal)` 和 `0xcb (b, 295, b, 234)`；顯示的回覆是完整的十六分之一，即使缺少的 HP 更少。青草場地在天氣的指令之後、吃剩的東西之前，按速度順序為每個未滿 HP 的接地對戰者恢復其記錄 HP 的十六分之一：`0xa7 (b 的位置, 51)`、`0x03 (b, heal)`、`0x9a (b, heal)`、`0xcb (b, 130, b)`。心情不定（特性 141）在 `0x44` 列表之後、回合結束時生效：一次 `below(20)` 抽取 v 選出被提高的能力（攻擊到速度）v // 4，以及其餘四項中被降低的能力 v % 4；`0x25 (b)`、`0xc7 (b, 0)`、提高 2 級（從 +5 起為 1 級）、降低 1 級（`0x0d`、`0x93`、`0xcb (b, 31 + stat, b, stat)`）、`0xc8 (b)`（語料中每個心情不定的回合結束都如此；±6 時的能力未測量）。其他攜帶道具在回合結束時的表現未測量。

目標屬性免疫的傷害招式不抽取任何東西，連命中率也不抽，並執行 `0x05`、`0x07`、`0xc9 (A, 0, M, P, 1)`、`0x7b`、五個 `0xcf` 組（20、5、5、5 和 19 個零位元組）、`0xcb (A, 72, T)`、`0x52 (A, 3)`、`0x08 (A, slot)`、`0x52 (A, 0)`、`0x1d (A, P, type, 0, 0, M, M)`、兩次 `0x5b (A, M)` 和 `0x1e (A, 0)`：oracle 語料中 5,550 次訊息 72 執行裡的 5,353 次（其餘會開啟一次特性發動）。地面屬性招式命中擁有飄浮（26）且其屬性本身不免疫的目標時，以同樣方式執行，訊息 72 位於目標的特性發動之內：`0x25 (T)`、`0xc7 (T, 0)`、`0xcb (T, 72, T)`、`0xc8 (T)`，然後是 `0x52 (A, 3)`。草屬性招式命中食草（157）、或電屬性命中電力引擎（78）時，作為免疫招式執行，其發動會把目標的攻擊或速度提高一級（`0x25 (T)`、`0xc7 (T, 0)`、`0x0c (T, stat, 1)`、`0x92`、`0xcb (T, 10 + stat, T)`、`0xc8 (T)`），然後是 `0x52 (A, 2)`。

命中率抽取失敗的傷害招式會作為免疫招式執行，以訊息 73 和 `0x52 (A, 1)` 代替訊息 72 和 `0x52 (A, 3)`。沒有剩餘 PP 的玩家招式（隊伍記錄的 PP，每次使用減 1，對壓迫感為 2）只執行 `0xc9 (A, 0, M, 10, 1)`、`0xca (A, 578, A)`、`0x52 (A, 0)`、兩次 `0x5b (A, M)` 和 `0x1e (A, 0)`，在麻痺抽取其 `chance(25)` 之前。

玩家的招式若不在《朱／紫》中（Showdown 的 `isNonstandard` 為 Past 或 LGPE：追打、查封、Sizzly Slide 以及其他）會在其他一切之前失敗，不抽取也不消耗 PP：`0xca (A, 567, A)`、`0x52 (A, 0)`、兩次 `0x5b (A, M)` 和 `0x1e (A, 0)`，在其處理器的 `0x5a` 之後（若它註冊了一個——芳香治療、Sappy Seed 和 Freezy Frost 都會）。oracle 語料中此類執行的 2,622 次中的 2,622 次符合；沒有任何遊戲外玩家的招式會到達 `0xc9`。無法獲得的那些（居合斬和各 Torque 招式）作為普通招式執行（語料中 183 次執行）。

傷害招式若在其被指向之後目標已經瀕死（頭目的額外行動招式在其條目加入列表時就被指向），會作為免疫招式執行，以 `0xc9 (A, 0, M, P, 1)` 和 `0xca (A, 567)` 代替訊息及其 `0x52 (A, 3)`。

在頭目開盾期間指向它的變化招式會在執行之前失敗，不抽取：`0x05`、`0x07`、`0xc9 (A, 0, M, P, 1)`、`0xca (A, 567, A)`、`0x52 (A, 0)`、`0x1d (A, P, type, 0, 0, M, M)`、兩次 `0x5b (A, M)` 和 `0x1e (A, 0)`（oracle 語料中 120 次降低能力和施加異常狀態的招式命中護盾中的 120 次；指向其使用者的招式仍會執行）。降低能力的招式若目標被降低的能力全在 -6，會作為免疫招式執行，對每項能力使用 `0xcb (A, 59 + stat, T)`（攻擊為 60）代替訊息 72 和 `0x52 (A, 3)`，不抽取；提高能力的招式若其使用者身上相關能力全在 +6，以同樣方式執行，對每項能力使用 `0xcb (A, 52 + stat, A)`。傷害招式的追加效果在相應能力為 +6 時不顯示任何內容。

命中率抽取失敗的變化招式會作為傷害落空執行（訊息 73 和 `0x52 (A, 1)`）。其異常狀態被目標屬性免疫的變化招式（電磁波命中電屬性）會作為免疫招式執行，帶 `0xcb (A, 72, T)` 而沒有 `0x52 (A, 3)`，不抽取；使中毒的招式命中已中毒目標時以同樣方式，帶 `0xcb (A, 84, T)`。睡眠招式會在其命中率之前，通過抽取日誌不顯示的那次呼叫抽取其回合數。

天氣招式（大晴天、求雨、下雪、沙暴）作為帶場地類別（10）的能力等級變化招式執行，並以天氣的開始代替能力變化：`0x6a (0)`、`0x69 (0, w)`、`0x79 (w, 5, 0, A, 0)` 和 `0x88 (w, A, 0)`，w 為 1 晴天、2 雨天、3 下雪、4 沙暴；施加異常狀態的變化招式（電磁波、鬼火、劇毒、蘑菇孢子）會在那裡執行施加過程（[狀態](#statuses)）。被傷害招式命中的 吐沙（245）會在命中的 `0x42` 及其追加效果的指令之後升起沙暴：`0x25 (b)`、`0xc7 (b, 0)`、w 為 4 的天氣開始、`0xc8 (b)`，且沒有訊息，若該命中擊倒其持有者則在擊倒指令之前；在已經升起的沙暴下它不顯示任何內容。在另一種天氣之上升起的天氣（天氣招式或 吐沙）只顯示自己的開始並替換舊的，舊天氣的結束不顯示任何內容。場地招式以同樣方式執行，帶有場地的開始：`0x32 (t, 0, 42, A)`、`0x6a (8)`、`0xb2 (0)`、`0xaa (t)`、`0x69 (8, t)` 和 `0xca (A, text)`，開始文本為青草 704、薄霧 706、電氣 708、精神 828；已有場地時它會以文本 567 失敗。場地招式的 `0x8b` 無論被命令的是什麼位置都攜帶位置 10。在 `0x6a`、`0x69` 和 `0x44` 中，天氣是場地槽位 0，場地是場地槽位 8。

反作用力招式會在命中的 `0xd1` 之後、以及任何擊倒的指令之後新增 `0x01 (A, A, r, 4)`、`0x9a (A, -r)`、`0xcb (A, 127, A)` 和 `0x37 (A, 4, r)`，其中 r 是造成的傷害（至多為目標當時擁有的 HP）乘以招式的比例、四捨五入（半數進位）、至少為 1。葉綠爆震以同樣的方式結束，代價是其使用者最大 HP 的一半。鐵蹄光線在其 `0x8b` 之後、傷害指令之前支付其使用者最大 HP 的一半：`0x01 (A, A, cost, 0)` 和 `0x9a (A, -cost)`，沒有訊息。攜帶生命寶珠（道具 270）的玩家會在造成傷害的招式之後、命中的 `0xd1` 之後損失其最大 HP 的十分之一：`0x01 (A, A, cost, 29)`、`0x9a (A, -cost)`、`0xcb (A, 328, A)`；它對頭目的命中不帶 1.3 倍傷害加成（9 次命中構建一致，另有 7 場戰鬥在帶加成時的第一次此類命中處出現分歧）。

聚氣作為作用於其使用者的變化招式（類別 7）執行，其效果為 `0x1e (A, 9)`、`0x7d (9, A, 0, 0)` 和 `0xcb (0, 336, A)`；此後使用者的擊中要害等級提高兩級（等級 0 的招式變為 `below(2)`）。蓄力的第一層以同樣方式執行，帶 `0x35 (A, 0, 1)`、`0xcb (0, 236, A, 1)`、防禦提升、`0x35 (A, 1, 1)`、特防提升和 `0x35 (A, 2, 1)`（語料中 18 次中的 18 次；未出現第二次蓄力）。

唯一效果是能力等級的變化招式執行 `0x05`（玩家的招式）、`0x07 (A, 0)`、`0xc9 (A, 0, M, P, 0)`（P 為被命令的位置）、`0x7b (M, n, A)`、一個 20 個零位元組的 `0xcf` 組、`0x7e (0, 0, 0, 0, 0, 0)`、`0x7e (1, 0, 0, 0, 0, 0)`、`0x7e (2, 7, 7, 7, 7, 7)`、`0x8b (A 的位置, T 的位置, M, type, 0, 0, 0, 0, class, 0)`（對自身使用時 T 是 A，類別 7）、能力變化，然後是 `0x7c ()`、`0x08 (A, 0)`、`0x1d (A, P, type, 1, 0, M, M)`、兩次 `0x5b (A, M)` 和 `0x1e (A, 0)`。提升是 `0x0c (b, stat, n)`、`0x92 (b, stat, n, 0)` 和 `0xcb (b, text, b)`；下降是 `0x0d (b, stat, n)`、`0x93 (b, stat, n, 0)` 和 `0xcb (A, text, b, stat)`。text 對於提高 1、2 或 3 級是 10、17 或 24 加上該項能力，對於下降 1 或 2 級是 31 或 38 加上該項能力（能力 1 攻擊到 7 閃避），按 Showdown 原始碼中的順序，也就是能力順序（盤蜷提高攻擊、防禦，然後命中率），但換擋（速度，然後攻擊）和 V熱焰（速度、防禦、特防）例外，覆蓋 oracle 語料中的每一次能力變化。不會落空的招式（Showdown 的 accuracy 為 `true`）不抽取命中率。恆淨之軀、白色煙霧和金屬防護（29、73、230）會阻止傷害招式的追加下降，不帶指令也不帶訊息，正如對 -6 的能力的追加下降一樣（其機率仍會抽取）。不服輸和好勝（128、172）會回應對手對一項能力的下降，在其訊息之後：`0x25 (b)`、`0xc7 (b, 0)`、`0x0c (b, 1 或 3, 2)`、`0x92`、`0xcb (b, 18 或 20, b)`、`0xc8 (b)`。

範圍招式（Showdown 的 target 為 `allAdjacent` 或 `allAdjacentFoes`）只命中其指令指定的位置，使用單目標傷害且沒有範圍修正：包含這類招式的每個 oracle 回合都作為單目標命中構建一致，`class` 為 4 或 5。招式按優先度分組順序執行，然後按能力等級上的速度：頭目的水流噴射或影子偷襲會比更快的玩家先行動。

擊倒頭目的一擊贏得戰鬥。其 `0x42` 之後是 `0x49 (2, A, M)`、`0x09 (A, slot)`（`slot` 是 M 在 A 招式表中的索引；383 次 oracle 擊倒中的 382 次）、`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、`0x5d (2)`、按 id 順序對每個玩家的 `0x41 (b, 2)`、對 k 為 0 到 13 的 `0x33 (2, k)`（僅當有場地存在時才為 8）、`0x80 (2)`、`0x29 (2)` 和 `0x38 (A)`，然後是招式通常的結束。此後沒有人行動，回合只以仍站立的對戰者的 `0x43`、`0x23` 列表和 `0x2d (0)` 結束。`0x85 (7, damage)` 和傷害指令攜帶頭目剩餘的 HP。

字首以 `0xb5 (0)` 開始，然後按 id 順序對該回合的行動者執行一次 `0x51 (b, 1)`，再按第一次行動排序的順序執行一次；在第二次執行中，擁有 慢出（特性 100）的對戰者攜帶 `0x51 (b, 0)`，此後其行動在其分組中排在最後；該回合的第一次排序仍把它計為 1。菌絲之力（298）僅在變化招式上以同樣方式攜帶 `0x51 (b, 0)`，惡作劇之心（158）把變化招式的優先度提高 1。每次行動排序（[速度相同](#speed-ties)）先按列表順序計算每個招式行動的順序鍵，註冊了自己處理器的招式會將其顯示為 `0x5a (b, M, speed)`（speed 處於其能力等級）和 `0x5b (b, M)`。該回合第一個執行的招式會再計算一次每個招式行動的鍵，而招式註冊了處理器的行動者會在其 `0x05` 之前新增 `0x5a (b, M, key)`，鍵為 (priority + 7) << 16、其 `0x51` 值 << 13，再加上其速度（優先度為 0 的招式為 `0x72000 + speed`；慢出 為 `0x70000`）。排序的 `0x5a` 只攜帶能力等級上的速度值；執行的則攜帶計入順風和麻痺的速度（oracle 的指令日誌與其排序和行動執行交織）。631 個招式中有 347 個註冊了一個（硬撐和泰山壓頂在列，暗襲要害不在）。

頭目從一開始就太晶化：其太晶屬性的傷害招式若在基礎威力修正之後低於 60 威力、沒有優先度且只有一次命中，則按 60 計算，這是第九世代的太晶規則（奧利瓦的太晶一般屬性撞擊造成 4，而 40 基礎威力給出 2；擁有鬥爭心的頭目以太晶惡屬性咬住命中另一性別的玩家造成 25，即未修正的 60 威力傷害，而鬥爭心的 45 至多給出 21）。招式的每個追加效果會按 Showdown 的順序抽取 `chance(n)`，但對頭目的畏縮不抽取：玩家的冰凍牙命中頭目只抽取其冰凍機率（冰凍顯示為 `0x13 (2, 3, 0, 1, 4)`，訊息為 97 和 98，且頭目在行動前抽取 `chance(20)` 以解凍），頭目的冰凍牙命中玩家時兩者都抽取。擊倒頭目的一擊先抽取 `chance(0)`，無論是否有追加效果。

用 Showdown 的招式資料和第九世代傷害公式這樣構建，554 場 oracle 戰鬥中有 56 場的第一回合與 oracle 逐位元組一致，且沒有一場不同（其餘包含被拒絕的某種東西）；20 場完整戰鬥在每個回合都與 oracle 一致，而在針對指令碼主機的服務中，19 場中的 19 場都在同一幀發出 oracle 伺服器發出的每一幀。當行動或被命中的對戰者擁有其 Showdown 回撥可能改變該回合的特性或道具時（活力帶來的攻擊、鬥爭心的威力、友情防守的 0.75、受驚在惡屬性命中後的速度提升、疾風之翼的優先度），該回合會被拒絕，除非語料測得該特性或道具處於閒置狀態；或者當戰鬥擁有在上場時生效的特性時（威嚇在第一回合之前降低攻擊方的攻擊）。

### 行動

一個回合的行動頭（請求塊，0x238 位元組）是五個 0x70 位元組的塊，每個客戶端槽位一個，每塊最多七個 16 位元組的行動（一個 u64 行動字、一個 u32 行動者對戰者 id、4 個沒有程式碼寫入的位元組），並在 +0x230 處每個槽位一個位元組，統計其塊中的行動數。伺服器按槽位順序把它們解碼成 0x8c 位元組的行動條目（`0x1145e40`，解碼器 `0x11461b4`）。行動字的低四位是 kind：

| kind | 條目 kind | 字中的欄位 |
|---|---|---|
| 1 | 1，一個招式 | 位 4..7 目標的對戰位置，8..23 招式，位 25 一個標誌 |
| 2 | 2 | 位 4..19 和 20..27；下一個 u32 |
| 3 | 3，一個替換 | 位 4..7 隊伍索引（行動者就是該隊伍成員），8..11，位 12 |
| 4 | 6 | 位 4..11、12..15 和 16..23 |
| 5 | 4 | 位 4 |
| 6 | 5 | 位 4..11 |
| 7、10、11 | 7、8、9 | 無 |
| 9 | 10 | 位 4..11 |
| 12 | 11 | 位 4..11；下一個 u32 |
| 13 | 14 | 位 4..7、8..11、12..15、16..27、32..43、44..55、56..59、60..63 |

位 0..3 為 3 且位 12 置位的字會被跳過，kind 0、8、14 和 15 也一樣。一條記錄的玩家行動 `41 67 03 00 ...` 是一個招式（kind 1），目標位置 4，招式 871（閃焰高歌）。

團體戰中的對戰者 id：1 是槽位 0 的寶可夢，2 是頭目，3 是槽位 2，4 是槽位 3，5 是槽位 4。站點的 type-0x06 指令是 0xe8 位元組：0x20 位元組的頭（+0x19 是槽位）、+0x20 處一個計數字節，然後是從 +0x28 開始的 (u64 字, u64 行動者) 對。它攜帶該槽位自己的行動以及頭目對該槽位的回應：一個訪客對槽位 2 的指令包含 `move 871 at position 4 by battler 3` 和 `move 204 at position 1 by battler 2`。站點為其自己的寶可夢選擇頭目的招式。

### 戰鬥開始的正文

訊息 0x11 的正文是一個沒有長度字的指令佇列（[伺服器的指令佇列](#the-server-command-queue)）。對戰者 id 為：槽位 0 是 1，頭目（槽位 1）是 2，槽位 2 是 3，槽位 3 和 4 是 4 和 5；對戰者位於位置 id − 1。正文按 id 順序送出每個對戰者，然後執行上場事件，最後以 `0x2b (0)` 結束：

| 指令 | 作用 |
|---|---|
| `0x3d (pos)`、`0x16 (pos, 0, 0, 0)`、`0x5e (id, ability)`、`0x61 (id)`、`0x6b (id)`、`0x4e (id)` | 一個對戰者被送出；`ability` 是其特性 id |
| `0x25 (id)`、`0xc7 (id, 0)`、效果、`0xc8 (id)` | 一次特性發動 |
| `0xcb (id, text, params..., 0xffff0000)`，用零補齊到十個引數 | 一條戰鬥訊息 |

| 上場事件 | 效果 |
|---|---|
| 壓迫感（46） | 圍繞 `0xcb (id, 162, id)` 的發動 |
| 威嚇（22） | 圍繞每個目標的 `0x0d (target, 1, 1)`、`0x93 (target, 1, 1, 0)`、`0xcb (id, 32, target, 1)` 的發動 |
| 察覺（119） | 圍繞每個攜帶道具的對手的 `0xcb (0, 146, id, target, item)` 的發動 |
| 緊張感（127） | `0x25 (id)`、`0xc7 (id, 127)`、`0xca (id, 679, side, 0xffff0000)`、`0xc8 (id)`，在其他每個事件之前；`side` 對玩家的緊張感為 1，對頭目的為 0 |
| 預知（107） | 當對手知道一個對其效果絕佳的傷害招式或一擊必殺招式時，圍繞 `0xcb (id, 145, id)` 的發動 |
| 複製（36） | `0x25 (id)`、`0xc7 (id, A)`、`0x89 (id, 36, A)`、`0xcb (id, 128, S, A)`、`0x5f (id)`、`0x24 (id, A)`、`0x5e (id, A)`、兩次 `0xc8 (id)`，從 S 複製特性 A：玩家的複製複製頭目，頭目的則複製 `below(4)` 在對戰者 1、3、4、5 中選出的玩家（6 場戰鬥中的 6 場） |
| 界限盾殼（197） | 對於 HP 高於一半的流星形態（形態 0 到 6）的小隕星沒有；核心形態（7 到 13）顯示 `0x25`、`0xc7`、`0x57 (id, form − 7, 0)`、`0xac (id)`、`0xca (id, 842)`、`0xc8`（9 場戰鬥中的 9 場） |
| 攜帶氣球（541） | 在對戰者的特性之後 `0xcb (id, 137, id)` |

這些事件按對戰者的速度順序執行（隊伍記錄速度），緊張感最先。威嚇按 id 順序影響每個對手。擁有我行我素的對手會在其中以自己的 `0x25`/`0xc7`、`0xcb (F, 69, F, 0xffff0000)` 和 `0xc8` 回應，且不損失任何東西。擁有不服輸的對手會在其下降之後以 `0x0c (F, 1, 2)`、`0x92 (F, 1, 2, 0)` 和 `0xcb (F, 18, F, 0xffff0000)` 回應。察覺用 `0xcb (0, 146, I, F, item, 0xffff0000)` 指出第一個攜帶道具的對手，之後的每個用 `0xca (0, 752, F, item, 0xffff0000)`；對手中沒有任何道具時它沒有事件。這樣構建，554 個 oracle 開始正文中有 420 個一致，且沒有不同的。

回合結束會為列表的每個條目放置一個 `0x37 (b, 7, 1)`，無論是否執行過，按列表最後的順序：護盾、一次額外的頭目重置，以及三個條目被護盾再次入隊的額外招式時為 7。`0x75 (3, n)` 只計入有玩家條目的回合，而團體戰行動回合仍計入 `0x7b (M, n, A)`。團體戰行動回合在其他方面與指令回合一樣結束：三次對戰者排序、按第二次排序順序的 `0x43` 和 `0x23 (2)`。

| 結果為 0 且 N+0x94 = 2 被保留在 N 中，除非已經有一個結果 | `0xe7d570(N, 0, 2, 0)` |
| server+0x208 處的 0x29 正文：N 的槽位、結果（`0x166882c`）、N+0x94 | `0xe7d4c8` |
| 團體戰（setup +0x499 的位 2）：ExitBattleEnd，訊息 0x2b | `0x201602c`（雜湊 `0x2da7b4584624a364`，建構函式 `0x1882dbc`） |
| 否則：AddExpBattleEnd，kind 0 | `0x16e5230`（雜湊 `0x23607a0597b3a656`） |

狀態機只在沒有作業執行時執行，因此在一個回合期間耗盡的時間會在該作業結束後才被看到。團體戰的時間耗盡不傳送 0x25：先是頭目最後一個計時回合，然後是帶正文 `00 00 00 00 02 00` 的 0x2b、0x35 和 0x37（[戰鬥的結束](#the-battles-end)）。頭目獲勝的團體戰以同樣的方式結束：主機或零售主機的寶可夢每次瀕死（不是 NPC 夥伴的）都會從計時器上扣掉 n 秒（`[[module+0x1b0]+8]` 處的 i16，`0x287f3d4`）：n 是時間上限乘以 0.125 再乘以四個玩家的平均等級與頭目等級之比，以 float32 計算並截斷（339 場 oracle 戰鬥中的 339 場；300 秒計時器上為 28 到 61 秒），而擊倒的佇列攜帶 `0x81 (-n)`。

寶可夢已瀕死的槽位會經過其讀取器的子狀態：

| 訊息 | 發給 | 內容 |
|---|---|---|
| 0x21 | 瀕死的槽位，僅頭部 | 在該槽位沒有可戰鬥成員之後；其回答 0x22 啟動讀取器的計時器（reader+0x50），時長按該槽位寶可夢的瀕死次數為 5、10、15、20、25 或 30 秒（`0x1ffe4e8`，表 `0x3c69d1c`） |
| 0x23 | 每個槽位，20608 位元組 | 該計時器耗盡之後（`0x2016bc8`，該槽位一個行動的 kind 0x23 塊，kind 8），由 kind 35 構建（`0x1153350`）：恢復的 HP（`0x288cde8`）、指令 3（對戰者，HP）、被重新派上場的成員（`0x2887044`、`0x11482a0`：指令 0x98） |

一次復活的佇列：帶其滿 HP 的 `0x03 (b, HP)`、`0xcb (0, 1, b)`，然後是以客戶端槽位 c 的戰鬥開始的派上場（`0x3d (c)`、`0x16 (c, 0, 0, n)`，其中 n 是到目前為止的回合數、`0x5e (b, ability)`、`0x61`、`0x6b`、`0x4e`）、`0x98 (c, 0, 0, 1)`、`0x20 (b, 18)` 及其上場時的特性（壓迫感的訊息 162）。其能力變化已消失，而被玩家的重置壓制過的特性又成了它自己的（`0x5e` 攜帶它）。下一回合的 `0x23` 列表以自上一回合以來復活的戰鬥者開頭，按復活順序，然後是那一回閤中尚未列出的行動者。

玩家的寶可夢被擊倒時，在該次命中的 `0x42` 之後，用其自己的 id 執行頭目的擊倒指令（[回合佇列中的一個招式](#a-move-in-the-round-queue)）：`0x49 (V, A, M)`、`0x09 (A, slot)`、`0x37 (V, 1, 1)`、`0xcb (V, 0, V)`、`0x94 (V, 0)`、`0x37 (V, 8, 1)`（其瀕死次數）、`0x5f`、`0x62`、`0x6c`、`0x5d`，按 id 順序對每個仍站立的戰鬥者 `0x41 (b, V)`，對 k 0 到 13 的 `0x33 (V, k)`（僅在場地存在時才有 8）、`0x29 (V)`，對主機或零售主機的寶可夢是計時器的 `0x81 (-n)`，最後是 `0x38 (A)`；沒有 `0x80`。其在該回合的行動被標記為已執行，該次命中像頭目的擊倒一樣抽取 `chance(0)`，降低能力變化類的追加效果不抽取，而畏縮或混亂類的追加效果以及接觸特性仍會抽取。持有氣球的玩家會在該次命中的 `0x42` 之後、這些指令之前使其爆開（訊息 138，`0x1e (T, 15)`、`0x26 (T, 0)`、`0x4f (T, 0)`、`0x62 (T)`）。

當頭目的護盾以 value 1 結束時，其記錄把五個按槽位的計數器（記錄 `+0x7c` 處的 u16）設為 -1（`0x15661e0` 事件 2）。在每個回合開始時（`0x114d390`），瞄準計數器為負的槽位的頭目招式會隨頭目的其他行動一起被丟棄，計數器重置（事件 6），並在回合開始的 `0x51` 執行之後入隊 `0x85 (6, slot)`：每個玩家的下一回合都得不到回應（oracle 語料中 271 個這樣的回合）。

### 伺服器的流程

在零售主機上，這些步驟是作業：Wild::Setup、ServerRequest（`0x138d178`，發給一個槽位的訊息 5）、ServerCommand（`0x16e4f10`，把一個已投遞的請求塊作為回合）、RaidAction 和戰鬥的結束。Wild::Setup（`0x2a1f54c`，跳轉表 `0x3c61c1e`）傳送訊息 1，等待每個回答，傳送 0x11，等待，清除每個槽位傳送的內容（`0xe0f5f8`），只在啟動標誌 [[o+0x40]+0x28] 為 1 時傳送訊息 3（只有 `0x2840fac` 會設定它；團體戰讓它保持 0），並啟動戰鬥計時器。團體戰的 setup +0x30 是 kind 0。每幀狀態機（`0xf6d538`）步進五個按槽位的讀取器（`0xf6df44`）和頭目的列表：

| 讀取器狀態 | 條件 | 然後 |
|---|---|---|
| 0 | 該槽位的已傳送條目中不包含 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d 中的任何一個 | 為該槽位發一個 ServerRequest（`0xf70078`），狀態 1 |
| 0 | 否則 | 擦除每個已回答的對（`0xf6edf4`） |
| 1 | 該槽位收到了 5 且傳送了 6 | 一個帶該槽位指令的塊（`0xf6e6a8`、`0xf702ec`）作為 ServerCommand 投遞，狀態 2 |
| 2 | 該槽位回答了一個回合（0x15 / 0x16） | 狀態 0 |

伺服器按槽位保留它傳送的訊息和該槽位傳送的訊息，按到達順序；`0xf6edf4` 擦除某型別的第一個已傳送訊息和第一個已收到的回答，每次呼叫一對，而狀態 0 每幀對每一對 (0x15, 0x16)、(0x23, 0x24)、(0x11, 0x12)、(0x13, 0x14)、(0x17, 0x18)、(0x19, 0x1a)、(0x1b, 0x1c)、(0x1d, 0x1e)、(0x25, 0x26) 和 (0x1f, 0x20) 各呼叫它一次。因此，在回合發出的同時讀取器被停住的槽位（一個瀕死的槽位）會在再次被詢問之前每幀擦除一個回合的積壓：復活後 12 回合要 12 幀。Wild::Setup 的結束會清除兩個列表。

頭目的槽位（用表 `0x3c6a45a` 對照 N+0x95）只擦除已回答的對。其他讀取器路徑：傳送了 4 的槽位會得到一個 kind 0x13 的塊；在團體戰中 N 的一側，reader+9 處的子狀態處理瀕死的槽位（[戰鬥計時器耗盡](#the-battle-timer-running-out)）；0xd/0xe 投遞 kind 0x1b；7/8、0xb/0xc、0xf/0x10 和收到的 0xa 分別投遞 kind 0x17、0x19、0x15 和 0x17。

每幀的 run 步驟 `0x2d383b8(N)` 步進伺服器的入站鏈路（`0xe0f040`、`0xe0fd68`、`0xe0f854` 作用於 [N+0xb0]），然後步進作業圖 `0xfc363c(G, 1)`，G = [N+0xa8]（vtable `0x44ee6e8`）：

| G+ | 物件 | |
|---|---|---|
| 0x98 | 請求工廠 | 已投遞的請求是一個 0x50 位元組的物件：作業型別雜湊、計數器、載荷 |
| 0xa0 | 排程器（vtable `0x44eea68`） | +0x40..+0x50 處的已投遞請求，由 `0x1479b10` 追加 |
| 0xa8 | 來源（vtable `0x44947d8`） | vf 0x68 `0x14641ec` 選擇要啟動的請求 |
| 0xb0 | 每幀狀態機（vtable `0x4493530`） | vf 0x68 `0xf6d538` |
| 0xb8 | 執行器（vtable `0x4493688`） | 一個作業棧 |

`0xfc363c(G, 1)` 在執行器持有作業時只執行執行器。否則它執行狀態機，然後執行來源的選擇：在團體戰中第一個已投遞的團體戰行動（雜湊 `0x5c307d44ea569b63`），在模組啟動第一個 Wild::Setup（雜湊 `0x2e9e7a3009002c36`）之前，否則第一個已投遞的。執行器（`0xfc38dc`）執行棧頂作業的 vf 0x68：0 結束該幀；2 彈出它，壓入其續體 [job+0x70] 並結束該幀；其他任何值都會再次執行它。每幀啟動一個已投遞的請求，而團體戰行動會插隊。

狀態機的定時檢查把其頭目列表的副本作為訊息 0x51 送入伺服器自己的入站鏈路（`0xe0f440(server, N+0x95)`）；下一幀 `0x2016290` 把它的 0x24 位元組複製到狀態機的頭目列表，後者投遞團體戰行動。沒有這一步，定時行動永遠不會觸發。狀態機的 vf 0x70 `0x20162bc` 還接受 `0x0ab4bce035f3012b`（投遞到 `0x201665c`）和 `0xde3856ecc4fe200c`（一個 kind-14 行動，作為 ServerCommand 投遞）。

在沒有作業的幀上，狀態機（`0xf6d538`）先讀取戰鬥計時器，剩餘時間為 0 或更少時投遞時間耗盡；然後，在已武裝時（`+0x118`，0x51 發出時清除，團體戰行動被投遞時再次置位），如果其頭目列表持有行動就結束該幀，否則在副本上評估時間觸發，有觸發時傳送 0x51 並結束該幀；持有行動的頭目列表會作為團體戰行動投遞，幀隨即結束；只有到這時才步進讀取器。一個頭目列表持有護盾的回合會先投遞團體戰行動本身（`0x16e5ad0`）；團體戰行動會插到已投遞佇列的前面。在語料 794 場 oracle 戰鬥中，這樣構建的伺服器在它拒絕的第一個回合之前，以相同的伺服器時間傳送 oracle 傳送的每條訊息（31,581 條訊息；25 場經過一次瀕死，8 場經過一次復活，5 場經過護盾的 0x47）。

狀態機的時鐘是 19.2 MHz 的系統滴答：每幀把它推進到該幀的時間（若更晚），每次讀取 `nn::os::GetSystemTick` 都會加 256 個滴答。因此，在同一時間再次執行的幀（主機會在上一批幀結束的時間啟動每一批幀）讀到的時間會稍有延後。整秒正好落在某幀時間上的計時器，只有當它的檢查在該幀時間內讀取時鐘不早於其啟動時讀取的時刻，才會在該幀結束；否則它會晚一幀結束。

讀取順序如下：

| 時機 | 讀取 | 程式碼 |
|---|---|---|
| 建立計時器 | 兩次，第二次將其暫停 | `0xf70a58` |
| 恢復已暫停的計時器 | 一次，其 start | `0xe63ac4` |
| Wild::Setup 結束，即每個槽位都回答 0x11 之後的那一幀 | 一次，戰鬥計時器的 start | `0xe63ac4` |
| 每個狀態機幀，戰鬥計時器執行時 | 一次，用於時間耗盡 | `0xf6d538` 中的 `0xf91070` |
| 時間觸發，以空列表武裝 | 護盾未升起且低時間行動尚未執行時一次；低時間行動尚未執行時一次；每個尚未觸發的基於時間的額外行動各一次 | `0xf6f87c`、`0xf6dd84`、`0xf6fa5c` |
| 每個狀態機幀 | 按槽位順序為每個等待復活計時器的瀕死槽位各一次 | `0xf71020` |

瀕死槽位的計時器在其 0x22 被擦除時建立並恢復，因此其 start 是這些讀取中的第三次。

`Server` 是這一流程的 Python 移植，按狀態機的時鐘每秒執行 30 幀；任何幀都不能跳過，因為等待瀕死槽位計時器的讀取器每幀都會推動狀態機。主機把它伺服器讀取的每條訊息按一個佇列轉發給訪客，因此該佇列的順序就是伺服器讀取它們的順序。從模擬主機的引導和轉發的訊息出發，該移植逐位元組傳送零售主機全部 24 幀（未寫入的位元組除外），而在 unicorn 下，遊戲自身程式碼對這 216 個移植函式的執行留下相同的頁，包括時間耗盡和頭目獲勝。

### 復現一個回合

在 unicorn 下，從一個停在構建器 `0x113c8a0` 處、型別為 0x15 的模擬零售主機出發，一個回合可以精確重放：記憶體通過 GDB stub 一次一頁地取回，`tpidrro_el0` 背後的執行緒區域性頁是一個替身，其 `+0x1f8` 命名一個假執行緒，SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d 和 0x1e 返回 0。一個回合會觸及 159 到 353 頁。

伺服器的 Python 移植為每個遊戲函式執行一個函式，以其相對 main 的偏移為鍵：kind 1、5、17 和 21 的構建器、回合驅動 `0x113e3d0`（傷害 `0xf7c344`、瀕死 `0x1144df8`、回合結束 `0x114a094`）、戰鬥開始 `0x113dca8`、構建步驟 `0x2891748`、`0x2892ac0`、`0x2d381a4` 和 `0x2892dd4`，以及 SDK 的 `nn::mem::StandardAllocator` 及其執行緒快取和 TinyMT32 金鑰（`0x525f448`）。在 86 臺停住的零售主機上，它留下的正文和記憶體頁與遊戲相同。當位元組 0 和位元組 1 都未置位時，`__cxa_guard_acquire`（`0x53c49a0`）返回 1 並把 guard 的位元組 1 設為 2。

資料表是由函式區域性靜態變數持有的 romfs 檔案：

| 靜態變數 | 檔案 | 物件 |
|---|---|---|
| `0x47420b8` | `avalon/data/personal_array.bin` | 對映，鍵為物種 * 10000 + 形態（u32） |
| `0x47420d8` | `avalon/data/growTable.bin` | FlatBuffers 根，經由 [T+0x30] 的 vf +0x70 |
| `0x4742568` | `avalon/data/waza_array.bin` | 對映，鍵為招式（u16） |
| `0x4742548` | `avalon/data/tokusei_array.bin` | 對映，鍵為特性（u16） |
| `0x4734e50` | `world/data/battle/battle_item_conversion/battle_item_conversion_array.bin` | 陣列 |

對映是 +0x68 處的 libc++ `unordered_map`：桶 +0x68、桶數 +0x70（不小於記錄數的下一個素數）、首節點 +0x98、大小 +0xc0、負載因子 +0xc8（1.0）、預設記錄 +0xd0。節點是 {next, hash = key, key, 記錄指標}；+0x30 是檔案資源（FNV 雜湊 +0x48，路徑 +0x50）。道具陣列（由 `0x1821674` 填充）從 +0x28 起持有 0x18 位元組的條目：u32 索引、u32 0、u64 雜湊（main `0x3c61260 + 8 * index`）、u16 道具、6 個零位元組。這些檔案出自 `arc/data.trpfs`（`tools/switch/trpfs_read.py`；Oodle 經由遊戲的 `OodleLZ_Decompress` `0xcc8750`）。資料系統的初始化 `0x1641afc` 執行 `0x1643a48`（personal、growth）、`0x1641cf0`（招式）和 `0x1641d78`（特性）；每張表被重置進其靜態變數（`0x1643e68`），並通過 `0xf0ba9c` 追加到 `0x4763a18` 處的登錄檔。在預留記錄數之後按檔案順序插入一個檔案的記錄，就得到零售主機的節點列表。

### 實測的伺服器流程

以下適用於在 [為戰鬥提供服務](#serving-the-battle) 的指令碼化零售主機之上執行的 oracle 伺服器，而按這些規則構建的伺服器在玩家獲勝的九場完整戰鬥中，向零售主機發送相同的幀（包括通知）：

| 規則 | 實測 |
|---|---|
| 頭部計數器 | `step` 每次傳送、廣播或一個請求增加一；`round` 對訊息 1 為 0，從 0x11 起為 1，並隨每個 0x15 以及 0x25 增加 |
| 一幀一個作業 | 訊息 1 啟動 Wild::Setup，它在每個槽位都回答了 1 之後傳送 0x11，並在每個槽位都回答了 0x11 之後一幀結束 |
| 請求 | 在沒有作業執行的幀上，向沒有未回答內容的槽位投遞一個請求（5）；請求每幀啟動一個，按槽位順序 0、2、3、4 |
| 一個指令 | 該槽位的 6 被作為作業投遞，向每個槽位傳送該回合（0x15） |
| 再次被詢問 | 已經回答了發給它的每個回合的槽位會在下一幀再次被詢問 |
| 獲勝 | 獲勝的回合之後，在下一幀是一個空回合 0x25（20576 個零位元組），然後是帶正文 `00 00 01 00 01 00` 的 0x29、0x49、0x35 和 0x37，每個都在每個槽位回答了前一個之後傳送一次：在最後一個回答對 0x25 和 0x49 之後 2 幀，對其他訊息則是同一幀 |
| 時間耗盡 | 帶正文 `00 00 00 00 02 00` 的 0x2b（233 場戰鬥中的 63 場） |
| 通知 0x46 | 每個有作業啟動的幀各一個，或者在沒有作業執行時讀取了某回合的回答（0x16）的幀各一個 |

### 為戰鬥提供服務

`bin/sv_host.py --raid-serve [NAME]` 在整個戰鬥期間保持網路，並用 `pokeldn.sv.raid_battle.RaidBattle` 從主機的站點為它提供服務：這是外掛的戰鬥伺服器（[戰鬥伺服器](plugins.md#a-battle-server)），由引導和兩個 NPC 夥伴構建，再加上零售主機為自己保留的站點。pokeldn 不附帶戰鬥伺服器；如果沒有新增它的外掛，該標誌會被拒絕。所服務的會話讓我們的寶可夢、頭目、一臺位於站點索引 1 的零售主機（引導參與者 1，槽位 2）和兩個 NPC 夥伴就座，因此該標誌只接受一臺零售主機。

| 部分 | 主機發送什麼 |
|---|---|
| 伺服器發給零售主機的訊息 | 定址為 (0x2713, 1, 2) 的幀 |
| 槽位 0、1、3 和 4 | 每個奇數步驟在 0.05 秒後用型別 + 1 回答；對槽位 0、3 和 4 的請求（5）帶一個型別 6 的指令，其中該槽位的寶可夢對頭目使用其第一個招式，頭目對該寶可夢使用其第一個招式（[行動](#actions)） |
| 伺服器讀取的每條訊息，包括零售主機自己的 | 轉發給零售主機，定址為 (0x2713, 3, 5) |
| 每個推動了戰鬥的伺服器幀 | 在該幀的訊息之後，從槽位 0 發一個通知 0x46（步驟 0，4 位元組的零正文），定址為 (0x2713, 3, 5) |

每個幀都在 0x80 埠 0 上作為一個 deflate 壓縮的可靠訊息發出（標誌 `COMPLETE_ZLIB`）；見過的最大者壓縮後為 903 位元組。復現 Scarlet 4.0.0 傳送內容的伺服器會把零售主機發送的六條戰鬥開始訊息（`raid.HANDOFF`）作為其前六幀（其棧填充的頭部位元組除外）按相同順序傳送，因此 `--raid-serve` 會用它們代替 `HANDOFF` 來發送。

零售主機一回答 0x37，或 0x37 發出後 5 秒，主機就停止提供服務並關閉網路。回答 0x37 本身會在伺服器上重新執行時間耗盡（[伺服器的流程](#the-servers-flow)），因此本地站點不回答它。失敗（伺服器丟擲異常或無法構建）會停止服務，並像不帶該標誌的主機那樣移交網路；零售主機隨後會故障轉移並打自己的戰鬥（[哪個站點執行伺服器](#which-station-runs-the-server)）。

## 加入

`bin/sv_join.py --raid-pokemon FILE` 加入一個場景 7 的網路並作為訪客參與。零售主機的玩家開啟一個結晶，選擇以團體挑戰，然後等待；應用的太晶團體戰（加入）工具會執行它。`pokeldn.sv.raid.RaidGuest` 和加入者按順序做這些事：

| 步驟 | 訪客 |
|---|---|
| Net | 在訊息標誌 0x11 下回答 0x11 和 0x50 |
| Session | 不回答隨加入響應而來的站點列表，至少 1 秒後再確認其重傳，然後確認之後的每個列表，併發送位元組 9 置位的時鐘請求 |
| 通道 | 把主機的六鍵表拆成四個和團體戰的兩個，宣佈四個，0.24 秒後加入埠 2，並在該表之後 0.79 秒宣佈團體戰的鍵；把其 0x7C 確認延遲 0.25 秒 |
| 身份 | 在就座後 0.44 秒傳送標準記錄集（`pokeldn.sv.reference`），記錄 1 使用訓練家名 |
| 大廳 | 在此之後 0.27 秒傳送狀態 0x18 及其寶可夢；2 秒後傳送狀態 0x01 |
| 開始 | 主機的狀態 0x0c 到達後傳送狀態 0x0d；把 0x0d 作為準備訊號傳送的訪客被確認，但從未顯示為已準備 |
| 戰鬥 | 確認主機的 0x3480 0x93，每 0.5 秒傳送 Session 型別 3 的離開，直到型別 4 為止（至多四次傳送）並離開網路；戰鬥中的一臺零售 Scarlet 對四次都沒有回答 |
