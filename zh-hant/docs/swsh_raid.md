# 極巨團體戰

本地極巨團體戰是劍／盾在 LDN 場景 60006 上最多四個站點的會話。主機在巢穴處用「邀請他人」開設，訪客在自己的 Y 通訊列表裡找到它，對著主機的名字用「開始對戰」加入。大廳執行在可靠廣播協議 0x80 上，戰鬥在 0x7C 上。`bin/swsh_connect.py --preset raid` 在一臺主機的大廳裡佔一個訪客席位，用選定的寶可夢（`--offer-file`）和招式（`--raid-move`）準備並戰鬥；應用的「極巨團體戰（加入）」工具執行它。

## 網路

| 欄位 | 值 |
|---|---|
| LDN 場景 id | 60006（曠野地帶為 65535） |
| 參與者 | 開設時為 4 箇中的 1 個 |
| 廣播資料位元組 `0x97` | `0x11` |
| Pia 會話上限 | 4（`0x0110e5e0`，從巢穴大廳 `0x01031c74` 呼叫） |
| 廣播 `0xb0` 與 `0xd4` | 頭目和巢穴記錄（[巢穴記錄](#the-den-record)） |

巢穴大廳的程式碼位於 `0x0102aba4..0x010370cc`（`View_NestHole`、`StateGuestReady`、`StateHostReady`）。訪客的 Y 通訊列表會略過廣播攜帶其自身裝置 id 和賬號 uid 的團體戰。

## 大廳訊息

每條大廳訊息的 id 都是 2000，`net_contents.nesthole.protocol_buffers.NestholeAsyncDataHolder`（`main` 中的描述符 `0x1bfde43`、`0x20677b0`）。每個欄位都是一個 holder，帶一個 `bytes` 欄位 1。

| 欄位 | 名稱 | 大小 | 內容 |
|---|---|---|---|
| 1 | NestholeTimeLimit | 4 | u32 剩餘秒數；主機每秒發三次 |
| 2 | NestholePlayerInfo | 40 | 8 個零位元組、u32（零售版劍 0x11，模擬的盾 0x12）、13 個字元的 UTF-16 名字、`00 03` |
| 3 | NestholeBattleReady | 16 | 玩家按下準備後第 8 位元組為 1；戰鬥開始後第 12 位元組為 1 |
| 4 | NestholeSelectPokemon | 352 | 8 個零位元組，然後是選定寶可夢的加密隊伍 PK8（0x158） |
| 5 | NestholeBattleStart | 32 | 參與者的 Pia 常量 id，共四個 u64，主機的排第一，未用的槽為零 |
| 6 | NestholeBossPokemon | 364 | 19 個零位元組和 `ff`，然後是頭目的加密隊伍 PK8 |
| 7 | NestholeRewards | 120 | 十五對 u32：道具 id、數量；未用的對為零 |
| 8 | NestholeBattleSeed | 16 | u64 種子，然後是 `00 ff ff ff 1e 00 03 00` |

PlayerInfo 以 4 KB 視窗的 zlib（頭部 `48 4b`）在可靠標誌 0x10 下發出；其餘明文發出。`pokeldn/swsh/raid.py` 構建每個欄位。頭目記錄完整攜帶頭目；BattleSeed 餵給什麼尚未讀出（把巢穴的團體戰生成器用在它上面，既得不到頭目的加密常量，也得不到它的 PID）。

## 訪客的序列

快照在 0x84 上交換（主機的先發）；PlayerInfo、BattleReady 和 SelectPokemon 在 0x80 埠 0 上；準備時發第 8 位元組置位的 BattleReady。所有玩家都準備好後，主機依次發 BattleStart、SelectPokemon、BossPokemon、Rewards、BattleSeed 和第 8、12 位元組都置位的 BattleReady；訪客用自己的 SelectPokemon 和同樣的 BattleReady 應答，戰鬥在 0x7C 上開始（埠 0 上 ping 80，埠 1 上框架 40000，之後每回合 10000 和 20000）。在第 8 位元組置位的 BattleReady 之後停下的訪客，會讓零售版劍主機停在 "Connexion en cours"，最終報錯 2-ALZAA-0016。

## 戰鬥

主機跑戰鬥；訪客在 0x7C 上應答（`pokeldn/swsh/raid_battle.py`）。從網狀網加入起，訪客執行 SyncClockProtocol 0x1C（每秒一次請求），併發送一次 ClockProtocol 0x77 請求（16 個 `00` 然後 `00 6f`），兩者都發往目的地點陣圖 1。

| 埠 | 訊息 | 訪客 |
|---|---|---|
| 0 | sync 80：ping、pingReply、pingSynced | 用 ping 和 pingReply 應答 ping，用 pingSynced 應答 pingSynced |
| 1 | 40000，內容 0 的框架：欄位 2 基準（10000 或 20000，0 時預設）、3 站點常量 id、4 時鐘、5 主體 | 在 pingSynced 之後發三對 base-10000 / base-20000（主體 `00000000`、`000018fc`），然後用自己的站點 id 映象主機的每個 base-20000 主體 |
| 0 | 10000，欄位 3 {1 站點、2 槽、3 版本} | 在主機列出自己的座位後發一次（base 0，16 位元組主體：常量 id、槽、版本位元組 0x6e） |
| 0 | 10000，欄位 1 為空 | 在主機的 base-8 訊息（24 位元組主體，戰鬥的種子）之後發 |
| 0 | 20000，欄位 1 {1 傳送者、2 槽、3 計數、4 資料} | 應答主機的每條命令 |
| 0 | 20000，欄位 3 {1 狀態、2 槽} | 在自己的行動之前發 {1: 2, 2: 槽} |

主機命令的資料以四個 u16 開頭：序號、型別、長度、一個標籤。訪客用相同的序號、型別和標籤、長度 4 和四個零位元組應答，例外是型別 0x02（狀態訊息，然後是它的行動：序號、0x02、0x58、標籤、88 位元組）和型別 0x21（結束：傳送者 1，資料 `0000 1e00 0000 2f00`）。見過的主機型別：0x01、0x0d、0x07、0x0e、0x02、0x10、0x09（該回合的日誌，zlib）、0x04、0x11、0x0a、0x21。

### 哪個站點做伺服器

伺服器是 ServerVersion 記錄在每臺主機各自維護的表裡勝出的那個站點。ServerVersion 是 `btl.net.protocol_buffers.BtlDataHolder`（id 10000）的欄位 3：站點 id u64、客戶端 id u32、版本 u32（版本 `0x6e`）。八個 {站點、客戶端 id、版本、有效} 槽位於戰鬥網路物件 `+0x190 + 16 * i`；`0x8b4030` 取版本最高的第一個有效槽，`0x8b1990`（IsServer）把它的客戶端 id 與主機自己的比較。一臺主機的客戶端 id 是它在 BattleStart 中的位置（`0x1025120`）。收集方站點把各槽作為 40000 框架物件 0 到 7 釋出。

### 行動

88 位元組的行動是十一個 8 位元組條目。條目 2 作為小端 u24 是 `move id << 13 | target << 8 | 0xc1`。

| 招式 | 條目 2 | 目標 |
|---|---|---|
| 拍擊（1） | `c1 28 00` | 8 |
| 綁緊（20） | `c1 88 02` | 8 |
| 叫聲（45） | `c1 a2 05` | 2 |
| 水槍（55） | `c1 e8 06` | 8 |

叫聲打每個對手，目標碼為 2；單體招式的目標碼為 8。訪客無法行動的回合把條目 2 發成全零。`raid_battle.action(move, target)` 構建它；`--raid-move N` 選擇招式槽。0x7C 的確認攜帶 32 個槽；只有槽 0 追蹤訪客的流，所以以各槽最大值為門檻的重發永遠不會重發。

## 巢穴記錄

巢穴主機的廣播描述它的團體戰；訪客的 Y 通訊條目構建器（`0x00fa1560`）讀取它。

| 偏移 | 內容 |
|---|---|
| `0x5F` 第 1 位 | 主機的版本：清零為劍，置位為盾 |
| `0xAF` | 活動種類：0 星為 `0x11`，以上為 `0x13 + 2 (rank - 1)`；`0xFF` 從不列出 |
| `0xB0` | 展示的頭目：u16 物種（第 0 到 9 位）和形態（10 到 15 位）、一個第 4、5 位為 1 普通 2 超極巨化的位元組，以及 u32 加密常量 |
| `0xD4` | 巢穴記錄，同樣的八位元組佈局 |
| `0xDC` | 高半位元組：星級，0 到 4 |
| `0xDD` | 第 3 到 5 位：巢穴種類，普通巢穴為 0 |
| `0xDE`、`0xE0` | u16 遭遇表，在主機版本的表裡計數，以及 u16 槽 |
| `0xE6` 到 `0xED` | `bin/archive/field/resident/data_table.gfpak` 第 8、6、7、9 號檔案的 CRC16 |

`0xD4` 處物種非零時，訪客只有在自己的表 CRC 匹配、巢穴種類為 0、且主機版本的 `0xDE` 表 `0xE0` 槽持有該物種、形態和超極巨化標誌時才列出該團體戰（`0x00ea5160`）。物種為 0 時跳過這些檢查。`0x02510b2c` 處的位元組為 1 或 2 且主機不是好友時，星級不得超過訪客自己的星級（由徽章數得出）。`0xB0` 處的記錄只做範圍檢查。訪客會丟棄裝置 id 和賬號 uid（`0x1F` 到 `0x3E`）都與自己相同的站點（`0x0111b160`）。`pokeldn/swsh/data/nest_slots.json` 儲存 1.3.2 的槽（`scripts/gen_swsh_nest_data.py`）；`raid.den_advert` 把巢穴記錄指向持有頭目的槽，或把它清零。

### 頭目記錄

訪客在發出自己已開始的 BattleReady 之前檢查 BossPokemon 和 Rewards（`0x01030d14`）；檢查失敗就以 2-ALZAA-0016 離開。

| 檢查 | 程式碼 | 通過條件 |
|---|---|---|
| 頭目 | `0x01032270` | 物種、形態和隊伍 `+0x156`（1 普通，2 超極巨化）與巢穴記錄指名的條目相同：種類 0 用廣播版本的 `0xDE` 基表、槽 `0xE0`；種類 1 到 3 用訪客自己存檔中的活動遭遇、槽 `0xE0`；種類 4 用它存檔中的極巨結晶遭遇 |
| 獎勵 | `0x01032570` | 每對帶道具和數量，要麼是該槽獎勵表在廣播星級下恰好該數量的加成行，要麼是它掉落表中在該星級有機率的道具（數量不限） |

等級、招式、個體值、PID、特性、異色和訓練家欄位都不比較。全零的巢穴記錄指種類 0、表 0、槽 0（巴爾郎）。在零售版劍訪客上觀察到：帶訓練家資料的頭目記錄、隊伍極巨化型別為 0，或對任何基表巢穴都不持有的頭目（夢幻、某活動的超極巨化顫弦蠑螈）使用全零巢穴記錄，即使團體戰被列出也會以 2-ALZAA-0016 離開；只改物種的巢穴頭目記錄，以及 `raid.boss_record` 構建的頭目，都被接受。基表巢穴不持有傳說或幻之寶可夢，所以託管的頭目必須是 `nest_slots.json` 列出的物種、形態和超極巨化狀態；只有另一版本持有該頭目時，`raid.den_advert` 切換廣播的版本，並把活動頭目顯示成持有該物種的基表巢穴槽。`bin/swsh_host.py` 和應用的主持工具都拒絕基表巢穴不持有的頭目。

帶 `--raid-boss-as-is` 時，`raid.boss_record` 保留巢穴頭目的 TID 28222 和 SID 36500。異色是 PID 對照它們算出的，所以 `raid.same_shine` 會移動 PID 的高半，以保住頭目在自身檔案訓練家下的方形、星形或普通閃光；為玩家做成異色卻按原 PID 傳送的頭目，被畫成了普通。`raid.reward_choices` 列出該槽在某星級下允許什麼；`raid.den_rewards` 構建該槽自己的行。

巢穴頭目的隊伍 HP 種族值和當前 HP 是普通 HP 種族值乘以 `(150 + 5 * 極巨化等級) / 100` 後向下取整；其他能力值是普通值。極巨化等級在 `+0x90`，特性槽位在 `+0x16` 的第 0 到 2 位，經驗值是該等級所需的最小值。

### 捕獲後仍然合法的頭目

巢穴主機的 BossPokemon 是某顆種子的團體戰擲骰 [PKHeX RaidRNG]。模擬的盾主機發出的兩個巢穴頭目都是一次擲骰：種子 `0xF41D53DF6C576FFD` 的豆豆鴿（`raid_boss_template.ek8`），種子 `0xBA7E50A969044287` 的咕咕，各自靠搜尋加密常量留空的 32 個種子位找到（`tests/test_swsh_raid.py`）。以該種子和 `0x82A2B175229D6A5B` 播種的 xoroshiro128+ 的抽取，依序為：

| 抽取 | 欄位 |
|---|---|
| u32 | 加密常量 |
| u32 | 記錄的 TID（低半）和 SID（高半） |
| u32 | PID；其閃光對照該 TID 和 SID 判定 |
| rand(6)，直到抽到尚無個體值的項 | 巢穴的每一項滿值個體值 |
| rand(32) | 其餘每項個體值，按 HP、攻擊、防禦、特攻、特防、速度的順序 |
| rand(3) 或 rand(2) | 特性槽，限於巢穴會抽的那種 |
| rand(253) + 1 < 性別比例 | 雌性，限於有雙性的物種 |
| rand(25) | 性格；顫弦蠑螈按其形態的表抽 |
| rand(129) + rand(128)，兩次 | 先身高，再體重 |

同一顆種子上的第二個生成器給出等級，即該星級的最小值（15 + 10 rank）加 rand(6)，然後是極巨化等級，rank + 1 加 rand(2)，4 星時為 6 加 rand(3) [PKHeX EncounterStatic8N]。當該物種、形態和超極巨化狀態的某個巢穴遭遇的某顆種子給出上述全部，且其 PID 把擲骰的閃光帶給它的訓練家時，PKHeX 接受捕獲來的巢穴寶可夢；在共用巢穴（地點 162）相遇時，任何巢穴表的遭遇都算匹配。檔案自帶的頭目作為捕獲會通不過該檢查："PID+ correlation does not match"，或沒有巢穴會在該等級給出的遭遇。

訪客的捕獲保留頭目記錄。模擬的盾訪客捕獲了從種子 `0xF3D291D263CC680F` 託管的毛辮羊：捕獲記錄帶擲骰的加密常量、PID、個體值、性格、性別、體型、特性槽和極巨化等級，頭目的招式和 17 級，並取用捕獲者的訓練家、相遇地點 162、相遇等級 17、一顆精靈球和日期。同樣方式捕獲的異色毛辮羊保留了擲骰的各項值，只換了 PID 的高半，使捕獲者 TID 和 SID 下的閃光為 1（擲骰在原記錄自己的 TID／SID 下是 5）；主機把它畫成了異色。PKHeX 兩者都接受（`tests/test_pokemon_service.py`）。

`bin/swsh_host.py --raid-boss` 傳送一次擲骰：PKHeX 輔助的 `raid_boss` 按頭目物種、形態和超極巨化狀態，在其等級所指的星級（或巢穴給出的最近星級）上取 PKHeX 的巢穴遭遇，並取一顆擲骰結果帶檔案閃光的種子，優先匹配其性格和性別。記錄保留檔案的招式。`--raid-boss-as-is` 傳送檔案自己的等級、個體值、性格、體型和 PID。活動頭目（`raid_event.boss_pk8`）是對隨機種子的一次擲骰，套用活動表的滿值個體值、特性、性別、性格和閃光規則，等級取表裡的。

## 主持

`bin/swsh_host.py --raid-boss PK8 --raid-console-serves` 託管一個巢穴大廳，主機從 Y 通訊列表加入（`pokeldn/swsh/raid_host.py`）。廣播和快照來自一臺模擬的盾巢穴主機，使用全新的站點配置、板子的名字且無賬號 id（`pokeldn/swsh/data/raid_advert.bin`、`raid_snapshot.bin`；`--advert` 和 `--snapshot` 替換它們）。`--raid-boss` 通過 `raid.boss_record` 接受任何 PK8。主機的快照先於訪客發出。`--raid-reward ITEM:COUNT` 填充 Rewards，`--raid-seed` 填充 BattleSeed；主機拒絕廣播的巢穴槽在其星級下不給出的行，並列印該槽給什麼。

應用的「極巨團體戰（主持）」工具用這些開關執行，帶一個頭目（或基表巢穴持有的曠野地帶活動頭目，`raid_event.hostable`）、玩家的寶可夢和最多 15 行獎勵；不給行時，主機給出巢穴槽自己的獎勵。它的獎勵編輯器只提供頭目所在廣播巢穴槽的道具（`raid.boss_den`、`pokeldn.app.raid_rewards.swsh_den`），並修正加成道具的數量。

帶 `--raid-console-serves` 時，加入的那臺主機做伺服器，我方主機作為客戶端 1 應答（`raid_battle.Master`）：

| 步驟 | 主機 |
|---|---|
| BattleStart | 把主機列在第一位，所以它的客戶端 id 是 0 |
| 0x7C 埠 0 | 發 ping；應答主機的 ping 和 pingSynced |
| 框架物件 | 釋出物件 0 = 主機的 ServerVersion 記錄，物件 1 = 自己的 |
| 0x7C 埠 0 | 發自己的 ServerVersion（客戶端 id 1） |
| base 20000 | 釋出計數器和自己的主體，0000 / 00000100，然後 0100 / 01000100、01000200、0200 / 02000200，每次都在主機映象上一主體之後 |
| 物件 8 | 由主機發布（24 位元組，一顆種子）；主機回 EmptyCommand（10000 欄位 1） |
| 戰鬥命令 | 按訪客的方式應答，行動指名主機寶可夢的第一個招式 |

一臺零售版劍這樣打完了整場團體戰、贏下它並收到主機的 Rewards，然後髮網狀網離開請求。

我們自己的記錄以版本 `0x6d` 發出，比主機的 `0x6e` 低一，所以無論各自落在哪個槽，主機的記錄都是唯一最高版本。在 LAN 模式下，零售版劍把會話主機的記錄歸到槽 0（主機的 Pia 站點索引），所以版本相同時它選了我方主機，把我方記錄釋出為物件 0，發出 EmptyCommand，然後黑屏等待一個從未啟動的伺服器；用 `0x6d` 時它做了伺服器，戰鬥正常載入。

### 多臺主機

最多三臺主機共用一個託管大廳（`raid_host.RaidParty`）。每臺加入的主機都準備好後，我方主機才開始戰鬥；BattleStart 按加入順序列出各主機，然後是我方主機。第一臺主機做伺服器。我方主機把框架物件 k 釋出為主機 k 的 ServerVersion 記錄，自己的放在最後，並在每臺主機映象其主體後推進 base-20000 的屏障。

第二臺主機需要從 Pia 主機得到：投遞給它的會話更新（在迴環上每個站點得到自己的一份）；網狀網加入響應的第 8 位元組，即活躍站點上限，要高於已入座的站點數（否則結果為 1、錯誤 2618-0502）；以及在傳送者流的埠（主機 0，第一個加入者 1，第二個 2）上的確認，因為未被確認的流會無休止重複。

訪客之間直接相連：站點連線請求、0x84 上彼此的快照，以及 0x80 上同時定址主機和另一訪客的大廳訊息。

## 活動團體戰

曠野地帶活動是一次 BCAT 下發，包含巢穴遭遇表和獎勵表，每次下發一個編號索引。Project Pokemon 的 EventsGallery 把每個都放在 `Released/Gen 8/SwSh/Wild Area Events/Index NNN/` 下。`pokeldn/swsh/raid_event.py` 讀取一個；`pokeldn.app.events_gallery` 在遊戲 `swsh` 名下儲存副本。

| 檔案 | 內容 |
|---|---|
| `normal_encount` | 曠野地帶各巢穴的活動遭遇 |
| `normal_encount_rigel1`、`normal_encount_rigel2` | 鎧之孤島和王冠雪原的（在 Index 080 和 117 中，010 裡沒有） |
| `drop_rewards`、`bonus_rewards` | 該次下發的獎勵表 |
| `dai_encount` | 極巨結晶遭遇 [pkNX `NestHoleCrystalEncounterArchive`]；未讀出 |

每個檔案都以 0x20 位元組的頭部開頭：偏移 0 是 u8 的 BCAT 索引，4 處是 `ff ff ff ff`，8 處是 u32 `0x20`，`0x10` 處是 u32 檔案大小減 4。FlatBuffer 從 `0x20` 到末尾四個位元組之前，後者是 CRC [pkNX `GameDumperSWSH.GetDistributionContents`]。

遭遇檔案是一個表向量（欄位 0）：TableID u64、GameVersion u32（1 劍，2 盾）和 Entries（欄位 4）。條目欄位：0 索引；1、2、3 物種、形態、等級；4 極巨化等級；11 特性（0、1、2 為第 1、第 2、隱藏特性；3 為前兩者之一；4 任意）；12 超極巨化；13、14 掉落表和加成表的 id（u64）；15 五個星級機率，單位為百分比（每個版本各星級合計 100）；16 性別（0 抽取，否則性別 + 1）；17 滿值個體值個數；18 異色（0 抽取，1 從不，2 總是）；21 性格（25 抽取）；23 到 26 四個招式；30 盾牌和 31 到 36 兩個額外招式，按 PyNXBot 的 schema。

其他欄位未讀出。Index 010 解碼為曠野地帶活動 #7：3 到 5 星的超極巨化顫弦蠑螈、每星都有的超極巨化小仙奶、劍裡的巨鉗蟹和長毛巨魔、盾裡的以歐路普和布莉姆溫；它的 5 星顫弦蠑螈等於 PKHeX `encounter_sw_dist.pkl` 中索引 10 的記錄。

下發獎勵檔案是一個表向量（欄位 0）：TableID u64 和 Entries（欄位 1），每個條目是 1 到 5 星的五個 u8 值（欄位 0 到 4）和一個 u16 道具（欄位 5）。遊戲自己的表 `data_table.gfpak` 第 7 號（掉落）和第 6 號（加成）持有 TableID，然後是 u32 條目索引、u32 道具和一個五值的 u32 向量（`pokeldn/swsh/data/nest_rewards.json`、`scripts/gen_swsh_nest_data.py`）。遭遇用 id 在兩者中指名它的表，遊戲自己的優先 [pkNX `NestHoleDistributionEncounterTable`]。加成值是數量，掉落值是百分比機率。1 星巢穴的 Rewards（`raid.DEN_REWARDS`）以加成表 `0xf966212316b78eb6` 在 1 星、按其數量的行開頭（經驗糖果 XS x5、S x1、極巨糖果 x1），然後兩個道具各一。`raid_event.rewards` 先構建加成行，然後每個掉落一行，擲每個掉落的機率或全部保留。

`raid_event.boss_pk8` 在 `raid.boss_record` 上構建頭目：表裡的物種、形態、等級、招式、超極巨化和極巨化等級，以及表所允許的特性、個體值、性格、性別和 PID，隊伍能力值來自 `pokeldn/swsh/data/species.json`（`scripts/gen_swsh_species_data.py`）。

    bin/swsh_host.py --raid-event "FOLDER/Index 010" --raid-stars 5 --raid-event-boss 4 --raid-console-serves

不給 `--raid-stars` 或 `--raid-event-boss` 時，主機列出它取什麼。`--raid-version` 選擇表的版本（預設取廣播的），`--raid-area` 選巢穴區域，`--raid-event-drops all` 要全部掉落；`--raid-reward` 的行替換活動自帶的。

## 極巨大冒險

極巨大冒險（Max Lair，二進位制中為 `chika`）在本地通訊中，當每個玩家都在極巨巢穴選擇「邀請他人」時匹配：第一個開網路，其餘掃描並連線。Y 通訊從不列出它：主機廣播活動種類 0xFF。該網路使用本地通訊 id `0x0100abf008968000`、場景 50000、NodeCountMax 4（從 `0x00bd9b30` 呼叫的 Pia 上限，位於 `ChikaMatchingState*` `0x00bd1978..0x00bda158`）。主機在 "Communicating" 下從 3:00 倒數；沒有訪客時它取消冒險。冒險開始後，電腦夥伴填補空席位。

場景不是固定的。`0x00bd7e80` 從 `[comm+0x80]` 讀兩個 u32，先一個標誌再一個值，並從 `comm+0x74` 讀連線密碼。`0x006a9cb0` 返回 false 時，它把場景設為 50000 + 該值，標誌置位時再加 1000（`0x00bd7fdc`）。一臺玩家的零售主機在場景 50480 廣播了極巨巢穴網路；480 是 由克希，極巨巢穴的傳說寶可夢之一。該值是玩家選擇要針對的傳說寶可夢，這只是一個假設；此處實測的主機都廣播 50000。另一條路徑上游戲模式是 50000，標誌置位時為 50001，非零值進入一個搜尋屬性。`swsh_lair.is_scene` 接受 50000 + 0，或極巨巢穴某傳說寶可夢的物種 + 0 或 1000。

極巨巢穴的匹配引數以 `0x0101` 結尾（`0x00bd7f60`），儲存在 `[matching+0x280]`；交換傳零（`0x010967e0`）。`+0x281` 位元組置位時，對找到的網路場景的匹配（`0x006cba10`、`0x006cb5e8`）先比千位再比餘數；清零時兩個場景必須相等：

| 搜尋方的場景 | 它接受的找到的場景 |
|---|---|
| 50000 | 任何 50xxx |
| 50480 | 只有 50480 |
| 51000 | 任何 51xxx |

`swsh_host.py --lair-legendary` 在一塊射頻上掃描主機自己的大廳並廣播它的場景，找不到時為 50000；`--lair-scene` 設定它。所以帶有目標的主機會越過 50000 的主機去搜索，而且它必須在主機啟動之前就處在「邀請他人」。在 LAN 下游戲模式保持 50000 或 50001，所以目標在那兒從不隱藏大廳。

可靠 0x80 埠 0 上執行兩個訊息 holder，每個欄位都是一個帶單個欄位 1 的 holder：

- id 7000，`net_contents.chika.protocol_buffers.ChikaAsyncDataHolder`（描述符 `0x1c3adb5`、`0x2066654`），大廳；
- id 8000，`net_contents.underground.protocol_buffers.UndergroundAsyncDataHolder`（描述符 `0x1c36fab`、`0x20681cc`），戰鬥之間。

送進極巨巢穴大廳的巢穴訊息（id 2000）會被確認，但不安排任何座位。戰鬥像巢穴團體戰那樣在 0x7C 上執行，有兩處不同：

- 行動是條目 1 為 `01 ff ff ff ff ff ff ff`，條目 2 是巢穴團體戰那樣的招式，其餘九個條目 `0xff`；條目 2 的第 3 位元組在極巨化回合為 `0x80`，它之前的狀態訊息隨後攜帶狀態 1 而不是 2；
- 訪客的寶可夢倒下後，主機發型別 0x04、資料 `01 00 ff ff ff ff`；訪客用一個 88 位元組的行動應答，其條目 2 為零。

`pokeldn/swsh/lair.py` 是這兩個 holder 的訪客側；`bin/swsh_connect.py --preset lair`（應用的「極巨大冒險（加入）」）作為玩家 1 入座，並取主機留下的第一個提供位（租借按輪選擇，主機的先）。`lair.rental_pk8` 構建的租借是所記錄租借的記錄，加上該行的物種、形態、65 級和招式、四項 31 的個體值其餘隨機、隨機性格、特性槽 1 或 2、性別、PID 和加密常量；初訓家為研究員，精靈球，相遇等級 65，隊伍能力值不含極巨化加成。一臺零售版劍主機接受了它。

### 主持一場冒險

`bin/swsh_host.py --lair-legendary SPECIES [--lair-seed N]`（`pokeldn/swsh/lair_host.py`）用一臺模擬的盾主機的廣播（場景 50000）廣播極巨巢穴網路，像連線交換那樣交換快照，然後發大廳：PlayerInfo、BattleReady 和 BigBoss，限時每秒三次，以及準備；訪客準備好後，BattleStart、BattleSeed、RentalPokemonSeed 和 PlayerNumber；訪客應答已開始後，已開始的 BattleReady 和 BigBossFixed。五秒後它像主持的劍那樣離開（[離開](swsh_session.md#leaving)）：MIGRATION_START `44 00 01`、帶主機遷移位元組的會話更新、每 0.33 秒一次 START_HOST_MIGRATION，並在主機離開後或 10 秒後關閉網路。

應用的「極巨大冒險（主持）」工具執行這些開關：傳說寶可夢、可選的連線密碼和種子。它的種子選擇器顯示 `lair.adventure` 為某顆種子給出的三個租借和十次遭遇，可以抽新的，並搜尋符合指定租借的種子（約每 75 個有一個提供該租借）。地圖盡頭的傳說寶可夢是 BigBossFixed 指名的物種；訪客自己的 BigBoss 全為零。租借按輪選擇，主機的先，電腦夥伴會接替已離開玩家的席位。

極巨巢穴的連線密碼在接待員處用 + 設定。廣播攜帶該密碼十進位制值的 CRC32，前導零去掉（0000 7777 為 `7777`）；用不同的密碼或不帶密碼搜尋永遠不會列出該大廳。帶密碼時，未發 MIGRATION_START 就關閉網路的主機會讓訪客停在租借介面的錯誤 2618-0006；有移交時，訪客在 MIGRATION_START 後 0.1 秒離開，冒險繼續。

### 冒險種子

冒險的寶可夢是 RomFS `bin/appli/chika/data_table/underground_exploration_poke.bin` 的行，一個 273 行的 FlatBuffer：226 個 65 級的租借和遭遇，然後 47 個 70 級的傳說寶可夢（頭目標誌置位）。一行攜帶物種、形態、等級和四個招式。

ChikaBattleSeed 決定六個租借的提供和遭遇；`lair.adventure(seed)` 計算它們。Xoroshiro128+ 用該 u64 和 `0x82A2B175229D6A5B` 播種。每次選取用下一個 32 位輸出為 MT19937 播種，打亂 273 個行索引（索引 i 與 i 加一個到 272 - i 的抽取交換，抽取按 `0x1ff` 掩碼並在超出時重抽），然後取第一個既不是傳說寶可夢、也未被選過的行。四次選取，然後在接下來兩次選取之前各一次 0 到 2 的抽取，再一次，分別在入座的電腦夥伴多於 2、1、0 個時；然後是 0 到 2 和 0 到 9 的抽取，再是十次遭遇選取，每次在該行有兩個屬性時再跟一個輸出。有三個電腦夥伴時，先有一次 0 到 27 的抽取。

租借介面顯示提供位 0 到 2。每個席位依次選擇，主機的先，它取走的位由下一個未用的位（3，然後 4，然後 5）補上。電腦夥伴在玩家之後選擇，從不經過網路：各自取自己 0 到 2 抽取給出的介面位置，第一個夥伴取第一個抽取。`lair.partner_places(seed, taken)` 計算它；它在三次記錄的冒險中（一臺模擬主機與訪客、我方訪客對模擬主機、以及對零售版劍主機）點名兩個夥伴的租借，依據是每個戰鬥位在主機型別 0x10 命令中使用的招式。該規則只需要 ChikaBattleSeed。某條路徑會遇到哪些遭遇未知。

`swsh_connect.py --preset lair` 作為零售版劍主機的訪客走過了每條路徑和每次捕獲選擇，經過三次遭遇和傳說寶可夢（雷公），其租借在每場戰鬥中都用了第一個招式；主機的玩家輸掉了最後一場戰鬥，會話無錯結束。

## 離開

玩家的獎勵介面一結束，零售版劍主機就以每 0.33 秒一次 START_HOST_MIGRATION 關閉網路，持續 10 秒，與連線交換之後相同（[離開](swsh_session.md#leaving)）。不離開的訪客會把主機的玩家凍結在曠野地帶直到超時；`--leave-with-host` 在第一次時就離開。

### 戰鬥中離開

在本地巢穴團體戰中離開的站點不會為其他人結束戰鬥。戰鬥的離開服務（由 `0x8b7830` 構建，儲存在 btl-net `+0x3b8`）在處理函式 `0x8c4570` 中聽到 Pia 會話的站點離開事件（`0x6b4850`，型別 1）。在本地巢穴團體戰中（設定 `+4` = 2，`+0x3b8` = 1，由 `0x7e7c50` 在 `nn::pia::local` 模式下設定），它把該座位保持為已連線 30 秒（`0x7530`），然後移除該站點（`0x8c3f70`、`0x8b4140`）並重跑伺服器選擇；做伺服器的那臺主機把該座位的備用客戶端（`main+0x1c0 + 8 * i`、`0x8dfcb0`）放進其中（`0x7f8450`）。丟失會話（型別 3）經 `0x10f8e30` 丟擲錯誤 (2,4)。

在模擬的盾 1.3.2 上實測，戰鬥中殺掉板子的程序且不傳送任何東西：

| 板子 | 主機做了什麼 |
|---|---|
| 主機巢穴大廳裡的訪客 | 戰鬥繼續，無錯誤；下一回合的選單照常出現 |
| 主機，由主機做伺服器（`--raid-console-serves`） | 戰鬥暫停約一分鐘，然後繼續，無錯誤；下一回合頭目受到傷害 |

在經 ESP32 板子的零售版劍上，戰鬥進行 10 秒時殺掉板子的程序，兩種角色結果相同：無錯誤，戰鬥繼續。

改為乾淨移交（戰鬥中 5 秒時 MIGRATION_START，然後關閉網路）時，主機在 0x18 埠 0 上應答 `48 01`，0.1 秒後離開網路並顯示 2618-0006，之後戰鬥離線繼續。在戰鬥開始前離開的主機會讓主機停在 "Connexion en cours"（[訪客的序列](#the-guests-sequence)）。
