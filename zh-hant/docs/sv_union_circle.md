# 聯盟集友圈

聯盟集友圈是 朱/紫 中最多四名玩家共享同一場地的會話。它的程式碼稱之為團隊集友圈
（`TeamCircle`），藍莓任務（BBQ）則是 `bbmission`。pokeldn 以訪客身份加入一臺主機的
本地聯盟集友圈，上報為主機帶來 BP、並放出 Snacksworth 的傳說的寶可夢的 BBQ 完成，
還在主機的玩家周圍生成野生寶可夢
（[野外遭遇](#overworld-encounters)）。應用的兩個聯盟集友圈工具位於
[應用指南](gui.md#union-circle)。

下面的 Lua 是 朱 4.0.0 的 chunk `be21e65463b9a98f`（`main.blua`，SHA-256
`c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`，也就是
[太晶團體戰](sv_raid.md)所用的 chunk），除非它標著 `main_dynamic`。一個 `0.N` 是 chunk 主函式
從 0 計數的第 N 個原型。這些原型編號在公開的 3.0.1 反彙編（Martmists-GH/SV-Script-RE）中相同。
尖括號裡的名字來自它的雜湊表；其餘仍是雜湊。

## 獲取 Lua

該 chunk 是 `arc/data.trpfs` 中的 `script/lua/bin/release/main/main.blua`，以 Oodle 儲存。4.0.0
更新的虛擬 RomFS 需要基礎遊戲的 RomFS：`arc/data.trpfd` 的一部分位於基礎遊戲中。

    ./.venv/bin/python tools/switch/nso_read.py main main.bin
    ./.venv/bin/python tools/switch/trpfs_read.py --update UPDATE.nsp --base BASE.nsp --keys prod.keys \
        --image main.bin --extract script/lua/bin/release/main/main.blua --out-dir OUT

`--image` 會執行 `main` 的 `OodleLZ_Decompress`（`0xcc8750`）。該 chunk 是 Lua 5.4 位元組碼，含
30,829 個頂層原型；`main_dynamic`（`script/lua/bin/release/main_dynamic/main_dynamic.blua`）
存放事件指令碼，提取方式相同。

## BBQ

任務進度由原生程式碼處理，位於 Lua 模組 `c5137FC87` 中。Lua 遊戲事件通過
`C00099C1DFBF96B11.S110BDDB84DEB4379`（`0.7064`）上報給它，後者把（任務型別、兩個值、計數）
傳給 `c5137FC87.f4246D9CA`；例如一次進化會上報型別 28、計數 1。任務在聯盟集友圈這一側的處理
是第二個原生模組 `c4D400AC0`。

每個任務都有一個等級，即俱樂部資料（`arc/worlddataclubMissionDifficultyWeightAdvanced.bin.trpak`）
中其 `MissionInfo` 行的 `mission_grade`：0 普通，1 獎勵，2 團隊。Snacksworth 把團隊任務稱為
團體任務。完成事件攜帶其任務的等級。

資料包的 quest 表是一個由 64 個 `MissionInfo` 結構組成的 FlatBuffer：類別（1 對戰，2 場地，
3 相機）、`mission_type`、`mission_id`、目標、獎勵 BP、重新整理 BP（用來換掉該任務）、放出型別、
等級、難度（0 入門到 2 高階）與權重。每條訊息裡的任務 id 就是其所在行的 `mission_type`；
`mission_id` 區分同一型別的多行，它們在等級、難度、目標或 BP 上不同。BBQ 列表按這一對值查詢
任務（`0x29de0f4`）。第二張表 `MissionSettings` 給出某個型別在每種變體下的文本（一種寶可夢
屬性、一個生物群系、一種口味），位於 `club_bbmission`。任務表使用的型別：

每個普通行支付 20 到 40 BP，每個獎勵行 100 到 200，每個團隊行 400 到 600。

BBQ 管理器建立時（`0.7062`），會把若干 getter 交給原生側。`c16FE4B25` 取得玩家自己的場地
（`f61488ABA`，存檔的 `currentFieldId`）與某個成員的場地（`f45B80F87`，某站點索引對應的 110
值）。`c5137FC87` 取得玩家是否在場地中（`f01FF34BD`）以及兩個俱樂部等級標誌
`FSYS_CLUB_BBMISSION_LVUP_01` 與 `_02`。

管理器的 `PreUpdate`（`0.7069`）每幀排空三個原生佇列：

| 佇列 | 來源 | Lua 做什麼 |
|---|---|---|
| `c5137FC87.fB8D11637` / `f35493666` | 玩家自己的完成 | 在 `c4D400AC0.f5770F782` 成立期間，把每次完成交給 `c4D400AC0.fAC449469`。在集友圈中做出的獎勵完成（`c4D400AC0.f48603105`）交給主機上的 `c4D400AC0.f263D7D28` 與 `f07578A96`（`c4D400AC0.fE8E53DDE`），訪客不會為它記任何賬。其他任何完成則為 BP 排隊 |
| `c4D400AC0.fD7C6549F` / `f37737462` | 其他成員的完成 | 把每次作為提示顯示；除非是獎勵完成，否則為 BP 排隊 |
| `c4D400AC0.fD961BFD2` / `f541C4B17` | 來自集友圈的 BP 發放 | 把每筆發放為 BP 排隊 |

`0.7075` 把排隊的事件合併進同等級的事件並求其 BP 之和（`fBCA6AEB8`）。`0.7076` 把排隊的總和
加進貨幣管理器，`0.7077` 顯示 BP 訊息。管理器的加法（`0.15120`）把玩家的 BP 夾在 0 到
9,999,999（`0.15128`），所以即使某次完成的 BP 是 s32，單次完成最多也只計 9,999,999 BP。

Lua 什麼都不校驗：成員的普通或團隊完成直接從第二個佇列付給主機，獎勵完成則只通過原生集友圈
模組放進第三個佇列的發放來支付。

## 原生模組

以下地址位於 朱 4.0.0 的 `main` 中。

原生模組與函式名是 `main` rodata 中的普通字串；每個模組在 `.data` 中有一張 `luaL_Reg` 風格的
{name, function} 表：`c4D400AC0` 位於 `0x442e500`（22 個函式），`c5137FC87` 位於 `0x4420630`
（45 個）。完成事件是一份 userdata（方法位於 `0x441dc50`）：`fBCA6AEB8` 返回 BP（`+0x10` 處的
s32），`f0C278E84` 返回等級（`+0xd` 處的 s8）。`0x29dd878` 從任務所在行構建它：任務 id
（`+0x0` 處的 u16）、`+0x4` 處的 u32、等級與 BP。

`c4D400AC0` 的函式作用於一個集友圈物件，即位於 `0x4739410` 的惰性構建單例：

| 函式 | 作用 |
|---|---|
| `f5770F782` | 集友圈是否就緒（`0xa0d038`） |
| `f48603105`, `fE8E53DDE` | 玩家是否在集友圈中，以及是否為房主（`0xa0e9ac`） |
| `fAC449469` | 把玩家的完成作為訊息 3 發出（`0xa0db20`） |
| `f263D7D28` | 在主機上，把一次獎勵完成作為訊息 5 發出（`0xa0dcf4`） |
| `f07578A96` | 在主機上，為自己的一次獎勵完成記賬（`0xa0df34`，隨後是發放推送 `0xa0e164`） |

集友圈在自己的通道上（物件的 `+0x70`）傳送這些訊息：0x80 埠 0 上、遊戲金鑰 0x0048，訊息型別
放在 kind 位元組裡。每條先是遊戲帶標記格式的完成事件（`0xb9`，18 個欄位，由 `0xa17694` 讀取），
然後是傳送方的訊息序號（`+0xb8`）。訊息 3 還攜帶傳送方的 BBQ 狀態記錄（`0xa0f37c`，由
`0xa17170` 讀取）。在這種帶標記格式中，-64 到 127 的整數就是自身一個位元組，更寬的整數放在有符號
標記之後（0x84 到 0x86），浮點數放在 0x88 之後。

完成事件的欄位：

| 欄位 | 值 |
|---|---|
| 0 | 任務 id |
| 3, 11 | 任務所在的槽位 |
| 4 | 等級 |
| 5 | BP |
| 6 | 傳送方站點 id 構成的元組（u64，標記 0x83） |
| 7 | 任務的 `MissionInfo` 行 |
| 12, 13 | 接替該槽位的任務，及其行 |

其餘欄位為零或空行。在一次完成前十分之一秒，主機會發送 kind 2：任務、-1、-1、其進度（1.0）、
其序號，以及其狀態記錄。

### BBQ 狀態記錄

每個玩家的 BBQ 管理器把狀態記錄存在自己的 `+0x40`；集友圈把它（`0xa0f37c`）寫入訊息 1、2 和 3。
訊息 1（kind 1）只有傳送方的訊息序號和這份記錄。玩家在集友圈啟動時發一份，step 1，然後一條
無實體的 kind 4（`480004`），然後 step 2；主機在每位成員完成之後也會再發一份。該記錄是一個
11 元組：

| 元素 | 記錄偏移 | 值 |
|---|---|---|
| 0 | `+0x0` | 每條記錄中都是 1：管理器 `+0x40` 處的位元組 |
| 1 到 3 | `+0x4`, `+0x50`, `+0x9c` | 玩家的三個任務槽位 |
| 4 | `+0xe8` | 一個位元組的位元組串，每條記錄中都是 1 |
| 5, 6 | `+0xec`, `+0x138` | 另外兩個槽位，在見到的每條記錄中都為空 |
| 7 | `+0x184` | 一個有符號位元組，在每條記錄中都等於元素 9 |
| 8 | `+0x185` | 玩家面向下一次發放的獎勵完成數 |
| 9 | `+0x188` | 單人總計（管理器的 `+0x1c8`） |
| 10 | `+0x18c` | 團隊總計（管理器的 `+0x1cc`） |

一個槽位（`0xa0fa18`）為 0x4c 位元組，記錄從中取任務 id（u16，空時為 0）、其進度（float）、其文本
變體（即 `MissionSettings` 的變體，沒有則為 0）以及該行的 `mission_id`。若主機第五個槽位指名的
任務與其自己的不同，成員就採用主機的（`0xa14290`）。

`circle.bbq_record` 讀取訊息 1、2 或 3 末尾的記錄。

零售主機的槽位存放其任務型別的入門級普通行（`mission_id` 為 0：20 BP，任務 1 的目標是擊敗
10 次，其他任務為 1），進度為 0，直到某次上報完成其中之一；更靠後的槽位保持為空，獎勵計數
為 0。

### 成員在主機任務上的進度

成員通過訊息 2（kind 2，0x80 埠 0）上報進度，來完成主機的一個任務：任務、兩個值（沒有變體
的任務為 -1、-1）、計數、其訊息序號及其自己的狀態記錄。主機以其顯示該進度的記錄作答，然後
傳送自己的訊息 3：這次完成記在成員的站點 id（欄位 6）名下，帶上 BP、槽位與接替它的任務。它的
單人總計加一。

訊息 2 攜帶 Lua 的進度上報（`c5137FC87.f4246D9CA`）所傳的內容：任務、它的兩個值與計數。主機的
接收處理器把這四個值，連同成員標誌與傳送方，交給它自己的上報所到達的同一個原生進度分發器
（`0x29dc838`）（`0x29dc6b0`）。因此主機會把成員的進度當作自己的來計，自己完成任務並結算，
這次完成也像它自己的任何一次那樣計入其單人總計。

`circle.progress_message` 構造訊息 2。一次 Snacksworth 執行（[加入](#joining)）會按主機最新
記錄所示，把每一份依次發往主機三個槽位中的下一個，計數為 500（普通行的最大目標），第一個值為
該槽位的變體，沒有變體則為 -1；零售主機會逐個完成它們。

## 主機如何處理成員的完成

接收處理器（`0xa13b00`）通過 `0x3c5b7a4` 處的跳轉表按型別分發。對於一條訊息 3，主機：

1. 把該成員的獎勵計數存入其 BBQ 狀態中該成員的槽位；
2. 在自己的 BBQ 列表中查詢該任務（`0x29de0f4`，按任務 id 與 `+0x4` 處的 u32）。只有匹配上它
   自己的某個獎勵任務，這次完成才計入主機自己的計數，也只有這時主機才為它排隊自己的提示。
   除了第 4 步中的一個標誌，這個結果不影響下面任何事；
3. 把這次完成作為成員提示排隊（`fD7C6549F` 佇列）；
4. 如果這次完成是獎勵，把事件的 `+0x7c` 設為 min(3, 主機自己的獎勵計數加三個成員槽位之和)，
   把 `+0x80` 設為第 2 步是否匹配，把它作為訊息 5 發給每位成員，並按收到的樣子通過發放推送
   給自己記賬；
5. 如果這次完成是團隊完成且主機的 BBQ 管理器處於活動狀態，就給主機的團隊總計加 1（見下文）。

只有在這之後，主機才把該訊息的序號與該成員的上一個序號比較，而這個序號只用於把關該成員的狀態
記錄。

收到訊息 5 的成員會通過同一個發放推送為該事件記賬，除非其序號比從主機見到的上一個更舊。

主機照成員訊息裡寫的付：沒有任何地方校驗 `+0x10` 處的 BP，也不校驗任務是否存在。普通或團隊
完成由 Lua 立即支付。獎勵完成要經過發放推送，這是唯一的排序。它把每個事件暫存，僅當其 `+0x7c`
比上一個已放出事件的多 1、或少 2，或兩者都為 0 時，才把它放進發放佇列（物件的 `+0x108`）。該值
由槽位算出，所以成員的下一次獎勵完成必須上報比上次多 1 的計數。

## Snacksworth

BBQ 管理器維護兩個累計總計，分別由 `c5137FC87.f6ED7C9B6`（`+0x1c8`）與 `fECB0EBF0`（`+0x1cc`）
讀取：

| 總計 | 何時上升 | 還被誰讀取 |
|---|---|---|
| 單人，`+0x1c8` | 玩家自己的普通或獎勵完成（`0x29dda40`） | 俱樂部的 BBQ 升級事件，在 15 與 45 時 |
| 團隊，`+0x1cc` | 玩家自己的團隊完成，以及在主機上訊息 3 中每位成員的團隊完成（`0xa14918`） | |

Snacksworth 是事件 `s2_sub_012`，他的 25 只傳說的寶可夢是事件 `s2_sub_013` 到 `s2_sub_037`，
各自的狀態在 `WEVT_S2_SUB_0NN_STATE` 中。該事件在 `main_dynamic` 中的類（原型 `0.1995` 到
`0.2032`）通過 `0.2019` 讀單人總計、通過 `0.2020` 讀團隊總計。

當玩家與他交談時，`0.2002` 會在單人總計減去單人路線上已放出的每隻傳說的寶可夢所對應的
`missionReleaseCount` 之後達到 `missionReleaseCount` 時，放出下一隻單人路線的傳說的寶可夢；
`0.2003` 對團隊路線做同樣的事，用團隊總計與 `teamMissionReleaseCount`。兩個計數都來自該事件的
配置表（`s2_sub_012.ReleaseConfigTable`，位於
`arc/worlddataeventcommandcommand_data_rootcommand_data_root.bin.trpak`）。資料包中唯一形如
該表的表存的是 10 與 1。

同一資料包中的 `s2_sub_012.ReleasePokeTable` 把每隻傳說的寶可夢放在四條路線中的兩條上，兩條
單人（`MissionA`、`MissionB`）與兩條團隊（`TeamMissionA`、`TeamMissionB`）：

| 位置 | 傳說的寶可夢 |
|---|---|
| 兩條單人路線 | 急凍鳥、閃電鳥、火焰鳥、熊徒弟 |
| 兩條團隊路線 | 烈空坐、酋雷姆、奈克洛茲瑪 |
| 各一條 | 其餘 18 只 |

指令碼向 `CA4C5F9FA83D2AF80.SDF0C255E6E08D740` 詢問玩家處在哪一對路線上，A 路線還是 B 路線；
朱 在 A 路線上（一次團隊完成放出了捷克羅姆，而它只在 `TeamMissionA` 上）。每一對都把 25 只
傳說的寶可夢分開且不重疊：單人路線 13 只，團隊路線 12 只。一次交談最多放出一份零食，先嚐試
團隊路線。每條路線在其尚未放出的傳說的寶可夢中隨機選擇（`0.2007`）。一條路線的下一次放出需要
其總計達到「其計數 ×（該路線上已放出的傳說的寶可夢數 + 1）」。所以全部 25 只需要單人總計
130 與團隊總計 12，以及 25 次交談。

沒有任何訊息指名零食：指令碼拿主機自己的總計與配置比較。每條攜帶團隊完成的訊息 3 都給主機的
團隊總計加一，既不校驗該任務是它擁有的團隊任務，也不做防重複的序號校驗；在
`teamMissionReleaseCount` 為 1 時，每一次就是團隊路線的一份零食。成員完成的每個主機任務
（[成員在主機任務上的進度](#a-members-progress-on-the-hosts-quests)）都給其單人總計加一，從而
供給單人路線上的那 13 只。

## 加入

`bin/sv_join.py --union-circle` 以團體戰訪客加入團體戰的方式加入一臺主機主持的集友圈
（`pokeldn.sv.circle`）。它佔下座位，傳送自己的身份記錄，在 0x7C 埠 1 上映象主機的通道表，
並在 `--hold` 期間保持座位，預設是整個 `--seconds`。它不傳送大廳訊息，主機離開時也不接管主機
角色。當主機的場地就緒後，它把自己的玩家放上去（`circle.Member`，[場地](#the-field)）。它列印
使用者需要跟隨的內容；`--verbose-circle` 還會加上它傳送的每條集友圈訊息與區域搜尋的每一步，這些
`--capture` 檔案本來也會儲存。

    ./.venv/bin/python bin/sv_join.py --union-circle --code 3707 --hold 540 --capture circle.jsonl

在連線密碼下主持集友圈的零售 朱 4.0.0 會廣播場景 5、最多四名參與者，以及交換的應用程式資料：
連線碼在密碼中也在遊戲位元組中，其長度在 +0x24。遊戲位元組還在 +0x21 處有 `aa 08 3e`，而搜尋中的
主機把那裡留為零。

它像連線交換或太晶團體戰主機那樣讓訪客入座：加入響應、站點列表、通道表（金鑰 0x007B、0x0132、
0x0232 與 0x0332）、兩條流的開啟、時鐘應答及其身份記錄。之後訪客等待主機的玩家啟動集友圈。

## 啟動集友圈

啟動時，主機發送 Net 0x50，其廣播計入成員人數，並在 0x80 埠 2 上傳送型別 7 的通告（以及對
每位成員各一條接受它的型別 9），還在 0x80 埠 0 上傳送其集友圈訊息。

集友圈訊息就是 Lua 的 net 訊息。每條都是金鑰 0x0132 下的一條遊戲訊息（處理鍵、kind、step，
然後是序列化器頭；[太晶團體戰](sv_raid.md#the-lobby)），其 kind 就是 Lua 訊息 id。團體戰的
「loading」與「loaded」（0x0132，kind 0x6E 與 0x73）就是同一個接收器的訊息 110 與 115。有些
載荷是 FlatBuffer 表，其餘是固定結構；104 與 106 經過 LZ4 壓縮（序列化器壓縮 2）。

| 訊息 | 來自 | 載荷 | `TeamCircleUI` 的處理 |
|---|---|---|---|
| 100 | 主機，在啟動時 | 一個只含一個 u32 的表，總是 12345678 | 啟動音效；訪客的啟動標誌 |
| 101 | 每個站點，主機緊接其 100 之後，成員在主機的 100 之後 | 32 位元組：站點所站的位置（場地 id、三個寶可夢中心標誌） | 按站點 |
| 103 | 每個站點 | 一個只含一個 u32 的表，即同步點的 id | 1 與 2 交給 UI（啟動演示已載入、已結束），其餘 id 交給同步物件 |
| 111 | 主機 | 5916 位元組：四個零位元組，然後是兩個表向量（30 與 10）的 FlatBuffer | 只用一個標誌；內容由原生程式碼讀取 |
| 104 | 主機 | 一個表：遊戲時間、現即時間及其經過的秒數（float）、天氣種子（u64）、抽籤的長度，以及當前與下一個天氣的 {type, duration} 對 | 時鐘與天氣，送進遊戲時間管理器與 `WeatherManager.Sync` |
| 102 | 主機 | 兩個 u32：成員傳送到的飛行點 | 傳送 |
| 106 | 每個站點 | 300 個六位元組槽位，其太晶團體戰結晶；`ffffffff0000` 表示空槽 | 按站點 |

主機按表中順序傳送它們，在其 101 之後還有三條金鑰 0x0048 的訊息，都在啟動後兩秒內。

每個站點都到達同步點 2215，等待每個站點的 101，傳送自己的 106，並等待其他各方的 106
（`IsGemInfo`）；啟動演示中 id 為 1 與 2 的 103 也以同樣方式等待。當每位成員都發送了帶該 id 的
103 時，一個同步點即算到達（`CEEE8D2836ABEDE23`）。

零售主機會把超過 1395 位元組的訊息拆成分片，而對未分片的更長訊息不予確認，所以 106 會走 LZ4
壓縮，主機自己的 106 也是如此。

全部 106 到齊後，主機傳送到其 102 的飛行點，併發送 115（1，0）。

## 場地

隨後主機的玩家進入場地。它通過向每位成員在 0x7C 埠 1 上傳送一條更新（經 zlib 壓縮），再開啟
14 個通道金鑰（低位元組 0x1E 到 0x2A，其中一些帶子通道 0 與 1）。零售成員以同樣方式回發同樣的
更新。主機發送金鑰 0x0024、kind 1、step 1，沒有主體，此後傳送它的玩家：

| 內容 | 方式 |
|---|---|
| 動畫狀態 | 可靠，0x80 埠 0，金鑰 0x001E、kind 5，狀態的名稱（`Top/pc_field/move/defaultwait01`），每 3 到 7 s 一次 |
| 變換 | 不可靠協議 0x68（像 0x80 那樣按網格定址），金鑰 0x011E、kind 4，38 位元組的 float，每秒約 20 次；kind 6 與 7 各一次 |

在構建啟動演示之前，主機會等待（`F9FFADFE613D572B7`），直到其他每個站點的玩家物件都出現在其
場地上。不傳送玩家的成員會讓它停在黑色的「通訊中」畫面。主機通過原生模組 `c2A8846F6` 把成員
生成為 `playables.Player` 物件（其 `f6BD530B6` 就在等待之前執行）。

玩家物件在每位成員與主機之間經 0x7C 埠 0 傳輸，緊接在場地金鑰之後：

| 金鑰 | 訊息 | 內容 |
|---|---|---|
| 0x001F | id（u16）、type（u16） | 一臺主機宣告它自己的一個物件 |
| 0x001E | kind 0、0、id（u16） | 一臺主機請求對方已宣告的某個物件 |
| 0x001E | kind 1、2 或 3、0、id（u16）、狀態 | 應答：物件的狀態，其 kind 為 1、2 或 3，取決於該物件在宣告中的位置 |

每臺主機宣告四個物件（型別 0、1 或 2、3 與 10），id 從站點索引起以 4 遞增。一臺主機會請求對方
宣告的每個物件；沒有人應答對型別 10 物件的請求。狀態為 70 位元組（kind 2）或 214 位元組（kind 1 與
3），經 zlib 壓縮：控制代碼、縮放、旋轉、位置；kind 1 是玩家，並攜帶一個 FlatBuffer。主機在成員的
kind 1 應答之後半秒啟動它的演示。

隨後成員在金鑰 0x0025 上向主機詢問若干 u64 id 列表，主機對每個列表以標誌作答
（[野外遭遇](#overworld-encounters)）。

金鑰 0x0048 屬於 BBQ 模組（[原生模組](#native-modules)），位於主機的第一張通道表中。在其埠 2
通告前後，主機發送 kind 1 step 1、一條無實體的 kind 4（`480004`）以及 kind 1 step 2，兩個 step
都攜帶其狀態記錄（[BBQ 狀態記錄](#the-bbq-status-record)）。

`circle.Member` 做以下事情：
- 它用主機自己的 101 的副本應答主機的 100，於是訪客的玩家站在主機玩家所在的位置。
- 它回顯主機發送的每一條 103。
- 它用 300 個空槽位應答主機的 106，經 LZ4 壓縮：一個沒有結晶的世界。
- 它把主機發送的每條 110 與 115 作為自己的副本發出，跟隨主機的場地。
- 一旦 `sv_join` 回發了場地金鑰，它就宣告站點 1 的四個物件，並請求主機的每個物件。對主機的
  每次請求，它都用主機自己該型別物件在訪客 id 下的狀態作答，於是訪客的玩家與主機站得一樣。

使用 `--follow-host` 時，訪客的玩家也會隨主機移動：0x68 上的每幀主機資料與金鑰 0x001E 上的物件
訊息，都以訪客對應的物件發出，按訪客自己的 60 Hz 時鐘，延遲 0.3 s 重放主機（主機的變換每秒
到達約 27 次）。訪客保持在主機 5 m 以內，面朝主機，並按自己的步速縮放主機的移動混合。

使用 `--circle-task` 時，任務完成後訪客的玩家離開集友圈，執行隨即結束：
- `snacksworth` 從第一條狀態記錄讀取主機的單人總計與團隊總計。從啟動演示結束（其 id 為 2 的
  103）起，它每秒傳送一條，補足團隊總計還差的團隊完成以達到 12，然後上報完成主機任務直到其
  單人總計為 130（[成員在主機任務上的進度](#a-members-progress-on-the-hosts-quests)），再在其
  團隊總計仍有缺口時多發一條團隊完成（[Snacksworth](#snacksworth)）。每次團隊完成都是按遊戲
  抽取方式抽出的團隊任務（`circle.TEAM_QUESTS`，每個任務與 BP 及其機率），並支付該任務的 BP。
  它隨主機總計上升列印進度，並在連續 20 次傳送都沒有上升時停止。
- `bp` 在啟動演示結束後一秒，傳送一次任務 29 的普通完成，支付 `--bbq-clear` 的 BP，1 到
  9,999,999。

每次完成都是一條訊息 3，帶上其 BP、訪客的站點 id 與訪客的狀態記錄。

零售主機會支付每一條這樣的完成，即使訪客此前沒有發過訊息 1；提示與 BP 會在其玩家關閉 BP 側欄
後顯示。任意任務的一次團隊完成都會放出下一隻團隊路線的傳說的寶可夢（[Snacksworth](#snacksworth)），
無論主機在藍莓學園內還是外。

## 野外遭遇

集友圈中的每臺主機都按自己的遊戲版本、圍繞自己的玩家生成野生寶可夢，並把每一隻廣播給其他人，
因此成員能捕捉另一版本的獨佔寶可夢（零區中的 朱 主機生成 dev id 982，紫 成員生成 992）。版本
不會交換，主機也沒有特殊角色。

共享的寶可夢經 0x80 埠 0 與不可靠協議傳輸，由其所有者廣播；只有對其中一隻的請求及其拒絕會
發給單個站點，在 0x7c 埠 0 上：

| 金鑰 | 訊息 | 內容 |
|---|---|---|
| 0x0026 | kind 1，其 96 位元組記錄作為位元組串 | 所有者生成了實體（station, n） |
| 0x0026 | kind 2，(station, n) | 該實體已消失 |
| 0x0026 | kind 5，((station, n), (station, n)) | 一臺主機向所有者請求該實體以便與之對戰，使用請求方自己的 id；只在 0x7c 埠 0 上發給所有者 |
| 0x0026 | kind 6，同一對 | 所有者拒絕；回到請求方 |
| 0x0026 | kind 7，同一對 | 該實體現在屬於第二個 id 的站點，由它與之對戰；有一次出現在該實體 kind 2 之前的 15 s |
| 0x0126 | kind 3，(station, n)、(一個 float、0.0、0.0、0、0 或 1) | 實體的狀態，每 0.2 s（成員）到 0.5 s（主機）一次；最後一個元素是其狀態 |
| 0x011E | 0x68 上的 kind 4，按物件 id | 實體的變換，與玩家相同 |

實體的物件 id 是 station + 4n，即其記錄開頭的那個 u16。一臺主機只把自己的實體分享給玩家站在
其附近的那位成員。每個 id 都是一對無符號整數（分發器 `0x1dbd4b0` 不讀取有符號標記）。

零售主機在其每個實體存活期間每秒傳送其變換約 27 次，實體會遊蕩：離開生成處 0 到 41 m，310 s
內 70 個實體中有 61 個在 15 m 以內。每個變換中的高度就是地面的高度。在主機玩家與其實體都經過的
1 m 方格上，兩者的最低高度相差在 0.15 m 以內（52 個方格，中位數 0.00 m）。

一臺主機把別人的實體標為未穩定（狀態 1），並拒絕與之對戰（`BattleStartWait`），直到某個狀態
指明狀態 0。撞上一個已穩定的實體時，它顯示「!」並向所有者請求（`0x1972664`）：它為這個實體取
一個自己的新 id，存下這對值與一個回撥，其管理器更新（`0x1593884`）把 kind 5 發給發出該實體
記錄的站點。隨後遭遇（`GameEventEncount`，NetInitWait）無超時地等待所有者給出指名同一對值的
應答（`0x1dbdd70`）。當該實體是它自己的、且沒有其他主機持有時，所有者就會交出（`0x1dbdc20`，
然後是更新在 `0x15934c8` 處的廣播），否則拒絕（`0x1593914`）。交出時，每臺主機都把該實體改名
為請求方的 id（`0x1595a1c`）並標記為已交戰；請求方把它收為自己的並開始對戰。當它與自己的實體
對戰時，一臺主機廣播一條 kind 7，把這對值重複兩次。

記錄為 96 位元組。`EncountManager.UpdateNetworkSpawn` 通過 Lua 模組 `c4CF1D719` 繫結的 getter
（原生 `0x90e344` 到 `0x90e588`）把其欄位複製進一個 `pml.pokepara.InitialSpec`，然後在寶可夢
本身上設定緞帶、太晶屬性與一隻霜奶仙的裝飾。捕獲到的每條記錄都符合這個佈局：

| 偏移 | 位 | 欄位 |
|---|---|---|
| 0x00 | u16 | 物件 id |
| 0x04 | u64 第 0-10 位 | 開發用物種 |
| | 11-22 | 攜帶道具 |
| | 23-30 | 尺寸 |
| | 31 | 性別（1 為雌性） |
| | 32 | 閃光；置位時生成的寶可夢為閃光 |
| | 33-37 | 形態 |
| | 38-44 | 等級 |
| | 45-52 | 按 PKHeX 的 `RibbonIndex` 計的緞帶（標記），非 0 時應用 |
| | 53-57 | 性格 |
| | 58-62 | 太晶屬性 |
| 0x0C | u32 第 0-3 位 | 霜奶仙裝飾 |
| | 8-27 | 個體值 體力、攻擊、防禦、速度，各 5 位 |
| 0x10 | u16 第 0-9 位 | 個體值 特攻、特防 |
| | 10-11 | 特性槽位 |
| 0x24 | s32 | -1；在所見唯一一隻百變怪與索羅亞中為 0 |
| 0x30 | 3 個 float | 位置 |
| 0x40 | 4 個 float | 旋轉，在每個樣本中都是單位量 |

其餘位元組為 0（零售記錄在 0x02、0x28 與 0x54 處留有陳舊記憶體）。在記錄之前，所有者會在 0x68 上
傳送該實體的幀：沒有父級的 kind 6
（`00000000 00000000 0000003f 0000003f 00000000 0000003f 0000003f`）與尺寸為 1.0 的 kind 7。
`circle.Spawner` 以同樣方式傳送訪客自己的生成物（[自定義遭遇](#crafted-encounters)）。

`UpdateNetworkSpawn` 只憑記錄構建寶可夢；閃光位把稀有度字（`+0x18`）設為 `0x2ffffffff` 或
`0x1ffffffff`，所以兩種情況都由所有者決定。記錄不含招式、PID 或加密常量；捕獲時會加上捕獲者
的訓練家、球、地點、日期與等級。

遊戲接受任何記錄；PKHeX（Core 26.8.26）把這次捕獲判定為在捕獲地點的一次野生遭遇：

| 欄位 | PKHeX 接受條件 |
|---|---|
| 物種、形態、等級 | 捕獲地點處有一個 朱/紫 野生槽位，其物種與形態相符、等級範圍包含該等級；閃光鎖定或僅限固定出現的物種（如烈空坐）永遠不行 |
| 太晶屬性 | 該物種自身屬性之一，除非該處有配信的大量發生覆蓋該物種 |
| 性別 | 在該物種的比例之內 |
| 標記 | 不能是最強之證或泰坦之證；巨無霸僅在尺寸 255 時，迷你僅在尺寸 0 時；天氣標記只在某個槽位指名該天氣處 |
| 閃光、性格、個體值、特性槽位（含隱藏特性）、尺寸、攜帶道具 | 任意 |

PKHeX 在兩個版本下列出所有 朱/紫 野生槽位，所以另一版本的獨佔也合法，且分時段的槽位不會限制
已存下的寶可夢。記錄中的物種是內部索引（`gen9.national` 給出全國圖鑑編號）。

場地的其餘部分：

| 內容 | 金鑰 |
|---|---|
| 主機的大量發生 | 0x0029 kind 1，場地開啟時每次大量發生廣播一次 |
| 主機自己的狀態 | 0x0024 kind 1 與 0x002A kind 3 到 5，幾個小整數 |
| 成員的 id 查詢 | 0x0025，僅成員發給主機 |

兩款遊戲每張地圖都帶一張遭遇表（`world/data/encount/pokedata/pokedata*_array.bin`），包含兩個
版本的行；欄位 28 指明某行在哪些版本中出現。

一條大量發生訊息是一個元組：中心（三個 float，來自 `world/data/encount/point_data/
outbreak_point_data`）、它附近的第二個點、物種、0、形態、0、90 到 110 的數量、地圖（0 帕底亞，
1 北上，2 藍莓）以及 0。

金鑰 0x0025 是成員定期發給主機的查詢：kind 1 列出 u64 id，kind 3 對每個 `((id,), flag)` 以 0 或
1 作答，kind 2 列出成員放掉的 id。id 的最高五位是類別；成員大約每九秒遍歷類別 1、2、3、4、5、
9、10、13 與 16。

## 自定義遭遇

`sv_join --spawn SPECIES:LEVEL` 以成員身份加入集友圈，並在主機的玩家周圍維持三個使用者自造的
寶可夢生成；配合 `--follow-host` 時訪客的玩家跟隨主機的玩家。`--spawn-*` 標誌設定一條記錄所
攜帶的內容：形態、閃光、太晶屬性、性格、性別、特性槽位、尺寸、攜帶道具、標記與個體值。未指定的
項按主機自己的野生寶可夢的方式抽取：尺寸、性格與每項個體值隨機，特性槽位 0 或 1，沒有攜帶道具，
沒有標記。`--spawn-mark` 接受 PKHeX 的 `RibbonIndex`（53 午餐時間到 97 萎靡）；遊戲按同一套
編號讀取記錄的緞帶欄位：一臺零售 朱 捕獲了以 58 傳送的生成物，帶著雨天之證（PK9 在 0x34 處標誌
的第 58 位，沒有附加稱號），PKHeX 判定其合法。主機與之對戰（其請求，被交出）、移除（一條指名它
的 kind 2）或走出 50 m 以外的生成物會被放掉，另一個會在主機附近出現。

記錄裡沒有地面資料，因此 `circle.Ground` 儲存主機所顯示的地面：在每個 1 m 方格中，其玩家（或
坐騎）與實體站過的最低高度。一個生成物出現在離主機玩家 15 到 25 m 處，且只在最近 120 s 內有
主機的某個實體站過、並且 6 m 內至少有八個已知方格的方格上，所以我們沒有任何生成物會出現在主機
不生成的地方（一臺零售 朱 在其玩家站在城鎮中時，沒有顯示任何發出的生成物）。每個生成物停留
2 到 6 s，然後以 1 m/s 走向其生成處 6 m 內的一個已知方格，高度每 0.5 m 取地面的高度；上升或
下降超過 0.6 m 的一步，或跨過沒有已知地面的方格，都不會走。行走中生成物的變換每 1/30 s 發出。
一臺零售 朱 顯示這些生成物站在地面上並行走，其玩家撞上正在行走的一個就開始了對戰。

使用 `--spawn-legal` 時由 PKHeX 決定：輔助程式的 `wild_areas` 命令按地點列出 朱/紫 的野生槽位，
`wild_legal` 對從每個地點捕獲的自造生成物執行 PKHeX 的合法性分析，每種太晶屬性各一次；只要某
地點有任一槽位接受該生成物，該地點就算數，所以天氣標記需要一個指名該天氣的槽位（9 級的烏波可以
帶雨天，絕不能帶下雪）。應用提供 42 種野生標記：時間、天氣、命運、罕見、稀有與個性。PKHeX 在
任何地點都不接受的生成物會中止執行。

隨後生成物等待主機的區域（`wild.Locator`）。主機分享的每隻野生寶可夢（金鑰 0x0026 kind 1，
在訪客的玩家靠近後）把地點收窄到那些有槽位匹配其物種、形態與等級的地點。當剩下的每個地點都是
PKHeX 接受該生成物的地點時，區域就算找到；它不必只剩一個地點。然後生成物出現，當主機走出找到
區域時所站的 50 m 以外，它們全部消失，尋找重新開始。在那之前，當主機離它衡量過的某個生成物、
或離一個已無地點支援的生成物超過 100 m 時，尋找也會重新開始。沒有任何野生槽位支援的生成物
（團體戰的、活動的）會被排除。

在零區，主機的玩家不傳送其玩家的變換。連續 2 s 沒有變換時，主機被放在最近 30 s 內最新的六個
生成物的中間；一個都沒有時，不會有新生成物出現。距原點 10 m 以內的變換從不用來放置主機。

搜尋在應用中以 id 為 `zone` 的 `[panel]` 狀態卡片顯示。
